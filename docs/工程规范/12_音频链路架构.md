# 12 音频链路架构

> 本文件梳理工程内**五条音频链路**（WiFi 推流 / 蓝牙推流 / 蓝牙接收 / SD 卡本地播放 / TCP 录音）的
> 接口与数据流，记录共用底座、已知架构问题与优化方向。
> 与 `01_工程分层架构.md`（目录分层）、`通信接口规范_ICD.md`（对外协议）配套阅读。
> 最后更新：2026-09-24（补 F42 共用 `i2s_data_if` 更正；§8 行数表按 `wc -l` 刷新）

---

## 1. 总览

工程内共有 **五条**占用音频通路的业务，其中四条是「播放/推流/接收」：

| 链路 | 模块 | 数据源 | 方向 | 格式决定权 | 输出端 | 时长/生命周期 |
|---|---|---|---|---|---|---|
| **WiFi 推流** | `middleware/audio/udp_voice.c/h` | 实时采集（mic） | 双向（TX+RX） | **我方写死** 16k/mono | UDP → PC | 跟随信令开关 |
| **蓝牙推流** | `middleware/bluetooth/bt_push_service.c/h` | 文件（SD 卡 MP3） | 单向（只出） | **对端协商**（耳机 A2DP） | GMF → io_bt → 耳机 | 跟随 A2DP stream 四态 |
| **蓝牙接收** | `middleware/bluetooth/bt_sink_service.c/h` | 对端推流（手机/PC） | 单向（只入） | **对端协商**（A2DP Sink） | io_bt → GMF → ES8389 → 板载喇叭 | 跟随 A2DP stream 四态 |
| **SD 卡本地播放** | ⚠ **`ui/tabs/tab_audio.c`** | 文件（SD 卡 MP3） | 单向（只出） | **写死** 44.1k/2ch | GMF → ES8389 → 板载喇叭 | 跟随 Tab 生命周期 |
| TCP 录音 | `middleware/audio/record_service.c/h` | 实时采集（mic） | 单向（设备→PC） | 我方写死 16k/mono | TCP → PC | 跟随录音会话 |

> ⚠ **注意第 4 行的模块位置**：SD 卡本地播放链路**没有任何 middleware 模块**，
> 它的全部逻辑（GMF pool、codec 初始化、播放控制）都在 **UI 层**的 `tab_audio.c` 里
> （文件由原 `tab_music.c` 改名/合并而来，见 §4）。
> 详见 §5.5 —— 这是一处应当修正的分层问题。

### 1.2 五条链路的会话归属

| 链路 | 申请的 `SESSION_*` | 申请的模块 | 是否互斥 |
|---|---|---|---|
| WiFi 推流 | `SESSION_UDP_CALL` | `udp_voice` | ✅ |
| 蓝牙推流 | `SESSION_BT_PUSH` | `bt_audio_service` | ✅ |
| **蓝牙接收** | **（无）** | `bt_sink_service`（middleware，但**未接** session_manager） | ❌ **不互斥** |
| **SD 卡本地播放** | **（无）** | `tab_audio.c`（UI 层） | ❌ **不互斥** |
| TCP 录音 | `SESSION_TCP_RECORD` | `record_service` | ✅ |

> 五条链路里三条规规矩矩走 `session_manager`，另两条（本地播放 + 蓝牙接收）**在体系之外**。
> `session_manager.h` 目前只有 `SESSION_IDLE / UDP_CALL / TCP_RECORD / BT_PUSH` 四个枚举，
> **没有 `SESSION_LOCAL_PLAY` / `SESSION_BT_SINK`** —— 两者各自 `bsp_audio_codec_speaker_init()`
> 拿独立 codec 句柄，与 `audio_service` 的句柄指向同一个 ES8389。见 §5.5。

### 1.1 三条播放链路的共同点与分歧

```
                    ┌─────────────────────────────────┐
   文件源           │  MP3 / WAV / AVI 文件            │
  （SD 卡 / littlefs）└──────────┬──────────────────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              ▼                  ▼                  ▼
    ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
    │ 蓝牙推流         │ │ SD 卡本地播放    │ │ WAV 播放页       │
    │ bt_push_service │ │ tab_audio.c     │ │ page_wav_player │
    ├─────────────────┤ ├─────────────────┤ ├─────────────────┤
    │ GMF pool        │ │ GMF pool        │ │ (无 GMF)         │
    │  aud_dec(MP3)   │ │  ch/bit/rate/alc│ │  手工读 WAV 头    │
    │  aud_asrc       │ │  (无 asrc)      │ │  逐块写 codec     │
    │  aud_enc(SBC)   │ │  (无 enc)       │ │                  │
    │  io_file → io_bt│ │  render → codec │ │  codec            │
    └────────┬────────┘ └────────┬────────┘ └────────┬────────┘
             ▼                   ▼                   ▼
        蓝牙耳机            板载 ES8389         板载 ES8389
```

**关键分歧**：

| 维度 | 蓝牙推流 | SD 卡本地播放 | WAV 播放页 |
|---|---|---|---|
| 是否需要编码 | **要**（SBC，A2DP 要求） | **不要**（直接 PCM 给 codec） | **不要** |
| 是否需要重采样 | **要**（`aud_asrc` 转耳机协商率） | **要**（`rate_cvt` 转 codec 率） | 否（文件即 16k） |
| 重采样实现 | `aud_asrc`（**硬件 ASRC**） | `aud_rate_cvt`（**软件处理链**） | — |
| 框架 | `esp_gmf_pipeline`（手工搭） | `esp_player` + `esp_audio_render`（高层封装） | 无框架，手工循环 |
| 代码位置 | ✅ middleware | ⚠ **UI 层** | ✅ UI 层（调 middleware 的 `post_cmd`） |

> **蓝牙推流与 SD 卡本地播放的核心差异是「要不要编码」**：
> 蓝牙要把 PCM 压成 SBC 才能过 A2DP；本地播放直接把 PCM 写 codec。
> 这个差异决定了蓝牙侧用 `aud_asrc`+`aud_enc`，本地侧用 `rate_cvt`+`ch_cvt`。

## 2. 链路 A：WiFi 推流（`udp_voice`）

### 2.1 对外接口（`udp_voice.h`，7 个 API）

```c
#define UDP_VOICE_TX_PORT 50000   /* 设备 → PC：mic 音频 */
#define UDP_VOICE_RX_PORT 50001   /* PC → 设备：喇叭音频 */

typedef enum {
    VOICE_CMD_TX_ON = 0,   /* 上行开：device mic -> PC */
    VOICE_CMD_TX_OFF,
    VOICE_CMD_RX_ON,       /* 下行开：PC -> device speaker */
    VOICE_CMD_RX_OFF,
} voice_cmd_id_t;

typedef enum {
    VOICE_EVT_TX_ON = 0, VOICE_EVT_TX_OFF,
    VOICE_EVT_RX_ON,     VOICE_EVT_RX_OFF,
    VOICE_EVT_NO_PEER,   /* 对端离线，命令被拒 */
} voice_evt_t;
typedef void (*voice_evt_cb_t)(voice_evt_t evt);

void udp_voice_init(void);
void udp_voice_post_cmd(voice_cmd_id_t cmd);
bool udp_voice_tx_active(void);
bool udp_voice_rx_active(void);
void udp_voice_set_evt_cb(voice_evt_cb_t cb);
```

**调用方**：`ui/tabs/tab_call.c`
- `tx_btn_cb` / `rx_btn_cb` → `udp_voice_post_cmd(...)`（双 toggle，各自独立开关）
- `on_voice()` 回调（`udp_voice_ctl` 任务上下文）→ 只 post 到本地事件队列，
  由 100ms `lv_timer` 抽出后更新 UI
- 掉线（`LINK_EVT_OFFLINE`）时主动下发 `TX_OFF` / `RX_OFF`

### 2.2 内部任务模型

```
control_task (udp_voice_ctl, core0, 8192B, prio5)
   └── 串行消费 s_cmd_queue(8)，按需 xTaskCreate / 回收 tx/rx 任务

tx_task (udp_voice_tx, core0, 8192B, prio7)   ← 仅 TX_ON 期间存活
rx_task (udp_voice_rx, core0, 8192B, prio7)   ← 仅 RX_ON 期间存活
```

**音频通路的开合由「首路开、双关关」决定**：

```c
/* 任一路激活且此前都未激活 → 申请会话 + 开流 */
static void ensure_audio_start(void) {
    if (!s_tx_active && !s_rx_active) {
        if (session_manager_begin(SESSION_UDP_CALL) == ESP_OK
            && audio_stream_start() == ESP_OK) { /* ok */ }
        else { session_manager_end(SESSION_UDP_CALL); }
    }
}
/* 两路都关 → 停流 + 释放会话 */
static void maybe_audio_stop(void) {
    if (!s_tx_active && !s_rx_active) {
        audio_stream_stop();
        session_manager_end(SESSION_UDP_CALL);
    }
}
```

### 2.3 上行（TX）数据流

```
mic ──I2S──▶ audio_stream_read_mic(pcm, 640)   [640B / 20ms]
                  │
                  ▼
        ┌─────────────────────────────────────┐
        │ 12B 帧头（packed 结构体，小端）        │
        │ magic[2]=0xA5 0x5A | ver=1 | type=0 │
        │ seq(u16) | ts_ms(u32) | len(u16)=640│
        └─────────────────────────────────────┘
                  │  652B/包
                  ▼
        link_manager_get_peer() → sendto() → PC:50000
```

- 打包用 **packed 结构体直接写字段**，非手工字节拼装
- 每 2s 打一次 `TX_RMS=%.0f frames=%u` 诊断
- `link_manager_is_online()` 为假时**主动退出循环**（链路掉线即停发）

### 2.4 下行（RX）数据流

```
PC:50001 ──recv()──▶ 校验(magic/ver/type/len)
                        │
                        ├─ 不符 → ++bad，直接丢
                        ├─ seq 大幅回退(< -0x4000) → 判 PC 重启，重同步 + 清槽
                        └─ 合法 → slots[seq % 32] 暂存
                                    │
                 每 20ms 到点取 expected 槽 ──┴──▶ 命中 → write_spk
                                                  ├─ 未到且<60ms → continue（等）
                                                  └─ 未到且≥60ms → 补静音，++lost
```

- 重排窗口 **32 槽**（`REORDER_SLOTS`），槽结构 `{used, seq, pcm[640]}`
- 补齐阈值 **60ms**（`now - last_play_us >= 60000`）
- 每 2s 打一次 `STAT: rx=%u lost=%u bad=%u reorder=%u RX_RMS=%.0f`
- 出帧节拍用 `last_play_us` 单调推进，**不依赖 `select` 超时**

### 2.5 与 ICD 的对应

| 项 | 设备端（C） | PC 端（Python） |
|---|---|---|
| 帧头 | `voice_frame_hdr_t`（packed） | `HEADER = struct.Struct("<2sBBHIH")` |
| 帧常量 | `FRAME_MAGIC0/1`、`FRAME_VERSION` | `MAGIC = b"\xA5\x5A"`、`VERSION = 1` |
| 打包 | 结构体字段赋值 | `pack_voice_frame(seq, ts_ms, pcm)` |
| 校验 | 逐字段比对 | `unpack_voice_frame(packet)` |

> ⚠ **设备端常量与 ICD 文档存在数值不一致**，详见 §5.2。

## 3. 链路 B：蓝牙推流（`bt_push_service`）

### 3.1 对外接口（`bt_push_service.h`，9 个 API）

```c
void      bt_push_service_early_init(void);   /* 开机早期建池，必须在 bsp_display_start() 前 */
esp_err_t bt_push_service_set_uri(const char *path);   /* 登记 MP3 路径（外部触发 A2DP 流） */
esp_err_t bt_push_service_pause(void);
esp_err_t bt_push_service_resume(void);
esp_err_t bt_push_service_stop(void);
bool      bt_push_service_is_playing(void);
void      bt_push_service_request_destroy(void);
/* 由 bt_audio_service 在 STREAM_STATE_CHG 里调用，跑在 BT/GMF 线程 */
void      bt_push_service_on_stream_state(void *stream, int state);
```

**调用方**：`middleware/bluetooth/bt_audio_service.c`
- `bt_audio_service_play_source()`（332-353 行）→ `session_manager_begin(SESSION_BT_PUSH)`
  → `bt_push_service_set_uri(path)`；失败则回滚 `session_manager_end`
- `stop_source()` → `bt_push_service_stop()` + `session_manager_end(SESSION_BT_PUSH)`
- `STREAM_STATE_CHG`（176-182 行）→ `bt_push_service_on_stream_state(handle, state)`
  （转发**完整四态 + stream_handle**，不再压成 bool）

### 3.2 数据流（GMF pipeline）

```
io_file(MP3) ──▶ aud_dec ──▶ aud_asrc ──▶ aud_enc(SBC) ──▶ io_bt ──▶ 耳机
   SD 卡           MP3 解码     硬件重采样      编码          A2DP 输出
                              (目标由耳机协商)
```

**目标格式不写死**——在 `STREAM_STATE_ALLOCATED` 事件里向组件查询：

```c
esp_bt_audio_stream_codec_info_t ci = {0};
esp_bt_audio_stream_get_codec_info(st, &ci);
uint8_t ch = (uint8_t)__builtin_popcount(ci.channels);   /* 位图 → 声道数 */
if (ch == 0) ch = 2;                                     /* 兜底立体声 */
set_asrc_dest(0, ci.sample_rate, 2, ch);                 /* rate + ch + 混音矩阵 */
esp_gmf_audio_enc_reconfig(..., &enc_cfg);               /* 按 ci.codec_type 重配编码器 */
```

### 3.3 四原则（方案 B2「延迟常驻」）

| 原则 | 落地 |
|---|---|
| **P1 时机前置** | pool + pipeline + GMF task 全在 `early_init()` 建，插在 `controller_init()` 之后、`bsp_display_start()` 之前，抢内部 RAM 最空窗口 |
| **P2 显式外置** | GMF task `stack_in_ext=true`（栈进 PSRAM）；`s_uri`(256B) / `s_asrc_weight` 用 `heap_caps_malloc(MALLOC_CAP_SPIRAM)`；`proc_task` 用 `xTaskCreatePinnedToCoreWithCaps(..., MALLOC_CAP_SPIRAM)` |
| **P3 建一次不毁** | `STOPPED` / `RELEASED` 只 `stop()` + `reset()`，**从不 destroy**；反复播放复用同一 pipeline |
| **P4 销毁异步** | `request_destroy()` 只投递命令，绝不在 BT 事件回调里做重活 |

> 补充：`bt_push_service.c` 里定义了 `REAPER_TASK_*` 宏，但**当前实现并未真正创建 reaper 任务**；
> `request_destroy()` 实际只 `post_cmd(CMD_STOP_RESET)`，`CMD_DESTROY` 分支为空。
> 这是「有意保持 pipeline 常驻」的现状，与 P3 一致，但代码里留有未兑现的注释，见 §5.6。

### 3.4 任务与串行化

```
BT/GMF 事件线程（栈小，只做非阻塞动作）
   ├── esp_gmf_io_bt_set_stream()      ← 绑定 BT stream
   ├── esp_bt_audio_stream_get_codec_info()
   ├── set_asrc_dest() / enc_reconfig()
   └── post_cmd(CMD_PREPARE / RUN / STOP_RESET)

bt_push_proc (proc_task, core1, 4096B 栈→PSRAM, prio20)
   └── 串行消费 s_cmd_queue(8)：
       CMD_PREPARE    → set_in_uri + loading_jobs（会阻塞）
       CMD_RUN        → pipeline run
       CMD_STOP_RESET → stop + reset
       CMD_PAUSE/RESUME
       CMD_DESTROY    → （空实现）
```

**这是方案 B2 的核心设计**：把所有会阻塞的 pipeline 操作从 BT 事件线程挪到独立任务串行执行，
对齐官方 `stream_proc.c` 的做法。

### 3.5 四态状态机（`on_stream_state`）

| 状态 | 动作 |
|---|---|
| `ALLOCATED` | 存 `s_stream` → 绑 io_bt → 查 codec info → `set_asrc_dest` + `enc_reconfig` → `post_cmd(CMD_PREPARE)` |
| `STARTED` | `s_playing = true` → `post_cmd(CMD_RUN)` |
| `STOPPED` | `s_playing = false` → `post_cmd(CMD_STOP_RESET)` |
| `RELEASED` | `s_playing = false`；若 `s_stream == st` 则清空；**不 destroy** |

### 3.6 反向链路：A2DP 接收（Sink）—— `bt_sink_service`（2026-09-22 新增）

> §3.1~3.5 讲的是 **Source**（本机把文件推给耳机）。本机还能反过来当**蓝牙音箱**：
> 手机/电脑连上来推音乐，本机解出来放板载喇叭。这条链路独立成
> `middleware/bluetooth/bt_sink_service.c/h`，与 `bt_push_service` **对称但方向相反**。

#### 3.6.1 数据流与管线

```
手机/PC ──A2DP──▶ io_bt(reader) ──▶ aud_dec(SBC/AAC) ──▶ aud_asrc ──▶ io_codec_dev ──▶ 板载 ES8389
                   读 BT stream         解码              重采样       写 codec
```

- 方向与 Source 完全相反：**Source 是 `io_file → … → io_bt(WRITER)`（出去）；
  Sink 是 `io_bt(READER) → … → io_codec_dev(WRITER)`（进来）**；
- `io_codec_dev` **自己不 open codec**，必须在 `SINK_CMD_PREPARE` 里显式
  `esp_codec_dev_open()`（`bt_sink_service.c:381`，只开一次 —— 反复 open/close 会有功放爆音）。

#### 3.6.2 四原则（与 Source 同款「方案 B」策略）

| 原则 | Sink 落地 |
|---|---|
| **P1 时机前置** | `bt_sink_service_early_init()`（`main.c`）紧跟 `bt_push_service_early_init()`，**仍在 `bsp_display_start()` 之前**；pool + pipeline + task 全在此建 |
| **P2 显式外置** | GMF task 栈进 PSRAM；asrc 权重显式 PSRAM |
| **P3 建一次不毁** | pipeline 在 `early_init()` 建一次；`STOPPED` / `RELEASED` 只 `stop()` + `reset()`，**从不 destroy** |
| **P4 线程纪律** | 所有回调跑在 BT/GMF 线程，**绝不碰 LVGL**；只更新 volatile / 投队列，UI 侧 500ms `lv_timer` 抽取 |

#### 3.6.3 AVRCP 元数据拆分（本链路最特别的一处）

国内音乐 App 的「车载蓝牙歌词」是**把当前歌词行覆盖写进 AVRCP TITLE(0x01) 属性**，
让老车机把歌词当"歌名"显示。所以对端推来的 TITLE 是**曲名与歌词共用的一条通道**，
服务侧必须自己拆（`bt_sink_service_get_lyric()` + `burst_resolve()`）：

| 规则 | 判据 |
|---|---|
| ① 真曲名 | 一次完整元数据突发（TITLE→ARTIST→ALBUM）里的**第一个** TITLE 锁住 |
| ② 歌词行 | 之后 TITLE 再变 → 当歌词，走 `get_lyric()`，带递增 `seq`（UI 只在 `seq` 变化时推进动画） |
| ③ 换曲 | **专辑变了** 或 **歌手不再包含已锁歌手**（歌词模式下对端会把 ARTIST 改写成 `"<曲名> (<译名>) - <歌手>"`，故用"包含"仍成立） |

UI 侧 `tab_btsink.c` 把歌词画成「三行窗口」（上一行暗 / 当前行亮 / 待入行全透明），
新句到达时整列上滑一行 + 三行各自做透明度插值，**只用一个 `lv_anim`**。
实测依据与完整日志见 `docs/项目规划/改动记录.md` §28.28 / §28.29。

#### 3.6.4 已知问题

| 项 | 说明 |
|---|---|
| **封面链路已整条删除** | AVRCP Cover Art 在安卓侧默认关闭（默认 AVRCP 1.5 + OEM overlay 常为 false + App 未必交图），实测对端从不推送。删掉后省 ~337KB PSRAM、一个解码任务与一个队列（§28.28）。若将来要封面，git 可回滚，或改走 WiFi 查图兜底 |
| **未接 `session_manager`** | 与 `tab_audio.c`（链路 C）同款问题：自己 `bsp_audio_codec_speaker_init()` 持**独立 codec 句柄**，播放期间若与 UDP 通话/本地播放并发，会同时写同一个 ES8389。见 §5.5 |
| **角色切换是全局动作** | A2DP 是单例，SOURCE ⇄ SINK 切换必须重建整个 host、必然断开当前连接，因此**唯一入口是 page_bluetooth 的按钮**（`bt_audio_service_switch_role`）；切 tab 绝不改角色（`page_main.c` `tab_changed_event` 不变量） |

## 4. 链路 C：SD 卡 MP3 本地播放（`tab_audio.c`）

> 这条链路是**四条播放/接收链路里唯一不遵守分层的**（Source 在 middleware、
> Sink 也在 middleware，只有本地播放把整套逻辑放在了 UI 层），所以单独用一节讲清楚，
> 问题诊断见 §5.5。

### 4.1 模块位置与接口

链路**没有 middleware 模块**，全部实现在 UI 层：

```
main/ui/tabs/tab_audio.c   (538 行，2026-09-22 由 tab_music.c + tab_btpush.c 合并)

```

### 4.5 生命周期与资源

```
tab_audio_build()   → init_player()
                        ├── register_media_defaults()   /* 幂等：s_media_registered 门控 */
                        ├── init_codec()                /* 开 ES8389 @44.1k/2ch */
                        ├── init_gmf_pool()             /* ch/bit/rate/alc 四元素 */
                        └── esp_audio_render_create + esp_player_init
tab_audio_destroy() → esp_player_stop + deinit
                    → esp_audio_render_destroy
                    → esp_gmf_pool_deinit
                    → esp_codec_dev_close
```

**每次 `tab_audio_build()` 都重新建一遍全套资源，`destroy()` 再全拆掉** ——
与蓝牙推流的"建一次不毁"（P3）完全相反的策略。
注意：**LOCAL 出口才有这套本地资源**；BT PUSH 出口复用常驻的 `bt_push_service`
（那边是"建一次不毁"），两者在同一页里是两种截然不同的策略。

### 4.6 与 `session_manager` 的关系 ★

**这条链路完全没有接入 `session_manager`**：

- 它不开 `SESSION_*`，也不检查当前会话模式；
- 但它**独立打开了自己的 codec 句柄**（`bsp_audio_codec_speaker_init()`），
  与 `audio_service` 的 `spk_codec_dev` **是两个不同的句柄指向同一个 ES8389**；
- 结果：**切到 AUDIO tab 用 LOCAL 出口听歌时，若 UDP 通话或 TCP 录音正在跑，
  两条链路会同时向同一个 codec 写数据** —— 听感上是混音或杂音，
  严重时可能触发 codec 驱动内部状态冲突。

> ⚠ 这是当前**最实际的并发风险**，已提升为独立问题 **§5.5** 正式登记
> （含修法：下沉为 `middleware/audio/local_player.c` 并纳入 `SESSION_LOCAL_PLAY`）。
> 同类问题在 **SINK 链路**（§3.6.4）也存在 —— 它也自己开了 codec 句柄。

## 5. 共用底座与架构问题

### 5.0 共用底座：`audio_service` 流式 API

```c
esp_err_t audio_stream_start(void);      /* 开：codec open + 起 audio_stream_task */
void      audio_stream_stop(void);
bool      audio_stream_is_active(void);
size_t    audio_stream_read_mic(uint8_t *buf, size_t len);   /* 从 mic_tx_rb 取 */
size_t    audio_stream_write_spk(const uint8_t *buf, size_t len); /* 写入 spk_rx_rb */
```

`audio_stream_task`（core1 / 8192B / prio8）是 `audio_service` 内部**唯一碰 codec/I2S 的任务**：

```
循环：
  esp_codec_dev_read(mic_codec_dev, mic_frame, 640)
     → ringbuffer_put_force(&mic_tx_rb, ...)      [池 5120B]
  ringbuffer_get(&spk_rx_rb, spk_frame, 640)       [池 3840B]
     → 不足则补零
     → esp_codec_dev_write(spk_codec_dev, spk_frame, 640)
```

`udp_voice` / `record_service` 只读写 ringbuf，**完全不接触 codec**——这是当前分层做得最干净的一块。

> ⚠ 但注意：**"唯一碰 codec"只对 `audio_service` 内部成立，对整个工程不成立** ——
> `ui/tabs/tab_audio.c`、`ui/tabs/tab_video.c`、`middleware/bluetooth/bt_sink_service.c`
> 各自持有**独立的 codec 句柄**（`bsp_audio_codec_speaker_init()`），完全绕过了 `audio_service`。见 §5.5。
>
> ★★ **F42 更正（2026-09-24）——"独立句柄"这个说法只对了一半，是后面一系列静默故障的根**：
> BSP 的 `bsp_audio_codec_speaker_init()` / `microphone_init()` **每次都调 `esp_codec_dev_new()`**，
> 只有 `i2s_data_if` 是 `static` 缓存 ⇒ 工程里那 **5 个 `esp_codec_dev` 对象共用同一个 `i2s_data_if`**。
> 后果（全部**静默**）：
> - `in_enable` / `out_enable` / `fs`（采样率）**是共享的**，而 `input_opened` / `output_opened`
>   **每个对象私有** ⇒ `esp_codec_dev_close()` 与 `open()` 都有**提前返回**分支
>   （不调 `data_if->enable(false)`、也不 `set_fmt`），且 `open()` **不检查 `set_fmt` 返回值**
>   ⇒ 采样率冲突时 `open` 照样打印 "Open codec device OK"，44.1k 被 16k 会话悄悄改掉（或反之）。
> - ⇒ **"让位"不能只 close 自己那个句柄，必须做总线级复位**。落地在 §28.50：
>   `audio_stream_start()` 里先 `bt_sink_service_audio_yield()`，再
>   `close(mic)` → `close(spk)` → `force_reset_shared_i2s()`
>   （对共享 `data_if` 依次 `enable(OUT,false)` → `enable(IN,false)`，**先 OUT 后 IN** 避开
>   `out_disable_pending`）。
> - 生效判据：日志 `I2S_IF: Paired data: ... in_enable: 0, out_enable: 0`（命中快分支）
>   + MIC `frames/2s` 由 ~276 降到 ~100（44.1k stereo → 16k mono）。
> - ⚠ **结构隐患仍在**：根治应把 5 个句柄收敛成 `codec_bus` 单例（列在 `todolist.md` 收尾项）。

### 5.1 问题一：`audio_service` 双职责 + 互斥耦合

`audio_service` 同时提供两套语义不同的 API：

| 套件 | API | 用途 |
|---|---|---|
| **命令式** | `audio_service_post_cmd()` → 播放文件 / 录音 / 音量 / 重复 | WAV 播放页、REC tab |
| **流式** | `audio_stream_*` | UDP 通话、TCP 录音 |

两者**互斥**：`audio_task` 内 `if (!stream_active)` 门控文件播放，
真正的仲裁在 `session_manager`。

**问题在于实现细节泄漏**：帧长 `AUDIO_FRAME_BYTES`、ringbuf 水位策略（"保留最新 6 帧"）
是 `audio_service` 的内部约定，却散落在调用方代码里：

```c
/* udp_voice.c —— 调用方自己知道"帧"是 640B */
uint8_t packet[FRAME_HEADER_BYTES + AUDIO_FRAME_BYTES];
audio_stream_read_mic(pcm, AUDIO_FRAME_BYTES);
```

**边界观察**：`spk_rx_rb_pool[3840]`，而"保留最新 6 帧" = 6 × 640 = **3840B**，
两者**恰好相等**。`audio_stream_write_spk()` 的判定：

```c
while (ringbuffer_data_len(&spk_rx_rb) + len > 6 * AUDIO_FRAME_BYTES) { 丢弃最旧帧 }
```

池容量 = 阈值时，实际稳态只能保住 **5 帧多**（不是 6 帧）。不构成 bug，但
"容量"与"策略"两个独立常数巧合相等，容易被后来的修改误伤。
建议二选一：池扩到 8 帧（5120B，仍远低于 ringbuf 14-bit index 上限 16383B），
或阈值明确降为 5 帧并加注释说明。

### 5.2 问题二：格式假设硬编码散落五处 ★ 最实际的风险

同一组 "16000 / 16bit / mono / 20ms / 640B" 出现在：

| # | 位置 | 形式 |
|---|---|---|
| 1 | `main/middleware/audio/audio_service.h` | `SAMPLE_RATE`、`AUDIO_FRAME_BYTES` |
| 2 | `main/middleware/audio/udp_voice.c` | `FRAME_HEADER_BYTES`、`REORDER_SLOTS`、重排/补齐时长硬编码 |
| 3 | `main/middleware/audio/record_service.c` | `RECORD_CHUNK_PAYLOAD`、`REC_BEGIN` 里写死 `"sample_rate":16000,"channels":1,"bits":16` |
| 4 | `docs/项目规划/通信接口规范_ICD.md §1` | 表格形式 |
| 5 | `pc_host/protocol.py` | `SAMPLE_RATE`、`PCM_BYTES`、`FRAME_MS` |

**改一处要改五处**，且 C 侧与 Python 侧**无法用编译器互相校验**，只能靠人眼比对。

**已证实漂移（2026-09-21 三方对表）**：

| 参数 | 代码实际（C / Python） | ICD 原描述 |
|---|---|---|
| 重排窗口 | **32 槽**（设备端） | "16 帧" |
| 缺帧补齐 | **60ms** | "40ms" |
| 心跳周期 | **200ms** | "PC 每 1s 发" |
| 离线判定 | **5s**（两端） | "2s" |

**对表时额外发现的「双端不对称」**（只对照文档 + 单端代码查不出来）：

| 项 | 设备端（C） | PC 端（Python） |
|---|---|---|
| 重排缓冲 | 定长 **32 槽** `slots[32]`，`seq % 32`（**会覆盖未播帧**） | **无界字典** `dict[seq]`（不覆盖，但内存无上限） |
| 缺帧处理 | **补静音**（保时间轴，计 `lost`） | **直接跳过**（计 `miss`，不补）→ PC 回放时长会短于录制时长 |
| 重同步阈值 | 回退 **> 0x4000** 判重启 | 回退 **> 0x7FFF** 判重启 |

> **这三处不对称当前无害**（重排逻辑只在接收侧用，两端不同时为接收方），
> 但**必须知情**——未来若改为双端都做重排，需要重新评估。
> 结论：**对表必须是三方对表（文档 × C × Python）**，本次四处漂移 + 三处不对称
> 全部靠三方对表才暴露。

**处理结论（用户决策）**：**以代码为准，代码跑过没问题**。
ICD 已升级 V1.2 回填上述全部内容，见 `通信接口规范_ICD.md` §1 / §3.2 / §4.3 / §6。

### 5.3 问题三：`udp_voice` 职责过重

288 行里装了三种变化原因完全不同的东西：

| 职责 | 代码位置 | 变化驱动 |
|---|---|---|
| ① 协议编解码 | `voice_frame_hdr_t` + 字段逐项校验 | ICD 版本 |
| ② 网络重排序 | `slots[32]` + `expected` + 补齐逻辑 | 网络质量调优 |
| ③ 音频送取 | `audio_stream_read_mic` / `write_spk` | `audio_service` 接口 |
| ④ 会话与任务 | `control_task` / `ensure_audio_start` | 业务模式变更 |

②③ 各自都还是**纯逻辑**（无 IO 依赖），却被焊死在同一个 `.c` 里，
导致无法单独测试、无法单独调参。

### 5.4 问题四：`link_manager` 反向依赖 `udp_voice` ★ 分层方向倒挂

`link_manager.c` 位于 `middleware/bluetooth/`，却：

```c
#include "middleware/audio/udp_voice.h"      /* ← bluetooth → audio */
...
if (strstr(packet, "SESSION_START")) {
    udp_voice_post_cmd(VOICE_CMD_TX_ON);
    udp_voice_post_cmd(VOICE_CMD_RX_ON);
}
```

**三重问题**：

1. **目录与依赖矛盾**：`link_manager` 管的是 **UDP 50003 信令与 peer 状态**，
   本质属网络层，被放进 `bluetooth/` 已经勉强（`01_工程分层架构.md` 的
   "依赖方向"节里写着 `audio → bluetooth（link_manager）`，即设计意图是 audio 依赖它）；
2. **反向依赖**：它又反过来 `include udp_voice.h`，形成 `bluetooth → audio`，
   与文档声明的方向**相反**；
3. **信令分发硬编码到具体业务**：`SESSION_START` 本该是"广播一个事件"，
   现在直接调具体模块的 API，加第三条链路时必须再改 `link_manager`。

**好消息**：它已经有 observer 机制（`LINK_MAX_OBSERVERS = 4`、`notify_observers()`），
改造代价很低。

### 5.5 问题五：本地播放 / 蓝牙接收 两条链路绕过 `session_manager` ★ 最实际的并发风险

`ui/tabs/tab_audio.c` / `tab_video.c` / `middleware/bluetooth/bt_sink_service.c`
**都不开 `SESSION_*`，也不检查当前会话模式**，却各自
`bsp_audio_codec_speaker_init()` 拿到一个**独立于 `audio_service` 的 codec 句柄**。

| 项 | `audio_service` | `tab_audio` / `tab_video` / `bt_sink_service` |
|---|---|---|
| codec 句柄 | `spk_codec_dev`（`audio_service.c` 内部） | `s_codec`（各自持有） |
| 是否登记 `session_manager` | ✅ `SESSION_UDP_CALL` / `SESSION_TCP_RECORD` / `SESSION_BT_PUSH` | ❌ **无**（枚举里没有 `SESSION_LOCAL_PLAY` / `SESSION_BT_SINK`） |
| 写入者 | `audio_stream_task`（单任务） | UI 层回调 / GMF `io_codec_dev` 任务 |

**多个句柄指向同一个 ES8389**。切到 AUDIO（LOCAL）/ VIDEO tab 播放、或 SINK 收到推流时，
若 UDP 通话或 TCP 录音正在跑，多条链路会**同时向同一 codec 写数据** ——
听感上是混音或杂音，严重时可能触发 codec 驱动内部状态冲突。

> ⚠ 这是当前**最实际的并发风险**。修法见 §6 的「★★ 优先级最高」小节
> （把本地播放下沉为 `middleware/audio/local_player.c`，纳入 `SESSION_LOCAL_PLAY`；
> SINK 同理需要新增 `SESSION_BT_SINK` 并在 `bt_sink_service` 的 PREPARE 前申请）。

## 6. 优化方向（按收益/成本排序）

### ★★ 优先级最高：修 §5.5 —— 把本地播放链路搬出 UI 层

这是**唯一一条同时踩了两个红线**的链路：

| 红线（`01_工程分层架构.md` 明令禁止） | 实际违反处 |
|---|---|
| ❌ "ui 层直接 `esp_codec_dev_write`" | `tab_audio.c`（LOCAL 出口的 `audio_out_write`）、`tab_video.c` |
| ❌ "ui 层直接 `xTaskCreate` 硬件任务"（精神上：直接管硬件资源） | `tab_audio` / `tab_video` 各自 `bsp_audio_codec_speaker_init()` + `esp_gmf_pool_init()` |

**建议方案**：新增 `middleware/audio/local_player.c/h`，把这条链路整体下沉：

```c
/* middleware/audio/local_player.h —— 与 udp_voice 同层的"播放器"抽象 */
typedef enum { LOCAL_PLAYER_EVT_FINISHED, LOCAL_PLAYER_EVT_ERROR } local_player_evt_t;

void      local_player_init(void);          /* 建 pool + render + codec（幂等，建一次） */
esp_err_t local_player_play(const char *path);
esp_err_t local_player_pause(void);
esp_err_t local_player_resume(void);
esp_err_t local_player_stop(void);
bool      local_player_is_playing(void);
void      local_player_set_evt_cb(void (*cb)(local_player_evt_t));
```

**收益（三层）**：

1. **分层归位**：UI 回到"只 post_cmd / 收事件"，与 `tab_call` / `tab_record` 一致；
2. **解决并发风险**（§5.5）：下沉后可统一纳入 `session_manager`，
   申请 `SESSION_LOCAL_PLAY`，与 `UDP_CALL` / `TCP_RECORD` / `BT_PUSH` **互斥**，
   彻底消除"两条链路同时写同一 codec"；
3. **顺手修掉 §5.5 所属链路缺失的完成回调**：`local_player_set_evt_cb` 天然带事件面。

> 蓝牙推流（`bt_push_service`）已经证明了这套做法是可行的 ——
> 同样是"文件 → 解码 → 输出"，它规规矩矩待在 `middleware/bluetooth/` 里。
> **本地播放没有理由做不到。**

### ★ 推荐做：C —— 拆解 `udp_voice`

```
udp_voice.c          编排层：状态机 + 任务生命周期 + 事件通知（~80 行）
voice_protocol.c/h   纯函数：帧头 pack/unpack、magic 校验          ← 可单测
voice_jitter.c/h     纯逻辑：重排环形 + 水位策略 + 补齐判定         ← 可单测
```

**收益**：
- 前两层是**纯函数/纯数据结构，零 IO 依赖**，可以直接在 PC 上跑单元测试，
  甚至与 `pc_host/tests/test_protocol.py` **共用同一张测试向量表**
  （同一组 seq/payload 输入 → 双端结果对拍），把 §5.2 的漂移问题变成"测试能发现的问题"；
- 常量集中到 `voice_protocol.h`，从五处收敛到两处（C 侧头文件 + ICD 文档）；
- 重排策略独立后，调网络抗抖动不用读 288 行代码。

### ★ 推荐做：修 §5.4 —— `link_manager` 依赖方向

方案：`link_manager` 新增信令事件（复用现有 observer 队列），
`udp_voice` 自己订阅 `LINK_EVT_SESSION_START / STOP`，`link_manager` 不再 include `udp_voice.h`。

更彻底的方案是把 `link_manager` 归入 `middleware/network/`（它管的是 UDP 信令，不是蓝牙）。
**但归属变更会牵动 `01_工程分层架构.md` 与 §20 的重构记录，
建议与 §5.4 的事件解耦一起做，不要单独搬家。**

### ★ 推荐做：修 §5.1 边界

`spk_rx_rb_pool` 3840B ↔ 阈值 6 帧 3840B：二选一（池扩到 5120B 或阈值降为 5 帧）。

### 可做：A 最小版 —— 抽"音频出口"薄封装

在 `audio_service` 之上加极薄一层，把 `AUDIO_FRAME_BYTES` / ringbuf 水位收进去：

```c
esp_err_t audio_out_read_mic(uint8_t *buf, size_t *inout_len);   /* 帧长由服务决定 */
esp_err_t audio_out_write_spk(const uint8_t *buf, size_t len);
```

`udp_voice` 与 `record_service` 改用它。**注意：不要做成"统一推流接口"大抽象**——
三条播放链路的差异（实时 vs 文件、双向 vs 单向、写死 vs 协商、编不编码）是本质的，
强行统一会退化成一堆 `if (mode)` 分支。

> 若 §5.5 的 `local_player` 落地，这一层可以顺带一起做 ——
> **`local_player` 本质上就是"音频出口"的一个特例**（只出不进、走自己的 GMF pool）。

### 暂不做：B —— 格式转换抽象化

蓝牙与本地播放的格式转换**都已由 GMF 承担**（蓝牙用 `aud_asrc` + `aud_enc`，
本地用 `rate_cvt` + `ch_cvt`），再叠一层 C 侧抽象是重复投资；
WiFi 链路格式写死、不需要转换。现在做属过度设计。

### 明确不建议：大规模重构

三条播放链路都在正常工作，`session_manager` 的单槽仲裁设计正确。
§5.5 + C + §5.4 + §5.1 属于局部手术，风险可控。**在没有新链路需求前，
不要为了"看起来对称"去改主体结构。**
