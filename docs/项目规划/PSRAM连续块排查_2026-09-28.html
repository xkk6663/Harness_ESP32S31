拍照/录像 720p 起流失败 · 根因与修复

2026-09-28 · 分支「端侧人脸识别」· 工程 display_audio_photo · 用户报告："偶尔会出现拍照存 SD 失败的 BUG"

一句话结论：不是"偶发 bug"，是 PSRAM 预算问题。 拍照/录像/取景器都走 1280×720 JPEG，起一次流要从 PSRAM 拿 3 块各 921,600 B、且必须连成一片 = 2,764,800 B（2.64 MB）。 而实测「加载 FACE 检测模型之后」的 PSRAM 最大连续块只剩 2,686,976 B（2.56 MB） —— 差 77,824 B，拿不到。
largest 在 2.7 MB 附近上下抖动 ⇒ 有时够（成功）、有时不够（失败）= "偶尔"。

取景器（VIDEO 页，同一个病）

两条路都走 CAM_MEDIA_W/H = 1280×720 JPEG ⇒ 同一个根因。 "拍照失败"只是它最容易被看见的那一面。

2 根因：三块连续块，拼不出来

#块谁分配单块字节源码位置
①V4L2 mmap 缓冲 ×2esp_videoesp_video_buffer_create()921,600esp_video_buffer.c:47
②DVP backup buffer ×1ESP-IDF DVP 驱动921,600esp_cam_ctlr_dvp_cam.c:262-278 / :866
合计（BUF_CNT=2）2,764,800 B（2.64 MB），且必须是一段连续空间

单块尺寸真源：esp_video.c:84 里 JPEG 的 bpp = 8 ⇒ w*h*bpp/8 = 1280×720 = 921,600。backup buffer 用的是同一个数 （get_frame_size() 对 JPEG 直接给 h_res*v_res）。

★ 先把 caps / DMA 这条猜测彻底排除

backup buffer 请求的是 MALLOC_CAP_SPIRAM | MALLOC_CAP_DMA，看着像"要一块 DMA 能用的 PSRAM"，很容易怀疑 S31 上不存在这种内存。**但 IDF 在查 heap 之前就把 DMA 位摘掉了**：

/* components/esp_hw_support/heap_align_hw.c:101-108 */
// Workaround: the heap allocator doesn't have regions marked
// `MALLOC_CAP_DMA | MALLOC_CAP_SPIRAM` so we need to request those
// without the DMA flag.
if (caps & MALLOC_CAP_SPIRAM) {
    caps &= ~MALLOC_CAP_DMA;
}

（真因：S31 的内存类型表里 SPIRAM 一栏确实没有 DMA —— heap/port/esp32s31/memory_layout.c:52。）
⇒ 这个分配实际就是 MALLOC_CAP_SPIRAM 分配 ⇒ 只可能是"PSRAM 里找不出这么长一段空地"，与 caps、DMA、SD 卡、sensor 全都无关。 这也是"PSRAM free 还剩几 MB 却分配失败"的唯一解释。

4 本轮改动（2 个文件）

4.1 main/middleware/mem_diag.h —— 补 PSRAM largest

该文件自己写着判读口径"只看 largest_free_block，不看 free_size"， 但 PSRAM 那一栏只打了 free。代价已出现两次（§61 POSE、§67 本次）——两次都只能靠 组件自己打的日志反推。

-  "want=%u B | INT free=%u largest=%u | DMA free=%u | PSRAM free=%u"
+  "want=%u B | INT free=%u largest=%u | DMA free=%u | PSRAM free=%u largest=%u"

MEM_DIAG_FMT 与 MEM_DIAG_ARGS 是配对宏，两边同时改；引用它的 12 个文件全部复验。

4.2 main/middleware/camera/camera_service.c —— 预检 + 缓冲数可调

  • 新增 MEDIA_BUF_CNT（#ifndef 包住，可 -D 覆盖）： 媒体档单独一份缓冲数，默认 = 1。预览档仍用 BUF_CNT=2。
    连续块需求vs 实测 worst case（2,686,976）
    MEDIA_BUF_CNT=22,764,800（2.64 MB）不够
    MEDIA_BUF_CNT=11,843,200（1.76 MB）富余 843,776
    另加 _Static_assert(MEDIA_BUF_CNT <= BUF_CNT) 钉住 s_buf[] 数组尺寸。
  • REQBUFS / mmap 循环改用 nbuf = cam_stream_buf_cnt(fmt)（原来写死 BUF_CNT）。
  • 新增 cam_stream_mem_check()：在 camera_service_start_fmt_owner() 里、 任何硬件动作之前（ov3660_fmt_lookup 之后）打一行诊断。 位置刻意选在"上一次的流已拆干净、本次缓冲还没分配"⇒ 这一行就是驱动将要面对的真实 heap。
  • STREAMON 失败分支不再只打 STREAMON fail，改为把 largest vs need 与"大概率是碎片"一起打出来。

5 ★ 代价与回退（务必读）

MEDIA_BUF_CNT=1 意味着： 帧回调执行期间来的帧会落到驱动 backup buffer 上被丢弃 （cap_frame_cb / rec_frame_cb 里是 fwrite / avi_muxer_add_jpeg 同步写盘）。

路径影响
CAM 页预览（240×240 RGB565）不受影响（走另一份计数 BUF_CNT=2）
VIDEO 页取景器无影响：本来就按 VF_MIN_INTERVAL_US=150 ms 限速主动丢帧
拍照无影响：只要 1 张可用帧（预热帧本来就丢）
录像可能掉帧：帧率 ≈ 1 / (写盘耗时 + 1~2 个帧周期)。 标称 12 fps（83 ms/帧），若 100 KB JPEG 写盘 50 ms ⇒ 实际约 5~7.5 fps

怎么当场判定：VIDEO 页已有的两个指标就够 —— fps（s_stats.fps_x100）与 VFD: ... dropped=N。

回退 / 后续路线（代价从低到高）：
1. 只给录像恢复 2 个缓冲：把缓冲数做成 camera_service_start_fmt_owner() 的参数， capture_service 传 1、record_video_service 传 2 ⇒ 录像保住 12 fps， 但录像仍暴露在本 bug 下。
2. 让 muxer 不再同步写盘：帧回调只把 JPEG 拷进 PSRAM 队列，由独立任务写 SD （rec_local_service 那套模式）⇒ 对录像零代价，这是真解。

⚠ 明确不做（会 panic）：不要同时"关掉 DVP backup buffer"。 esp_cam_ctlr_dvp_cam.c:179-181 在拿不到任何缓冲且 bk_buffer_dis 时走 assert(false && "no new buffer, and no driver internal buffer") ⇒ 把"SD 卡卡一下丢帧"升级成"直接 panic"。

6 上机验证判据

CAM: [streammem] JPEG 1280x720 need=1843200 B contiguous
     (1 x 921600 B + 1 backup) | PSRAM free=.. largest=..
  • 这一行必须每次拍照/录像/进取景器都出现（不出现 = 预检没接线）。
  • largest >= 1843200 ⇒ 起流应成功：CAPTURE: capture -> /sdcard/... + capture done: err=ESP_OK。
  • 若 largest < 1843200 ⇒ 会跟一行 [streammem] NOT ENOUGH CONTIGUOUS PSRAM: + 空闲块分布 ⇒ 把那段贴回来，能直接判是碎片还是总量。
  • 录像同时看 fps 与 VFD dropped，按上面第 5 节决定要不要走回退路线。

7 这一轮没做的事（写明白，免得以为是修好了）

  • 没有改 engine_mem_ok() 的阈值。§66 那次 MFN 失败 （Failed to alloc 820.75KB PSRAM, largest 720.00KB）现在能算清楚了： 加载时 PSRAM 里同时要有 1,295,200 B 的模型文件缓冲 + 820.75 KB 的 arena （fbs_loader.cpp SDCARD 模式整块读；root_alloc() 再要一块）， 而现有预检只要求 largest ≥ 最大单文件 + 64 KB ⇒ 阈值偏松，没拦住。 属于 S8 那条线，等下一次上机的 PSRAM largest 实测值再定阈值。
  • 没有改取景器 / 文件预览的常驻缓冲策略（"开机一次性拿齐、永不释放"仍是正确策略）。
