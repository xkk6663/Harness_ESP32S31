## 1. 原理：内存到底分几块

### 1.1 物理内存分区

ESP32-S31（及同类 SoC）上，内存不是"一块"，而是**若干块物理上独立、访问特性不同**的区域：

```
┌─────────────────────────────────────────────────────────┐
│  Internal SRAM（内部 SRAM）—— 稀缺、快、DMA 可达          │
│  ┌───────────────┬───────────────────────────────────┐  │
│  │ .bss / .data  │ 内部堆（_heap_start ~ _heap_end）  │  │
│  │ 静态变量       │ malloc 从这里出                    │  │
│  │ 静态池 ←───────┤                                   │  │
│  └───────────────┴───────────────────────────────────┘  │
├─────────────────────────────────────────────────────────┤
│  SPIRAM / PSRAM（外部，16MB）—— 大、稍慢、DMA 视 SoC 而定 │
│  ┌───────────────────────────────────────────────────┐  │
│  │ PSRAM 堆（被分成 SPIRAM_0 / SPIRAM_1 两个物理池）   │  │
│  └───────────────────────────────────────────────────┘  │
├─────────────────────────────────────────────────────────┤
│  Flash（16MB）—— 只读，不能放运行期数据                   │
│  ├─ .rodata / .text                                      │
│  └─ NVS / FATFS / littlefs 分区                          │
└─────────────────────────────────────────────────────────┘
```

**关键点：**

1. **`.bss` / `.data`（静态变量、静态数组）不在堆里。** 它们是链接期就定址的段，
   和"堆"是**并列关系**，不是包含关系。
2. **堆只是 `_heap_start ~ _heap_end` 之间的一段。** 内部堆和 PSRAM 堆是
   **两个独立的堆管理器**，各自维护自己的空闲链表。
3. **PSRAM 有 SPIRAM_0 / SPIRAM_1 两个物理池**，粒度比内部堆粗，
   碎片化后更难恢复。

### 1.2 静态分配 vs 动态分配

| | 静态分配 | 动态分配 |
|---|---|---|
| 写法 | `static uint8_t buf[5120];` | `malloc(5120)` / `heap_caps_malloc(...)` |
| 所在段 | `.bss`（或 `.data`）**不在堆里** | 堆里 |
| 定址时机 | **链接期**（编译完就定了） | **运行期** |
| 大小可否变化 | 否（编译期常量） | 是 |
| 是否参与碎片 | **完全不参与** | 参与（分配/释放产生空洞） |
| 失败路径 | **不存在**（编译不过就是编译不过） | 存在（返回 NULL） |
| 能否审计 | `idf.py size` 直接看 | 只能跑起来看 |
| 灵活性 | 低（要预留最坏情况） | 高 |

**一句话概括差异：**

> 静态分配是**"提前买好地"**，地是你的，永远不会被别人的房子夹住。
> 动态分配是**"当场找地"**，找得到找不到、找到的是不是一整块，全看运气。

### 1.3 碎片化的机制：为什么"内存够用"却"申请不到"

**碎片化的本质不是"内存变少"，而是"空闲内存被切成了不连续的小块"，
导致"总空闲量够"但"最大连续块不够"。**

用一张图说明。假设内部堆有 100KB 空闲，但分布如下：

```
[已用: LCD 32KB][空洞 4KB][已用: WiFi 18KB][空洞 2KB][已用: BT 24KB][空洞 6KB][已用: 音频 14KB]
                                                       ↑
                                          总空闲 = 4+2+6 = 12KB
                                          最大连续块 = 6KB
```

此时：
- 申请 5KB → **成功**（拿到 6KB 那块）
- 申请 8KB → **失败**（总空闲 12KB 够，但没有 8KB 的连续块）
- 申请 32KB → **失败**（哪怕总空闲有 60KB）

**这就是 `ESP_ERR_NO_MEM (0x101)` 的真面目。** 它不是"内存用完了"，
而是"内存被切碎了"。

### 1.4 空洞是怎么产生的

```c
void *a = malloc(1024);   /* 分配 */
void *b = malloc(2048);   /* 分配 */
void *c = malloc(1024);   /* 分配 */
free(b);                  /* ← 产生一个 2048B 空洞，被 a 和 c 夹住 */

void *d = malloc(4096);   /* 2048B 空洞装不下 4096B → 只能去更远处找 */
                          /* 结果：原处的空洞被"浪费"，堆的连续性下降 */
```

**碎片化速率取决于三个因素：**

| 因素 | 影响 |
|---|---|
| **分配/释放的频率** | 越频繁，产生空洞越多 |
| **尺寸的不一致性** | 尺寸越杂（1KB/2KB/4KB 混用），越难复用空洞 |
| **生命周期的不一致性** | 长短命对象交错，长命对象会"钉住"位置，把空洞隔开 |

**三个因素叠加时碎片化最快。** 本工程恰好三条全中 —— 见 §3。

### 1.5 一个反直觉但极重要的推论

> **把一块 buffer 从"动态"改成"静态"，不仅不加剧碎片，反而减轻碎片。**

原因：静态池占的是 `.bss`，**压根不进堆**。
它不产生空洞、不被空洞夹住、永不释放。

**代价只有一个：内部 SRAM 的静态占用增加。**

所以"改成静态"这个动作的本质是
**"用一块确定的、显式的内存，换掉一块不确定的、运行期的内存"**。

**决策问题不是"要不要花这块内存"，而是"花在静态池上划算，还是留着当堆的余量划算"。**
判断标准见 §4。

### 1.6 分配器到底做了什么、做不到什么 ★

> 这一节纠正一个常见误解：**"换了好分配器就不碎片了"** —— 不成立。

#### 1.6.1 本工程用的不是 FreeRTOS heap4，是 TLSF

先纠正一个容易搞错的认知。本工程 sdkconfig 里的证据：

```
CONFIG_ESP_ROM_HAS_HEAP_TLSF=y            # ROM 内置 TLSF 实现
CONFIG_HEAP_TLSF_USE_ROM_IMPL=y           # 实际使用 ROM 里的 TLSF
CONFIG_ESP_ROM_MULTI_HEAP_WALK_PATCH=y    # 多堆遍历补丁
```

而 **`CONFIG_FREERTOS_HEAP_*` 在本工程的 sdkconfig 里根本不存在** ——
因为 **ESP-IDF 不使用 FreeRTOS 的 heap_1~5**。

**为什么不用 heap4？** 因为 heap4 只能管理**一个连续内存区**，
而 ESP 的内存**不是一个堆**：

| 堆 | 说明 |
|---|---|
| 内部 DRAM 堆 | 主堆 |
| 内部 DMA-capable 子集 | 从内部堆中划出的、能被 DMA 访问的部分 |
| PSRAM 堆 | 还被分成 **`SPIRAM_0` / `SPIRAM_1` 两个物理池** |
| RTC 内存堆 | 本工程开了 `CONFIG_ESP_SYSTEM_ALLOW_RTC_FAST_MEM_AS_HEAP=y` |

`heap4` 管不了这个结构，所以 IDF 换成了 **TLSF（Two-Level Segregated Fit）**。

**TLSF 的核心特点：分配与释放是 O(1) 常数时间** ——
用**位图 + 分级空闲链表**实现，不遍历链表。这是为**实时性**设计的。

#### 1.6.2 TLSF 解决的是速度，不是碎片

这是全节最重要的一句话：

| 问题 | TLSF 能否解决 |
|---|---|
| 分配速度慢（遍历链表） | ✅ 解决（O(1)） |
| 相邻空闲块合并 | ✅ 解决（coalesce，见下） |
| **外部碎片** | ❌ **解决不了** |
| **"总空闲够但无大块"** | ❌ **解决不了** |

**任何分配器都躲不过这个数学事实。** 碎片化不是"管理器的缺陷"，
是"程序分配模式"的必然结果。

#### 1.6.3 空闲块确实会自动拼接 —— 但只在"物理相邻"时

TLSF（和 heap4）**确实**会自动合并相邻空闲块，这个动作叫 **coalesce**，
在 `free()` 里执行：

```
释放一个块时，检查它物理相邻的前/后块是否也空闲：
  ├─ 相邻块空闲 → 合并成一个大块
  └─ 相邻块在用 → 本块独立存在
```

**所以碎片不是"系统不会拼"，而是"拼不起来"。**

```
[已用: LCD][空闲 4KB][已用: WiFi][空闲 2KB][已用: BT][空闲 6KB][已用: 音频]
                 ↑                ↑              ↑
            这三个空闲块物理上不相邻 —— 中间隔着的都是 still-allocated 的块
```

合并的前提是**"相邻且都空闲"**，而这里永远不满足。

#### 1.6.4 为什么不能让碎片"压缩合并"（compaction）

要让碎片连片，理论上有两条路，但**只有一条在嵌入式可行**：

| 手段 | 做法 | 嵌入式可行性 |
|---|---|---|
| **compaction（压缩）** | 把已用块搬到一起，空闲自然连片 | ❌ **不可行** —— 有指针指向这些块，搬家会让**所有指针失效**。除非有 GC 或句柄表，嵌入式没有 |
| **等待释放** | 等"钉子户" `free()` 掉，自然合并 | ⚠️ 但长生命周期对象（LCD 帧缓冲、协议栈缓冲）**永不释放** |

> 这正是"内存池 / arena / 静态化"这类手法存在的根本原因 ——
> **既然不能事后整理，就只能事前避免。**

#### 1.6.5 三种"看起来像内存不足"的故障，必须区分

这是 §3.3 那条"日志打三元组"规则的**理论依据**：

| 现象 | `free_size` | `largest_free_block` | 含义 | 对策 |
|---|---|---|---|---|
| 真的用完了 | 小 | 小 | 内存总量不足 | 省内存 / 换区域 |
| **碎片化** | **大** | **小** | 内存够但被切碎 | **改分配模式**（本工程 F23） |
| 分配器元数据耗尽 | 大 | 大 | 极少见 | 检查 TLSF 结构/堆损坏 |

**只看 `free_size` 永远分不清是哪种病。**

F23 当时如果日志里有这一行，**一眼就能判定是碎片化**，
不必去读 `sdmmc_cmd.c` 源码靠"减半重试"反推。

### 1.7 三种"去碎片"手段的区别与选择 ★★

> 常被笼统说成"把动态改成静态"，但**实际有三种手段，机制完全不同**。
> 分不清会导致"用错药"或"以为只有一条路"。

| 手段 | 做法 | 内存去哪 | 消灭了什么 | 本工程实例 |
|---|---|---|---|---|
| **A 静态池** | `static uint8_t buf[N]` | **`.bss`，不进堆** | 该块内存**完全不参与**碎片 | 音频 `mic_tx_rb_pool` / `spk_rx_rb_pool` / `play_rb_pool` / `rec_rb_pool` |
| **B 预分配常驻** | 开机 malloc 一次、**永不释放、反复复用** | **仍在堆里** | 把 **N 次不确定分配压成 1 次确定分配** | **F23 的 `s_dma_bounce`** |
| **C 换区域** | 改 caps 挪到 PSRAM | 换个堆 | 内部 RAM 被释放（**不治碎片**） | **F19 的 jpeg_buf** |

#### 为什么 B 也有效（关键）

有人会问：B 还在堆里，凭什么治碎片？因为**碎片产生速度取决于"分配/释放的频次与尺寸杂度"**：

```
修复前：每次读盘 → malloc(不确定大小，可能减半重试) → 用完 free
        1 分钟读盘 100 次 = 100 次 malloc/free = 100 次制造空洞的机会

修复后：开机 malloc(32KB) → 永不 free → 复用
        1 次 malloc = 1 次机会，且此后为 0
```

**B 的价值在于"把变动量变成常量"。** 没有分配就没有碎片。

#### 什么时候**只能**选 B（不能选 A）

F23 就是典型 —— 那个缓冲**必须由驱动持有**：

```c
host->dma_aligned_buffer = s_dma_bounce;   /* 指针要交给驱动，且驱动靠"非 NULL"判断是否复用 */
```

两个约束让它**无法改成 `.bss` 静态数组**：
1. 指针要交给驱动（`host` 结构体持有），生命周期由驱动决定；
2. 32KB 若放内部 `.bss`，会**反过来挤压内部 RAM**，违背 F23 的本意。

**所以"该选哪个手段"不是偏好问题，是约束决定的。**

#### 选择判据（三问）

```
1. 尺寸是编译期常量吗？
   ├─ 否 → A 不可用（如 MP3 解码缓冲，尺寸取决于码流）
   └─ 是 → 继续

2. 必须交给外部模块（驱动/框架）持有吗？
   ├─ 是 → 只能 B（预分配常驻）
   └─ 否 → 继续

3. 生命周期是整个程序吗？
   ├─ 是 → A（静态池）最优
   └─ 否（跟 UI/会话走）→ 先问"能否改成建一次+开关复用"？
                          ├─ 能 → B
                          └─ 不能 → 收进中间层统一管理，不要散在 UI 回调里
```

## 2. 结合本工程：默认配置为什么格外脆

这不是"写错了"，而是**默认配置恰好在这块板子上是最脆的组合**。

### 2.1 四个叠加的结构性因素

#### 因素一：内部 RAM 有多个"启动期大头"，且互相钉死

| 占用者 | 性质 | 时机 |
|---|---|---|
| bluedroid（BTU/BTC 队列 + HCI mempool） | **启动时静态分配**，事后改堆布局会使其申请失败 | 开机早期 |
| LCD 帧缓冲（800×480） | 大块常驻 | 显示初始化 |
| WiFi / LWIP | 大量缓冲 | 连接时 |
| GMF 音频解码器工作区 | 不等长、跟随播放 | 推流常驻时 |

**这是最关键的一点**：bluedroid 的内存池是**启动时一次性静态分配**的。
这意味着**开机那一刻的堆布局是"定死的"** —— 后续任何改变堆布局的操作
（比如临时 malloc/free 大块）都可能让 bluedroid 的后续申请失败。

这正是"方案 B 四原则"里 **P1 时机前置**的由来：

```
P1 时机前置：pool + pipeline + GMF task 全在 early_init() 建，
            插在 controller_init() 之后、bsp_display_start() 之前，
            抢内部 RAM 最空窗口
```

**你不是在跟"内存不够"斗，你是在跟"内存被谁按什么顺序占走"斗。**

#### 因素二：`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0` 让裸 malloc 行为不直观

本工程的 PSRAM 配置：

```
CONFIG_SPIRAM_USE_MALLOC=y                  # PSRAM 并入堆
CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0       # ← 小于阈值也优先给 PSRAM
CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y      # WiFi/LWIP 占 PSRAM
CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL=32768 # 内部保留 32KB
CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y
CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y
```

`ALWAYSINTERNAL=0` 意味着：**小块分配也优先落到 PSRAM。**

后果有两面：

- **好处**：内部 RAM 省下来了；
- **坏处**：**PSRAM 分配器只有两个物理池，粒度粗，碎起来比内部堆严重得多**；
  而且"需要内部 RAM 的东西"（DMA 缓冲、`spi_flash` 缓存、中断栈）
  在需要时可能已经拿不到了。

**所以：裸 `malloc()` 在本工程是一个"行为不直观"的操作 ——
你无法从代码一眼看出它落到哪块内存。**
这就是规范里 **C1「使用 `heap_caps_*` 而非裸 malloc」** 的由来。

#### 因素三：业务层有"按需重建全套资源"的模式

**链路 C（`ui/tabs/tab_audio.c`，原 `tab_music.c`）** 是典型：

```c
tab_music_build()   → init_player()
                        ├── register_media_defaults()
                        ├── init_codec()          /* 开 ES8389 */
                        ├── init_gmf_pool()       /* ch/bit/rate/alc 四元素 */
                        └── esp_audio_render_create + esp_player_init
tab_music_destroy() → esp_player_stop + deinit
                    → esp_audio_render_destroy
                    → esp_gmf_pool_deinit
                    → esp_codec_dev_close
```

**每次切进 MUSIC tab 都 malloc 一整套，切出去再 free 一整套。**

这是碎片最经典的制造机：
- **反复** malloc/free → 高频（因素一：频率）
- GMF 各元素的缓冲**尺寸不一** → 尺寸杂（因素二：不一致性）
- 有些资源（codec、pool）**生命周期长于单次播放** → 长短交错（因素三：生命周期）

对比蓝牙推流的 **P3「建一次不毁」**：

```
P3 建一次不毁：STOPPED / RELEASED 只 stop() + reset()，
             从不 destroy；反复播放复用同一 pipeline
```

**同一个工程里，两条链路的内存策略完全相反。**
蓝牙那条（常驻复用）是对的，本地播放这条（反复重建）是脆的。

#### 因素四：GMF 解码器的工作缓冲是动态申请的

MP3 解码器 `aud_dec` 内部的 window / huffman 表 / 帧缓冲、
`esp_audio_render` 的处理链缓冲，**都走 malloc**，尺寸不一、生命周期跟随播放。

**一次播放/停止就是一轮碎片循环。**

### 2.2 两个"诊断开关"是关着的

```
CONFIG_HEAP_POISONING_DISABLED=y    # 越界 / use-after-free 不会被抓
CONFIG_HEAP_TRACING_OFF=y           # 崩了查不到是谁干的
```

配置本身**合理**（省 RAM、提速），但意味着：

> **你的崩溃基本是"事后诸葛"式的 —— 只能靠日志反推，没有工具兜底。**

F23 的定位过程就是最好的例子（见 §3.2）。

## 3. 本工程踩过的坑，逐条反推"错在哪"

### 3.1 F19 —— JPEG 输入缓冲误标 `MALLOC_CAP_DMA`

> **现象**：`WP_OVERLAY: no dma mem for jpeg buf`，壁纸不显示。
> **根因**：JPEG **输入**缓冲（存压缩文件字节流）被标成 DMA-capable，占内部 SRAM；
> 摄像头/LCD/粒子一起跑时内部 RAM 不够。
> **解决**：JPEG 输入缓冲改 SPIRAM；只有**输出**缓冲（解码器 DMA 写屏）才需要 DMA。
> **经验**：判断要不要 DMA 看"谁访问这块内存"。CPU 读文件 → SPIRAM/普通堆；
> DMA 外设搬数据 → `MALLOC_CAP_DMA`。

**错在哪**：把"DMA 相关"当成了整个模块的属性，而没有**逐个缓冲**判断。

"JPEG 解码要用 DMA" 这句话没错 —— 但只对**输出**成立（解码器把像素搬给 LCD）。
**输入**缓冲是 CPU 去读文件的产物，DMA 根本不碰它。

**根本原因**：`MALLOC_CAP_DMA` 是一个**稀缺**标记，加错了会白占内部 SRAM；
而错误加它的成本是隐性的（不报错，只是让别的地方申请不到）。

**提炼成规则** → `13_内存管理规范.md` §1.3：
判断"要不要 DMA"的唯一标准是**"这块内存是被谁读写的"**。

### 3.2 F23 —— SDMMC 的 DMA bounce buffer 分配失败

这是最有价值的一条，因为它完整展示了"碎片化崩溃的定位过程"。

> **现象**：耳机连接成功、管线也起来了，一点播放立刻报错，
> **看起来像蓝牙问题，实际与蓝牙无关**：
> ```
> I ESP_GMF_TASK: One times job is complete, del[... aud_dec_open]   ← 解码器 open 成功
> I ESP_GMF_PORT: ACQ IN, new self payload:0x504f85e0, el:...-aud_dec
> E sdmmc_cmd: allocate_dma_buf: not enough mem, err=0x101           ← ★真凶在这
> E diskio_sdmmc: sdmmc_read_blocks failed (0x101)
> E ESP_GMF_FILE: The error is happened in reading data, error msg: I/O error
> E ESP_GMF_ASMP_DEC: esp_gmf_audio_dec_process(407): Failed to acquire in, ret: -1
> E BT_PUSH: pipeline error
> ```

**错在哪（三层）：**

**第一层 —— 没意识到"驱动会现场申请内存"。**

`esp_gmf_io_file` 从 SD 卡读数据时，交给驱动的 payload **不是 DMA 对齐**的，
于是 SDMMC 驱动**必须现场** `heap_caps_malloc(..., MALLOC_CAP_DMA)`：

```c
static esp_err_t allocate_dma_buf(size_t* actual_size, size_t block_size, void **buf) {
    do {
        if (*actual_size < block_size) {
            ESP_LOGE(TAG, "%s: not enough mem, err=0x%x", __func__, ESP_ERR_NO_MEM);
            return ESP_ERR_NO_MEM;
        }
        *buf = heap_caps_malloc(*actual_size, MALLOC_CAP_DMA);
        if (!*buf) { *actual_size /= 2; }         /* 拿不到就减半重试 */
    } while (!*buf);
}
```

而 `SDMMC_HOST_DEFAULT()` 里 `dma_aligned_buffer = NULL`，
**每次读盘都要现场申请**。

**关键推论**：正常失败会一路减半重试；能打出 "not enough mem"
说明**减到不足一个 512B 扇区都没成功** → 内部 DMA 堆已经碎到连 512 字节连续块都没有了。

**第二层 —— 日志里没有诊断三元组。**

当时的日志只有 `not enough mem` 一句话。
**没有 `largest_free_block`**，所以无法一眼判断"是总量不够还是被切碎"，
只能去读 IDF 源码反推。**这是 §3.3 A4 的直接由来。**

**第三层 —— 被显眼的 TAG 带偏方向。**

```
ESP_GMF_FILE: ... I/O error
BT_PUSH: pipeline error
```

这两个 TAG 最显眼，但**都不是根因**。真凶是它们上面紧邻的那一行 `E sdmmc_cmd`。

**解法（已落地）**：预分配常驻 DMA 缓冲，驱动直接复用，永不现场分配。

```c
s_dma_bounce = heap_caps_malloc(32 * 1024,
                                MALLOC_CAP_SPIRAM | MALLOC_CAP_DMA | MALLOC_CAP_8BIT);
if (!s_dma_bounce) s_dma_bounce = heap_caps_malloc(32 * 1024, MALLOC_CAP_DMA);  /* 退回内部 */
host.dma_aligned_buffer = s_dma_bounce;   /* ★ 驱动看到非 NULL 就一定走复用分支 */
```

**这个解法的本质就是"池化"**：把"运行期不确定的现场申请"
变成"启动期确定的提前占位"。

**提炼成规则** → `13_内存管理规范.md` §3.3 A4（日志三元组）、§4.2 C2（caps 优先级）。
还有一条通用经验：

> **凡是"驱动内部现场申请 DMA 缓冲"的路径，都能用预分配常驻缓冲的手法消掉。**

### 3.3 池边界那个"巧合" —— 容量 = 阈值

```c
static uint8_t spk_rx_rb_pool[3840];      /* 容量 */
...
while (ringbuffer_data_len(&spk_rx_rb) + len > 6 * AUDIO_FRAME_BYTES) {  /* 阈值 3840 */
    ringbuffer_get(&spk_rx_rb, discard, AUDIO_FRAME_BYTES);
}
```

`data_len + 640 > 3840` 即丢帧 ⇒ **稳态最多囤 5 帧多**，第 6 帧永远留不住。

**错在哪**：不是 bug，是**两个独立常数巧合相等**。
"容量"是内存预算决策，"阈值"是抗抖动策略决策 —— 两者本来独立，
却因为都等于 3840 而**互相绑架**，后续改任一处都会静默改变行为。

**提炼成规则** → `13_内存管理规范.md` §2.3 S5。

### 3.4 链路 C 的反复重建

见 §2.1 因素三。**错在把"资源的生命周期"绑到了"UI 的生命周期"上**，
而 UI 的切换频率远高于资源的必要重建频率。

**提炼成规则** → `13_内存管理规范.md` §6 L1/L2。

### 3.5 用 A/B/C 三种手段重新归位你的两个坑

用 §1.7 的框架回头看你修过的两个坑，会看得更清楚 ——
**它们用的是不同的手段，而"最稳的音频链路"用的是第三种。**

| 故障 | 你实际做的 | 属于哪种手段 | 关键认知 |
|---|---|---|---|
| **F19** 壁纸 JPEG 缓冲 | 改 `MALLOC_CAP_SPIRAM` | **C 换区域** | 这是**区域放错**，不是碎片问题。它治的是"内部 RAM 被无关数据占用" |
| **F23** SDMMC bounce buffer | 开机 `heap_caps_malloc` + 挂 `host.dma_aligned_buffer` | **B 预分配常驻** | **它仍然在堆里**（PSRAM 堆），只是"申请一次、永不释放、反复复用" |
| **音频链路** | 四个 `*_rb_pool` 静态数组 | **A 静态池** | 从头就在 `.bss`，**从未参与过碎片游戏** |

**两个容易搞错的点：**

1. **F23 不是"动态改静态"。** `s_dma_bounce` 是 `static` **指针**，指向堆内存，
   不是静态数组。它治碎片靠的是"消灭反复分配这个**行为**"，不是"换掉这块**内存**"。
2. **F19 根本不是碎片问题。** 它是"把 CPU 用的数据放进了 DMA 区"，
   属于**区域选择错误**。就算当时内存完全不碎，那个缓冲放错地方也是错的。

**提炼成规则** → `13_内存管理规范.md` §1（区域判据）、§6 L1/L2（生命周期）。
本节的三手段对照表 → 上文 §1.7。

### 3.6 为什么音频链路最稳 ★

"音频链路最稳"这句结论，**不能简化成"因为它用了双环形缓冲区"** ——
环形缓冲只是一个**读写协议**，不是内存管理手段。真正的稳来自**三层叠加**：

| 层次 | 具体做法 | 消灭了什么 |
|---|---|---|
| **① 帧缓冲静态化** | `audio_stream_task` 内 `static uint8_t mic_frame[640]` / `spk_frame[640]`；`udp_voice.c` 的 `static uint8_t packet[652]` ×2、`static uint8_t silence[640]` | 运行期分配 |
| **② 重排窗口定长** | `slots[32]` 是编译期定长数组（槽内 `pcm[640]` 内嵌） | 动态扩容（对比 PC 端是无界字典 `dict[seq]`） |
| **③ 流缓冲静态池 + ringbuffer 协议** | `ringbuffer_init(&mic_tx_rb, mic_tx_rb_pool, sizeof(mic_tx_rb_pool))` | 动态分配 + 跨任务数据竞争 |

> **注意第 ③ 点的措辞**：`ringbuffer_init()` 的第一个参数是**你提供的静态数组**，
> ringbuf 库**自己不分配任何内存**。它是一个**使用协议**，不是一个**分配器**。
> 换句话说 —— **稳的不是"环形缓冲"，是"池本来就是静态的"。**

**结论：流一启动，全部缓冲已就位；整个运行期间零 malloc / 零 free。**

**是"不产生"，不是"产生得少"。**

#### 为什么另外两条链路做不到（不是写错了，是数据形态不同）

| | 音频流 | 蓝牙推流 / 本地播放 |
|---|---|---|
| 数据源 | 实时采集（**定长** 640B/20ms） | 文件（MP3 解码，**尺寸不定**） |
| 需解码器工作区 | ❌ 不需要 | ✅ GMF 内部动态申请 |
| 尺寸可预测 | ✅ 编译期完全确定 | ❌ 取决于码率/采样率 |
| **稳态分配次数** | **0** | **> 0**（本地播放还叠加反复重建） |

**根本原因**：音频流是**定长帧流**，天然适合静态池；
MP3 解码是**变长、依赖码流**的，解码器内部**必须有**动态工作区。

> **所以音频链路"稳"= 一半靠设计 + 一半靠数据形态简单。**
> 不要把它的经验不加区分地套到所有链路上 ——
> **判据见 §1.7 的三问**：MP3 解码在第一个问题（尺寸是常量吗）就卡住了，
> 所以它**只能选 B，不能选 A**。

**提炼成规则** → `13_内存管理规范.md` §2（静态池优先）、§6（生命周期纪律）。

## 4. 决策准则：什么时候该"静态化"

### 4.1 决策树

> **完整的三问判据（含"必须交给驱动持有"这一约束）见 §1.7。**
> 下面是按"静态池 vs 预分配常驻"细化的版本：

```
这个缓冲/任务栈，尺寸是编译期已知的常量吗？
│
├─ 否 → 必须动态分配。→ 走 caps 分级（§4.2），
│        并确保：初始化期分配、运行期不重新分配（R3）
│        ※ MP3 解码缓冲属于此类 → 只能选 B，不能选 A
│
└─ 是 → 它的生命周期是"整个程序"吗？
        │
        ├─ 是 → 【优选项：静态】
        │        ├─ 尺寸 ≤ 4KB 且高频访问 → static 数组（留内部）
        │        └─ 尺寸 > 4KB 或低频     → 外置 PSRAM（stack_in_ext / WithCaps）
        │
        └─ 否（跟 UI / 会话走）→ 进入下一个判断
                 │
                 ├─ 能否改为"建一次 + 开关"复用？
                 │   ├─ 能 → 【强烈推荐】改常驻复用（学蓝牙 P3）
                 │   └─ 不能 → 统一收进一个中间层模块管理，
                 │             不要散在 UI 回调里（学 local_player 方案）
                 └─

※ 另有一条硬约束：若该缓冲必须交给外部模块（驱动/框架）持有指针，
  则只能选 B（预分配常驻）—— F23 的 host.dma_aligned_buffer 即此类。
```

### 4.2 判断"改静态划算不划算"

改静态的代价是**内部 SRAM 静态占用 +N 字节**。判断方法是：

**看当前内部 RAM 的"最大连续块"离关键申请还有多少余量。**

在关键节点打三元组：

```c
ESP_LOGI(TAG, "INTERNAL free=%u largest=%u | SPIRAM free=%u",
         (unsigned)heap_caps_get_free_size(MALLOC_CAP_INTERNAL),
         (unsigned)heap_caps_get_largest_free_block(MALLOC_CAP_INTERNAL),
         (unsigned)heap_caps_get_free_size(MALLOC_CAP_SPIRAM));
```

**建议打点位置**（现状参考）：

| 位置 | 已有打点？ |
|---|---|
| `bt_audio_service.c:222-224` | ✅ 已有 |
| `bt_push_service.c:308-310` | ✅ 已有 |
| `bt_push_service.c:418` | ✅ 已有 |
| `sdcard_service.c:65-66` | ✅ 已有 |
| `audio_service` 流启动/停止 | ❌ 建议补 |
| `tab_audio`（原 `tab_music`）build/destroy 前后 | ❌ 建议补 |
| 通话 / 录音进行中 | ❌ 建议补 |

**判据：**

- 若 `largest_free_block(INTERNAL)` **长期 > 16KB** → 有余量，改静态是安全的；
- 若 **在 4~8KB 之间** → 谨慎，优先做外置 PSRAM 而非静态占内部；
- 若 **< 4KB** → 已经在危险区，任何新增内部占用都要重新评估，
  且应优先做"减少内部占用"的改造（把可外置的搬走）。

### 4.3 回到那个池边界问题

扩大 `spk_rx_rb_pool` 从 3840B → 5120B，**代价是内部 SRAM 少 1280B**。

**收益与代价的对称性：**

| | 说明 |
|---|---|
| 代价 | 内部 RAM 静态占用 +1280B（**显式、静态、零碎片**） |
| 收益 | 消除"容量=阈值"的巧合，让"保留 6 帧"名副其实 |

**判断**：按 §4.2 的判据，先用 §4.2 的三元组打点拿到基线。
如果 `largest_free_block(INTERNAL)` 有充足余量，这 1280B 值得花；
如果已经逼近关键申请（如 GMF、bluedroid 的运行期申请），
则应优先考虑**改为不扩池、而是把阈值明确降为 5 帧**（零内存代价，行为显式）。

**注意这条取舍本身也是"显式化"**：无论选哪个，都要在代码里写清理由，
不能让它继续停留在"巧合"状态。

## 5. 成熟工业项目的做法

### 5.1 核心思想

> **把"运行期不确定的分配"尽可能变成"启动期确定的占位"。**

这句话是全部手段的源头。

### 5.2 手段一览

| 手段 | 做法 | 消灭了什么 | 本工程对应 |
|---|---|---|---|
| **静态池 / arena** | 启动时一次性大块，内部自行切分，永不再 malloc | 运行期分配的全部不确定性 | ✅ `audio_service` 的四个 `*_rb_pool` |
| **固定块内存池** | 建 N 个等大块，分配即取块，杜绝外部碎片 | 外部碎片（内部碎片的根源） | ❌ **未使用**（改进点） |
| **启动期预分配** | 所有大缓冲尽早申请，之后再不申请 | "晚到的大块申请失败" | ✅ F23 的 32KB bounce buffer |
| **分层内存（caps）** | 明确划分"内部只给 DMA/ISR/栈，其余一律 PSRAM" | 内部 RAM 被无关数据占用 | ✅ P2 显式外置；⚠️ 但裸 `malloc` 仍在用 |
| **栈静态化** | `xTaskCreateStatic` 而非 `xTaskCreate` | 任务栈参与碎片 | ⚠️ 配置已开，**代码几乎没用** |
| **栈外置 PSRAM** | `stack_in_ext` / `WithCaps` | 大栈占内部 RAM | ✅ 蓝牙已用 |
| **水位监控** | 定期打 `free` / `largest_free_block` | "崩了才知道不够" | ⚠️ 散落 printf，无系统化监控 |
| **失败降级** | 申请失败走高格调降级路径 | 可恢复故障变成崩溃 | ❌ 多处 `assert()` 直接 abort |
| **内存所有权契约** | 每个 malloc 写明释放责任人 | 泄漏 / 双重释放 | ❌ 未成文（见规范 L3） |

### 5.3 工业界的经验值

从大型嵌入式项目（车规 / 医疗 / 工业 HMI）提炼的几条经验值：

1. **堆使用率目标**：常驻堆占用控制在容量的 **60% 以下**，
   留 40% 余量给峰值与碎片；
2. **堆分配次数上限**：稳态运行后**应当为零**。
   所有需要的内存在初始化阶段全部分配完毕；
3. **`largest_free_block / free_size` 比值**：健康状态应 > 0.5。
   若长期低于 0.3，说明碎片严重，需要重构分配模式；
4. **禁止在中断中分配**：ISR 中禁止任何 malloc（本工程未违反）；
5. **优先静态化"高频 + 小尺寸"**：收益/成本比最高；
6. **优先外置"低频 + 大尺寸"**：PSRAM 访问慢，低频不影响性能。

### 5.4 本工程现状评分

| 维度 | 现状 | 评级 |
|---|---|---|
| 音频流缓冲 | 全静态池，设计干净 | ✅ 优 |
| DMA 缓冲策略 | F23 后已用预分配 + PSRAM 直访 | ✅ 优 |
| 蓝牙资源外置 | P2 显式外置，栈进 PSRAM | ✅ 优 |
| 通用分配纪律 | 裸 `malloc` 仍在用，caps 使用不统一 | ⚠️ 中 |
| 固定块内存池 | 未使用 | ❌ 缺 |
| 任务栈静态化 | 配置已开但代码未用 | ❌ 缺 |
| 失败降级 | `assert` 遍地，运行期也断言 | ❌ 差 |
| 水位监控 | 有零散打点，无系统化基线 | ⚠️ 中 |
| 内存所有权契约 | 未成文 | ❌ 缺 |

**结论**：本工程在**"特定场景的手工优化"上做得相当好**（F23 的解法是教科书级的），
但在**"系统性纪律"上还是空白** —— 这直接解释了
"为什么每个具体坑都解决了，但坑还是会不断出现"。

## 7. 一句话总结

> **本工程的问题从来不是"内存不够用"，而是"内存被切碎了"，
> 而切碎它的主要是"运行期反复的、尺寸不一的、生命周期交错的分配"。**
>
> 解法不是"省内存"，而是**"把运行期的不确定性搬到启动期去"** ——
> 该静态的静态、该预分配的预分配、该外置的外置。
>
> 你踩过的每个坑（F19 / F23 / 链路 C / 池边界），本质都是同一条原因的不同表现。

### 7.1 三个最容易搞错的认知（速查）

| # | 常见误解 | 正确认知 |
|---|---|---|
| 1 | "本工程用 FreeRTOS heap4 管理动态内存" | ❌ **是 TLSF**（`CONFIG_HEAP_TLSF_USE_ROM_IMPL=y`），IDF 不用 heap_1~5。TLSF 解决**速度**（O(1)），**不解决碎片** |
| 2 | "碎片会自己拼起来，系统会整理" | ⚠️ **只合并物理相邻的空闲块**（coalesce）；相邻位置被"活着的分配"占住就永远拼不起来。**compaction 在嵌入式不可行**（指针会失效） |
| 3 | "把动态改成静态 = 加 `static`" | ⚠️ 实际有 **A 静态池 / B 预分配常驻 / C 换区域** 三种手段，机制完全不同。F23 用的是 B、F19 用的是 C，**都不是 A**（见 §1.7） |
| 4 | "内存占用大 = 总量不够" | ⚠️ 先看 **`largest` 掉了多少**。总量够但 `largest` 掉得比申请量还多 → 是**被切碎**（见 §1.6.5）。本工程真正的失败模式是碎，不是少 |

## 8. 上电内部 SRAM 占用实测账单（2026-09-21）

> 目的：把"开机那一刻内部 RAM 被谁按什么顺序吃走"变成一张**可核对的账**。
> 数据来源：`docs/_log_212621.txt` 串口实测，日志点由各模块自己打印。

### 8.1 实测序列

| 时刻(ms) | 事件 | internal free | largest | Δ free |
|---|---|---|---|---|
| 1561 | `esp_psram` 保留 32K 内部 | — | — | — |
| 1572 | `SDCARD` DMA bounce buffer 32KB | **241659** | — | 起点 |
| 1638 | `BT_SVC` early controller init | **241131** | **155648** | −528 |
| 1806 | `BT_PUSH` early init | **198935** | **131072** | **−42196** ⚠ |
| 1813 | `BT_PUSH` ready (resident) | **197687** | — | −1248 |

`SDCARD` / `BT_SVC` / `BT_PUSH` 三处日志点相邻，中间只隔微秒级，可以认为
**241659 是"早期空窗"的真实起点**，之后每一行都是净消耗。

### 8.2 两个异常点

**① `BT_PUSH` 吃掉 42KB，且 `largest` 掉 24KB**

`bt_push_service_early_init()` 的显式分配**本来都是 PSRAM**：
`uri`(256B, SPIRAM) / `asrc_weight`(64B, SPIRAM) / GMF task 栈(`stack_in_ext` → PSRAM) /
`proc_task`(SPIRAM|8BIT) / 命令队列(8 项, 内部小对象)。

**剩余的 42KB 来自第三方组件的内部预分配**，代码层看不到、也不受本项目 caps 控制：

| 来源 | 说明 |
|---|---|
| `esp_gmf_pool_init` + 3 个元素（`aud_dec`/`aud_asrc`/`aud_enc`） | 每个 element 自带**内部工作缓冲**，`aud_asrc`（硬件重采样）最大头 |
| `esp_gmf_io_bt` / `esp_gmf_io_file` | IO 对象及其缓冲 |
| GMF task 对象 / 事件组 / 互斥量 | 小对象，内部 |

`largest` 从 155648 → 131072（**掉 24KB = 24×1024**）说明：
**大块连续区被吃掉了整整 24KB**，而 free 只掉 42KB ——
这个比值本身就在提示"吃掉的是一整段连续区间，不是一堆碎片"。
→ 结论：**这部分在代码里无法"改小"，只能靠"时机前置"让它抢到最空的窗口**
（这正是方案 B 四原则里 P1 的由来）。若将来还要压，方向是
**给 `aud_asrc` 减配或让 A2DP Source 不用 asrc**（需评估音质/兼容性），而不是改 caps。

**② `FS_SVC: jpeg out buffer 1152000 bytes` —— 尺寸勘误**

| 项 | 早期认知 | 实测/核实 |
|---|---|---|
| 表达式 | `800*480*2` | `800*480*sizeof(lv_color_t)` |
| `sizeof(lv_color_t)` | 2（RGB565） | **3**（`CONFIG_LV_COLOR_DEPTH=24`） |
| 结果 | 768000 ≈ 750KB | **1152000 ≈ 1.10MB** |
| 落点 | 内部 RAM（F30 前） | **PSRAM** `0x5000d8c0` ✅ |

`0x5000_d8c0` 落在 PSRAM 地址空间 → **F30 的显式 caps 修正确实生效**。
但**尺寸比原估算大 50%**：做内存账、评估 PSRAM 余量时，
必须按 **1.10MB** 算，不要照抄 750KB。

### 8.3 结论

- **`FS_SVC` 不占内部 RAM**（已在 PSRAM）。之前"内存占用夸张"的观感，
  主要来自 **`BT_PUSH` 的 42KB** 这一项；
- `BT_PUSH` 那 42KB **是设计要付的代价**（换来"推流不再因碎片崩溃"），
  不是回归 bug。它换来的收益见 F23 / §19.5；
- 真正该盯的指标不是 `free`，是 **`largest`**。
  本次 largest 一路 155648 → 131072，**全程 ≥ 128KB**，对 16KB 级的
  mbedtls `SSL_IN_CONTENT_LEN` 是够的 ——
  也就是说 **"开机后"内存并不紧张**，TLS 失败更可能发生在
  **WiFi 起来之后**（LWIP 缓冲再切一刀）。要定位它，
  需要在 `esp_http_client_perform()` 前**打一次三元组**，
  而不是在上电日志里找原因。

## 9. 内部 RAM 的"非对称消耗"：为什么 PSRAM 还有 13MB，内部却只剩 7KB（F35）

### 9.1 现象（实测，2026-09-21）

同一台设备，两个时刻的内部 RAM 差了 **185KB**：

| 时刻 | 场景 | internal free | largest |
|---|---|---|---|
| 1813ms | 开机 `BT_PUSH ready` | **197687** (193KB) | — |
| 811234ms | 切到 SYS tab **点蓝牙开关** | **7787** (7.6KB) | **7168** (7KB) |

同时 **TLS 也起不来**（`mbedtls_ssl_setup returned -0x008D`
= `PSA_ERROR_INSUFFICIENT_MEMORY`），且错误码**在 -0x0080 / -0x008D 之间飘**。

→ **两个功能同时因内存失败，说明不是各自的 bug，是同一个根因。**

### 9.2 为什么"上电账单"看不出问题（上一轮结论错在哪）

§8 的账单只覆盖 `app_main()` 内部那 2 秒。但 `app_main` 在 **5287ms 就返回了**，
而故障发生在 **811234ms** —— **两个数量级之后**。
账单里的 193KB 是"开机那一刻快照"，不是"你按开关那一刻的余额"。

**★ 教训：任何"内存很宽裕"的结论都必须带时点。**
快照够用 ≠ 长期够用。**没有时点的内存数字等于没有信息。**

### 9.3 关键工具：三个"内部 RAM 判定域"

排查这类问题时，**不能只看 `MALLOC_CAP_INTERNAL` 一个数**。必须并列看：

| 域 | API | 物理位置 | 本工程实测 |
|---|---|---|---|
| 内部 RAM 堆 | `MALLOC_CAP_INTERNAL` | `2F046700`+ (210KB) + `2F07AFB0`+ (16KB) | 7.6KB |
| **DMA 可达堆** | `MALLOC_CAP_DMA` | 内部，受 `SPIRAM_MALLOC_RESERVE_INTERNAL=32768` 保底 32KB | 待测 |
| PSRAM 堆 | `MALLOC_CAP_SPIRAM` | `0x50000000`+ | 待测（开机 16.7MB） |

**两个容易漏掉的账**：

1. **RTCRAM（31KB）不算进 `MALLOC_CAP_INTERNAL`**；
2. **开机保留的 32KB 内部 DMA 池也不在 `free` 里** ——
   `esp_psram: Reserving pool of 32K of internal memory for DMA/internal allocations`。
   所以"物理 210+16KB"与"free 显示 193KB"本来就差着 30+KB，
   **这是正常的，不是内存被偷了**。

**诊断口诀**：

```
PSRAM 也告急                → 总量不足 / 内存泄漏
PSRAM 还有余，内部只剩个位数  → 内部 RAM 专项被吃
                              → 凶手是"只用内部 RAM 的大额消费者"
```

### 9.4 本工程的"内部 RAM 专项消费者"清单

这些**永远落在内部 RAM**，不吃 PSRAM，是本工程最需要盯的：

| 消费者 | 规模 | 为什么只能在内部 | 何时吃 |
|---|---|---|---|
| **mbedtls TLS** | `SSL_IN_CONTENT_LEN=16384` + `SSL_OUT=4096` + 握手/DRBG ≈ **20~25KB** | `CONFIG_MBEDTLS_INTERNAL_MEM_ALLOC=y` 强制 | 每次 HTTPS |
| **WiFi / LWIP** | 驱动缓冲 + pbuf + netif ≈ **数十 KB** | 协议栈约束（`TRY_ALLOCATE_WIFI_LWIP` 只能缓解） | `esp_wifi_start()` |
| **bluedroid host** | BTU/BTC 队列 + HCI mempool | 协议栈约束 | 开蓝牙 |
| **LVGL 对象 / 字体 bss** | 对象堆 + 字体静态数组 | 访问频率高 | 建页面 |
| **任务栈**（未外置的） | `audio_task`/`audio_stream` 等 8192 ×N | 默认 `xTaskCreate` 走内部 | 建任务 |
| **adc_button / led_strips / i2s** | 小数 KB | 驱动约束 | 各 init |

### 9.5 本工程最可疑的一处非对称消耗：`ESP_TLS_USE_DS_PERIPHERAL`

```
CONFIG_ESP_TLS_USE_DS_PERIPHERAL=y     ← 当前为 y
```

DS（Digital Signature）外设路径**本身会用更多内部 RAM**：
它需要把密钥、哈希中间态、RSA/ECC 运算上下文放进**内部可访问**的内存，
且为 per-operation 分配（`esp_ds_context` 每次握手都建一次）。

**这解释了两个"飘"的现象**：

| 现象 | 用"内存不足"解释 |
|---|---|
| 错误码在 `-0x0080`(=`BAD_INPUT_DATA`) 与 `-0x008D`(=`INSUFFICIENT_MEMORY`) 之间变 | 中间分配**碰运气成功/失败**：`setup` 阶段拿到就继续（后续才炸），拿不到就 `-0x008D` |
| 天气"以前成功过、现在坏了" | 每次数据量/时序略有差异，**临界点两侧抖动** |

> **★ 通用判据：错误码飘 = 资源竞争；错误码稳定 = 逻辑写错。**
> 见 §1.6.5 三种"假性内存不足"。

**待验证的候选措施（按"证据强度"排序，不要一次全改）**：

| # | 措施 | 预期收益 | 风险 |
|---|---|---|---|
| 1 | **先加诊断日志**（本轮已加），确认真凶在哪一步 | 0（只取证） | 无 |
| 2 | `CONFIG_ESP_TLS_USE_DS_PERIPHERAL=n` | 减少 per-handshake 内部 RW 分配 | 可能拖慢握手（改回软件大数运算） |
| 3 | `CONFIG_MBEDTLS_SSL_IN_CONTENT_LEN=8192` | 省 8KB 内部 RAM | 响应 >8KB 时需分片；和风 JSON 仅几 KB，**够用** |
| 4 | `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y` | TLS 全部改走 PSRAM，**治本** | 安全模型变化（IDF 文档：开 flash encryption 后可接受） |

**建议顺序：1 →（看日志）→ 2 或 3 → 最后才考虑 4。**

### 9.6 通用经验

- **★ 内存结论必须带时点**。"内存够用"这句话，不加"在 t=xxx ms / 在 xxx 场景下"就是废话；
- **★ "功能 A 和功能 B 同时因内存失败" = 同一个根因**，
  不要去分别调 A 和 B 的代码，要去找**共同吃内部 RAM 的那一块**；
- **★ 大额缓冲全部显式 PSRAM ≠ 内部 RAM 就安全了**（F30 的教训只解决了"业务缓冲偷内部"）。
  协议栈/加密/驱动这类**只能用内部**的消费者，规模是硬约束，**必须单独核算**；
- **★ 排查要打 `MALLOC_CAP_DMA` 和 `MALLOC_CAP_SPIRAM` 一起看**，
  单看 `INTERNAL` 分不清"总量问题"还是"专项问题"；
- **★ 别用"上电 2 秒的账单"解释"13 分钟后的故障"**。
  排查的搜索边界是**故障时点**，不是最方便取证的那个时点。

### 9.7 已经验证的最大一笔：任务栈 ≈ 93KB（F35 结案）

**用户一句追问命中了最大的一块。** 定量清点：

| 来源 | 量 | 说明 |
|---|---|---|
| 本项目 8 个 8192 任务 | 65536 B | `audio_task`/`audio_stream`/`udp_voice_ctl`/`tx`/`rx`/`record_service`/`link_manager`/`net_time` |
| `led_task` 4096 + `bt_vol_sync` 2560 | 6656 B | — |
| **本项目小计** | **72192 B ≈ 70.5 KB** | — |
| IDF 自带（main/esp_timer/sys_evt/ipc0+1/**wifi driver 6656**/tmr/idle0+1） | 23296 B ≈ 22.8 KB | 不可控 |
| **合计** | **95488 B ≈ 93 KB** | **占 177 KB 亏损的 53%** |

**★ 这 93KB 本来一分钱都不必占内部 RAM。**

```
CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y    ← 允许
CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y    ← 允许
```

两个开关都开着，而**全项目 11 处任务创建里只有 `bt_push_proc` 用了 `WithCaps`**。

> **这是"知道但没推广"，不是认知缺口。** 样板就在同一个工程里
> （`bt_push_service.c:409`），配置也在同一个 `sdkconfig` 里，
> 仍然有 10 处漏了 —— 说明**"最佳实践"必须落成清单项才会被执行**，
> 光有样板不够。这就是 §7 那种"准入检查清单"存在的意义。

**修复**：11/11 处全部改 `WithCaps(MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT)`，
回收 **≈70.5 KB** 内部 RAM。详见 `13_内存管理规范.md` §5.1.1 与 F35 记录。

**★ 新增规则 T5（外置栈的失败分支必须说话）**：

```c
BaseType_t ok = xTaskCreatePinnedToCoreWithCaps(..., MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT);
if (ok != pdPASS) {
    ESP_LOGE(TAG, "task create failed (stack->PSRAM); check "
                  "CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY");
}
assert(ok == pdPASS);
```

理由：`WithCaps` 返回 `pdFAIL` 时**大概率不是内存不足**（PSRAM 往往还剩十几 MB），
而是外置栈路径被配置关掉了。**只写 "task create failed" 会把排查带偏到内存不足上**
—— F35 前期就走错了这个方向。

**★★ 附带一条工程方法论教训（非固件本身）**：

本轮批量改 11 处代码时，有 **3 处 `Edit` 报"成功"但内容回退**。
若以编辑工具的返回值判定完成，就会交付一份**只有 8/11 生效**的修复，
且症状（内存回收量不足预期）会再次被误读成"还有别的消费者"。
**→ 批量改造后必须做一次机器可校验的独立复核**（如全项目正则扫描 + 分类计数），
**不得以编辑工具返回值为完成依据**。本轮正是靠这一步才发现 3 处回退。

### 9.8 ★★ 关键区分：「能挪没挪」与「挪不动」

任务栈修完后，`WIFI_DIAG` 数据回来。结论是两笔大账**性质完全不同**，
**必须分开对待** —— 这是本节最重要的认知。

| | 任务栈（70.5 KB） | `esp_wifi_init`（44.5 KB） |
|---|---|---|
| 性质 | **能挪没挪** | **物理上挪不动** |
| 证据 | 配置已开、样板已有，只是没用 | **INTERNAL 与 DMA 跌幅完全相同** |
| 处置 | 改 `WithCaps` 即可 | **改 caps 无效**，只能减配或改架构 |
| 教训 | 执行遗漏（管理问题） | 硬约束（物理问题） |

#### ★★ 判据：`INTERNAL` 与 `DMA` 跌幅**完全相同** → 该块是 DMA 硬性内部

本次实测（`13_内存分配规范` §DMA 域的含义见 §1.6）：

```
after netif+event_loop -> after esp_wifi_init:
   INTERNAL  −45616 B
   DMA       −45616 B   ← 一个字节不差
   PSRAM     −66716 B
```

**为什么这个"相等"如此有说服力**：
`MALLOC_CAP_DMA` 必然是 `MALLOC_CAP_INTERNAL` 的子集（DMA 可达的只能是内部 RAM）。
若某次分配**只吃 DMA 子集**，则 INTERNAL 与 DMA 的跌幅**必然相等** ——
因为吃掉的每一字节**既属内部、又属 DMA 可达**。

**反过来**：若 INTERNAL 跌得多、DMA 跌得少（或不跌），说明吃的是"内部但非 DMA"的部分，
**那部分是可以挪到 PSRAM 的**。

> **→ 这是一个零成本的分类判据**：
> **看 INTERNAL 与 DMA 的跌幅差**，就能立刻回答"这块内存能不能挪走"。
> 跌幅相等 → 挪不动（别浪费时间改 caps）；
> 跌幅不等 → 有一部分能挪（去查那部分是谁）。

#### ★ 纠正误读：`WiFi/LWIP prefer SPIRAM` ≠ 全进 PSRAM

```
I (2160) wifi_init: WiFi/LWIP prefer SPIRAM
```

**极易误读成"WiFi 缓冲已经放 PSRAM 了，内部不受影响"。**
实际含义是三层，逐层递减：

| 词 | 含义 | 本次实测 |
|---|---|---|
| `prefer` | **倾向**，不是强制 | — |
| `SPIRAM` | 只作用于**允许**放 PSRAM 的那部分 | PSRAM 掉了 65.2 KB ✓ 生效了 |
| （未说的） | **DMA 可达的部分仍强制内部** | 内部掉了 44.5 KB ✗ 挪不走 |

> **→ 一般化规则：看到配置里写 `prefer` / `try` / `auto`，必须追问"哪部分不在这个偏好范围内"。**
> 框架的"智能选择"永远只覆盖**它认为可以覆盖**的部分，剩下的会静默落回原处。

#### ★ "随重试次数线性增长"的消耗是最危险的形态

`t=2363 → t=6778`（仅 4.4 秒，重连 2 次）内部掉了 **21.7 KB**，
即**每次重连 ≈ 10 KB 内部**。

而**旧日志里重连了 5 次**（到 20769ms）→ 外推 ≈ **50 KB 内部**。

**为什么这类消耗特别危险**：
- 它**不是开机常驻**，所以上电账单里看不到；
- 它**随故障次数增长** —— 而"连不上"恰恰是最常见的现场状况；
- 它**在故障时最需要内存**（TLS 重试、蓝牙开启都在这时发生）→ **雪上加霜**。

> **→ 经验：凡是"重试 / 重建 / 重扫"路径，都要单独核算其内存增量，
> 并假设它会跑满最大重试次数。** 不能只看"成功一次"的消耗。

#### 处置优先级的修正（WiFi 调优的收益被高估）

原计划"调 `CONFIG_ESP_WIFI_*` 缓冲配置"被验证为**收益有限**：

- 能调的只有**已在 PSRAM 的那 65.2 KB**（调小它只是让 PSRAM 多剩点，**对内部无帮助**）；
- **动不了 44.5 KB 那块** —— 它是 DMA 硬性需求；
- 且降 `rx buffer` 会**直接伤吞吐**（与 F34 保留 `BT_PUSH` 的取舍逻辑相反）。

**修正后的优先级**：

| 优先级 | 措施 | 预期收益 |
|---|---|---|
| **1** | **补埋点覆盖那 99.1 KB 无埋点区段** | **找到剩余的"能挪没挪"** |
| **2** | **降低重连次数**（5→2）/ 降低扫描频率 | **省 30~40 KB 内部** |
| 3 | `SSL_IN_CONTENT_LEN=8192` | 把 TLS 的 `largest` 门槛从 20KB 降到 ~12KB |
| 4 | WiFi 缓冲配置调优 | **有限**（见上） |

**★ 优先级排序的依据是"收益/成本比"，不是"听起来是否治本"。**
本次差点又去调 WiFi 配置（听起来最对症），但数据表明那里没有多少可回收的空间。

### 9.9 ★★ "重试"不是免费的：把重试次数当成资源预算

**用户追问**："为什么每重连一次都减一点，不能初始化好、重连不减少吗？"

#### 先纠正一个假设：重连**本来就不重新初始化**

查 `wifi_manager.c` 的实际路径：

| 函数 | 做了什么 |
|---|---|
| `apply_candidate()` | `esp_wifi_set_config()` + `esp_wifi_connect()` ← **只切换候选 AP 时走** |
| `reconnect_timer_cb()` | `s_retry_num++` + **仅** `esp_wifi_connect()` ← **不含 set_config** |

**→ 现存设计已经是"初始化一次、重试只重连"。**
所以"能不能初始化好之后重连不减少"这个方向**代码里已经做到了**，
问题不在重复初始化。

#### 那 10 KB/次 从哪来？三个来源

1. `esp_wifi_connect()` **每次都会重跑一遍 auth/assoc 流程**，
   `wpa_supplicant` 侧要重建 EAPOL / 握手状态机 / PMK 缓存 —— **走内部 RAM**；
2. **失败路径（`reason=2` 认证失败）不是正常断开**，
   驱动的清理路径**不保证把本次尝试申请的临时缓冲全部归还**；
3. 每次尝试还会**新申请 beacon/probe 相关缓冲**，释放时机滞后于下一次尝试。

**★ 这是 ESP-IDF WiFi 驱动的内部行为，应用层不可控。**
应用层只能做两件事：**减少尝试次数**、**避免无谓的失败尝试**。

#### ★ 一般化：任何"失败就重来"的设计都要先量"重来一次的代价"

```
重试次数 × 单次不可归还资源 = 必须显式设定的资源预算
```

| 若重试消耗的是… | 则重试次数是… |
|---|---|
| 纯 CPU 时间 | 可随手设大，无所谓 |
| **不可归还的内存 / 句柄 / 连接数** | **必须当成资源预算显式设定** |

本次实例：`WIFI_MAX_RETRY=5` → 5 × 10 KB = **50 KB 内部 RAM**。
这个数字**从来没有被当成"预算"审视过**，它只是当年随手填的一个常数。
而 50 KB 恰好超过了 mbedTLS 需要的 20 KB 连续块 → 直接表现为"天气永远失败"。

> **→ 结论：改一个重试常数前，先测"单次重试的不可归还代价"。**
> 测法就是本文 §9.8 那套：在重试路径的三个点各埋一个 `free/largest` 埋点。

#### 本次配套改动（已落地）

| 项 | 改动 |
|---|---|
| `WIFI_MAX_RETRY` | 5 → **3**（省约 20 KB 内部 RAM） |
| 语义澄清 | 明确为"**总尝试次数（含首次连接）**"，旧注释"重试次数"含混 |
| 日志文案 | `(%d/%d)` → `(attempt %d/%d)`，消除"重试 5 次"的误读 |
| 连带清理 | 多处硬编码 `5 次` 的注释改为宏引用（**避免数字在注释里腐烂**） |

**★ 一个小而普遍的教训**：改常数值时，
**必须连带搜索注释与日志里的同一数字**。
本次 `WIFI_MAX_RETRY` 从 5 改 3，就有 4 处独立文案写着"5 次"
（头文件设计说明、`WIFI_EVT_OFF` 注释、`next_candidate_or_giveup` 注释、
`retry` 日志）—— 漏掉任何一处，注释就会开始骗人。

### 9.10 ★★★ 结算验证：三处修复生效，以及三条新的方法论

新固件日志（19 处 `BOOT_DIAG` + `[diag-retry]` 全部命中）把 §9.7~9.9 的推断**全部证实**，
同时给出三条值得单独记住的方法论修正。

#### 验证结果速览

| 指标 | 修复前 | 修复后 | 判定 |
|---|---|---|---|
| `largest` 开机段最小 | 15360 | **31744** | ✅ 翻倍 |
| `PageManager_Load(splash)` 时内部 | 25991 | **53743** | ✅ +27.8 KB |
| 天气 TLS | `-0x008D` | **`weather ok`** | ✅ 通过 |

#### ★ 方法论 1：**看 `largest`，不要只看 `free`**

任务栈外置回收的是**零散小块**（8 KB / 4 KB 一堆）。
`largest` 从 15360 回到 31744 **翻倍**，说明回收的恰好是**连续区**。

```
free  +28 KB   →  只是"多了点内存"
largest ×2     →  "连续区回来了"  ← 这才是 TLS 能不能起的决定项
```

> **★ 判断"内存够不够"永远是 `largest` 视角，不是 `free` 视角。**
> 一次回收若只让 `free` 涨、`largest` 不动，说明收的全是碎片间隙，**对启动大块需求毫无帮助**。
> 这也是"任务栈外置"这次能一击命中的原因 —— 栈是连续整块，回收的就是连续区。

#### ★ 方法论 2：**同一步骤里，`INTERNAL` 与 `DMA` 跌幅相同 = 挪不动**

本次 RGB panel 段（`fs_service_init → bsp_display_start`）掉 **73756 B**，
若只看 `INTERNAL` 会以为"又找到一块能挪的"，但**同期 `DMA` 跌幅完全相同** →
**是 DMA 硬性内部、改 caps 无效**（§9.8 判据的第二次实战应用，第一次是 `esp_wifi_init`）。

> **→ 现在这条判据已有两次独立验证，可视为本工程的标准动作：
> 量到任何一块大消耗，先问"`DMA` 掉了多少"。**

#### ★ 方法论 3：**排查内存不能默认"每步只减不增"**

本次 `SCAN_DONE` 事件里内存**涨了 4292 B**（53743 → 58035）——
扫描期驱动预扣的缓冲多于实际所需，事件回调里做了一个净释放。

> **★ 结论：事件回调（`*_DONE` / 异步通知）里同样可能有净释放，
> 埋点必须成对前后各一个，不能只在前一步埋。**

#### 附：本轮拆出的完整账单（`app_main` 全程，含三域）

| 区间 | 净消耗 | 性质 |
|---|---|---|
| `app_main enter` → `bsp_i2c_init` | 976 B | 基础 |
| `bsp_i2c_init` → `bt ctrl init` | **42196 B** | BT controller（硬约束） |
| `bt ctrl init` → `bt_push early` | 1248 B | GMF |
| `bt_push early` → `fs_service_init` | **0 B** | ✅ 确认在 PSRAM（F30 生效） |
| **`fs_service_init` → `bsp_display_start`** | **73756 B** | **★ RGB panel，DMA 硬性** |
| `bsp_display_start` → `audio_service_init` | 13792 B | I2S + codec |
| `audio_service_init` → `led_service_init` | 1240 B | LED |
| `led_service_init` → `button_service_init` | 316 B | adc_button |
| `button_service_init` → `vol_out_cb` | 88 B | 回调 |

**★ "0 B" 这一格和 "73756 B" 这一格同样重要** ——
前者证明约束被守住了（大缓冲确实进了 PSRAM），后者是下一个待攻坚目标。
**拆账单的价值在于同时确认"哪些防线还立着"。**

### 9.11 ★★★ 第三类处置：**"可以缩，但要付代价"**（bounce buffer 实例）

上面 §9.8 建立了二分：**"能挪没挪"** vs **"挪不动"**。
本次追查 RGB panel 时发现了**第三类**，二分不够用。

#### 先把"名字相似的三块东西"分清（这是最容易搞错的地方）

用户问"RGB panel 帧缓冲是干啥的"，直觉会把它当成**一块**。实际是**三块独立缓冲**：

| # | 名字 | 大小 | 落点 | 谁在用 |
|---|---|---|---|---|
| 1 | RGB 帧缓冲 `fbs[]`×2 | 1500 KB | **PSRAM** | RGB 硬件扫描输出 |
| 2 | **bounce buffer**×2 | **62.5 KB** | **内部 DMA** | RGB DMA 逐行搬运 |
| 3 | LVGL 绘制缓冲 | **0 B** | — | （被 `avoid_tearing` 省掉了） |

**吃内部的那 72 KB ≈ #2 + 驱动结构体。而"帧缓冲"（1500 KB）一分内部都没吃。**

> **★ 经验：名字里带 "frame buffer" 的东西可能有三四种，
> 归属和落点全不同。看到大块消耗，必须先定位到"哪一行代码在分配"，
> 不能按名字归类。** 本次若按名字归到 #1，就会得出"帧缓冲在 PSRAM、不占内部"的
> 错误结论，从而认为这 72 KB 是别的东西。

#### 第三类：可以缩，但要付 CPU 代价

| 类别 | 判断依据 | 处置 | 本工程实例 |
|---|---|---|---|
| **A. 能挪没挪** | `INTERNAL` 跌幅 > `DMA` 跌幅 | 改 caps，收益大成本低 | 任务栈 70.5 KB |
| **B. 挪不动** | `INTERNAL` 与 `DMA` 跌幅**完全相同** | 只能减需求或改架构 | `esp_wifi_init` 44.5 KB |
| **C. 可以缩，但要付代价** | 是**尺寸参数**而非落点问题 | 改配置值，**代价在别处** | **bounce buffer 62.5 KB** |

**C 类的识别特征**：那块内存的**大小由某个配置常数决定**，而不是"该不该在这里"。
所以改 `caps` 无用（它本来就该在内部），**但改常数有用**（代价转移到了 CPU/性能）。

**本工程 C 类清单**：

| 项 | 当前 | 可缩到 | 省 | 代价 |
|---|---|---|---|---|
| `CONFIG_BSP_LCD_RGB_BOUNCE_BUFFER_HEIGHT` | 20 | 10 | **31.25 KB** | DMA 中断变频繁，CPU 占用升高 |
| `CONFIG_BSP_LCD_RGB_BUFFER_NUMS` | 2 → 1 | — | PSRAM 省 750 KB | 撕裂风险（**不是内部收益，别搞混**） |
| `MBEDTLS_SSL_IN_CONTENT_LEN` | 默认 | 8192 | ~8 KB | 大响应体截断 |

> **★ C 类最容易和 B 类混淆**：两者都"改 caps 无用"。
> 区分点：**B 类无解（除非改架构），C 类有解（改常数）但代价外移。**
> 遇到"改 caps 无效"的大块，**先问一句"它的大小是哪个常数定的"** ——
> 若有常数，就是 C 类，有救；若没有，才是 B 类。

#### ★ 附带确认：`avoid_tearing=1` 是**省内存**的

直觉上"avoid tearing（防撕裂）"听起来像"多花内存换画质"。本工程实际相反：
`avoid_tearing` 让 LVGL **借 RGB 帧缓冲当画布**，**不分配自己的 draw buffer**（省 0 B 实际是省了 1500 KB）。

```
avoid_tearing=0 + direct_mode=1:
  buffer_size 必须 = 384000 px（direct_mode 强制整屏）
  buf1+buf2 = 768000 × 2 = 1500 KB, buff_dma=true → 【硬性内部 DMA】
```
**→ 误关它会让内部 RAM 多花 1500 KB，多 20 倍。**

> **★ 一般化：`avoid_tearing` / `double_buffer` / `direct_mode` / `full_refresh`
> 这些"画面质量"开关同时是内存开关，而且方向不直观。
> 改之前必须读实现 —— "名字听起来像优化" 的东西可能是反向的。**

### 9.12 ★★★ 调用上游私有符号的三步法：静态变量拿不到，但有公开 getter（F36 沉淀）

F36（蓝牙音量失败）本身是协议缺陷，不属堆管理；但它逼出了一套
**"应用层要调用 IDF 内部函数/读内部状态"**的通用做法，且已经在 `.map` 文件上验证过，
以后遇到同类问题可直接复用。

#### 问题形状

需要调用一个 IDF 内部函数（`BTA_AvOpenRc()`），前提是拿到一个内部状态值
（`btc_av_cb.bta_handle`）。但：

- 目标头文件在 IDF **私有目录**（`btc/profile/std/include`），加进 `INCLUDE_DIRS`
  会在上游升级时碎掉；
- 承载状态的 `btc_av_cb` 是**文件级 `static`**（本工程因
  `# CONFIG_BT_BLE_DYNAMIC_ENV_MEMORY is not set` → `A2D_DYNAMIC_MEMORY == FALSE`
  → `btc_av.c:123` 走 `static btc_av_cb_t btc_av_cb = {0};`），**外部根本看不见**。

#### 三步法

**第 1 步：先在 `.map` 文件里查符号是否已被链接进固件**

```bash
python -c "
import io
p='build/display_audio_photo.map'
for ln,line in enumerate(io.open(p,encoding='utf-8',errors='ignore'),1):
    if 'BTA_AvOpenRc' in line or 'btc_a2d_conn_handle_get' in line:
        print(ln, line.rstrip()[:130])
"
```

得到**确定地址**，证明是**全局符号**（不是 `-fvisibility=hidden`）：

| 符号 | `.text` 地址 | 来源 |
|---|---|---|
| `btc_a2d_conn_handle_get` | `0x400d19ae` | `libbt.a(btc_av.c.obj)` |
| `BTA_AvOpenRc` | `0x400f49c4` | `libbt.a(bta_av_api.c.obj)` |

> **★ 只要 `.map` 里有地址，就说明链接器已经采纳，`extern` 声明即可用。**
> **这一步能把"能不能调"从猜测变成事实 —— 5 秒钟的事，不要跳过。**

**第 2 步：找公开 getter，而不是想办法访问那个 static 变量**

顺着"这个值一定有人需要"的思路去搜：

```bash
grep -rn "return btc_av_cb.bta_handle" $IDF/components/bt/
```

一次命中 `btc_av.c:2275`：

```c
uint16_t btc_a2d_conn_handle_get(void) { return btc_av_cb.bta_handle; }
```

> **★★ 经验：IDF 里几乎所有"内部 CB 的某个字段"都存在一个配套的非 static getter，
> 因为上层模块之间也要互相读。** 遇到 `static` 不要立刻放弃 ——
> 先搜 `grep -rn "cb_name.field" --include=*.c`，看有没有现成的读口。

**第 3 步：用 `extern` 声明，不 include 私有头**

```c
extern uint16_t btc_a2d_conn_handle_get(void);
extern void     BTA_AvOpenRc(uint16_t handle);
```

> **★ 收益**：不动 CMake、不动 `INCLUDE_DIRS`、不引入私有头路径依赖。
> 代价：签名若在上游变了，编译期**不会报错**（只有链接期报）。
> 因此**必须写清楚签名出处**（`btc_av.h:313` / `bta_av_api.h:882`）
> 并在注释里注明"升级 IDF 后需重新核对"。

#### 附带的两个"不要"

- **不要再调一遍公开 API 去触发同一件事** —— 本工程想补 AVRCP 连接，
  若再调 `esp_a2d_source_connect()` 会被 `btc_profile_queue.c:43` 的
  **按 uuid 去重**静默丢弃（`if (node->uuid == p_param->uuid) return;`）。
  **需要绕开队列时，必须找到不过队列的那条函数。**
- **不要相信"某条件满足就会自动好"的注释** —— 原注释写"AVRCP CT 连上就会注册
  `vol_ops`"，字面正确，但"连上"这个前提**在本工程永远不成立**。
  **凡是注释里出现"只要……就会……"，都要去验证那个前提。**

- 2026-09-21（同日九追 · F36 蓝牙音量）：新增 **§9.12 调用上游私有符号的三步法**
  （`.map` 验符号 → 搜公开 getter → `extern` 声明不 include 私有头），
  并记录两条禁令（别用公开 API 绕队列 / 别信"只要…就…"型注释）。

### 9.13 ★★★ 排障方法论三条：先测量再动刀 / dump 是快照不是账本 / 默认值 ≠ 安全值（F37 沉淀）

F37（两次 `Stack protection fault` 误判）不是堆问题，是**任务栈**问题；
但它踩的三个坑与堆排障（F23/F30/F35）完全同构，值得并排记——
**同一个错误模式，换了内存域还会再犯一次**。

#### 坑一：判读方法没对着底层机制校验过

第一轮拿"panic dump 的 `Stack bounds` 差值 == ISR 栈大小"判"中断栈溢出"，
看起来闭环，实际上 **`portasm.S` 进中断时会先把 SP 切到 ISR 栈顶、再把边界寄存器
改写成 ISR 栈区间** ⇒ dump 里的 bounds/SP 永远是 ISR 栈快照，与真凶无关。
判读方法恒真、恒无信息量，第一轮整个推理链建立在它上面，错了一整轮。

> **★ 任何"从现象到根因"的判读方法，先去读 port/驱动源码确认
> "这个值是谁在什么时机写的"，再决定信不信。** 与 §9.4 的"三个判定域"
> 同一精神：先搞清测量工具量的是什么，再读数。

#### 坑二：不测量就动刀 —— "水位日志"一锤定音

第一轮的三处修复全是"推断驱动"；第二轮只加了一个
`uxTaskGetStackHighWaterMark(NULL)` 水位日志，实测 HWM=9128B ⇒
峰值已用 7256B、恰好越过旧上限 7168B —— **一行日志完成定位+实锤+结案**。
这与 F35 的 `BOOT_DIAG`/`DISP_DIAG` 埋点是同一个教训的第三次重演：
**内存（含栈）问题的正确顺序永远是"埋点 → 测量 → 量化解说 → 动刀"，
跳过前两步的动刀都是赌。**

> **★ 栈的"三元组"对应物**：栈域问题不打印 free/largest，而是
> `uxTaskGetStackHighWaterMark()`（嫌疑任务的剩余水位，单位 = 字节，本移植
> `StackType_t = uint8_t`）——哪个任务贴 0，真凶就是谁。

#### 坑三：组件代建的资源不在"账本"里，默认值 ≠ 安全值

taskLVGL 是 esp_lvgl_port 组件代建的（默认 task_stack=7168、内部 RAM），
它不在本工程"11 处任务栈外置台账"（§5.1.1 / 13 号文档）里——**台账漏了
它，预算就漏了它**。7168 在 UI 简单时"能跑"，UI 加重（bin 字体动态字形加载、
歌词/EQ 动画、整页重建）后被压穿。

> **★ 凡是"别人替你建"的资源（组件任务栈、组件缓冲池、组件堆），
> 要么找到配置入口纳入自己的账本（`bsp_display_start_with_config()` 这类），
> 要么至少在台账里记一笔"它存在且多大"。** "能跑"是当场快照，
> 不是容量承诺。

#### 元教训：修完复现 ⇒ 先质疑判读，再谈剂量

第一轮修完复现、签名一字不差，这是**判读错误的强信号**；正确反应是
回头重读 portasm.S，而不是把 4096 加大到 8192（那将是第三次白烧 + 白吃 4KB）。
**"修复无效"本身就是数据**——它与任何日志同等级别，必须消费掉，
不能只当成"再加大一点"的理由。
