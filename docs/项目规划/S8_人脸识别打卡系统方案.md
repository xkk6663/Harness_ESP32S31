## 0. 需求拆解（用户原话 → 可验收的语义）

> "在人脸识别模式下做人脸识别管理系统，识别正确的人脸拍照存进 sd 卡专属人物文件夹里，
> 而且如果是联网状态下图片要附上打卡具体年月日具体到秒的时间，做一个人脸识别打卡记录系统，
> 有录入模式和用户模式，录入人脸人数小于 10 人"

逐条拆成**可验收的判据**（这一节是后面所有设计的靶子）：

| # | 需求原话 | 可验收语义 | 归口 |
|---|---|---|---|
| R1 | 人脸识别模式下 | 仅在 `tab_camera` 的 FACE 档 + 检测开关 ON 时生效，HAND 档不参与 | UI |
| R2 | 人脸识别管理系统 | 有**库**（可增删查）→ 有**记录**（可浏览）→ 有**模式**（录入/用户） | 3 个新模块 |
| R3 | 识别正确的人脸 | 相似度 > 阈值才算"正确"；否则落"未知"，**不得误报成某人** | 识别引擎 |
| R4 | 拍照存进 SD 专属人物文件夹 | `/sdcard/attendance/<序号>_<姓名>/...jpg`，**每人一个目录** | punch_service |
| R5 | **联网状态下**图片附打卡时间 | 时间可信（SNTP 已校时）才附；**未联网必须降级且可辨认**，不得写 1970 | net_time + punch |
| R6 | 具体年月日具体到秒 | `YYYY-MM-DD HH:MM:SS` 全精度，**不是** `HH:MM` | punch |
| R7 | 人脸识别打卡记录系统 | 除照片外要有一份**可读的流水**（谁 / 何时 / 第几次） | attendance CSV |
| R8 | 录入模式 / 用户模式 | 两个明确区分的运行态，UI 可切、行为不同、状态显性 | 状态机 |
| R9 | 录入人脸人数 < 10 人 | 硬上限 10（含），第 11 人**明确拒绝**并提示，不是静默失败 | face_db |

**★ 需求 R5 的一个歧义，必须由用户拍板（本文按 (c) 设计，见 §7-D3）**：
"图片附上时间"有三种理解 —— (a) 文件名带时间、(b) 图片**像素里**印着时间、(c) 旁边有元数据文件。
本文默认 **(a)+(b)+(c) 三重**，其中 (b) 只有走 §7-D2 的 P1 路线才可能（原因见 §3 约束②）。

### 1.3 ★ 一个容易被忽略的重要事实：FACE 档**没有关键点**

`face_service_detect()` 的 FACE 分支只填 `x/y/w/h/score`，`label` 显式置空
（`face_service.cpp` 的 `out[n].label[0] = '\0';`，紧跟在 `fam == FAM_HAND` 判断之前）。

- 这意味着**当前没有 5 点关键点** ⇒ 无法做标准人脸对齐（`align + 5pt → 112x112`）。
- 5 点关键点模型其实是**现成的、且在本地**：
  `managed_components/espressif__human_face_detect/models/p4/human_face_detect_mnp_s8_v1.espdl`（**129,968 B**，MNP = 关键点网络）。
  与之配套的 MSR（人脸粗定位）是 **61,248 B**。
- 但母方案 §1 的档位表里 **MSR/MNP 档已在更早的迭代中阉割**（`face_service.h:11` 注释："原 416 / MSR/MNP 档已阉割"）。
  ⇒ **要做对齐就得把 MNP 加回来**（130 KB，体积代价很小），或者接受"不对齐"的精度损失。

> 这一条是 §7-D1 的核心输入：**不认识关键点，就谈不上"识别正确"**。

## 3. ★★ 四个决定方案形态的技术约束

这一节是全文最重要的部分。**四条里有两条款会直接推翻"直觉上最合理"的做法**。

### 约束① 内部 RAM 只剩 ≈4 KB 连续块

母方案 §8.1 实测：`INT free≈127 KB / largest≈55 KB`，而 WiFi 重建**要一次 51 KB 连续**
⇒ 余量 ≈ **4 KB**。本文**所有新增缓冲一律走 PSRAM**，一个字节都不许进内部堆。
（打卡照片的帧副本 240×240×2 = **115,200 B**，必须 `heap_caps_malloc(..., MALLOC_CAP_SPIRAM)`。）

### 约束② ⚠ **"把时间烧进 JPEG 像素"在 720p 硬编路径上做不到**

直觉做法是"抓一帧 → 在图上画时间 → 编码"。但：

- 母方案 §2.2 已确认 **OV3660 自带 JPEG 编码器**，720p JPEG 码流是 **sensor 直出**的
  （`esp_video` 的 V4L2 buffer 里拿到时**已经是压缩码流**，`capture_service.c:105` 是直接 `fwrite(data,1,size)`）。
- ⇒ **在码流外面无法"画"任何东西**。要叠水印只能在**编码前**拿到未压缩帧。

**结论**：只有两条路能实现"像素级水印"：

| 路线 | 能否烧水印 | 代价 |
|---|---|---|
| **P1** 240×240 RGB565 抓帧 → 叠字 → **软件编码 JPEG** | ✅ 能 | 软件编码耗时 + 115 KB PSRAM 帧副本 |
| **P2** 复用 `capture_service` 的 720p 硬编 | ❌ 不能 | 反而更贵：切格式 + 停预览 + 数百 ms 黑屏 |

★ 反直觉之处：**看起来"大材小用"的 P1，在打卡场景里才是对的**
（打卡要的是"这张图上有谁、几点"，720p 的高低分辨率不增加任何信息，却带来黑屏 + 无法水印）。
这也是 §7-D2 的推荐依据。

### 约束③ 打卡照片不能用 `s_last_frame`（悬垂指针的老坑）

`tab_camera.c:48 on_frame()` **只记指针不拷贝**，`cam_task` 回调返回后立刻 `QBUF`
（母方案 §1.1 已记录此坑，`tab_camera.c:85` 有专门的悬垂防护注释）。
⇒ 打卡取帧必须**在 LVGL 线程内、用 canvas 自己的缓冲**（`s_canvas_buf`，240×240×2，生命周期归本页），
**或** 在 `on_frame` 里同步 memcpy 到 punch_service 的 PSRAM 缓冲。二者选一，见 §5.3。

### 约束④ 本工程开了 `-Werror=format-truncation=`

`capture_service.h:50` 有一整段血泪注释：路径缓冲 96 曾被 GCC 在**内联后**证明会截断而编译失败。
⇒ 打卡路径比 `/photos/IMG_xxx.jpg` **更长**（多一层 `<序号>_<姓名>/`，而姓名是**中文 UTF-8，1 字 3 字节**）。
新模块的路径缓冲必须≥ 128 并配 `_Static_assert` + 入口容量检查。**姓名长度必须设上限**（建议 6 个汉字 = 18 B + NUL）。

## 4. SD 卡数据布局（定稿建议）

```
/sdcard/
├── face_db/                          ← 【系统数据】人脸库，掉了要重录
│   ├── persons.idx.0                 ← 索引（双份世代号，见 §5.2）
│   ├── persons.idx.1
│   ├── feats.bin                     ← 特征拼接区（按 idx 里的 off/len 定位）
│   └── thumbs/
│       ├── 01.jpg                    ← 每人一张底片，供库管理页列表显示
│       └── 02.jpg
│
└── attendance/                       ← 【用户数据】打卡记录，可整目录拷走
    ├── index.csv                     ← ★ 总流水（追加式，PC 端 Excel 直接打开）
    ├── 01_张三/                      ← ★ 专属人物文件夹
    │   ├── 20260928_103045.jpg       ← 文件名 = 年月日_时分秒
    │   ├── 20260928_103045.json      ← 同名元数据（可选，见 §7-D3）
    │   └── 20260928_183012.jpg
    ├── 02_李四/
    └── 99_访客/                      ← 未识别（阈值没过）落这里，不与真人混
        └── 20260928_104512.jpg
```

**为什么 `attendance/` 与 `face_db/` 分开而非合并进"每人文件夹"**：
- 库（`face_db`）是**系统状态**，打卡（`attendance`）是**业务记录**，两者生命周期、备份策略、删除权限都不同；
- FILES 页要能一键"清空打卡记录"而**不误删人脸库**（分母不同才能做到）；
- 一个真人一个目录 —— 满足 R4 的"专属人物文件夹"，且目录名带**序号前缀**保证排序稳定
  （纯中文名在 FATFS 里按字节序排会很乱）。

### 4.1 目录名规范（★ 受约束④制约）

```
<序号:2位>_<姓名:≤6 汉字>
   01_张三
   02_李四
   99_访客            ← 保留序号，不参与分配
```
- 序号从 `persons.idx` 的 `id` 来，**一旦分配永不变**（改名不改目录名，或改名时 rename 目录）；
- 姓名做**文件名安全化**：替换 `\ / : * ? " < > |` 与控制字符为 `_`（FATFS 非法字符）；
- 目录名总长 ≤ `2+1+18` = 21 B ⇒ 加上 `/sdcard/attendance/`（20 B）与 `/20260928_103045.jpg`（19 B）
  = **60 B**，远小于 128 ⇒ 安全，但仍按约束④加静态断言。

### 4.2 `index.csv` 格式（R7 的交付物）

```csv
seq,name,person_id,date,time,epoch_s,photo,score
1,张三,1,2026-09-28,10:30:45,1790000000,01_张三/20260928_103045.jpg,0.87
2,李四,2,2026-09-28,18:30:12,1790028612,02_李四/20260928_183012.jpg,0.91
3,访客,0,2026-09-28,10:45:12,1790000000,99_访客/20260928_104512.jpg,0.42
```

- **追加式**（`"a"` 模式）⇒ 掉电最多丢最后一行，不会毁整份文件；比"读-改-写"安全一个量级；
- 表头只在文件为空时写一次（`fseek/ftell` 判空）；
- `epoch_s` 一并存，便于 PC 端做时区无关的排序/统计；
- **未联网时** `date/time` 列写 `--`（见 §5.4 降级规则），**绝不写 1970**。

## 5. 模块设计

### 5.1 `middleware/net/net_time_service.h` —— **补一个取时间接口**（G5）

```c
/* 接口草案（仅设计，不落盘） */
typedef struct {
    bool     valid;        /* = net_time_service_time_valid()，调用方不必再查一次 */
    int      year, mon, day;
    int      hour, min, sec;
    time_t   epoch;
} net_time_t;

/** 取当前本地时间快照。未校时时 valid=false，其余字段为 0。任意线程可调。 */
void net_time_service_get(net_time_t *out);

/** 便捷格式化：valid 时输出 "2026-09-28 10:30:45"（19 B + NUL），
 *  否则输出 "---- -- -- --:--:--"（**可辨认的占位，不是 1970**）。 */
void net_time_service_format(const net_time_t *t, char *out, size_t out_len);
```

**理由**：现在每个调用方各自 `time(NULL) + localtime_r`（`capture_service.c:146` 就是），
一旦有人忘了先查 `time_valid()`，就会写出 1970 时间戳。**把"可信判定"和"取值"绑在一个函数里**，
让"忘了查"在编译期就不可能发生。这是纯增量改动，不改任何现有调用点。

### 5.2 `middleware/face_db/face_db.c/h` —— 人脸库（**新建**）

```c
#define FACE_DB_MAX        10      /* ★ R9：硬上限，含 */
#define FACE_NAME_MAX      24      /* UTF-8 字节，≤6 汉字 + NUL */
#define FACE_RECOG_DIM     512     /* 特征维度，随识别引擎定（§7-D1） */

typedef struct {
    uint16_t id;                   /* 1..FACE_DB_MAX，永不复用 */
    char     name[FACE_NAME_MAX];
    uint32_t feat_off, feat_len;   /* 在 feats.bin 中的位置 */
    uint32_t enroll_epoch;         /* 录入时间 */
    uint8_t  sample_cnt;           /* 录入时采了几张（质量参考） */
} face_person_t;

esp_err_t face_db_init(void);                       /* 开机加载索引到内部 RAM（10 人 ≈ 0.6 KB） */
int       face_db_count(void);
const face_person_t *face_db_get(int idx);          /* 只读，按槽位 */
const face_person_t *face_db_find_by_name(const char *name);
esp_err_t face_db_enroll(const char *name, const float *feat, int dim); /* 满 10 人返回 ESP_ERR_NO_MEM */
esp_err_t face_db_delete(uint16_t id);
esp_err_t face_db_rename(uint16_t id, const char *new_name);
esp_err_t face_db_load_feats(float *out, int max_persons, int *n);      /* 批量读特征用于比对 */
```

**落盘格式（`persons.idx`）**：

```
[Header 16B]  magic "FDB1" | schema_ver u16 | feat_dim u16 | count u8 | seq u32 | crc32 u32
[Entry × count]  face_person_t（紧凑序列化，不直接 memcpy 结构体 —— 避免对齐/padding 差异）
```

**★ 双份世代号（母方案 §6.2 已提，此处定稿）**：
FATFS 的 `rename()` **不是原子**（无日志，掉电可能两个名字都没了）。所以：
1. 读时取 `idx.0` / `idx.1` 中 **CRC 通过且 seq 更大**的那份；
2. 写时永远写"较旧的那份"，再更新 seq；
3. 十人规模下一次写 ≈ 300 B，**写两份的开销可忽略**。

`feats.bin` 用**追加式**（不回收空洞；10 人 × 512 × 4 B = 20 KB，浪费无所谓）。
删除一条 = 改索引 + 让 `feats.bin` 里的那段落成孤儿（不紧凑化，避免重写整个文件）。

### 5.3 `middleware/face/face_recog_service.cpp/h` —— 识别引擎（**新建**）

```c
/* 与 face_service.h 同风格：C++ 实现 + C ABI，供 C 的 UI 层调用 */
typedef struct {
    int      person_id;       /* 0 = 未知 */
    char     name[FACE_NAME_MAX];
    float    score;           /* 余弦相似度 */
    int      x, y, w, h;      /* 命中的检测框（透传给 UI 画框 + 打卡裁剪） */
    bool     valid;
} recog_result_t;

esp_err_t face_recog_request_load(void);   /* 异步加载（同 face_service 的受理制） */
void      face_recog_poll(void);           /* 挂在 cam_task，与 face_service_poll 同处 */
esp_err_t face_recog_stop(void);
face_state_t face_recog_state(void);
bool      face_recog_ready(void);

/** 对 240×240 RGB565 帧跑"检测 → 对齐 → 提特征 → 查库"。**在调用线程同步执行**，
 *  所以只允许从 cam_task 侧调（绝不在 LVGL 线程）。 */
int face_recog_run(const uint16_t *rgb565le, uint16_t w, uint16_t h,
                   recog_result_t *out, int max, float thr);
```

**内部流程**（每条都对应 §1.3 的缺口）：

```
① 检测框      ← 复用 face_service_detect()（**不重复建检测模型**，省 ~500 KB PSRAM）
② 关键点      ← [缺口 G1/1.3] 加回 MNP（130 KB）取 5 点
③ 仿射对齐    ← 5 点 → 112×112（超出边界的用边缘像素填充，不死循环）
④ 提特征      ← MFN 模型（§7-D1 决定从哪来）
⑤ 比对        ← 库内逐条余弦相似度，取最大；> thr 则命中，否则 person_id=0
```

**为什么复用 `face_service` 的检测而不自己建**：FACE 档模型已**常驻**
（`face_service.h:60`"模型常驻"），再建一份等于 PSRAM 里多 500 KB，且与约束①正面冲突。

### 5.4 `middleware/camera/punch_service.c/h` —— 打卡事务（**新建**）

```c
typedef struct {
    esp_err_t err;
    int       person_id;                 /* 0 = 访客 */
    char      name[FACE_NAME_MAX];
    char      path[PUNCH_PATH_MAX];      /* 落盘的 .jpg */
    bool      time_valid;                /* R5：本次打卡时间是否可信 */
    float     score;
} punch_record_t;

esp_err_t punch_service_init(void);      /* 建 115 KB PSRAM 帧暂存 + 一次性任务 */

/** 发起一次打卡（**非阻塞**，受理制）。
 *  @param rgb565le 当前帧（240×240 RGB565LE），**函数内立即 memcpy**，调用方可马上返回
 *  @param person  识别结果（id/name/score/box）
 *  @return ESP_OK / ESP_ERR_INVALID_STATE（SD 未挂载 / 上一次还在写 / 冷却期内） */
esp_err_t punch_service_request(const uint16_t *rgb565le, uint16_t w, uint16_t h,
                                const recog_result_t *person);

bool punch_service_busy(void);
void punch_service_get_last(punch_record_t *out);
```

**事务步骤**（照抄 `capture_service` 的"接管 → 干活 → 归还"骨架，但**不碰相机**）：

```
① 守卫：SD 已挂载；不在冷却期；无并发打卡
② memcpy 帧 → PSRAM 暂存（115 KB，**是唯一新增的常驻缓冲**）
③ 任务里：叠水印（姓名 + "YYYY-MM-DD HH:MM:SS"）→ JPEG 软编 → 落盘 → 写 CSV
④ 释放：暂存不算释放（常驻复用），只清 busy
```

**★ 与 `capture_service` 的关系**：两者**互不影响，也不互相调用**。
- `capture_service` = VIDEO tab 的 720p 高分辨率拍照（用户手动按）；
- `punch_service` = CAM tab 的 240×240 打卡存证（识别自动触发）。
- 二者都写 SD，但目录不同、相机归属不同（punch **不申请 owner**，只读 CAM 已有的预览流）。

**水印实现**（约束②下唯一可行路径）：
- 帧副本是 RGB565；先用现有 `s_scratch` 同款转换写 RGB888（240×240×3 = **172,800 B**，另需 PSRAM）；
- 文字用**离屏 LVGL canvas** 绘制（能直接用 `lv_font_cn_20`/`lv_font_cn_30` 输出中文姓名 + 数字时间），
  再 `lv_canvas_get_buf()` 取回像素叠加到帧副本上；
- ⚠ **离屏 canvas 的创建/绘制必须在 LVGL 线程**（LVGL 非线程安全，本工程铁律）。
  ⇒ 要么在 `tab_camera::refresh()` 里画好再投递，要么自绘 ASCII 点阵（只支持数字/英文，中文名退化成拼音/ID）。
  **这一条是 §7-D4 的决策依据。**

**冷却期（防"站着不动刷几百张照片"）**：
- 同一 `person_id` 在 `PUNCH_COOLDOWN_S`（默认 **60 s**）内只记一次，第二次**不落盘、不报错**，UI 提示"已打卡"；
- 计时基准用 `esp_timer_get_time()` 的单调时钟，**不用 `time()`** —— 未联网时 `time()` 会跳。

## 6. 内存 / 分区 / 体积预算

| 项 | 增量 | 区域 | 依据 |
|---|---|---|---|
| 打卡帧暂存 | **115,200 B** | PSRAM 常驻 | 约束①：不进内部堆 |
| 水印用 RGB888 转换缓冲 | **172,800 B** | PSRAM 常驻（复用 `face_service` 的 `s_scratch` 同款思路，但**不能共用**——分属不同任务/时刻） | 同上 |
| JPEG 软编输出缓冲 | ~64 KB | PSRAM | 240×240 Q80 典型 15–25 KB，留余量 |
| JPEG 编码器实例 | ~30 KB ⚠未实测 | PSRAM | `jpeg_enc_open` 内部 |
| 人脸库索引 | **~600 B** | **内部 RAM** | 10 × (2+24+4+4+4+1+对齐) |
| 特征向量（库，10 人） | **20,480 B**（512×4B×10） | PSRAM | 允许全量常驻，比对时零 SD 读 |
| 特征模型（MFN） | **~0.5–1 MB** ⚠未实测 | PSRAM | §7-D1 决定；**必须过 §61 的连续块预检** |
| MNP 关键点模型 | **129,968 B** | PSRAM | 已在本地，加回档位即可 |
| **合计新增 PSRAM** | **≈ 2.2–2.7 MB** | | 16 MB Octal PSRAM，余量充足 ⚠ 但**必须过连续块预检** |
| **合计新增内部 RAM** | **≈ 0.6 KB** | | 约束①的红线保住了 |

**★ 必须复用 §61 的 `model_mem_ok()` 预检**：MFN 模型是大块分配，
正是 POSE 档翻车（`free 够、largest 不够`）的同类场景。
识别模型的加载**必须**走同一道闸门，否则就是同一个坑踩第二次。
（`face_service.cpp` 里的 `model_bytes()/model_mem_ok()` 目前是 `static`，需要抽出为可复用函数或复制一份。）

**分区**：**不改 `partitions.csv`**。SD 卡不占 flash。
littlefs 现状 5,024,580 B / 9,306,112 B，剩 **≈4.28 MB**；
MFN 模型（≤1 MB）放进 `littlefs_content/models/` 后仍剩 ≥3 MB，**够用**。
（⚠ 若 §7-D1 选 A0 且组件模型 >1.5 MB，需重新评估。）

## 7. ★★ 待用户拍板的四个决策点

### D1 识别引擎从哪来（**最关键，决定整个 S8 的形态**）

| 选项 | 做法 | 优点 | 代价 / 风险 | 识别准确率 |
|---|---|---|---|---|
| **A0** 拉组件 | `main/idf_component.yml` 加 `espressif/human_face_recognition: '^0.3'` | 官方封装，MFN + 对齐 + 数据库一站式 | ① 组件**不在本地**，需联网拉（注册表可达但本工程有 403 史，需 7890 代理或离线 clone）② 其模型目录是否有 **s31/p4 变体未核实**（母方案 §6.1 末已标）③ littlefs 挤 ~1 MB | **高** |
| **A1** 手放模型 | 只拿 `mfn_s8_v1.espdl`（esp-dl model zoo），自己用 `dl::Model` + `dl_feat_postprocessor` | 不依赖组件管理器，绕开 403 | 对齐预处理要自己写（~150 行） | **高** |
| **B** 零新模型 | 用检测框裁剪 + PPA 缩放 + 分块直方图/梯度做轻量特征 | **零新组件、零新模型、零内存增量**，当天可跑通 | 准确率对光照/角度敏感，长相相近的两人可能混 | **中低**（<10 人 + 固定工位可能可用） |

**★★ 已定（2026-09-28，用户拍板）：A1 + MNP（130 KB 加回做对齐）**。以下推荐理由保留供追溯：

1. A0 的收益（封装）不足以抵掉三重不确定性（组件可达性 / s31 变体 / 与 `human_face_detect 0.4.2` 的版本约束）；
2. A1 只需要**一个权重文件**，落进 littlefs 即可，其余全用 esp-dl 已有的 `dl::recognition::DataBase` 基础设施
   （`managed_components/espressif__esp-dl/vision/recognition/` 已确认包含 `dl_feat_base` / `dl_feat_image_preprocessor` / `dl_recognition_database`）；
3. B 虽然最省，但**"识别正确"是 R3 的原话** —— 做不到就是没做需求，只适合当兜底/临时验证。

**⚠ 但无论选哪个，都建议先做 §8 的 `S8-0 前置验证`**（半天成本），因为 A0/A1 都受"模型能否拿到并在 s31 上跑起来"制约。

### D3 "图片附上时间"的形式（R5/R6 的落地）

| 形式 | 实现成本 | PC 端可见性 | 备注 |
|---|---|---|---|

| (c) 同名 `.json` 元数据 | 低（~30 行） | 需脚本/编辑器 | ARM 端结构最简单、字段最全 |
| (d) **EXIF** `DateTimeOriginal` | **中高**（要手写 APP1 段、改 SOI 后插入） | 相册软件直接读 | 一期建议**不做**（收益低、风险中） |

### 14.2 ★★ 实测性能（这张表决定了 S8-2 的形态）

| 项 | 官方 P4 | 官方 S3 | **本机 s31 实测** | 结论 |
|---|---|---|---|---|
| 加载（1,295,200 B，littlefs） | — | — | **1715 ms** | 一次性，可接受 |
| **单次推理**（预处理+MFN+后处理，112×112×3） | 96 ms | 254 ms | **324 ms** | ⚠ **比 S3 还慢 28%** |
| 特征维度 | 512 | 512 | **512 ✓** | 符合预期 |
| 输出 dtype | — | — | int8 | — |

**⚠ 324 ms 意味着什么**：CAM 页 `refresh()` 是 50 ms 一拍 ⇒ **一次识别要跨掉 6.5 帧**。
而且这 **324 ms 只是"特征提取"这一段**，完整的 `detect → keypoint → align → feat → query`
还要再加检测（`espdet_pico_224_224_face`）与对齐开销。
⇒ **原方案 §8-S8-2 验收项里那句"若 > 50 ms 必须挪到 cam_task"已经不够了**：
即使挪进 cam_task，324 ms 也会把预览从 20 fps 拖到 3 fps。

**S8-2 必须按下面三条来设计**（否则"识别一开，取景器就卡成 PPT"）：
1. **识别频率与预览帧率解耦**：每 N 帧（或每 ≥1 s）才做一次完整识别，其余帧只做检测画框
   —— 方案 §13.4 原估的"每 4~6 帧一次"要改成**每 7~10 帧**；
2. **先便宜后昂贵**：检测（便宜）确认有脸、且框稳定 N 帧后才触发 MFN（贵），
   避免"画面里没人也在空跑 324 ms"；
3. **打卡场景本身对延迟不敏感**（人站 1~2 秒完成识别即可），所以 324 ms **不是致命问题**，
   真正的痛点只是**取景器流畅度** ⇒ 认了延迟、别认了卡顿。

### 14.3 ★★ 一个新发现的副作用：加载会给 PSRAM 留下**碎片**

```
探针开始前：   PSRAM free=4413KB  largest=4352KB
探针跑完释放后：PSRAM free=4413KB  largest=3008KB
                  ↑ 完全恢复        ↑ 少了 1344 KB！
```

- `free` 分毫不差 ⇒ **没有泄漏**（这一条是好消息，说明 esp-dl 的释放是干净的）；
- 但 `largest` 从 4.25 MB 掉到 **2.94 MB** ⇒ MFN 的加载/卸载在 PSRAM 里**留下了不可合并的碎片**。

**这条直接影响以后的档位决策**：
§62 之所以能阉割 POSE，依据是"3.04 MB 连续块装不下"。现在看，
**只要 MFN 跑过一次，连续块就只剩 2.94 MB** ⇒ 未来任何 ≥3 MB 的档在新模型加载后都更难上线。
⇒ 结论不变（POSE 该阉），但**理由更强、且适用范围更宽**：
**任何 3 MB 级模型都必须排在 MFN 之前加载**，或干脆走 §12.4 的独立分区 mmap 路线。

```
I (10068) FACE_DB: idx slot 0 written: seq=11 count=9 dim=512 (380 B)  ← 删除写回较旧的 slot0
I (10093) FACE_DB: loaded from slot 0: count=9 dim=512                 ← ★ 又选中新的
```

**大小增长 60/100/…/420 B 与 `20 + N×40` 逐字节吻合**，说明紧凑序列化没有 padding 泄漏。

另附几条通过的断言：空库 `0/10` → 录 3 人（id 1/2/3）→ 重名 `INVALID_STATE` 挡下 →
`find_best` 命中李四 `score=1.0000`、库外特征最高分 `0.0000`（正交特征，符合预期）→
满 10 人 → 第 11 人 `ESP_ERR_NO_MEM` 拒绝 → 目录名 `01_张三` / `99_访客` /
`a/b:c*?` → `a_b_c__` → 模拟重启 10 人仍在 → 删除后重载 9 人。

### 15.2 ★★ 关键的边界声明：ENROLL 态现在**只做就绪度检查**，不做采集

方案 §5.5 原写的 ENROLL 交互是"提示输入姓名 → 连采 3 张（1/3 2/3 3/3）→ 入库"。
但**采集一张脸需要特征提取**（MFN + 5 点对齐），而那是 S8-2 的识别引擎。

⇒ 本阶段 `ENROLL` 态的职责是：把"录入一张脸所依赖的**全部**前置条件"逐条查出来，
告诉用户**卡在哪一条**。判据顺序（因果链，不可打乱）：

```
ENROLL: start camera first       ← 没预览 ⇒ 没帧可采
ENROLL: face db not ready (SD?)  ← 没库   ⇒ 采下来没处存
ENROLL: db full 10/10            ← 满库   ⇒ 录不进去（R9）
ENROLL: switch MODEL to FACE     ← HAND 档给的是"手"的框，过不了人脸门槛
ENROLL: model build FAIL         ← 模型构建失败
ENROLL: model loading...         ← 构建中（~1 s，别谎报 "no face"）
ENROLL: tap FACE to detect       ← 检测被用户关掉了
ENROLL: no face in view          ← 画面里没人
ENROLL: Move closer / Center the face / Hold still (low conf) (52%)
ENROLL: ready - 3/10 used        ← ★ 全部前置条件就绪
```

**这条"待补"只有一行**：最后那条 ready 分支，S8-2 把文案换成"1/3 2/3 3/3"即可，
其余判据（含 §5.6 的质量门槛）**原样复用**。

**为什么不先画个假的 "0/3"**：那会让用户以为按下去就能录，而实际什么都不发生 ——
正是母方案反复强调要消灭的"按下去没反应"。

### 15.4 三个实现要点（都是踩过或用血换来的）

1. **删除按钮不能在事件回调里重建列表**
   `list_rebuild()` 第一件事是 `lv_obj_clean(s_list)`，而回调**正运行在被清理的子对象上**。
   ⇒ 用 `lv_async_call()` 延后一拍（事件返回后执行）。这是本工程**第一个**这么干的回调
   （既有回调都只发动作、不重建），已在代码里写清原因。
2. **动态文本一律走拷贝语义**
   定时刷新时用 `lv_label_set_text_static()` 配**栈缓冲** ⇒ 标签持有失效指针
   （表现为"过一会儿乱码/崩"，复位后不可复现）。新增的
   `ui_common_set_label_text_if_changed()` 内部固定用 `lv_label_set_text()`（拷贝），
   并只在内容真的变了时才写（否则 50 ms 一次 malloc）。
3. **`LV_SYMBOL_*` 必须先核对内置字体里有没有这个字形**
   本工程 `UI_FONT = lv_font_montserrat_14`，它只含一个**精选**符号子集
   （`lv_font_montserrat_14.c` 文件头 `Opts:` 里的那一串十进制码点）。
   本次用的 `LV_SYMBOL_LIST`(61451) / `LV_SYMBOL_REFRESH`(61473) / `LV_SYMBOL_TRASH`(62189)
   **都确认在内**。核对方法见 §15.6。

### 16.2 ★★ S8-2 的三条设计（都由 §14.2 的实测数据逼出来）

| # | 设计 | 为什么 |
|---|---|---|
| ① | **识别绝不进 LVGL 线程** | `detect + align + feat` 实测 **324 ms**（比官方 S3 的 254 ms 还慢 28%）。放进 `refresh()` 就是"识别一开，取景器掉到 3 fps" |
| ② | **触发节奏与帧率解耦** —— `RECOG_PERIOD_MS 1500`，且**先便宜后昂贵** | MSR/MNP 检测（便宜）先跑，确认"有脸且框够好"才拉起 MFN（昂贵）。1.5 s 一拍 ⇒ 识别只占 27% 的时间 |
| ③ | **引擎开关用"对账"而不是"在回调里开关"** | 期望值由**四条外部状态**共同决定（`face_service_enabled() && face_model_active() && 相机 RUNNING && face_db_is_ready()`）。`recog_pump()` 每拍算一次期望值再决定 load/stop；`face_recog_stop()` 在作业进行中会**拒绝**（防 UAF），此时把期望值留在 true 下拍重试 |

配套：`face_recog_submit()` 在**调用线程**同步做 RGB888 转换（约 1 ms）后起一次性任务；
`RECOG_TASK_STACK 8192`、`PUNCH_TASK_STACK 4096`，**两块栈都必须在内部 RAM**
（做文件/storage IO 的任务栈一旦落 PSRAM，会在 flash cache 关闭窗口里崩 —— F35/F38/F40）。

### 16.3 ★★ 点序陷阱（本轮最容易静默降低准确率的一处）

`dl_feat_image_preprocessor.cpp` 里 `s_std_ldks_112` 的顺序是
**`[左眼, 左嘴角, 鼻尖, 右眼, 右嘴角]`** —— **不是**直觉的"左眼→右眼→鼻尖→左嘴角→右嘴角"。

MNP 的 `result_t.keypoint`（10 个 int = 5 点 × xy）**正好与之一致** ⇒
`recog_run_once()` 里必须**原样透传**，重排不会报错，只会**静默降低准确率**。
（S8-0 探针那一版里的 `kLandmark112` 顺序也一并订正了；探针测不出这个错。）

### 16.4 内存账（PSRAM）

| 项 | 大小 | 时机 |
|---|---|---|
| 识别帧缓冲（240×240 RGB888） | 172,800 B | 引擎加载时一次性分配 |
| `recog_result_t` 快照 | ≈ 2.2 KB | 同上 |
| 打卡帧缓冲（同步 memcpy 的副本） | 172,800 B | 第一次真正打卡 |
| JPEG 输出缓冲 | 64 KB | 第一次真正打卡 |
| 打卡流水缓存（S8-4，`PUNCH_LOG_MAX`=128 条 × ~120 B） | ≈ 15 KB | **第一次进 FACE 页**，之后永不释放 |

★ 顺序红线：**任何 3 MB 级模型必须排在 MFN 之前加载**。加载 MFN 会让
`free` 基本不变但 `largest` 从 4352 KB 掉到 3008 KB —— 这就是 §61 的
`model_mem_ok()` 预检要拦的东西。`engine_load()` 里先把帧缓冲/结果快照分好，再
`new HumanFaceDetect(...)`、最后 `new MFN(...)`。

### 16.5 ★ S8-4：为什么给 `file_mgr_service` 加了一个 getter

`file_mgr_service` 只有**一个**事件回调槽（`s_cb` / `s_cb_user`），由 `tab_files` 在
建页时无条件注册。而打卡记录页要复用 `FMC_PREVIEW`（方案 §8-S8-4 指定的"不新写浏览逻辑"）
就必须临时接住 `FME_PREVIEW_DONE`。

- 不加 getter 的话，借调方只能"猜原来是谁"（必错）或者"干脆不还"（**FILES 页从 FACE 页
  返回后会彻底收不到事件**，表现成"点了没反应"）；
- 加了 `file_mgr_get_evt_cb()` 之后就是标准三段式：**存 → 换 → 用 → 还原**（`face_destroy`
  里还原）。代价是 2 个静态变量 + 3 行代码。

⚠ 事件回调跑在 **file_mgr 服务任务**上下文：`face_file_evt_cb()` 只写一个 `volatile int`，
结果由 300 ms 轮询在 LVGL 线程里取走 —— 绝不在回调里碰 LVGL。

### 16.6 ★ S8-4：记录页的三条纪律

| # | 纪律 | 为什么 |
|---|---|---|
| ① | **分页渲染，不是"全渲染再滚动"**：`REC_PAGE_SIZE 20` | 128 条全建 = 约 900 个 LVGL 对象（≈100 KB 堆），而 flex 布局**每帧**都要遍历可见子对象 —— 那是"滚起来掉帧"的直接成因。20 行 = 140 个对象，与记录总数无关 |
| ② | **CSV 只在必要时重读**（进页 / 切分组 / 清空后 / 3 s 轮询；**预览开着时不重读**） | `punch_service_log_read()` 是**同步**读全文件、跑在 LVGL 线程里。预览开着时重读会把 `s_rec[]` 就地覆盖，而用户手上正按着某一行 —— 那会预览到**另一条记录**的照片 |
| ③ | **两种视图共用同一个 `s_list`，同时只有一个数据源在渲染** | 垂直预算只算一次；不会出现"两个滚动区各自记着位置"；切视图只有**一次** `lv_obj_clean()` |

配套的排序判据用 `epoch_s`（新增字段）而**不是** `date`/`time` 字符串：
未校时那批是 `"--"`，字典序会插在 `"2026-…"` **前面**，表现成"新记录被一堆 `--` 顶到下面"，
而数据少的时候根本看不出来。未校时的一律沉底。

#### 16.9.3 顺手修掉的一处**哨兵值滥用**

`recog_pump()` 原来用 `pr.elapsed_ms != 0` 当"这次任务跑完了"的判据。
但 `elapsed_ms` 以 tick（10 ms）为单位，而 `punch_task` 有几条**同一 tick 内立刻失败**的
早退路径（参数不对 / SD 未挂载 / 目录拼不出来）⇒ `elapsed_ms == 0` ⇒
**UI 永远不会提示"打卡失败"**，用户只看到"按了没反应"。

**修法**：`punch_record_t` 增加显式字段 `bool has_result`，`punch_task` 收尾无条件置位，
UI 改判它。这类"哨兵值被合法数据撞上"的 bug 本工程已出现过一次（§15.2 坑 1），
规矩统一为：**状态用显式标志位，不要拿测量值当哨兵**。

## 17. ★★★ P0 事故：ENROLL 卡在 `capturing 0/3`（2026-09-28 20:1x 上机，已定位 + 修复）

> 这是 S8 全阶段代码收口（§16）之后的**第一次上机**。结论先行：
> **烧录完全正确、模型都在；是我的代码漏了一行"接线"** ——
> `face_recog_poll()` 从没被调用过，于是引擎永远停在 `FACE_LOADING`。

### 17.1 现象（用户贴的串口日志）

| 观察 | 说明 |
|---|---|
| `RECOG: recog ON, engine load requested` 出现 2 次 | `face_recog_set_enabled(true)` 正常执行 |
| **整段日志没有 `starting recog load task ...`** | ★ **决定性证据**：poll 从未被调用 |
| **整段日志没有 `recog engine ready in ... ms`** | 引擎从未加载 |
| **也没有 `recog load never started within 8000 ms`** | 看门狗也从未被调用（它同样挂在没人调的函数里） |
| `TAB_CAM: enroll start: name=qwq` 之后再无 `enroll: sample n/3` | 采集一步都没走 |
| UI | 覆盖层/状态栏停在 `ENROLL: capturing 0/3` ⇒ 用户体感 = "按了没反应" |

### 17.2 根因：一行接线漏了（**不是模型、不是烧录、不是内存**）

失败链（每一环都有代码依据）：

| # | 环节 | 代码位置 |
|---|---|---|
| ① | `face_recog_set_enabled(true)` 只置 `s_state=FACE_LOADING` + `s_load_pending=true`，然后打日志 | `face_recog_service.cpp` |
| ② | **`s_load_pending` 的唯一消费者是 `face_recog_poll()`** | 同文件 |
| ③ | **UI 侧从没调用过它** | `tab_camera.c` 只调了 `set_enabled / stop / busy / result / result_consume / submit / frame / init` |
| ④ | ⇒ `s_state` 永远 `FACE_LOADING`，`face_recog_ready()` 永远 false | `face_recog_service.cpp` |
| ⑤ | ⇒ `face_recog_submit()` 每次都返回 `ESP_ERR_INVALID_STATE`，**且完全静默**（无日志） | 同文件 |
| ⑥ | ⇒ `recog_pump()` 每 50 ms 重试一次、每次静默失败 | `tab_camera.c` |
| ⑦ | ⇒ ENROLL 永远 `capturing 0/3` | 同上 |

**为什么这么明显的漏能过审**：S8-0 阶段引擎的唯一用户是**探针**（`face_recog_probe()`），
它自己在内部直接调 `engine_load()`、**根本不经过 poll** ⇒ 这条路径从写下到上机之间
**一次都没被执行过**。静态校验只能查语法，查不出"两个模块之间少了一根线"。

**为什么事故不留痕**：
- 看门狗写在 `face_recog_state()` 里，而 **UI 也不调它**（只调 `busy` / `ready`）⇒ 超时永不触发；
- `submit()` 的"未就绪"分支没有日志 ⇒ 串口里一点痕迹都没有；
- 状态栏只显示"在采集"，不显示"在等引擎" ⇒ 用户也拿不到线索。

### 17.3 修复（4 条，互相独立、缺一不可）

| # | 修复 | 为什么这么改 |
|---|---|---|
| ① | **加载改成一次性任务**：`face_recog_poll()` 不再同步跑 `engine_load()`，只 `xTaskCreate` 一条 `recog_load`（`RECOG_LOAD_STACK` **10240**、Core0、跑完自删并自报 hwm）。宿主调 poll 变成**非阻塞**。 | ① `cam_task` 只有 `CAM_TASK_STACK=3584`，本次上机报表自己写着 `used=2540 hwm=1044 need=4096` —— **它已经不够了**（连 face_service 那个 495 KB 的模型都只是勉强跑，P2-5 的问号至今没销）；② LVGL 线程栈 9728 / used 6688 / hwm 3040，同样放不下，而且会卡 UI 约 2 s；③ **10240 是实测过的数** —— 当年 S8-0 探针就是用 10240 栈任务跑通这条链路并打出 PROBE PASS 的 |
| ② | **看门狗搬进 `face_recog_poll()`**，条件加 `!s_load_running` | "请求了 8 s 却**连加载任务都没起来**"只可能是 poll 没被周期调用 —— 正是本次事故的形态。语义从"加载慢不慢"收窄为"poll 有没有被调"。`face_recog_state()` 退回纯 getter |
| ③ | **`face_recog_stop()` 同时看住 `s_load_running`** | 旧代码只挡"识别任务在跑"。加载任务跑起来后它正在写 `s_det/s_mfn/s_frame`，此时 `engine_unload()` = 把它脚下的指针删掉（重复 free / UAF）。现在拒绝并返回 `ESP_ERR_INVALID_STATE`，由宿主下一拍重试 |
| ④ | **UI 侧接线 + 让"没就绪"有话说**（`tab_camera.c`） | 见下 |
| ⑤ | **加载任务收尾时补做"加载期间被停"** | `face_recog_stop()` 被拒时**已经把 `s_enabled` 清成 false**；加载任务收尾一读就知道"有人要关"，当场 `engine_unload()`。不补的话：宿主每 50 ms 重试能兜住，**但 CAM 页一销毁就没人重试了**（`tab_camera_destroy` 删掉定时器）⇒ 1.29 MB 的 MFN 永远常驻 PSRAM。复用 `s_enabled`（改 `volatile`），不引入新标志位 |

④ 的三个具体动作：
- `recog_pump()` 在"引擎开关对账"之后调 **`face_recog_poll()`**。必须放在对账之后：
  这一拍刚置上的 `s_load_pending` 当拍就能被消费；
- `recog_pump()` 的两次 `face_recog_submit()` 失败**不再静默**：新增限频槽
  `SKIP_NOT_READY`（第 8 槽），打 `identify submit refused (ESP_ERR_INVALID_STATE) ready=0 engine=1`；
- `enroll_status()` 与 ENROLL 覆盖层在引擎没就绪时**明说原因**
  （`ENROLL: engine loading ...` / `engine load FAIL (see log)` / `engine idle - tap FACE`），
  而不是继续显示"在采集 0/3"。

> ⚠ `enroll_status()` 里那段检查必须排在 **CAPTURING 分支之前**，否则一进 CAPTURING
> 就再也看不到原因。它管的是**识别引擎**（MSR/MNP + MFN）；下面原有的
> `face_service_state()` 那段管**检测模型**（espdet）—— 两者独立加载，报错分开报。

**不做自动重试**：`engine_load()` 失败的两种原因（文件缺失 / 内存不足）都需要人工干预，
每 50 ms 重试一次只会刷屏。失败后停在 `FACE_FAIL`，用户看到明确文案，可切 FACE 开关重试。

### 17.4 现场澄清：**"烧 storage 占用空间没增加"是误解，不是症状**

用户的第二个疑问与本次故障**无关**，而且**镜像本身是对的**。两条硬证据：

| 证据 | 数据 |
|---|---|
| `build/storage.bin` 大小 | **9,306,112 B = 0x8E0000** —— 恒等于**分区大小**，与内容多少无关（littlefs 镜像按分区尺寸生成 / pad）⇒ esptool 每次写的字节数**必然相同**，看起来就是"没增加" |
| 三个模型的内容**字节**都在镜像里 | `..._msr_s8_v1.espdl` @`0x616000`、`..._mnp_s8_v1.espdl` @`0x5f6000`、`..._feat_mfn_s8_v1.espdl` @`0x625000`（按**文件头 48 B 原样搜索**命中，不只是文件名） |

正确的核对方法（已写进速查表）：
```bash
ls -l build/storage.bin          # 恒等于 0x8E0000
cat build/storage-flash_args     # → 0x720000 storage.bin
find littlefs_content -type f -printf "%s\n" | awk '{s+=$1} END {print s}'
#   ↑ 这才是"内容"的大小：6,510,996 B（加 MSR/MNP 之前是 6,319,780 ⇒ 真正的增量 +191,216 B）
```
⇒ **storage 余量 = 9,306,112 − 6,510,996 = 2,795,116 B（2.67 MB）**，没有超盘。

### 18.3 验收后的最终形态（源码口径）

- **CAM 页**：START / FACE / PUNCH 按钮（HSV 按钮已删）；240×240 canvas 预览；
  FACE 开 = det 模型加载，关 = `face_service_unload_sync()` 彻底卸载；
  PUNCH 在用户态识别成功即打卡，录入态三采三验入库。
- **记录页（page_face）**：NEW FIRST/OLD FIRST 时间排序、行内预览（等比 letterbox）、
  行内 DEL（两步确认）、bar2 SYNC 对账（SD 卡照片被手删后可清理孤儿记录）。
- **PSRAM 生命周期**：除 file_mgr `s_pv[2]`（921,600 B，按需化候选）与 JPEG 解码引擎
  （有意常驻）外，全部按需分配即用即释放——12 项总表见 `改动记录.md` §73.10。
- **VIDEO 页**：拍照/录像为右侧竖排 72 圆钮，按下即拍、按住录松手停（PRESS_LOST 收尾），
  按下颜色翻转（青→红 / 绿→青）——属 S2/S3 范畴的 UI 改版（§73.12）。
