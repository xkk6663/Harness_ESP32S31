# 11. 遇到的问题（Fault / 坑位复盘）

> 本文件记录项目自开发以来遇到的重大崩溃（fault/abort/闪屏）与典型坑位。
> 每条按 **现象 → 根因 → 解决 → 经验** 组织，供后续排障与新人参考。
> 新增故障时追加到末尾，编号递增。

---

## F1. ADC oneshot 配置直接 abort：`invalid attenuation`

- **现象**：`button_init` 里 `adc_oneshot_config_channel(..., &chan)` 触发
  `ESP_ERROR_CHECK failed: esp_err_t 0x102 (ESP_ERR_INVALID_ARG)`，
  日志 `adc_oneshot: invalid attenuation`，随后 `abort()` 复位。
- **根因**：在 ESP32-S31 + IDF v6.1 上手动配 `adc_oneshot` 并用 `ADC_ATTEN_DB_12`
  做电阻分压按键，本平台该 attenuation 取值/通道映射与预期不符，初始化即失败。
- **解决**：放弃自写 ADC oneshot，改用乐鑫 `iot_button` 组件的
  `iot_button_new_adc_device()` 统一管理分压按键；只提供
  `adc_channel` + 各键的电压阈值数组，组件内部完成校准/采样/消抖。
- **经验**：S31 是新芯片，底层 ADC 驱动 API 有差异；**优先用 BSP/组件现成封装，
  不要手撸寄存器级驱动**，省掉校准与 attenuation 的坑。

## F2. 电阻分压按键识别错乱 / 全部识别成一个键

- **现象**：四个功能键（PLAY/SET/VOL-/VOL+，GPIO42 单 ADC 分压）
  只有 mode 能识别，其余按了没反应或识别成别的键。
- **根因**：照搬别的板子的分压阈值，未按 Korvo-1 V1.1 实际分压电阻测量。
- **解决**：逐个按键读实测电压并标定（单位 mV）：
  | 键 | 实测电压 |
  |---|---|
  | SET（最上） | 260 |
  | MODE | 759 |
  | VOL- | 1237 |
  | VOL+（最下） | 1647 |

  阈值按相邻中点 ±100mV 设窗口。
- **经验**：**分压按键阈值必须用万用表/串口 log 在自己板子上实测**，
  不能抄原理图理论值或别的板子数值；预留足够迟滞窗口防抖。

## F3. 跑按键后屏幕黑白闪屏 / 栈溢出

- **现象**：刚加 ADC 按键时，屏幕开始黑白交替闪屏，日志出现大量
  `0xa5a5a5a5` 填充值、`audio_task ... at audio_service.c` 回溯。
- **根因**：按键初始化 abort 后系统状态异常/任务栈被踩；`0xa5a5a5a5`
  是 FreeRTOS 栈溢出哨兵填充值，说明某任务栈被写穿（音频任务栈不足 +
  异常路径叠加）。
- **解决**：修正 ADC 初始化（走 iot_button）；核对各任务栈大小
  （音频任务栈 ≥ 8192）；确保不经过 abort 路径。
- **经验**：
  - **看到 `0xa5a5a5a5` 直接定位栈溢出**，优先查任务栈大小；
  - 任何 `ESP_ERROR_CHECK` 在硬件初始化阶段失败都会 abort，
    硬件初始化失败要"先稳住再排障"，别让它拖垮正在跑的显示/音频任务。

## F4. 子页面返回按钮一点就崩溃（hard fault）★ 最经典

- **现象**：SYS 进任意子页（WIFI/BT/RGB/System），点左上角返回箭头立即重启/崩溃。
- **根因**：返回按钮的点击事件回调里，`PageManager_Back()` **同步**
  `lv_obj_del` 了整个子页 screen——而被点的返回按钮正属于这个 screen，
  此时 LVGL 事件派发器还在访问这个对象，删除"正在被事件使用的对象"直接 hard fault。
- **解决**：`PageManager_Back()` 改为两段式：
  1. 先 `lv_scr_load_anim()` 淡入切回上一页；
  2. 用一个**一次性 `lv_timer`（230ms）**在 LVGL 任务里异步调用
     该页 `destroy()`。事件与切页动画都结束后再释放对象，安全。
  - 配套：`pending_destroy_cb` 用静态结构 `{page, obj}` 传参，
    **不要**把 `destroy(lv_obj_t*)` 强转成 `lv_timer_cb_t(lv_timer_t*)`
    （参数类型不同，timer 回调拿到的是 timer 指针而非 page）。
- **经验**：
  - **LVGL 铁律：不要在事件回调里 `lv_obj_del` 事件源（或包含事件源的父对象）**。
    必须删时用 `lv_obj_del_async()` 或延迟 timer。
  - 页面栈切换动画与对象销毁要解耦：先切屏，后销毁。

## F5. RGB 灯开关关闭时，拖滑块灯仍点亮

- **现象**：RGB 子页把电源开关拨到 OFF，拖动 R/G/B 滑块，灯却跟着亮。
- **根因**：`apply_color()` 里无条件 `led_service_set_rgb()`（内部 start
  BSP_LED_ON），没读开关状态。
- **解决**：`apply_color()` 增加开关判断——仅当 power switch 为 ON 时才下发
  颜色到硬件；OFF 时只更新屏幕预览色块与 `#RRGGBB` 标签。开关切 ON 时用当前
  滑块色重新点亮，切 OFF 时 `led_service_set_on(false)`。
- **经验**：**硬件执行类操作必须受"使能开关"门控**；UI 状态（switch）
  与硬件副作用分离，预览可以实时动，但写硬件要判断当前是否使能。

## F6. LVGL PPA draw unit 在 S31 上编译失败

- **现象**：尝试用乐鑫 LVGL 的 PPA draw unit 做硬件加速，编译报错。
- **根因**：该 draw unit 当前只支持 P4 像素格式，与 S31 显示位宽不匹配。
- **解决**：回退，不启用 PPA draw unit；S31 的 2D-DMA/PPA 留给后续显示通路
  （JPEG 硬解等）单独验证。
- **经验**：乐鑫新芯片的加速组件 API/支持矩阵变化快，**先查组件 README 支持的
  芯片与色深**，不要想当然接上就用。

## F7. Windows 下 git push 失败 / ssh-agent 起不来

- **现象**：推 GitHub 仓库（SSH，key 有 passphrase）失败；
  `Start-Service ssh-agent` 报 error 1058。
- **根因**：Windows OpenSSH ssh-agent 服务被禁用，非交互 shell 又无法弹 passphrase。
- **解决**：写 `%USERPROFILE%\.ssh\askpass.bat`（内容 `@echo off` + `echo 密码`），
  push 前设 `$env:SSH_ASKPASS` 指向它、`$env:SSH_ASKPASS_REQUIRE=force`，
  git 自动从 askpass 读密码；ssh 走 ssh.github.com:443 代理。
- **经验**：非交互后台跑 git 时，**提前准备好 askpass**，别依赖 ssh-agent 或
  手动输密码。

## F8. md 文档中文变乱码

- **现象**：用 PowerShell `Set-Content`/`Out-File` 写 md，中文打开全是乱码。
- **根因**：Windows PowerShell 默认用 GBK/ANSI 写文件，覆盖了 UTF-8 md。
- **解决**：**改 md 文件只用专用 Write/Edit 工具**，不用 PowerShell 重定向写 md。
- **经验**：文档类 UTF-8 文件交给编辑器工具写，命令行只用于编译/烧录/查日志。

## F9. `-Werror=stringop-truncation` 编译失败

- **现象**：`strncpy(dst, src, sizeof(dst))` 触发 -Werror 编译不过。
- **根因**：`strncpy` 不保证结尾 `\0`，GCC 把它当错误。
- **解决**：改用 `snprintf(dst, sizeof(dst), "%s", src)`。
- **经验**：IDF 开了 `-Werror`，字符串拷贝一律 `snprintf`，别用 `strncpy`。

## 通用排障速查表

| 现象 | 第一怀疑点 |
|---|---|
| `abort()` + `ESP_ERROR_CHECK failed` | 硬件初始化参数错（ADC atten / GPIO / 句柄空） |
| 日志大量 `0xa5a5a5a5` | 任务栈溢出，加大栈 |
| 点某按钮立即重启 | 在事件回调里删了事件源对象，改异步删除 |
| 改完代码串口无输出/老日志 | 没真正烧进去，确认 flash 成功 + 板子复位 |
| CMake：`Failed to resolve component 'xxx': unknown name` | IDF v6.1 已移除该内置组件（如 `json`），vendored 到 `components/` 并改 `PRIV_REQUIRES`（F14） |
| ninja：`CreateProcess failed: cannot find the file specified`（命令首词是 ccache） | ccache 包装器拉起编译器失败，`IDF_CCACHE_ENABLE=0` 关掉即可（F15） |
| 中文 md 乱码 | 用 Set-Content 写坏了，用 Write/Edit 重写 |
| PS1 里变量赋值不生效且无报错 | 脚本是 UTF-8 **无 BOM** 且含中文，PS 5.1 按 GBK 解码串行，改存为 UTF-8 with BOM（F16） |
| 和风天气 403 空 body（去掉 key 也 403） | 公共域名已下线（`devapi` 2026-01-01 停服），改用控制台的**专属 API Host**（F17） |
| 改了密钥/host 但固件仍是旧值 | CMake `$ENV{}` 只在 configure 求值，**搜 bin 字符串**确认；改后必须 reconfigure / fullclean（F18） |
| HTTP 200 但 `cJSON_Parse failed` | 看 `Content-Encoding`：和风强制 gzip，body 以 `1f 8b` 开头 ⇒ 需 zlib 解压（F19） |
| `SAFE_DELETE_BULK_CONFIRM_REQUIRED` 导致 reconfigure/fullclean 失败 | 沙箱批量删除保护，**用改名代替删除**绕过（F20） |
| `cmake 找不到 Ninja (CMAKE_MAKE_PROGRAM is not set)` 但 ninja 明明在 | **别装 Ninja**：PS 5.1 把 cmake 的 stderr 判成致命错误掐断了调用链。改用 `tools/_run_idf.py` 启动器（F21） |
| `MSys/Mingw is no longer supported` 后 exit 0 什么都不干 | 环境里有 `MSYSTEM`，启动器里 pop 掉它（F21） |
| `TypeError: ... got 'NoneType'`（idf_component_manager） | 缺 `ESP_IDF_VERSION`，显式设成 `6.1`（F21） |
| 编译 `-Werror` | 看具体 error 行，warning 也可能被当 error |
| 串口 monitor 卡住/失败 | 非 TTY 别用 `idf.py monitor`，用 pyserial 脚本抓 |
| `Stack protection fault`（dump 显示 ISR 栈 bounds） | **dump 不可信**：bounds/SP 是中断入口快照，永远显示 ISR 栈。给嫌疑任务加 `uxTaskGetStackHighWaterMark` 水位日志，看谁贴 0；dump 里被打断的"当前任务"通常就是肇事者（F37） |

## F10. 拖动 LED 滑块触发 `Cache error` / Guru Meditation，屏幕闪屏卡死

- **现象**：RGB 子页拖亮度/颜色滑块时偶发 `Guru Meditation Error: Core 1 panic'ed (Cache error)`，
  崩在 `spimem_flash_ll_auto_wait_idle_init`；屏幕黑白闪屏。clean rebuild 后仍偶发。
- **根因**：UI 滑块回调运行在 **LVGL task**，WiFi 事件运行在 **esp event task**，两个任务
  **无锁并发调用同一组 `led_indicator_stop/set_rgb/start`（RMT 后端）**，踩坏硬件状态，
  并在 cache 访问时爆发。不是 flash/PSRAM 配置问题，也不是业务逻辑错。
- **解决**：`led_service` 重构为 **FreeRTOS 命令队列 + 独立 LED 任务**：
  - 内部 `xQueueCreate(8)` + `xTaskCreate(led_task)`（4KB 栈，prio 5）；
  - `set_status/set_rgb/set_on/set_manual` 全部只 `xQueueSend` 命令，**不在调用任务上下文碰 LED 驱动**；
  - LED 句柄、当前颜色、开关/手动模式标志全部收在 LED 任务里串行维护、串行应用；
  - 硬件 `bsp_led_indicator_create` 仍留在 app_main 上下文（验证过能亮的位置）。
- **经验**：**跨任务操作带硬件状态的外设（RMT/I2S/SPI 屏）时，不要让多个任务直接调同一组
  驱动 API**；用"命令队列 + 单 worker 任务"把硬件访问串行化，调用方退化成纯生产者。
  这与工程规范 07 章"常驻任务 + 命令队列"一致。注意区分：S31 软复位偶发 Cache error 多为
  PSRAM/MSPI 残留（硬上电可解），本故障是稳定复现的并发问题。

## F11. RGB 子页打开开关后灯不亮

- **现象**：进 RGB 子页开关 OFF 灯灭正常，但打开开关后灯不亮；退出回主界面状态灯也不亮。
- **根因**：`apply_color` 用 `s_led_on` 标志判断是否输出；进页时 `set_on(false)` 把 `s_led_on`
  置 false，而 UI 打开开关只发了 `set_rgb`、**没发 `set_on(true)`**，LED 任务收到 set_rgb 时
  `s_led_on` 仍为 false，直接 `start(OFF)` 不点亮。
- **解决**：UI `apply_color` 在开关 ON 时同时发 `led_service_set_on(true)` 再发 `set_rgb`；
  LED 任务 `ON(true)` 分支按当前 R/G/B 重新 `set_rgb` 后启动效果。
- **经验**：命令队列模型下，**状态机标志（s_led_on）的所有迁移都必须由命令显式驱动**，
  UI 不能假设"之前发过就还在"；用临时日志（post 命令 id、apply_color 参数）打印命令流
  能快速定位"命令到了但状态不对"。

## F12. esp_littlefs 组件拉取失败：registry 403 / submodule 镜像 DNS 不通

- **现象**：`idf.py build` 时组件管理器拉 `espressif/esp_littlefs` 返回 **403 Forbidden**（components-file.espressif.com）；
  改中国镜像 `components.espressif.cn` 也 URLError。手动 clone 后又报 `littlefs/lfs.h: No such file or directory`。
- **根因**：① 本网络访问乐鑫组件注册表被 403；② joltwallet/esp_littlefs 的 littlefs 核心是 **git submodule**，
  `--depth 1` clone 不带子模块；③ 本机全局 git 把 `https://github.com/` 镜像到 `jihulab.com/esp-mirror/...`，
  该 host DNS 解析失败，submodule 走 https 必失败；④ 走 SSH 又因未配 key 报 `Permission denied (publickey)`。
- **解决**：
  - 直接 `git clone https://github.com/joltwallet/esp_littlefs` 到工程本地 `components/esp_littlefs`（本地组件优先，绕开注册表）；
  - 删 `main/idf_component.yml` 里的 `espressif/esp_littlefs` 依赖行（不再让管理器联网求解）；
  - **只改该仓库** `.gitmodules`：submodule url 写 `git@github.com:littlefs-project/littlefs.git`（不动全局 git 配置）；
  - 用 `SSH_ASKPASS=askpass.bat`（输出密码 800）走 SSH `git submodule update --init` 拉到指定 commit；
  - 拉前若有失败残留，先 `git submodule deinit -f` + 删 `src/littlefs` 再 update。
- **经验**：组件注册表不通时，**把依赖 clone 到工程本地 `components/` 并从 idf_component.yml 删对应依赖**即可离线构建；
  不要为绕镜像去改全局 git config；SSH 非交互环境用 SSH_ASKPASS 喂密码。另：**ESP32-S31 ROM 不支持整片 `erase-flash`**，
  改分区后直接 `idf.py flash` 覆盖烧录即可。

## F13. 点 REC 按钮闪屏崩溃：业务任务跨任务操作 LVGL

- **现象**：REC 子页点 REC 按钮立即黑白闪屏崩溃；录音本身（mic→文件）逻辑正常。
- **根因**：`audio_service` 播放/录音完成后在 **audio_task** 上下文回调 `on_audio_event()`，
  该回调直接 `bsp_display_lock(0)`（timeout=0 非阻塞）后 `lv_obj_clear_state()` 操作按钮。
  `bsp_display_lock(0)` 拿不到锁也不检查返回值就继续，等于在非 LVGL task 裸碰 LVGL 对象，
  与 LVGL task 并发访问 → Cache error / 闪屏。本质是跨任务访问 LVGL 无保护。
- **解决**：UI 事件解耦为 FreeRTOS 队列：
  - `page_wav_player.c` 建 `s_audio_evt_q`（深度 8）+ `lv_timer(30ms)`；
  - `on_audio_event()`（audio_task）只 `xQueueSend` 事件 ID，**绝不 `lv_*`**；
  - `audio_evt_drain_cb()`（LVGL task）出队后才 `lv_obj_clear_state` / `tab_record_on_*`；
  - 删除原 `bsp_display_lock(0)` 竞态写法。物理按键音量本就走 `button_service` 队列 + `lv_timer` 抽队列，无需改。
- **经验**：**LVGL 只能在 LVGL task 上下文操作**。任何业务/中断/timer task 要更新 UI，
  一律 `xQueueSend` 事件、由 LVGL task 的 `lv_timer` 出队执行；禁止非阻塞 `bsp_display_lock(0)` 后不判返回值就碰控件。
  已写入 `07_模块实现规范.md`「跨任务访问 LVGL：队列解耦」红线。

## F14. ESP-IDF v6.1 已移除内置 `json`（cJSON）组件，`PRIV_REQUIRES json` 直接配置失败

- **现象**：新增 `net_time_service`（需要 cJSON 解析和风天气 JSON）后，CMake 配置阶段直接失败：
  ```
  CMake Error at tools/cmake/build.cmake:380 (message):
    Failed to resolve component 'json' required by component 'main': unknown name.
  HINT: The component 'json' could not be found.
  ```
- **根因**：**ESP-IDF v6.1 不再随 IDF 内置 `json`/cJSON 组件**。本机 `C:\esp\v6.1\esp-idf\components`
  下 146 个组件里根本没有 `json`/`cjson` 目录，也没有 `cJSON.h`（全盘搜索 IDF + managed_components +
  工程 components 均为 0 命中）。而本机访问乐鑫组件注册表仍返回 **403**（同 F12），
  无法用 `idf.py add-dependency "espressif/json"` 联网获取。
- **解决**：按 F12 的同样思路——**把 cJSON 源码 vendored 进工程本地 `components/`**（本地组件优先，绕开注册表）：
  1. 从 GitHub 取 cJSON v1.7.18 的 `cJSON.c` / `cJSON.h`（MIT）；
  2. 放到 `components/cjson/cJSON.c` + `components/cjson/include/cJSON.h` + `LICENSE`；
  3. 自建 `components/cjson/CMakeLists.txt`：`idf_component_register(SRCS "cJSON.c" INCLUDE_DIRS "include")`；
  4. `main/CMakeLists.txt` 的 `PRIV_REQUIRES` 写 **`cjson`**（本地组件名），不是 `json`。
- **经验**：
  - 新版 IDF 在持续把第三方库移出内置组件，**`json` 就是个典型例子**；遇到 `unknown name` 先查
    `esp-idf/components/` 目录里到底有没有该组件，别照抄老教程的 `PRIV_REQUIRES json`；
  - 注册表 403 的离线环境下，**vendored 到 `components/` 是通用解法**（esp_littlefs、cJSON 都这么办的）；
  - 另外 **`esp_crt_bundle` 也不是独立组件名**，它是 `mbedtls` 的一部分（`mbedtls/esp_crt_bundle/include/esp_crt_bundle.h`），
    `PRIV_REQUIRES` 要写 `mbedtls`；但 `#include "esp_crt_bundle.h"` 照常可用。

## F15. ninja 编译报 `CreateProcess failed: The system cannot find the file specified.`（ccache 包装器拉起 gcc 失败）

- **现象**：`idf.py build` 时大量 `*.obj` 编译失败，且**集中在后加入的组件**上（tcp_transport / esp-tls /
  http_parser / esp_wifi 等），每个都报：
  ```
  CreateProcess failed: The system cannot find the file specified.
  FAILED: esp-idf/esp-tls/CMakeFiles/__idf_esp-tls.dir/esp_tls_mbedtls.c.obj
  ```
  报错行开头的命令是 `ccache C:\Espressif\...\riscv32-esp-elf-gcc.exe -D... `。
- **根因**：**ccache 包装器**在拉起编译器时失败（不是编译器本身缺失）。已实测排除了几个干扰项：
  - 编译器本体单独可跑：`riscv32-esp-elf-gcc.exe --version` → 正常输出 15.2.0；
  - ccache 单独可跑：`ccache.exe ccache.exe gcc --version` → 正常输出（**注意**：用 bash 传 Windows 路径时
    `//c` 之类的转义会把路径搅坏，要用 Python `subprocess` 或纯 Windows 路径来验证，否则会误判成“ccache 坏了”）；
  - 在沙箱内/外都复现 → 排除沙箱拦截。
  即“编译器与 ccache 各自都好，但 ninja 通过 ccache 拉起 gcc 时失败”，属 ccache+Windows 高并发下的偶发拉起问题。
- **解决**：**禁用 ccache** 即可，ccache 只是编译加速，不影响产物：
  ```powershell
  $env:IDF_CCACHE_ENABLE='0'; idf.py build
  ```
  （IDF 默认在 PATH 上探测到 ccache 就自动启用；置 `IDF_CCACHE_ENABLE=0` 关闭。）
- **经验**：
  - 看到 `CreateProcess failed ... cannot find the file specified` **先别急着查编译器路径**，
    看**报错行第一条命令是不是 `ccache`**——若是，直接 `IDF_CCACHE_ENABLE=0` 绕过，比深挖 ccache 快得多；
  - ccache 是可选加速层，出问题就关掉，**不要为了它阻塞功能闭环**；
  - 验证“某工具到底能不能跑”要用 `subprocess.run([exe, args])` 这种**不经 shell 的调用方式**，
    bash/cmd 的路径转义会把结论带偏。

## F16. PowerShell 5.1 读 UTF-8 无 BOM 且含中文注释的 .ps1：脚本静默失效

- **现象**：`tools/idf_env.local.ps1` 里明明写了
  `$env:QWEATHER_KEY = 'a7928...'`，但点源加载后 `$env:QWEATHER_KEY` 读出来是**空串**，
  且**不报任何错**。构建照常进行，只是密钥没注入。
- **根因**：Windows PowerShell 5.1 **在没有 BOM 时按系统 ANSI 代码页解码脚本**
  （中文系统 = GBK/936）。该文件是 UTF-8 无 BOM，于是：
  - 中文注释被按 GBK 逐字节误解码，产生大量乱码字符；
  - 更致命的是，**某些 UTF-8 多字节序列在 GBK 下会吃掉换行/引号**，
    导致后面的赋值语句被并进注释行里，**整行不执行**。
  - 用 `[Text.Encoding]::GetEncoding(936).GetString($bytes)` 解码即可复现乱码与串行现象。
- **解决**：把该文件（以及所有含中文的 `.ps1`）**保存为 UTF-8 with BOM**：
  ```powershell
  $utf8Bom = New-Object System.Text.UTF8Encoding($true)
  $text = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
  [System.IO.File]::WriteAllText($p, $text, $utf8Bom)   # 首 3 字节应为 EF BB BF
  ```
- **经验**：
  - **凡是要被 PowerShell 5.1 执行的 `.ps1`，含非 ASCII 字符就必须带 BOM**；
    只含 ASCII 的无所谓；
  - 排查“赋值不生效且无报错”时，先查 **BOM**：`$bytes[0..2]` 是不是 `EF BB BF`；
  - 项目里 `tools/*.ps1` 已统一为 UTF-8 BOM，**新增脚本请沿用**；
  - 同理注意源文件本身：`docs/_serial_capture.py` 等 Python 文件用 UTF-8 无 BOM 是正常的
    （Python 3 默认 UTF-8），不要一刀切。

## F17. 和风天气 API 返回 `403`（空 body）：公共域名已下线，须改用专属 API Host

  需改为 `<host>/geo/v2/city/lookup`（多了 `geo` 前缀）。
- **经验**：
  - **判据口诀**：`根路径通 + API 路径 403 + 去掉 key 仍 403` ⇒ **域名/服务下线，不是鉴权问题**，

  - 排查第三方 API 的 4xx，**先做"无凭证对照请求"**：如果去掉凭证得到同样的错误码，
    就说明问题在请求本身/服务端，与凭证无关。

## F18. CMake `$ENV{}` 只在 configure 求值一次：改了密钥/Host 却静默沿用旧值 ★最隐蔽

- **现象**：把 `tools/idf_env.local.ps1` 里的 `QWEATHER_API_HOST` 从
  `devapi.qweather.com` 改成专属 Host `ke67cgkc3a.re.qweatherapi.com` 后，
  重新 build + flash，设备串口**仍然**打印 `http status=403`；
  加诊断日志一看：
  ```
  NET_TIME: host=devapi.qweather.com     ← 固件里还是旧值！
  NET_TIME: body[3]=锟?                   ← 空 body
  ```
  但同一 URL、同一 Key 在 PC 上请求新 Host 是 **200**。
- **定位方法（推荐抄）**：**直接搜固件二进制里的字符串**，比猜快得多：
  ```powershell
  $bytes = [System.IO.File]::ReadAllBytes("build\display_audio_photo.bin")
  $ascii = [System.Text.Encoding]::ASCII.GetString($bytes)
  $ascii.IndexOf("ke67cgkc3a.re.qweatherapi.com")   # -1 = 没进去
  $ascii.IndexOf("devapi.qweather.com")             # >=0 = 旧值还在
  ```
  再搜 `build/build.ninja` 和 `build/compile_commands.json`，即可确认编译命令里的真实 `-D`：
  ```
  build.ninja:  QWEATHER_API_HOST=\"devapi.qweather.com\"   ← 铁证
  ```
- **根因**：**CMake 的 `$ENV{VAR}` 只在 configure（cmake 配置）阶段求值一次**。
  之后只跑 `idf.py build` 属于**增量构建**，ninja 直接复用已生成的
  `build.ninja`，**不会重新读环境变量**。所以：
  - `QWEATHER_KEY` 是首次注入就没变过 → 正常；
  - `QWEATHER_API_HOST` 改过值 → 一直是旧的。
  同理适用于任何"靠环境变量注入编译宏"的做法。
- **解决**（三层保险，项目已落地）：
  1. `tools/build.ps1` **默认先 `idf.py reconfigure`**（`-NoReconfigure` 可跳过），
     强制刷新 `$ENV{}` 的求值；
  2. `tools/build.ps1` 构建后**自动校验**：把 bin 当 ASCII 读，断言当前
     Key/Host 字符串确实在固件里，不在就报 `INJECTION STALE` 并以 exit=3 失败；
  3. 改动环境变量后若仍异常，`idf.py fullclean` 一次彻底重来（`build.ps1 -Clean`）。
- **经验**：
  - **"配置改了但没生效"** → 优先怀疑 **configure 缓存**，而不是设备或服务端；
  - 排查编译期宏，**看 `build.ninja` / `compile_commands.json` 里的真实命令行**，
    或直接搜固件字符串——这是**唯一可信的"实际生效值"**；
  - `idf.py build` ≠ reconfigure。凡是依赖 `$ENV{}` 的注入，
    改环境后**必须 reconfigure 或 fullclean**；
  - 本坑与 F16（BOM）叠加时极易误判：F16 让值读不出来，F18 让读出来的值用不上，
    两者**都会静默失败、都不报错**，务必用"搜固件字符串"这招一次排除。

## F19. 和风 API 强制返回 gzip，须自行解压（`cJSON_Parse failed` 的真凶）

- **现象**：换专属 Host 后 403 消失，但新报错变成
  `NET_TIME: cJSON_Parse failed` —— HTTP 已是 200，可 JSON 解析不了。
- **根因**：**和风 API 无视 `Accept-Encoding`，一律返回 gzip**。实测三种请求头结果完全一致：
  ```
  Accept-Encoding 缺省       -> 200  Content-Encoding='gzip'  bytes=693  first2=b'\x1f\x8b'
  Accept-Encoding='identity' -> 200  Content-Encoding='gzip'  bytes=693  first2=b'\x1f\x8b'
  Accept-Encoding='gzip'     -> 200  Content-Encoding='gzip'  bytes=693  first2=b'\x1f\x8b'
  ```
  `0x1f 0x8b` 即 gzip magic。而 `esp_http_client` **自身不带解压层**，
  压缩数据被原样塞给 cJSON → Parse 失败。
- **解决**：引入 zlib 组件做**流式 inflate**：
  ```powershell
  idf.py add-dependency "espressif/zlib^1.3.2~1"
  ```
  然后：
  1. `main/CMakeLists.txt` 的 `PRIV_REQUIRES` 加 `zlib`；
  2. `http_evt_cb` 里监听 `HTTP_EVENT_ON_HEADER` 取 `Content-Encoding`，
     是 gzip 就用 `inflateInit2(&zs, 15 + 32)`（**+32 = 自动识别 gzip/zlib 头**）；
  3. `HTTP_EVENT_ON_DATA` 里循环 `inflate(..., Z_NO_FLUSH)` 边收边解压，
     `HTTP_EVENT_ON_FINISH` / `ERROR` / `DISCONNECTED` 里 `inflateEnd` 收尾。
- **经验**：
  - **HTTP 200 不等于拿到明文**。`Content-Encoding` 必须检查；
  - 判据：body 前两字节是 `0x1f 0x8b` ⇒ gzip（`0x78 0x9c` 则是 zlib），
    此时**先解压再解析**；
  - 嵌入式端优先**流式解压**（收一段解一段），不要"先全存再解"，省一半缓冲；
  - `czlib`/`zlib` 在 IDF v6.1 **不是内置组件**（`components/` 下没有 zlib，
    只有 `esp_rom/include/miniz.h` 头文件却无独立编译单元 / ROM 符号不保证导出），
    因此**必须用组件管理器拉 `espressif/zlib`**；
  - 排查此类问题，**在解析失败分支也打印 body 前若干字节**，
    否则只会看到"parse failed"而无从下手（本轮正是加了这行诊断才定位到 gzip）。

## F20. 沙箱安全删除策略阻断 IDF 的批量删除 / 组件重建

- **现象 A**：`idf.py fullclean` 失败：
  ```
  [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
  {"count":261,"threshold":50,"targets":["...\build\bootloader"]}
  ```
- **现象 B**：`idf.py reconfigure` 失败——组件管理器重解析依赖时想重建
  `managed_components/lvgl__lvgl`：
  ```
  [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
  {"count":4811,"threshold":50,"targets":["...\managed_components\lvgl__lvgl"]}
  ```
  这是**运行沙箱**对批量删除的保护，与工程代码无关。
- **规避手法（实测有效）**：
  1. **避开 `fullclean`**：改删少量关键文件（`build/build.ninja` 等）或依赖 `reconfigure`；
  2. **要重建某组件时，先手动把它 `Move-Item` 改名**（如 `lvgl__lvgl` → `lvgl__lvgl.bak`），
     让管理器往**干净路径**解压，从而不触发"删除"；确认构建通过后再删备份；
  3. 状态被搞脏（如 `CMakeCache.txt` 留着但 `build.ninja` 没了，报
     `unable to find a build program corresponding to "Ninja"`）时，
     **整体 `Move-Item build build.bak` 重命名**，比逐文件删更干净、也不触发策略；
  4. 弄完记得把 `*.bak*` 目录清掉，别留在工作区。
- **⚠ 最毒的一种脏状态（F20-b 补充，2026-09-17 实测）**：
  把 `build/` 里**只挪走了 `CMakeCache.txt` 和 `build.ninja`**、剩下的
  `CMakeFiles/ log/ toolchain/` 还在时，`idf.py reconfigure` 会**直接失败**：
  ```
  CMake Error: CMake was unable to find a build program corresponding to "Ninja".
    CMAKE_MAKE_PROGRAM is not set.  You probably need to select a different build tool.
  -- Configuring incomplete, errors occurred!
  ```
  根因：`build/` 目录**存在但不完整**——CMake 认为它是个"已配置过的目录"，
  于是不会重新探测 Ninja 路径（`CMAKE_MAKE_PROGRAM`），却又读不到缓存里的记录，
  于是找不到 Ninja。**结论：要么彻底干净（目录不存在），要么完整——不能半吊子。**
  正确做法是把整个 `build/` 改名挪走（本次改为 `build.broken_HHmmss`），
  让 CMake 在**全新空目录**里从零 configure，Ninja 就能被正常探测到。
- **★ 关键判据：别被 "Ninja not found" 骗去修环境（2026-09-17 实测）**
  报错字面是"找不到 Ninja"，极容易让人去查 PATH / 装 Ninja，**但那通常是误诊**。
  判定方法——在**同一套 IDF 环境**里手动跑一次纯净 cmake：
  ```powershell
  . tools\idf_common.ps1; Initialize-BuildEnv
  & "C:\Espressif\tools\cmake\4.0.3\bin\cmake.exe" -G Ninja -S <空目录> -B <空目录>\b
  # 实测输出：-- GEN=Ninja MAKE=C:/Espressif/tools/ninja/1.12.1/ninja.exe  → exit=0
  ```
  - 若**能成功** ⇒ 环境完全正常（Ninja 就在 `C:\Espressif\tools\ninja\1.12.1\`，
    且 profile 已把它 prepend 进 PATH）。此时 `build/` 里那句
    `CMAKE_MAKE_PROGRAM is not set` 是**假象**，去修 PATH 纯属浪费时间。
    ⚠ **但真正病因往往不是脏目录，而是 F21（PS 5.1 的 stderr 陷阱）**——
    本次实测：目录已彻底清空，`idf.py` 依然报这个错，根因是 PS 5.1 把 cmake 的
    stderr 警告判成致命错误、把整条 `idf.py` 调用链掐断。
  - 若**也失败** ⇒ 才是真的环境问题，去查 `$env:PATH` / `IDF_TOOLS_PATH`。
  另一个辅助判据：脏目录的特征是 `build/` 里**有 `CMakeFiles/`（含 `cmake.check_cache`、
  `CMakeConfigureLog.yaml`）却没有 `CMakeCache.txt` / `build.ninja`**。
  ⚠ 注意：**每次失败的 reconfigure 都会重新生成这堆 `CMakeFiles/` 残骸**，
  所以"挪走一次"后若不彻底（残留 `CMakeFiles`），下一轮照样失败——
  必须确认 `Get-ChildItem -Directory | ? Name -like 'build*'` 返回**空**，才算真干净。
- **经验**：遇到 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`，**先判断"这是不是沙箱策略而非真错误"**，
  然后用"改名代替删除"绕过，不要一条道走到黑去反复重试同一条命令。

## F21. PS 5.1 把原生命令的 stderr 判成致命错误，掐断整条 idf.py 调用链 ★最终真凶

- **现象**：`idf.py reconfigure` / `build` 在 `tools/build.ps1` 里跑，稳定报：
  ```
  CMake Error: CMake was unable to find a build program corresponding to "Ninja".
    CMAKE_MAKE_PROGRAM is not set.
  -- Configuring incomplete, errors occurred!
  ```
  但**同一台机器、同一套 IDF 环境**里手动跑
  `cmake -G Ninja -S <空目录> -B b` 却能成功找到 `ninja.exe`。
- **排除过程（都证明"不是它"）**：
  | 怀疑对象 | 实测结果 |
  |---|---|
  | Ninja 没装 | `C:\Espressif\tools\ninja\1.12.1\ninja.exe` 在，`ninja --version` → `1.12.1` |
  | PATH 没配 | profile 第 136 行已把 ninja 目录 prepend 进 PATH，`Get-Command ninja` 解析成功 |
  | build/ 目录脏 | **彻底清空后依旧报同一个错** ⇒ 不是目录问题 |
  | ccache | 关掉后 `ccache program not found` 警告消失，**Ninja 错误照旧** ⇒ 不是它 |
- **真因**：PowerShell 5.1 在 **zh-CN(GBK/936) 控制台**下，把任何**原生命令往 stderr 写的
  字节**包装成 `NativeCommandError`。cmake 一定会往 stderr 写
  `CMake Deprecation Warning ...`；配合脚本里的 `$ErrorActionPreference = 'Stop'`，
  这个错误被当成**致命的**，于是：
  - 轻则**静默掐断脚本**（后面的 `Out-File` 落盘全不执行，看起来"跑了一半就没了"）；
  - 重则在 `idf.py` 内部调用链里中断 cmake，让它拿不到完整的生成器初始化，
    最终表现为**"找不到 Ninja"的假象**。
  报错信息里的 `System.Management.Automation.RemoteException`、
  `NativeCommandError`、以及混码乱码（如 `鎵€鍦ㄤ綅缃?`）都是这个病征。
- **验证方法**：把原生命令的 stderr 单独吞掉（`2>$null`）再跑，
  或在 **cmd / Git-Bash** 等没有 `NativeCommandError` 概念的通道里跑。
  实测 Python 启动器（`tools/_run_idf.py`）一跑就过 ⇒ 疾病在 PS 层，不在 IDF。
- **解法（三管齐下）**：
  1. **构建入口改用 Python 启动器** `tools/_run_idf.py`：
     自己组装 IDF 环境变量、直接 `subprocess.call(idf.py ...)`，
     完全绕开 PS 5.1 的 stderr 陷阱（推荐，最稳）；
  2. 若仍想用 PS 脚本：加载环境时临时降级 `$ErrorActionPreference`，
     并**不要**把原生命令接进管道（`| Out-Null` / `| Out-String` 都会放大问题）；
  3. 统一控制台为 UTF-8 并设 `PYTHONIOENCODING=utf-8`，减少乱码噪声。
- **Python 启动器里另踩的两个坑（一并记下）**：
  - **`MSYSTEM` 残留**：从 Bash 通道调用时环境里有 `MSYSTEM`，
    IDF 一见就打印 `MSys/Mingw is no longer supported` 然后**直接退出**（exit 0，静默不作事）。
    ⇒ 启动器里要把 `MSYSTEM/OSTYPE/SHELL/TERM/MINGW_PREFIX/...` 全部 `pop` 掉。
  - **`ESP_IDF_VERSION` 缺失**：不设这个变量，组件管理器会抛
    `TypeError: expected string or bytes-like object, got 'NoneType'`。
    ⇒ 启动器里显式设 `ESP_IDF_VERSION=6.1`、`IDF_VERSION=6.1.0`。
- **经验**：在 Windows + 中文系统上跑 IDF，**"cmake 找不到 Ninja / make"这类生成器报错，
  先怀疑 PowerShell 的 stderr 包装，而不是去重装工具链**。
  最省心的做法就是彻底不用 `.ps1` 调 idf.py，改用 Python 启动器。

## 闭环排障流程（务必遵守）

1. 改代码 → `idf.py build`（看 error 行，不只是最后几行）；
2. `idf.py -p COM9 flash`；
3. 板子自动复位，pyserial 抓 12s 日志；
4. 有 panic 用 `riscv32-esp-elf-addr2line` 解 PC 地址；
5. 修复后重新 build→flash→抓日志，**现象消失才算完成**；
6. 把故障现象/根因/解决追加到本文件对应章节。

## F18 和风天气 cJSON_Parse failed / overflow=1

- **现象**：API 返回 HTTP 200，gzip 解压 `gz=1 out_used=2047 overflow=1`，body 截断在 `"moonrise`，cJSON_Parse failed。
- **根因**：`NET_TIME_HTTP_BUF` 原 2048 字节太小，和风 7 天 JSON 解压后 ~2.5KB，写满后 inflate 再写就 overflow，最后那不是合法 JSON。
- **解决**：缓冲改 8192。
- **经验**：流式 gzip 解压缓冲大小要按"解压后 JSON 全量"预估，不是按压缩后大小；天气/7d 类多日数据至少 8KB。

## F19 JPEG 输入缓冲用 MALLOC_CAP_DMA 导致 no dma mem

- **现象**：`WP_OVERLAY: no dma mem for jpeg buf`，壁纸不显示。
- **根因**：JPEG **输入**缓冲（存压缩文件字节流）被标成 DMA-capable，占内部 SRAM；摄像头/LCD/粒子一起跑时内部 RAM 不够。
- **解决**：JPEG 输入缓冲改 SPIRAM；只有**输出**缓冲（解码器 DMA 写屏）才需要 DMA。
- **经验**：判断要不要 DMA 看"谁访问这块内存"。CPU 读文件 → SPIRAM/普通堆；DMA 外设搬数据 → MALLOC_CAP_DMA。

## F20 视频播放闪屏撕裂 + 播完黑屏（LCD framebuffer 与 LVGL direct mode 冲突）

- **现象**：MJPEG 视频能出画面，但播放中画面闪屏撕裂；播完屏幕黑屏，LVGL 界面不恢复。
- **根因**：
  1. 本板 LVGL 配置 `CONFIG_BSP_DISPLAY_LVGL_DIRECT_MODE=y` + `AVOID_TEAR=y`，双 framebuffer，
     LVGL 的 draw buffer 直接就是 RGB panel 的两块 framebuffer，由 vsync 回调轮换显示。
  2. 视频 LCD backend 也通过 `esp_lcd_rgb_panel_get_frame_buffer` 拿到同一对 buffer，
     每帧 `esp_lcd_panel_draw_bitmap` 切换扫描的 buffer。播放时 LVGL 没停，二者同时切换同一对 buffer → 撕裂。
  3. 播完后 panel 当前扫描的 buffer 索引与 LVGL 内部记录错位，LVGL 认为画面无脏区不重绘 → 黑屏。
- **修复**：
  - 播放前 `lvgl_port_stop()` 真正停 LVGL 定时器（不能用 `bsp_display_lock` 互斥锁，
    因为播放点击回调本就跑在 LVGL 线程，锁不住自己）。
  - 注册 `esp_player_set_event_cb`，FINISHED/ERROR 时 `lvgl_port_lock` + `lv_async_call` 排队
    `lv_obj_invalidate(lv_screen_active())`，再 `lvgl_port_resume()` + `task_wake`，整屏重绘恢复 UI。
- **经验**：RGB LCD direct mode 下，任何"绕过 LVGL 直写 framebuffer"的播放/截图，
  都必须在播放前停 LVGL、播放后整屏 invalidate；跨线程回调不能直接画 LVGL，走 `lv_async_call`。

## F21 视频 PPA 缩放 Failed to blend ret -2 / 改 RGB888 屏幕纯色乱闪

- **现象**：视频 400x240 直接播，画面停在左上角不全屏，日志 `VIDEO_RENDER: Failed to blend ret -2`；
  改 `in_color_format=RGB888` + out_format=RGB888 后屏幕变纯色乱闪、无画面。
- **根因**：
  1. 本板 LCD 物理是 RGB565（`bsp_display.c` `LCD_COLOR_FMT_RGB565`），不支持 RGB888，改了就花屏。
  2. GMF 的 PPA 对非目标分辨率做缩放时 blend 失败。
- **修复**：out_format 固定 RGB565；视频 PC 端 ffmpeg 直接转成 800x480，设备端 PPA 只做 RGB888→RGB565 格式转换，不做缩放。
- **经验**：先确认 LCD 物理像素格式（看 bsp_display.c 的 in_color_format），别想当然；
  分辨率不匹配优先在 PC 端转码，不要赌设备端 PPA 缩放能力。

## F22. 首次调用 `esp_audio_enc_register_default()` 导致固件暴涨 558KB / OTA 分区溢出 ★隐蔽

- **现象**：接入蓝牙 A2DP Source 推流（引入 `gmf_audio`/`gmf_io`）后，`idf.py build` 编译与链接全部成功，
  但最后一步 `app_check_size` 失败：
  ```
  Error: All app partitions are too small for binary display_audio_photo.bin size 0x5401c0:
    - Part 'ota_0' @ 0x20000 size 0x500000 (overflow 0x401c0)
  ```
  固件从 4.71MB 涨到 **5.25MB**，超出 ota_0（5MB）**256KB**。
- **定位方法（推荐抄）**：**对比新旧两个 bin 的字符串集合**，直接看新增了什么：
  ```python
  old = set(re.findall(rb'[ -~]{8,}', open('build/display_audio_photo_flashed.bin','rb').read()))
  new = set(re.findall(rb'[ -~]{8,}', open('build/display_audio_photo.bin','rb').read()))
  # 新增字符串里出现大量编解码器符号
  ```
  一眼看到：
  ```
  AAC MP3 FLAC AMR AMRWB WAV M4A ATS OGG esp_gmf_audio_enc_open
  @esp_aac_enc_set_bitrate   @esp_amrnb_enc_set_bitrate   @esp_opus_enc_set_bitrate
  @esp_lc3_enc_get_frame_info  @esp_adpcm_enc_get_frame_info  @esp_g711_enc_...
  ```
- **根因**：新代码首次调用了 **`esp_audio_enc_register_default()`**（以及 `esp_audio_dec_register_default()`）。
  这两个函数是乐鑫的**"全家桶注册"**——把所有编解码器实现全部注册进来：
  编码器侧 11 个（AAC/G711/AMRNB/AMRWB/OPUS/ADPCM/ALAC/PCM/SBC/LC3/G722），解码器侧 13 个。
  - 在此之前工程**从未调用过**这个注册函数，所以链接器把所有编码器的 `.o` 当作无引用而 GC 掉 → 固件 4.71MB；
  - 一旦代码里出现对这个函数的一行调用，链接器立刻把**全部**编码器链进固件 → 5.25MB。
  - 而 A2DP Source 推流（MP3 解码 → SBC 编码）**只需要 SBC 一种编码器**。
  - 同时 `esp_hal_asrc`（S31 硬件重采样 HAL）也被首次引入（~100KB），但那是推流刚需，不能裁。
  - **我的业务代码 `bt_push_service.c` + `tab_btpush.c` 实际只占约 10KB**，其余 548KB 全是"被注册函数拖着进场"的编解码器。
- **解决**：官方在该头文件里就写明了做法（"This API behavior can be configured by `menuconfig`"）——
  在 `sdkconfig` 里**关闭不需要的编码器**，保留实际用到的：
  ```ini
  CONFIG_AUDIO_ENCODER_SBC_SUPPORT=y      # A2DP 强制编码，必须留
  CONFIG_AUDIO_ENCODER_PCM_SUPPORT=y      # 中间格式，建议留
  # 以下全部置为 "# ... is not set"
  # AAC / G711 / AMRNB / AMRWB / OPUS / ADPCM / ALAC / LC3 / G722
  ```
  `esp_audio_enc_register_default()` 会**自动跳过未启用**的编码器，**源码一行都不用改**。
  预计回收 ~320KB，固件回到 5MB 以内，**无需改分区表**。
  备份：`sdkconfig.bak_before_enc_trim`。
- **经验**：
  - **"加了点代码固件却暴涨几百 KB" → 先怀疑 barrel / register_default 这类全家桶注册函数**，
    它们会把一堆"本来被 GC 掉"的实现一次性拉进来；
  - 定位利器是**对比新旧 bin 的字符串集合**，比看 `.obj`（带调试符号，虚高）或用 `size` 工具都快、都准；
  - **嵌入式里"体积"和"代码是否被引用"强相关**：一行 `register_default()` 的代价可能是几百 KB。
    原则：**只注册用得到的编解码器**；
  - 遇到分区装不下，**优先裁配置（可逆、零风险），最后才动分区表**（改分区会动 flash 布局、影响 OTA 回滚）；
  - 乐鑫组件的 `*_register_default()` 一律去查它的 Kconfig 开关，别直接全量引入。

## F23. A2DP 推流首播即 I/O error，真凶是 SDMMC 的 DMA bounce buffer 分配失败 ★易误判

- **现象**：耳机连接成功、管线也起来了，一点播放立刻报错，**看起来像蓝牙问题，实际与蓝牙无关**：
  ```
  I BT_PUSH: set uri: file:///sdcard/music/xxx.mp3
  I BT_SVC : stream 0x502a9e74 state=1
  I BT_PUSH: pipeline run
  I ESP_GMF_FILE: Open, dir:1, uri:file:///sdcard/music/xxx.mp3
  I ESP_GMF_FILE: File size: 9406443 byte, file position: 0
  I ESP_GMF_TASK: One times job is complete, del[... aud_dec_open]     ← 解码器 open 成功
  I ESP_GMF_PORT: ACQ IN, new self payload:0x504f85e0, port:..., el:...-aud_dec
  E sdmmc_cmd: allocate_dma_buf: not enough mem, err=0x101               ← ★真凶在这
  E diskio_sdmmc: sdmmc_read_blocks failed (0x101)
  E ESP_GMF_FILE: The error is happened in reading data, error msg: I/O error
  E ESP_GMF_ASMP_DEC: esp_gmf_audio_dec_process(407): Failed to acquire in, ret: -1
  E ESP_GMF_TASK: Job failed[... aud_dec_proc], ret:-1, st:ESP_GMF_EVENT_STATE_RUNNING
  E BT_PUSH: pipeline error
  ```
- **定位方法（推荐抄）**：
  - 错误栈从下往上读：报错源头是 **`sdmmc_cmd`** 那一行，不是 `ESP_GMF_*`、更不是 `BT_*`。
    凡 `ESP_GMF_FILE` 说 "I/O error"，**先去搜它上面紧邻的那条 `E` 级日志**，那才是根因。
  - 打开 IDF 里的 `components/sdmmc/sdmmc_cmd.c` 看 `allocate_dma_buf()`：
    ```c
    static esp_err_t allocate_dma_buf(size_t* actual_size, size_t block_size, void **buf) {
        do {
            if (*actual_size < block_size) {          // ← 撞的就是这一条
                ESP_LOGE(TAG, "%s: not enough mem, err=0x%x", __func__, ESP_ERR_NO_MEM);
                return ESP_ERR_NO_MEM;
            }
            *buf = heap_caps_malloc(*actual_size, MALLOC_CAP_DMA);
            if (!*buf) { *actual_size /= 2; }         // 拿不到就减半重试
        } while (!*buf);
    }
    ```
    **关键推论**：正常失败会一路减半重试；能打出 "not enough mem" 说明
    **减到不足一个 512B 扇区都没成功** → 内部 DMA 堆已经碎到连 512 字节连续块都没有了。
- **根因**：`esp_gmf_io_file` 从 SD 卡读数据时，它交给驱动的 payload 缓冲区**不是 DMA 对齐**的，
  于是 SDMMC 驱动必须**现场** `heap_caps_malloc(..., MALLOC_CAP_DMA)` 申请一块内部 DMA bounce buffer。
  而 `SDMMC_HOST_DEFAULT()` 里 `dma_aligned_buffer = NULL`，**每次读盘都要现场申请**。
  我们的场景里内部 RAM 已被 bluedroid 静态池 + LCD 帧缓冲 + WiFi + 音频解码器工作缓冲切得很碎，
  这次推流管线又在开机时把 `aud_dec/aud_asrc/aud_enc` 一次性建常驻，内部 DMA 池被彻底榨干 → 复现。
  - **为什么以前 SD 卡放视频/图片没炸**：那些走 VFS 直接读进大 buffer，不一定触发不对齐的 bounce 路径；
    GMF 的 `io_file` payload 管理则必然触发。
- **解决**：**给 SDMMC 主机预分配一块常驻 DMA 缓冲**，驱动直接复用，永不现场分配。
  这是 **IDF 官方 sdmmc 测试的做法**（见 `components/esp_driver_sdmmc/test_apps/sd_test_utils/.../sdmmc_test_rw_common.c`
  的 "Test D: dma_aligned_buffer reuse path"）：
  ```c
  sdmmc_host_t host = SDMMC_HOST_DEFAULT();
  s_dma_bounce = heap_caps_malloc(32 * 1024,
                                  MALLOC_CAP_SPIRAM | MALLOC_CAP_DMA | MALLOC_CAP_8BIT);
  if (!s_dma_bounce) s_dma_bounce = heap_caps_malloc(32 * 1024, MALLOC_CAP_DMA);  // 退回内部
  host.dma_aligned_buffer = s_dma_bounce;   // ★ 驱动只要看到非 NULL 就一定走复用分支
  ```
  已落在 `main/middleware/system/sdcard_service.c` 的 `sdcard_setup_dma_buffer()`，在 `sdcard_service_mount()` 里调用。
  - **本板 `CONFIG_SOC_SDMMC_PSRAM_DMA_CAPABLE=y`，PSRAM 可被 SDMMC DMA 直访**，
    所以这块缓冲放 PSRAM，**一个字节内部 RAM 都不占**。
  - `esp_vfs_fat_sdmmc_mount()` 会把 `host_config` 原样透传给 `sdmmc_card_init()`，
    中途不复制不清空 → `dma_aligned_buffer` 能完整带到 card 里，运行时生效。
- **经验**：
  - **主动推内因**：`ESP_GMF_FILE: ... I/O error` → 先看它上一行的 `E` 日志，别顺着 GMF 往上猜；
  - **`err=0x101` 就是 `ESP_ERR_NO_MEM`**，SDMMC 场景下八成是**内部 DMA 堆碎片化**，不是卡坏也不是线没插好；
  - **凡是"驱动内部现场申请 DMA 缓冲"的路径，都能用预分配常驻缓冲的手法消掉**；
    配 `host.dma_aligned_buffer` 是 SDMMC 的标准做法；
  - **`SOC_SDMMC_PSRAM_DMA_CAPABLE` 这类"外存/DMA 直访"能力要主动用**：
    能放 PSRAM 的 DMA 缓冲就别占内部 RAM，内部 RAM 是稀缺资源；
  - **看到一个功能崩了先分辨"它的输入从哪来"**：本例蓝牙链路完全正常（stream STARTED、管线 run 都成功），
    崩的是**读盘**——被 `BT_PUSH`/`ESP_GMF_*` 这些显眼 TAG 带偏的话，很容易去查错方向。

## F24. 板载音量键调不动蓝牙耳机音量 / AVRCP 绝对音量"无法感知失败" ★认知陷阱

- **现象**：A2DP 推流正常、耳机正常出声，但按设备端 vol+/vol- 键，**屏幕音量条会动，耳机音量纹丝不动**。
- **根因（很简单，但容易查错方向）**：`button_service.c` 的 `adjust_volume()` 只改本地 `s_volume`
  并发消息给 UI 显示，**从头到尾没有调用过任何蓝牙音量 API**。UI 音量条（`tab_sys_entry.c`）
  也一样只写本地 codec。**两条路都到不了蓝牙**——数据压根没出门。
- **架构修正——一个"音量源"，多个"音量出口"**：
  硬件键和 UI 滑块必须走**同一个入口**，由上层按"连接状态"决定出口：
  ```
  vol+/vol- 硬件键 ─┐
                    ├─> set_volume(v) ─┬─> s_volume + UI 条（永远同步）
  UI 音量条 ────────┘                   └─> 输出回调 ─┬─ 蓝牙已连 → AVRCP 推给耳机
                                                      └─ 未连     → 本地 ES8389 codec
  ```
  实现：`button_service` 新增 `btn_vol_out_cb_t` 回调（**中间件不反向依赖蓝牙**，
  由 `main.c` 注册回调决定往哪送）。
  **顺带修掉一个隐藏 bug**：`tab_sys_entry.c` 原先在调 `button_service_set_volume()` 之外
  **又单独发了一次本地 codec 命令**；统一出口后若不删掉，蓝牙模式下会被"误调本地音量"。
- **★真正的认知陷阱——AVRCP 绝对音量无法自动降级**：
  直觉上会写"先用绝对音量，失败就降级到相对"，但**这条路不成立**。
  看 esp_bt_audio 源码 `src/classic/profiles/bt_audio_avrcp_ct.c:573-601`：
  ```c
  if (rc->conn_stat.connected) {
      vol_ops.set_absolute = avrcp_ct_set_absolute_volume;
      vol_ops.set_relative = avrcp_ct_set_relative_volume;
  } else {
      vol_ops.set_absolute = NULL;
      vol_ops.set_relative = NULL;
  }
  ```
  **`set_absolute` 只要 AVRCP CT 连上就被注册**，条件仅仅是"连接状态"，
  **与耳机是否支持 Absolute Volume 无关** → 命令发出去协议层就返回 `ESP_OK`，
  **耳机听不听、执不执行，我们完全感知不到**。
  → 所以"失败自动降级"是**假象**，不要写这种代码。
- **解决**：默认用**绝对音量**（A2DP 1.3+ 耳机普遍支持，且屏幕档位与耳机音量严格一致，
  不存在错位）；提供运行时开关 `bt_audio_service_set_abs_volume(false)` 切相对模式，
  给个别不响应绝对音量命令的老耳机兜底。
  - 量纲换算：本地 `s_volume` **0..90** → AVRCP **0..127**，用四舍五入，两端档位一一对应。
  - 连接后起一次性 `sync_vol_task`（延时 800ms 等 AVRCP 协商就绪），
    把当前本地档位同步给耳机，避免"屏幕显示 70、耳机实际是别的值"。
- **经验**：
  - **"改了这个值但另一个设备没反应" → 先确认"这个值到底有没有送出去"**，
    本例是纯粹的"没接线"，不是协议问题；
  - **一个用户概念（音量）对应多个物理出口（本地 codec / 蓝牙 AVRCP）时，
    必须收口成单一入口 + 按上下文分发**，否则必然出现"某个入口漏接线"的分裂；
  - **中间件不要反向依赖业务组件**：用**回调**把"往哪送"的决策上抛给 `main.c`；
  - **协议层返回 OK ≠ 对端执行了**：蓝牙 AVRCP 这类"命令下发即成功"的设计很常见，
    别把 `ESP_OK` 当成"对端已生效"。

## F25. 目录分层后编译全炸 / 裸文件名 include 的隐形依赖 ★重构陷阱

- **背景**：`ui/`（34 文件）与 `middleware/`（24 文件）长期平铺，按方案 A 分领域拆子目录。
- **现象**：目录拆完、`CMakeLists.txt` SRCS 路径全改完，`idf.py build` 报大量
  `fatal error: tab_call.h: No such file or directory`。
- **根因**：**代码里存在大量"裸文件名 include"，它们靠 C 预处理器的一个隐含规则活着——**
  **`#include "xxx.h"` 会先在"源文件所在目录"里找。**

  拆目录前，`ui/` 下所有文件同层，`ui/page_main.c` 里写 `#include "tab_call.h"`
  能直接命中同目录的 `ui/tab_call.h`。拆目录后 `page_main.c` 搬到 `ui/pages/`，
  同一个 include 就去 `ui/pages/` 找 `tab_call.h`，而它其实在 `ui/tabs/` → 找不到。

  **危险之处在于：这类代码在没有拆目录之前是完全正确、能编过的**，
  所以它不是"历史遗留脏代码"，而是"依赖了隐含前提的合法代码"。
  重构时如果不专门排查，就会集中爆雷。

- **本次规模**：全项目共 **49 处**跨目录裸 include、涉及 **24 个文件**，
  其中 `ui_theme.h` 14 处、`ui_common.h` 10 处、`page_manager.h` 9 处。
- **解决**：全部改写为从 `main/` 根开始的完整路径：

  ```c
  // 改前（拆目录后失效）
  #include "tab_call.h"
  #include "ui_theme.h"

  // 改后
  #include "ui/tabs/tab_call.h"
  #include "ui/common/ui_theme.h"
  ```

### 重构时的系统性排查方法

不要靠编译器一次次报错来"试出"漏网之鱼——一次编一次改会很慢。**用脚本静态扫描**：

1. 遍历 `main/` 下所有 `.c/.h`，正则抓出全部 `#include "..."`；
2. 先建一张"文件名 → 新路径"的表；
3. **检查重名**：如果同一个文件名在多个目录存在，按名映射会错，必须先解决重名；
   （本次运气好，`main/` 树内无重名文件，映射才安全）
4. 对每个 include，模拟编译器的搜索顺序判断能否命中：
   - 源文件所在目录；
   - `INCLUDE_DIRS` 列出的每个目录；
   - 都命中不了 → 就是需要改写的目标。

  本次扫描输出 **376 行 include**，其中真正需要改的是 49 处裸 include + 41 处
  `middleware/xxx.h` 旧路径，其余（`bsp/esp-bsp.h`、`freertos/*.h` 等组件头）不受影响。

- **经验**：
  - **`#include "x.h"` 是"相对源文件目录 + 搜索路径"双查找**，不是"相对项目根"。
    只要项目里出现了裸文件名 include，目录结构就和代码产生了**隐式耦合**；
  - **重构目录前，先扫 include，别先改 CMake**。SRCS 改错只是"文件没编进去"，
    include 改错是"整个编译炸掉"；
  - **重构后必须做全量 include 可解析性校验**，不能只看编译是否通过——
    编译通过只覆盖"被引用到的那些"，静态扫描能覆盖"全部 376 行"；
  - **规范的补丁**：`03_文件组织管理.md` 增加"禁止裸文件名 include"条目，
    把这条隐含规则变成显式约定，避免未来重新积累出同样的债。

## F26. ICD 文档与设备端/PC 端三方漂移：没有机制保证的"唯一契约" ★流程坑

- **背景**：`通信接口规范_ICD.md` 声明自己是"设备端（C）与 PC 端（Python）必须共同遵守的
  **唯一通信契约**；任何改动先改本文件再改代码"。
- **现象**：2026-09-21 梳理音频链路时对照三端，发现同一组参数**已经各说各话**：

  | 参数 | 代码实际（C / Python） | ICD 原描述 |
  |---|---|---|
  | 重排窗口 | **32 槽**（`udp_voice.c` `REORDER_SLOTS`） | "16 帧重排窗口" |
  | 缺帧补齐 | **60ms**（`rx_task` 里 `>= 60000`） | "超过 **40ms** 未到 → 补静音" |
  | 心跳周期 | **200ms**（`net/link.py` `>= 0.2`） | "PC 每 **1s** 发" |
  | 离线判定 | **5s**（两端均是） | "**2s** 未收到 → OFFLINE" |

  四处都不是 bug，**代码跑得通**，但文档与代码的"唯一契约"关系已经失效。
- **根因**：契约靠**人工纪律**维护，没有**机制**校验。三端常量分别写在
  `audio_service.h` / `udp_voice.c` / `record_service.c` / ICD 文档 / `pc_host/protocol.py`
  共五处，改一处不改其余四处，编译器和测试都不会报错。
- **为什么会漂移**：调试网络抖动时直接改代码里的常数最快（改 ICD 再改代码"流程太重"），
  改完能跑就忘了回填文档。这不是态度问题，是**反馈闭环缺失**。
- **对表时额外发现的两处「双端不对称」**（此前无人察觉）：
  1. **重排缓冲结构不同**：设备端**定长 32 槽环形数组** `slots[32]`（`seq % 32` 寻址，
     乱序超 32 帧会覆盖未播帧）；PC 端**无界字典** `slots: dict[int, bytes]`（不覆盖，
     但长会话下内存无上限）。当前场景（设备是接收方）不受影响，
     但若改为双端都做重排，必须重新评估；
  2. **缺帧处理不同**：设备端**补静音**（保时间轴，`lost` 计数）；
     PC 端**直接跳过**（`miss` 计数，不补）。
     导致 **PC 侧回放时长会短于实际录制时长**，设备侧不会。
  3. 顺带发现两端**重同步阈值也不同**：设备端 `> 0x4000` 判重启，PC 端 `> 0x7FFF`。
  > 这三处不是"文档写错"，而是**代码本身就是两端不同实现**——
  > 只对照文档与"某一端"的代码，永远查不出来。必须**三方对表**。
- **解决**（V1.2 已完成，2026-09-21）：
  1. **确定原则**：用户决策「**以代码为准，代码跑过没问题**」。
     ICD 描述**已实现的现状**，代码是唯一事实来源；不一致时回填文档；
  2. **回填内容**：§1 增加"控制类常量"表（8 项）；§3.2 改写为
     「公共语义 + 双端实现参数对照 + 已实现不对称」三段结构；
     §4.3 补设备端状态机与跃变通知语义；修正四处失实数値 + 列出三处不对称；
     §6 变更记录写清楚改了哪些、为什么；
  3. **仍未做（方案见 `12_音频链路架构.md` §6）**：
     - **常量收口**：C 侧收敛到 `voice_protocol.h`，PC 侧 `protocol.py`，
       ICD 只描述**语义**不重复数值（避免第三份副本）；
     - **契约测试**：`pc_host/tests/` 扩成"对拍测试"，同一组 seq/payload 双端结果必须一致；
     - **纯函数化**：协议编解码从 IO 拆出（`12_音频链路架构.md` §5 建议 C），
       拆成纯函数才能上 PC 端单测。
- **经验**：
  - **凡是"文档声明自己是唯一契约"的地方，都必须有一台机器在执行校验**，
    否则它迟早变成一份过期的注释；
  - **同一常量出现在 5 个地方 = 一定会漂移**，收敛副本数量比加强纪律有效；
  - **跨语言契约（C ↔ Python）没有编译器兜底**，只能靠测试向量表；
  - **对表必须是"三方对表"**：文档 × C 代码 × Python 代码。
    本次三处不对称全靠三方对表才暴露，只读文档或只读一端都发现不了；
  - **"以代码为准"是正确决策，但要有边界**：只有当代码是"跑过且验证过行为正确"时才成立。
    本次用户明确"代码跑过没问题"才落这一刀。若代码未验证，
    正确做法是**先验证行为再回填**，而不是默认代码对。

## F27. 编译报 `'s_abs_vol_ok' undeclared`：重构残留的"僵尸变量"与"孤儿函数" ★重构陷阱

- **背景**：蓝牙音量链路（§19.7）经历了一轮"绝对音量 → 不做自动降级"的方案修改，
  以及 `ui/`+`middleware/` 目录分层重构（§20）。
- **现象**：`idf.py build` 报
  ```
  bt_audio_service.c:159:13: error: 's_abs_vol_ok' undeclared (first use in this function)
  bt_audio_service.c:115:17: warning: 'active_role_bit' defined but not used
  ```
- **根因**：**方案改了，代码只删了一半**。
  1. `s_abs_vol_ok` —— 旧设计里"协商绝对音量是否成功"的状态变量。
     但 F24 已论证"**协议层无法感知耳机是否支持 Absolute Volume**"，
     "失败自动降级"是假象，于是**读取方（协商/降级逻辑）被删掉了，
     断开分支里那句 `s_abs_vol_ok = true;` 的写入却漏删**。
     变成"只写不读、且连声明都没了"的僵尸语句。
  2. `active_role_bit()` —— 旧设计里"按 `s_role` 返回 Source/Sink 角色位"的完整版函数。
     实际启用的是裁剪版 `classic_roles()`（只返 Source，因为同时注册 SRC+SNK 会让
     `esp_a2d_sink_init` 返回 `INVALID_STATE`，见 line 107-108 注释）。
     **调用点从旧函数切到新函数时，旧函数本体忘了删**，成了孤儿。
- **★ 关键判断：这不是"漏写声明"，而是"应当整条删掉"**。
  最省事的修法是补一句 `static bool s_abs_vol_ok = true;` 让它编译过 —— **这是错的**：
  - 其结果是一个**恒为 `true`、永不被读**的变量，纯噪声；
  - 更糟的是它在**断开分支**里，会让后来者误以为"重连时要重新协商绝对音量能力"，
    而这正是 F24 明确否决的设计 —— **错误注释比没有注释更害人**；
  - 同理，`active_role_bit()` 加 `(void)active_role_bit;` 抑制警告也只是骗编译器，
    函数会长期躺在文件里，且**无人知道它与 `classic_roles()` 是否已经漂移**。
- **解决**（2026-09-21）：
  1. 删除 `s_abs_vol_ok = true;`，并把那段误导注释改写为准确语义
     （"断开只重置下发基准 `s_last_sent_vol`；**不重置模式开关 `s_use_abs_vol`**，
     因为它是对端能力的选择结果"）；
  2. 删除整个 `active_role_bit()` 函数定义；
  3. **零语义变化**：删掉的是一个"从未被读的写"和一个"从未被调的函数"，
     运行期行为与改动前完全一致；`.h` 与 `main.c` 无需同步改。
- **经验**：
  - **方案变更时，"删旧"和"加新"要成对做**。只加新不删旧，就会留下
    僵尸变量、孤儿函数、失效注释 —— 它们**编译器不报错**（或只报 warning），
    却在下次改代码时持续误导；
  - **`undeclared` 错误先问"这行该不该存在"，而不是"补哪个声明"**。
    见过太多"补一句声明让编译过"，结果把死代码永久固化；
  - **warning 清零时区分"抑制"和"删除"**：`(void)func;`、`#pragma` 只掩盖症状；
    确认无用就删，确认有用就该有调用点。**留着不调用的实现 = 未来的认知负债**；
  - **重构后回扫三类残留**：① 只写不读的变量；② 无调用点的 static 函数；
    ③ 与当前方案相矛盾的注释。**这三类都不会让编译失败，但都会让下一个人踩坑**；
  - 排查手法：**全工程 `Grep` 变量名/函数名**，看"写入/定义"与"读取/调用"是否配平。
    本次两处都是靠这个手法一次确认的（写入 1 处 / 读取 0 处；
    定义 1 处 / 调用 0 处）。

## F28. 开蓝牙即崩溃重启：`future_ready` assert / 内部 RAM 不足但**没有护栏** ★内存坑

> **★ 重要补充（同日追问后核实）**：本坑**不是**"忘了做早期预分配"——
> controller/HCI 内存池**早就已经开机常驻了**（`bt_audio_service_controller_init()`）。
> 真正的原因是 **bluedroid host 在架构上无法常驻**，详见文末"为什么 host 不能常驻"。

- **现象**：主界面点蓝牙开关打开，立即崩溃重启：
  ```
  E BT_BTC: btc_config_init unable to create lock.
  E BT_OSI: future_new unable to allocate memory for the semaphore.
  assert failed: future_ready future.c:64 (future != NULL)
  ```
  复位原因 `rst:0xc (SW_CPU_RESET)` —— 是自身 abort 触发的软复位。
- **根因**：**内部 RAM 不够，但 host 初始化的失败路径没有护栏，直接 assert。**
  - `esp_bt_audio_init()` 内部要建 bluedroid host：BTU/BTC 任务栈 + **大量**小队列/信号量
    /`future` 对象，全部落在**内部 RAM**（具体字节数**未从源码核实**，勿当事实引用）；
  - 这些分配一旦失败，bluedroid 不会返回错误，而是在 `future_ready()` /
    `btc_config_init()` 里 `assert` → abort → 重启；
  - 此时机（开机 73s，UI + WiFi + GMF pipeline + LVGL 都在跑）内部 RAM 已被切得很碎，
    正是 **F23 / §19.6 那类"晚分配踩碎布局"** 的翻版。
- **旧代码的两处缺陷**（本次一并修）：
  1. `bt_audio_service_set_power()` **没有内存门槛**，无论多紧都硬着头皮调
     `esp_bt_audio_init()`，把"能不能开"的决定权交给了一个失败就 assert 的库；
  2. `page_bluetooth.c` 的 `bt_sw_cb()` **丢掉了返回值**：
     ```c
     bt_audio_service_set_power(on);   /* ← 返回值被丢弃 */
     ```
     即使将来能优雅失败，UI 也会显示"已开"，用户一直等扫描结果。
- **解决**：
  1. **开之前先体检**（`bt_audio_service.c` 新增 `host_mem_sufficient()`）：
     检查内部 RAM 的 `free_size` 与 `largest_free_block` 双指标，
     任一不够就 `return ESP_ERR_NO_MEM`，**主动拒绝打开**并打日志给出处置建议。
     门槛用 `BT_HOST_MIN_FREE_INTERNAL (48KB)` / `BT_HOST_MIN_LARGEST_BLOCK (24KB)`，
     经验值、可按实测调。诊断口径同 `14_堆管理宝贵经验.md` §1.6.5
     （free 小+largest 小=真不够；free 大+largest 小=碎片化，两者都拦）；
  2. **UI 正确处理失败**：打开失败时把开关**弹回 OFF** + 状态栏提示
     `Not enough RAM` / `Power on failed`，不再假装成功；
  3. **体检必须放在 `esp_bt_audio_init()` 之前** —— 进去之后再失败就没有优雅退出路径了。
- **经验**：
  - **判据：如果"调用某个库函数失败"会 assert / abort，就不能无脑调用。**
    必须先自查前置条件（这里是内存），不满足就自己返回错误码。
    **功能不可用 > 整机重启** —— 重启会让用户以为设备坏了，而且掩盖真实原因；
  - **`assert` 是"不可能发生"的声明，不是错误处理手段**。第三方库内部这么用很常见
    （本例 bluedroid），调用方要按"它可能 assert"来设计，而不是按"它会返回 ESP_FAIL"；
  - **错误返回值不能丢**。`f(x);` vs `if (f(x) != ESP_OK)`：前者的 UI 会在失败时骗人。
    凡是"用户可见的开关"类操作，返回值必须影响 UI 呈现；
  - **内存门槛要用"双指标"**：只看 `free_size` 会漏掉碎片化，
    只看 `largest` 会漏掉"总量本来就不够"。两个都看才准；
  - 这类坑的本质与 F23 一致：**大块/多次分配不要等到"功能已经跑起来"才做**。
    能前置就前置（如 controller 的 early init），不能前置就必须有门槛兜底。

### ★ 为什么 host 不能像 controller 一样开机常驻

这是本坑最容易误解的地方 —— 直觉会想"controller 都常驻了，host 也常驻不就行了？"

**答：controller 已经常驻了，但 host 在架构上常驻不了。**

| 层 | 能否开机常驻 | 依据（已读源码核实） |
|---|---|---|
| **controller / HCI 内存池** | ✅ **已常驻** | `bt_audio_service_controller_init()` 在开机空窗期 `esp_bt_controller_init/enable` 并一直不 deinit。这才是真正的"一次性分配" |
| **bluedroid host（BTU/BTC）** | ❌ **不能** | `esp_bt_audio_deinit()` → `bt_audio_host_bluedroid_stack_deinit()` → `esp_bluedroid_disable()` + `esp_bluedroid_deinit()` → `btc_deinit()` → `btc_deinit_bluetooth()`：内含 `vSemaphoreDelete(s_init_done_sem)`、`bte_main_shutdown()`、`osa_alarm_deinit()` —— **真的全部释放**。所以下次 ON 是**真正的重新 init**，照样可能崩 |
| **BTA / A2DP / AVRC** | ❌ **不能** | 属 `host_config`（host 层），必须在 controller 之后初始化，无法提到开机预初始化 |

**推论（重要）**：现有的"蓝牙开关"是**伪开关** —— OFF 时底层没有任何 host 资源被保留，
它只是让下次 ON 重新走一遍完整的、可能失败的重分配。所以：

- **内存闸门必须每次打开都走**，不能只在开机检查一次；
- 想要"开关"名副其实，只有两条路：
  1. **真常驻**：开机把 host 一次性起好、**永不关闭**，UI 开关只切软件状态
     （如 `esp_bt_gap_set_scan_mode` 控可被搜索/可连接）。代价是内部 RAM 长期被 host 占用，
     且 UI 开关语义要重新设计。**这与本工程"方案 B：GMF 建一次不毁"的思路完全一致**，
     是值得考虑的后续方向；
  2. **保底（当前采用）**：保留闸门，内存不足时拒绝并提示用户。
- **不要**试图用"host 常驻 + 开关只切 host"来规避 —— 那是把 OFF 语义改成假 OFF，
  必须由产品决策明确接受"关不掉、只隐蔽"这个行为变化。

## F29. WiFi 连上了却不拉天气：事件比服务初始化更早，通知被静默丢弃 ★时序坑

- **现象**：WiFi 连接模式下，能连上、屏幕也有 IP，但**校时和天气永远不刷新**
  （下拉壁纸的天气卡一直空着）。AP 模式下反而正常。
- **背景**：`net_time_service` 的契约是"WiFi 拿到 IP → app 层调 `net_time_service_start()`"。
- **根因**：**`GOT_IP` 事件的派发时机早于回调注册**，共三条独立成因，叠加起来几乎必然漏掉：

  | # | 问题 | 后果 |
  |---|---|---|
  | 1 | `main.c` 里 **先** `wifi_manager_init()` **后** `wifi_manager_set_sys_cb()` | `wifi_manager_init()` 内部就 `esp_wifi_start()` + `auto_connect()`；**开机自动连已保存路由**时 `GOT_IP` 在 `init()` 返回前就派发完，此时 `s_sys_cb == NULL` → 通知直接丢弃 |
  | 2 | `page_wifi` 进页面就 `wifi_manager_set_evt_cb()` 覆盖同一槽位 | 曾经两个回调合成一个槽位，**进一次 WiFi 页面就把 app 的回调顶掉**，后台服务从此再也收不到通知 |
  | 3 | 服务**只能**由"当时在线的 GOT_IP"拉起 | 若启动时已联网（事件早于服务初始化）→ 既没等到事件，也没人补调用，**永久不启动** |

- **解决**（三层，从根上消除"漏一次就永久失效"）：

  1. **注册顺序修正**（`main.c`）：`wifi_manager_set_sys_cb(on_wifi_evt)` 提前到
     `wifi_manager_init()` **之前** —— 先接线，再开机；
  2. **两个回调槽位语义分离并写进头文件**：`sys_cb` 是 app 级、进程级、只注册一次、
     **绝不覆盖**；`evt_cb` 是 UI 页面级、随页面进出增删。`notify()` 两者独立派发。
     并在 `page_wifi` 的 `destroy` 里 `wifi_manager_set_evt_cb(NULL)` 注销；
  3. **★ 服务改成"自愈式"启动**（`net_time_service.c`）：
     - 新增幂等入口 `net_time_service_notify_network_up()`：**任务已建** → 通知它刷新一轮；
       **任务没建** → 现在建（`s_net_up = true` 后建任务）。
       这条分支专门兜"IP 事件早于服务初始化"；
     - 任务改为**先建、再等网**：建任务只依赖内存（开机必然够），不等网。
       进循环后先 `while (!s_net_up) vTaskDelay(1s)`，联网后自然开始拉天气。
       → 无论事件早到晚到、漏没漏，只要**任何一次**拿到 IP，任务都会起来；
     - `main.c` 的 `WIFI_EVT_GOT_IP` 响应改用 `notify_network_up()`；
     - `page_wifi` 进页面时按 `wifi_manager_get_ip()` + `get_role() != WIFI_ROLE_AP`
       补发一次 `GOT_IP`，覆盖"事件发生在页面存在之前"。

     另修一个资源泄漏：`net_time_service_start()` 里 `xSemaphoreCreateMutex()` 成功
     但 `xTaskCreate` 失败时，原来既不删互斥锁也不清 `s_lock`，会永久卡死在"mutex create failed"
     分支 —— 现在失败路径正确回滚。

- **经验**：
  - **"事件驱动启动"必须假设事件可能先于订阅者到达。**
    标准解法不是"保证订阅够早"（做不到），而是**让启动条件可查询、可重放**：
    用状态标志（`s_net_up`）+ 幂等入口，让"通知"和"查询"等价。
    只要**任意一次**信息源到达就能启动，系统就是自愈的；
  - **"先注册回调、再调 init"是通用纪律**。凡是 `xxx_init()` 内部可能同步派发事件，
    回调就必须在它之前挂好 —— 这类 bug 的特征是**"偶发、时序相关、日志里什么都没有"**；
  - **一个模块只有一个回调槽位 = 迟早被覆盖**。只要存在"app 级"和"UI 级"两种订阅者，
    就必须分成两个槽位，并在头文件写清哪个是"只注册一次、不许覆盖"；
  - **UI 页面的回调要在 destroy 里注销**。否则页面销毁后回调仍指向本文件的静态变量，
    是悬垂风险；本次顺手补上（`wifi_manager_set_evt_cb(NULL)`）；
  - **"先建任务再等前置条件"优于"等前置条件满足再建任务"**：
    建任务几乎不会失败（内存要求小），而等条件可能永远等不到。
    把"等"放进任务循环里，顺带获得了自动重试能力。

## F30. 内部 RAM 被 750KB JPEG 缓冲偷走：`*_calloc_prefer` 的"优先内部"陷阱 ★★内存坑

- **现象**：F28 加了内存护栏后，点蓝牙被正确拒绝，日志给出真实数字：
  ```
  E BT_SVC: internal RAM too low for BT host: free=25987 (need 49152)
           largest=23552 (need 24576) -- refuse to power on
  ```
  **追问（关键）**："为什么之前蓝牙语音跑通了，加上按键控制音量功能后现在又不行了？"

- **答案：跟"按键控制音量"功能无关，是时序变了。** 而音量功能只是把问题**暴露**出来。
  两个嫌疑被逐一排除：
  - `on_volume_change()` 只在按键时执行，**不分配任何内存** —— 与本次无关；
  - `bt_push_service_early_init()` 用 `stack_in_ext=true` + `MALLOC_CAP_SPIRAM`，
  **在 controller 初始化之前**执行，不占内部 RAM —— 与本次无关。

- **★ 真正的根因：`fs_service_init()` 里的全屏 JPEG 输出缓冲落在了内部 RAM。**
  ```c
  file_buffer_size = 800 * 480 * sizeof(lv_color_t);   /* LV_DEPTH=24 → 1152000 ≈ 1.10MB */
  file_buffer = jpeg_calloc_align(file_buffer_size, 16);
  ```
  > ⚠ **尺寸勘误（2026-09-21 复核）**：本节早期版本写 `800*480*2 = 768000 ≈ 750KB`，
  > 那是按 `LV_COLOR_DEPTH=16` 算的。本工程 `sdkconfig` 里
  > `CONFIG_LV_COLOR_DEPTH=24`，`sizeof(lv_color_t) == 3`，**实际 1152000 字节 ≈ 1.10MB**。
  > 实测日志 `jpeg out buffer 1152000 bytes @ 0x5000d8c0` 可证。
  > 体积比原估算大 50%，但这**不改变结论** —— 1.10MB 比 750KB 更进不了内部 RAM，
  > 反而更凸显"必须显式指定 PSRAM"；只是做内存账时不要照抄 750KB。

  `jpeg_calloc_align()` 内部走的是 **`heap_caps_calloc_prefer()`** —— 语义是
  **"优先内部 RAM，内部不够才退到 PSRAM"**（已从
  `managed_components/espressif__esp_new_jpeg/lib/esp32s31/libesp_new_jpeg.a`
  的符号表核实：`jpeg_calloc_align_inner` → `heap_caps_calloc_prefer`）。

  而 `fs_service_init()` 原来的调用位置是 **`bsp_display_start()` 之后**：
  此时内部 RAM 还有约 1MB 连续空间，于是这 1.10MB **被吃在内部 RAM 里**，
  直接导致后续开蓝牙时 `internal free` 只剩 25KB。

- **为什么"之前能跑通"？** 因为开机自动连 WiFi 是**新增**的（F29 修完后才真正生效）。
  之前 WiFi 没连上 → 天气任务没起来 → 少了 HTTP/cJSON 的内部 RAM 占用 →
  剩余空间刚好够 bluedroid host 起来。F29 修好之后，任务起来了、内部 RAM 少了，
  于是 F30 这个**本来就埋着的坑**才显形。
  → 典型的"**修好一个 bug，暴露出另一个**"：不是新引入的问题，是原有隐患失去了掩盖。

- **解决（两处，双保险）**：
  1. **显式指定 PSRAM**（根治）：`fs_service.c` 改用
     `heap_caps_aligned_calloc(16, 1, size, MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT)`，
     优先 PSRAM；拿不到才退回 `jpeg_calloc_align()` 并打警告。
     16 字节对齐由 `heap_caps_aligned_calloc` 原生保证（JPEG 硬要求）；
  2. **时序前移**（纪律）：`fs_service_init()` 从 `bsp_display_start()` 之后
     移到之前，与 `bt_audio_service_controller_init()` / `bt_push_service_early_init()`
     同一个空窗窗口。

- **经验**：
  - **★ `xxx_calloc_prefer` / `malloc_prefer` 是"优先内部 RAM"的意思，不是"随便挑一处"。**
    对 750KB 这种大块，必须显式写 `MALLOC_CAP_SPIRAM`，否则它会默默吃掉
    宝贵的内部 RAM。**库函数帮你"自动选择"时，一定要读清它选的是什么**；
  - **★ 判断一块缓冲该放哪，先问三个问题**：① 多大？（>32KB 就别放内部）
    ② 谁访问它？（DMA？CPU？）③ 生命周期？（活到关机 → 越早分配越好）。
    本题：750KB + 仅 CPU 访问 + 活到关机 → 必须 PSRAM 且尽早分配；
  - **★ "大块 + 只分一次 + 活到关机"的缓冲必须在开机最空窗口拿完。**
    这类缓冲有一个算一个，漏一个就会在别处（常是蓝牙）表现成随机崩溃。
    **建议维护一份"开机预分配清单"**，见 `13_内存管理规范.md`；
  - **修好一个 bug 后要重新体检同类隐患**：F29 修完让 WiFi 真正工作，
    立刻改变了内存基线，把 F30 顶了出来。**凡是"修完 A 后 B 开始崩"，
    首先怀疑 B 本来就有问题、只是被 A 掩盖着**；
  - **护栏的价值在于"把崩溃变成一个数字"**：F28 的闸门没有让功能变好，
    但它把一次 assert 崩溃变成了一句 `free=25987 need=49152` ——
    **没有这个数字，这次排查会困难得多**。加护栏不只是"防御"，也是"可观测性投资"。


## F31. 开屏壁纸"上拉要划两次"：事件挂错层，被 CLICKABLE 画布吞掉 ★LVGL 命中测试坑

- **现象**：开机在 splash 壁纸上滑，第一次没反应，**必须再划一次**才进主界面。
  第一次的手指位移像是"丢了"。

- **根因：事件回调挂在父级，而真正接收触摸的是全屏 `CLICKABLE` 子对象。**

  `page_splash.c` 原来这么写：
  ```c
  s_wallpaper = overlay_wp_particles_build(page);      /* 返回 canvas */
  lv_obj_add_flag(s_wallpaper, LV_OBJ_FLAG_CLICKABLE);
  lv_obj_add_event_cb(s_wallpaper, splash_pressed_cb,  LV_EVENT_PRESSED,  NULL);
  lv_obj_add_event_cb(s_wallpaper, splash_pressing_cb, LV_EVENT_PRESSING, NULL);
  ```
  看起来是挂在"壁纸"上，但关键在 `overlay_wp_particles_build()` 内部
  （`overlay_wp_particles.c:194-200`）：
  ```c
  s_canvas = lv_canvas_create(parent);                 /* 全屏 800x480 */
  lv_canvas_set_buffer(...);
  lv_obj_center(s_canvas);
  lv_obj_add_event_cb(s_canvas, wp_touch_cb, LV_EVENT_ALL, NULL);
  lv_obj_add_flag(s_canvas, LV_OBJ_FLAG_CLICKABLE);    /* ← 命中测试停在这里 */
  ```
  **返回的是 canvas，不是父容器。** canvas 铺满全屏（800×480）且 CLICKABLE，
  于是 LVGL 的命中测试永远停在 canvas 上；而 canvas 自己注册了
  `LV_EVENT_ALL` 却**只处理 PRESSING/RELEASED**（做粒子避让），
  `PRESSED` 事件既不处理也不冒泡到父级 —— 父容器上的两个回调**形同虚设**。

  为什么"第二次能过"：第一次划动被 canvas 吃掉（`s_press_start_y` 从未被记录）；
  抬手后再按下，此时 `s_press_start_y` 是**上一次残留的坐标**，
  相对位移变得很大，于是"碰巧"触发了 `dy < -80` 判定。

- **为什么 `ui_common_page_root()` 也不行**：它是 `lv_obj_create()` 出来的普通容器，
  **默认不带 `LV_OBJ_FLAG_CLICKABLE`**（`ui_common.c:26-35`），
  挂在它上面的 `PRESSED/PRESSING` 同样收不到。

- **解决**：
  1. `overlay_wp_particles.c` 新增取画布接口
     `lv_obj_t *overlay_wp_particles_canvas(void)`；
  2. `page_splash.c` 把触摸事件挂到 **canvas** 上（拿不到时回退 `page` 兜底）；
  3. `wp_touch_cb` 的注册从 `LV_EVENT_ALL` 收窄为
     `LV_EVENT_PRESSING` + `LV_EVENT_RELEASED`
     —— 粒子避让只需这两个，注册 ALL 反而制造了"事件黑洞"。

- **经验**：
  - **★ LVGL 的事件只会送到命中测试的终点，不会自动冒泡给父级。**
    "事件挂在外层容器上就一定能收到"是错的 —— 只要子对象 CLICKABLE 且铺满，
    父级就永远收不到 `PRESSED/PRESSING`。**排查手势失灵，第一步是找出
    `lv_indev_get_act()` 到底停在哪个对象上**；
  - **★ 铺满全屏的 `CLICKABLE` 对象 = 事件黑洞。** 它会把整个页面
    所有触摸"截胡"。要么把事件也挂到它身上，要么去掉它的 CLICKABLE；
  - **★ `LV_EVENT_ALL` 是排查期的便利，不是上线期的好习惯。**
    它把不属于自己的事件也吸过来却不处理，等于替子/父层"截流"。
    **只注册真正需要的事件码**；
  - **"第一次无效、第二次才生效"是命中测试类 bug 的典型指纹**：
    因为第一次的起点坐标没被记录，第二次用的是陈旧的起点，位移被算大了。
    见到这个症状优先去查"谁在吃 PRESSED"。


## F32. 天气 Key 突然"没编译进去"：密钥注入链路被绕过（构建入口不统一）★★流程坑

- **现象**：日志打
  `W NET_TIME: QWEATHER_KEY not configured, skip weather (fill it and rebuild)`，
  而**之前一直是好的**（改动记录 §16 已确认注入闭环通过）。

- **排查（用构建产物反推，不靠猜）**：
  1. 读 `build/compile_commands.json`，找到 `net_time_service.c` 的编译命令：
     **完全没有 `-DQWEATHER_KEY`** —— 宏根本没进编译器；
  2. 读 `build/esp-idf/main/CMakeFiles/__idf_main.dir/middleware/network/net_time_service.c.obj`：
     既无真实 Key 也无占位符（占位符是被 `strcmp` 比较用的字面量，会被优化掉），
     确认编译期就是占位宏路径；
  3. 按 `mtime` 排序 `build/log/idf_py_stdout_output_*`，提取每次 configure 的
     CMake 状态行，得到**状态翻转的确切时刻**：
     ```
     09-21 13:45:04  INJECTED   (ninja all     → Re-running CMake)
     09-21 13:51:55  NOTSET     (cmake -G Ninja -B build ... ← 手敲的裸 cmake)
     09-21 15:08:04  NOTSET
     09-21 15:15:04  NOTSET
     09-21 19:37:09  NOTSET
     ```
     此前从 09-18 18:58 到 09-21 13:45，**二十余次构建全部是 INJECTED**。

- **根因：13:51 那次直接用裸 `cmake -G Ninja -B build ...` 重配了构建目录，
  绕过了 `tools/build.ps1`。** `idf_env.local.ps1` 是由 `build.ps1` →
  `idf_common.ps1:Initialize-BuildEnv()` 点源加载的，**裸 cmake 不会加载它**，
  于是 configure 阶段 `$ENV{QWEATHER_KEY}` 为空 → 走占位分支 →
  **这个"没 Key"的状态被写进 `build.ninja` 并固化**。
  之后即便再跑 `ninja all`／`ninja app`／`app-flash`，
  因为 `build.ninja` 里的宏已经是空的，**增量构建会一直沿用**（这正是 F18 的机制）。
  同一时段 20:21 的日志显示 `Command: ninja all` / `ninja app` ——
  说明后续确实在用裸 ninja，环境里没有 Key。

- **★ 关键判断：不需要"删除构建重新编译"。** 见下方排查建议。

- **解决**：
  1. **统一构建入口**：改用 `tools/build.ps1`（它默认先 `reconfigure`，
     会在重新配置时刷新环境变量，**自动把丢失的 Key 注入回来**，
     构建后还会校验固件里是否真的含 Key/Host，不含就 `exit 3`）；
  2. `tools/idf_common.ps1` 新增 **`Assert-LocalSecrets()`** 并挂进
     `Initialize-BuildEnv()`：**Key 为空或仍是占位符就直接抛错终止构建**，
     不再允许"静默产出一版没有天气的固件"；同时校验 `QWEATHER_API_HOST`
     （和风已下线公共域名，缺了会静默 403，见 F17）；
  3. `tools/build.ps1` 注释补上顺序红线说明。

- **经验**：
  - **★ `build.ninja` 会"记住"configure 时的环境。** CMake 的 `$ENV{}` 只在
    configure 阶段求值，一旦在**没有 Key 的环境**里配置过，
    后续所有增量构建都会沿用空宏 —— **表现就是"我没改任何代码，Key 却没了"**。
    这与 F18 是同一个机制，只是触发方式从"改了 key 没重配"变成"用裸命令重配了"；
  - **★ 排查"配置没进去"要直接看 `compile_commands.json`**，
    一行 `grep -D` 就能定性，比反复重编烧录快得多；
  - **★ 用日志的 mtime 排序找"状态翻转点"，是定位"什么时候开始坏的"的利器。**
    本次正是靠它锁定 13:51 那次裸 cmake；
  - **★ 把"静默降级"改成"硬失败"。** 密钥缺失时固件照样能编过、能烧进去，
    问题只在运行时以一句 WARN 出现 —— 这种"静默降级"是最贵的 bug，
    它把一次构建期就能发现的问题推迟到烧录后。**能前置到构建期的检查，就别留给运行时**；
  - **★ 构建/烧录入口必须唯一。** 只要存在"裸 ninja / 裸 cmake 也能跑"的路径，
    就一定会有人在赶时间时走它，然后丢掉只有脚本才注入的东西（密钥、宏、ccache 开关）。

- **本次两个 bug 的共同点**：都属于"**表面现象 vs 实际病灶**"错位 ——
  上拉失灵看着像手势灵敏度问题，实为事件挂错层；
  Key 丢失看着像"缓存脏了要清理重编"，实为构建经历了一次无密钥的重配。
  **两次都是先拿到证据（对象树 / compile_commands.json / 日志时间线），
  再下结论，避免了"删 build 目录碰运气"式的无效返工。**


## F33. `build.ps1` 误报 "RECONFIGURE FAILED"：PowerShell 返回流被 stderr 污染 ★★脚本坑

- **现象**：按 F32 的结论跑 `tools/build.ps1`，CMake 明明**配置成功**：

  ```
  -- QWEATHER_KEY: injected from environment (len=32, value hidden)   ← Key 已注入
  -- QWEATHER_API_HOST: injected -> ke67cgkc3a.re.qweatherapi.com
  -- Configuring done (57.4s)
  -- Generating done (3.8s)
  -- Build files have been written to: .../build
  ```

  脚本却打印：

  ```
  RECONFIGURE FAILED (exit CMake Deprecation Warning at CMakeLists.txt:5
  (cmake_minimum_required): Compatibility with CMake < 3.10 will be removed
  ... System.Management.Automation.RemoteException ...  0)
  ```

  **`exit` 后面跟的不是数字，是一大段 CMake 警告文本。**

- **★ 根因：`$c1` 不是 Int32，而是一个 `Object[]` 数组。**

  `Invoke-Build` 内部是：
  ```powershell
  & idf.py @Args 2>&1        # ← 2>&1 把 cmake 的 stderr 转成「错误记录对象」
  $rc = $LASTEXITCODE
  return $rc                 # ← 但整个函数输出流 = [错误记录对象们..., 整数0]
  ```
  `2>&1` 会把原生命令的 stderr **转成 `System.Management.Automation.ErrorRecord`
  混进 PowerShell 的输出流**（报错里那一串 `RemoteException` 就是它们的
  `ToString()`）。`return $rc` 只保证**最后一个元素**是整数，
  整个流却是"一堆对象 + 一个整数"；调用方 `$c1 = Invoke-Build reconfigure`
  收到的是**数组**。

  于是 `if ($c1 -ne 0)` 变成"**数组与 0 比较**"——
  PowerShell 的比较运算符作用于数组时是**过滤语义**，
  返回的是"不等于 0 的元素集合"，非空即真 →
  **配置成功也判 FAILED，且打印时把整个数组拼出来**，就有了那段离谱的报错文本。

- **实测复现（同环境对比）**：
  ```
  OLD: type=Object[]  value=[cmake warning 0]  is-array=True
  OLD: $old -ne 0  =>  cmake warning   <-- 非空即真 = 误报
  NEW: type=Int32     value=[0]                 is-array=False
  NEW: $new -ne 0  =>  False           <-- 正确放行
  ```

- **解决（两处同时改，双保险）**：
  1. `Invoke-Build` 里把 `& idf.py @Args 2>&1` 改为
     **`& idf.py @Args 2>&1 | Out-Host`** —— `Out-Host` 把 stderr 内容
     **只打到控制台**（用户照旧能看到全部警告），**不再留在函数输出流里**；
     并 `return [int]$rc` 强制类型；
  2. 调用点全部加 `[int]` 强转：
     `$c0 = [int](Invoke-Build fullclean)`、`$c1 = [int](Invoke-Build reconfigure)`、
     `$code = [int](Invoke-Build build)` —— 万一将来再被污染，
     会是一个**明确的类型错误**，而不是静默误判。

- **顺带修 `flash.ps1`**：它原来直接用裸 `idf.py build` / `idf.py -p $Port app-flash`
  + `$LASTEXITCODE`，正好踩中 F21（stderr 被判 NativeCommandError）。
  已改为走 `Invoke-Build`（`-BuildFirst` 时先 `reconfigure` 再 `build`），
  返回值同样 `[int]` 强转。

- **经验**：
  - **★ 原生命令 + `2>&1` 在 PowerShell 5.1 里会制造"错误记录对象"，
    它们会污染函数的输出流。** 只要函数要把结果 `return` 给调用方，
    就必须把这类噪音**导走**（`| Out-Host` / 写进变量 / `| Out-Null`），
    **不能让它和返回值待在同一个流里**；
  - **★ `$x -ne 0` 在 `$x` 是数组时不是布尔判断，是过滤。** 数组参与比较
    返回"满足条件的元素集合"，非空即真 —— 于是**任何非空数组都被判为"不等于 0"**。
    这是 PowerShell 最经典的静默陷阱之一；
  - **★ "报错文本长得不像报错"是个强信号。** `exit <一大段 CMake 警告>`
    这种荒谬输出，一眼就该想到"变量里装的根本不是我以为的东西"，
    而不是去怀疑 CMake 或工程配置；
  - **★ 修复方案要能"看到日志"且"拿到干净返回值"两者兼得。**
    直接 `| Out-Null` 能修返回值但会让用户看不到构建日志；
    `| Out-Host` 才是正解 —— 日志照常显示，输出流保持干净；
  - **★ 先复现、再改代码。** 本次用 30 行 PowerShell 把 OLD/NEW 两种写法
    并排跑出来，确认 `Object[]` → `Int32` 的变化，才动生产脚本。
    **"我大概知道问题在哪"不等于"我已验证问题在哪"**；
  - **★ 同一个坑要一次性扫干净。** `build.ps1` 修完必须回头看 `flash.ps1`
    有没有同样写法 —— 它们共用 `idf_common.ps1`，改一处就该想另一处。


## F34. 时序纪律被绕过：`BT_PUSH` 的 42KB 挪进了"内部 RAM 最空窗口"（2026-09-21）

- **现象**：上电账单（`docs/_log_212621.txt`）显示 `BT_PUSH` 一口吃掉 42KB：
  ```
  I (1638) BT_SVC : early controller init: free internal=241131 largest=155648
  I (1806) BT_PUSH: early init:           free internal=198935 largest=131072
  I (1812) BT_PUSH: ready:                internal free=197687
  ```
  `free` −42196，`largest` −24576（**恰好 24×1024**）。

- **★ 但这不是 bug，是设计要付的代价 —— 它换的是"推流不再崩"。**
  `bt_push_service_early_init()` 把 pool / pipeline / 3 个 GMF 元素 / 2 个 IO
  **全部提前**到 `controller_init()` 之后、`bsp_display_start()` 之前建好，
  代价是这 42KB 从此**常驻内部 RAM**（不随蓝牙开关释放）。

  它的显式分配其实**全在 PSRAM**：
  `uri`(256B, SPIRAM) / `asrc_weight`(64B, SPIRAM) / GMF task 栈(`stack_in_ext`) /
  `proc_task`(`SPIRAM|8BIT`)。**42KB 来自第三方组件的内部工作缓冲**
  （`esp_gmf_pool_init` + `aud_dec`/`aud_asrc`/`aud_enc` + `io_file`/`io_bt`），
  **不受本项目 `heap_caps_*` 控制**，代码层无法改小。
  其中 `aud_asrc`（硬件重采样）是最大头。

- **★ 这个决策确实拿掉了 24KB 的"整段连续区"。**
  `largest` 155648 → 131072 是**一步跳掉 24KB**，不是被碎片磨掉的。
  这 24KB 在"开机后"用不上，但在"运行 13 分钟后内部只剩 7.6KB"时，
  **它恰好就是压垮 TLS / bluedroid 的那一根稻草**（见 F35）。

- **处置**：**保留**（它的收益——推流稳定性——远大于成本）。
  若将来要回收，唯一方向是**给 `aud_asrc` 减配或让 A2DP Source 不走 asrc**
  （需评估音质与耳机兼容性），**不是改 caps** —— caps 管不到组件内部缓冲。

- **经验**：
  - **★ "某模块吃了 N KB"要区分"我显式申请的"与"组件内部预分配的"。**
    前者受 caps 控制、可优化；后者只能靠**换配置项**或**换时机**；
  - **★ `largest` 的下降比 `free` 的下降更能说明性质**：
    `largest` 掉 24KB（正好 24×1024）说明拿走的是**一整段连续区**；
    若是碎片化，`largest` 会下降但不会是这种整数；
  - **★ 早期预分配是"用长期占用换短期确定性"** ——
    必须清楚这笔账，才能判断后续功能还够不够用（见 F35 的核算）。

## F35. 内部 RAM 的"非对称消耗"：TLS 与蓝牙同时因内存失败（2026-09-21）★内存坑

- **现象**（用户截图 + 串口，同一台设备）：

  | 时刻 | 场景 | internal free | largest |
  |---|---|---|---|
  | 1813ms | 开机 `BT_PUSH ready` | **197687** (193KB) | — |
  | 811234ms | 切到 SYS tab **点蓝牙开关** | **7787** (7.6KB) | **7168** (7KB) |

  ```
  E BT_SVC : internal RAM too low for BT host: free=7787 (need 49152)
             largest=7168 (need 24576) -- refuse to power on（连拦 3 次）
  E esp-tls-mbedtls: mbedtls_ssl_setup returned -0x008D   ← PSA_ERROR_INSUFFICIENT_MEMORY
  E NET_TIME: 7d failed
  ```

  **两个功能同时因内存失败**，且 TLS 的错误码在 `-0x0080` 与 `-0x008D` 之间**飘**。

- **★ 先纠正上一轮的错误结论（这是本坑最重要的部分）**：
  我先前根据**上电日志**得出"内存现状其实不紧张（193KB free）"，
  **这个结论是错的**，错在时点：
  ```
  上电日志覆盖     : 1500ms ~ 5300ms   （app_main 在 5287ms 返回）
  故障发生时刻     : 811234ms          （两个数量级之后）
  ```
  用"开机 2 秒的快照"解释"运行 13 分钟后的故障"，**证据根本不在搜索边界内**。

  → **★ 教训：任何"内存很宽裕"的结论都必须带时点。**

- **根因：`app_main()` 返回后的 185KB 去哪儿了**

  `app_main()` 在 5287ms 返回，退出时内部 RAM ≈ 193KB。到 811s 只剩 7.6KB，
  **185KB 是在运行期被吃掉的**。吃它的是**只能用内部 RAM 的消费者**：

  | 消费者 | 规模 | 为什么只能在内部 |
  |---|---|---|
  | **mbedtls TLS** | `SSL_IN=16384`+`SSL_OUT=4096`+握手/DRBG ≈ **20~25KB** | `CONFIG_MBEDTLS_INTERNAL_MEM_ALLOC=y` |
  | **WiFi / LWIP** | 驱动缓冲+pbuf+netif ≈ **数十 KB** | 协议栈约束 |
  | **LVGL 对象 / 字体** | 6 个 tab + 各 tab 的控件 | 访问频率 |
  | **各任务栈** | `audio_task`/`audio_stream`/… 8192×N | 默认 `xTaskCreate` 走内部 |

- **★ 关键判据：为什么断定是"内部 RAM 专项被吃"而非"总量不足"**

  排查时必须并列看**三个域**（只看 `INTERNAL` 分不出来）：

  ```
  MALLOC_CAP_INTERNAL  7.6KB   ← 告急
  MALLOC_CAP_DMA       ?       ← 内部，受 SPIRAM_MALLOC_RESERVE_INTERNAL=32768 保底
  MALLOC_CAP_SPIRAM    ?       ← 若仍余十几 MB → 是"专项"问题，不是总量问题
  ```

  两个易漏的账（**不是内存被偷了**）：
  1. **RTCRAM（31KB）不计入 `MALLOC_CAP_INTERNAL`**；
  2. **开机保留的 32KB 内部 DMA 池不在 `free` 里** ——
     `esp_psram: Reserving pool of 32K of internal memory for DMA/internal allocations`。
     所以"物理 210+16KB"与"free 193KB"本来就差 30+KB。

- **★ 最可疑的单一嫌疑：`CONFIG_ESP_TLS_USE_DS_PERIPHERAL=y`**

  > **⚠ 本条已被实测推翻（见下节"实测结论"）。保留在此是为了记录"被排除的假设"。**

  DS 外设路径**本身比软件路径更吃内部 RW**：它需要把密钥、哈希中间态、
  RSA/ECC 运算上下文放进**内部可访问**内存，且是 **per-operation 分配**
  （`esp_ds_context` 每次握手都建一次）。

  **这恰好解释了两个"飘"的现象**：

  | 现象 | 用"内存竞争"解释 |
  |---|---|
  | 错误码在 `-0x0080`(=BAD_INPUT_DATA) 与 `-0x008D`(=INSUFFICIENT_MEMORY) 之间变 | 中间分配**碰运气**：拿到就往下走（后面才炸），拿不到就 `-0x008D` |
  | 天气"以前成功过、现在坏了" | 每次数据量/时序略有差异，**在临界点两侧抖动** |

  > **★ 通用判据：错误码飘 = 资源竞争；错误码稳定 = 逻辑写错。**

- **★ 另一个必须排除的：内存泄漏**
  185KB 可能是"一次性被占"（正常），也可能是"一直在漏"（严重）。
  **判据**：同一场景反复进出（切 tab 十几次、开关蓝牙几次），
  看内部 free 是否**单调下降**。

### ★★ 实测结论（同日，诊断日志回来）——真凶不是 TLS，是**内部 RAM 被总量型消费者吃干**

用户按建议加埋点后重跑，`[diag]` 两行给出了决定性证据：

```
I (25027) PAGE_MAIN: [diag] before page build: internal free=29843 largest=23552 | PSRAM free=11591984
I (27010) PAGE_MAIN: [diag] after  page build: internal free=25991 largest=23552 | PSRAM free=11548352
E (30287) BT_SVC : [diag] internal free=25991 largest=23552 | DMA-capable free=2215 largest=1728
                          | PSRAM free=11544988 largest=11534336
```

**三条硬结论**：

| # | 判据 | 结论 |
|---|---|---|
| 1 | `before page build` 时内部只剩 **29843**，而开机是 **206359** | **页面创建不是凶手**（只花 3.8KB）。亏损发生在**更早** |
| 2 | `PSRAM free=11544988`（**11MB 仍空闲**），而内部只剩 26KB | **不是总量不足，是"内部 RAM 被专项吃干"** |
| 3 | `DMA-capable free=2215` / `largest=1728` | **内部 DMA 堆见底**（保底 32KB 也几乎耗尽）→ 印证 **F23** 的机制 |

**★ 最重要的一条修正：TLS / `ESP_TLS_USE_DS_PERIPHERAL` 不是元凶。**

- 时序上不可能：内部 RAM 在 **25.0 秒**（页面创建前）就已经只有 29KB，
  而 TLS 首次尝试在 **11.5 秒** —— 且它在 `sntp` 之后才跑。
  11.5 秒时内部 RAM 已不足以完成 `SSL_IN=16384` 的分配，**TLS 是受害者，不是凶手**；
- 机制上也不成立：`-0x008D` 完全可以用"当时内部只剩 29KB"解释，
  不需要假设 DS 外设额外吃内存。

**真凶候选（按日志可验证顺序）**：开机 206KB → 25.0 秒的 29KB，**亏 177KB**，
而这段时间发生的、**只用内部 RAM** 的大事只有一件：

| 事件 | 时刻 | 吃内部 RAM 的量 |
|---|---|---|
| `wifi_init` / `esp_wifi_start` | 2035~2295ms | LWIP pbuf/netif/驱动缓冲，**数十 KB** |
| `WIFI_MGR: auto-connect` + 扫描 + **5 次重连** | 2301~20769ms | 每次重连重新分配，**可能是主要大头** |
| `RECORD: local cap=9600000` | 2316ms | 见下 |
| `LINK` / `UDP_VOICE` / 各服务任务栈 | 2306~2316ms | 8192×N |
| **页面创建** | 25027~27010ms | **仅 3.8KB（已排除）** |

→ **下一步取证：在 `wifi_manager_init()` 前后、以及每次重连前后各打一行 `[diag]`。**
这是唯一还没被量化的区间，也是唯一与 177KB 量级相符的区间。

**★ 方法论收获（比结论更重要）**：
- **二分埋点法一次就把 3 个嫌疑人降到 1 个**：`before/after page build`
  这两行只花了一次构建，就永久排除了"页面创建"这条线；
- **"PSRAM 还有 11MB"这一条直接把问题定性了**：
  凡是"PSRAM 富余而内部见底"的场景，凶手**必然**是只用内部 RAM 的消费者，
  业务代码（已全部显式 PSRAM）可以先排除；
- **不要凭"最可疑"下判断，要靠"最先被量化"**：
  我先前把 TLS/DS 列为"最可疑"，实测证明它连时序都对不上。
  **机制上可疑 ≠ 时序上可能**，先做时序核对的成本几乎为零。

### ★★ 用户追问命中：**任务栈就是最大的一块**（同日再追）

> 用户问："**会不会是任务栈太大了，占满了？**"

**答案：是，这是本项目最大的单笔内部 RAM 支出。** 逐个清点（见 `13_内存管理规范.md` §5.1）：

| 任务 | 栈 | 落点 |
|---|---|---|
| `udp_voice_ctl` | 8192 | **内部** |
| `udp_voice_tx` | 8192 | **内部** |
| `udp_voice_rx` | 8192 | **内部** |
| `record_service` | 8192 | **内部** |
| `audio_task` | 8192 | **内部** |
| `audio_stream` | 8192 | **内部** |
| `link_manager` | 8192 | **内部** |
| `net_time` | 8192 | **内部** |
| `led_task` | 4096 | **内部** |
| `bt_vol_sync` | 2560 | 内部（短命，同步完即退） |
| **小计（本项目）** | **72192** | **≈ 70.5 KB** |

再加上 IDF 自带任务（`main_task` 3584 / `esp_timer` 3584 / `sys_evt` 2304 /
`ipc0`+`ipc1` 2048 / **`wifi driver task` 6656** / FreeRTOS 定时器 2048 /
`idle0`+`idle1` 3072…）≈ **22.8 KB**

→ **任务栈合计 ≈ 93 KB，正好是 177 KB 亏损的一半以上。**

**★ 为什么它们必然落在内部 RAM（配置决定的，不是巧合）**：

```
CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0   ← 本意是"小块也优先给 PSRAM"
CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y   ← 允许栈进 PSRAM
CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y   ← 允许栈进 PSRAM
```

**两个开关都开了，但全项目只有 `bt_push_proc` 真的用了它**：

```c
/* bt_push_service.c:409 —— 全项目唯一正确外置的栈 */
xTaskCreatePinnedToCoreWithCaps(proc_task, "bt_push_proc", 4096, NULL,
                                PROC_TASK_PRIO, NULL, PROC_TASK_CORE,
                                MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT);
```

其余 10 处一律裸 `xTaskCreate` / `xTaskCreatePinnedToCore`，
**没有传 caps，所以走默认分配路径 = 内部 RAM**。

**这件事最反直觉的地方**：工程已经知道了正确做法（`bt_push_proc` 就是样板），
**却没有应用到其余 10 个任务上** —— 这是一个"**知道但没推广**"的典型缺口，
不是认知问题，是执行遗漏。

**可回收量估算（保守）**：

| 做法 | 回收 | 说明 |
|---|---|---|
| 把 8 个 8192 的常驻任务改 `WithCaps(SPIRAM)` | **≈ 64 KB** | 最大收益，风险低（栈不要求 DMA/内部） |
| `led_task`(4096) 一并外置 | +4 KB | — |
| `net_time` 等任务栈降到实测需求 | 另算 | 需先量 actual high-water mark |

**★ 为什么任务栈可以放 PSRAM（安全性论证）**：
栈只被 **CPU** 访问（压栈/出栈/局部变量），**不需要 DMA 可达**，
也不参与中断向量的物理约束（`IRAM_ATTR` 的 ISR 用的是被中断任务自己的栈，
而 PSRAM 栈在 CPU 视角下与内部栈等价）。
这正是规范 §1.1 表格里"**小尺寸高频小对象放内部**"的**反面**——
8192 字节的栈既不小也不高频，**属于该外置却漏了的那一类**。

> ⚠ 唯一注意点：PSRAM 上的栈访问比内部慢（本板 Octal PSRAM 200MHz，差距不大），
> 且 `CONFIG_SPIRAM_SPEED_200M` 已开。对 8 个非热路径任务无实质影响。

### ★★ 重连消耗的成因与处置（同日追问落地）

> 用户问："**为什么每重连一次都减一点，不能初始化好，重连不减少吗？**"

#### 代码事实：重连**本来就不重新初始化**

| 函数 | 做了什么 | 何时走 |
|---|---|---|
| `apply_candidate()` L237 | `esp_wifi_set_config()` + `esp_wifi_connect()` | **仅**切换候选 AP / 运行中掉线 |
| `reconnect_timer_cb()` L272 | `s_retry_num++` + **仅** `esp_wifi_connect()` | 连接失败重试 |

**→ 现存设计已经是"初始化一次、重试只重连"，正是用户期望的方向。**
所以问题**不在重复初始化**，而在 **WiFi 驱动在失败路径上不归还全部分配**。

#### 那 10 KB/次 的三个来源

1. `esp_wifi_connect()` **每次都会重跑 auth/assoc 流程**，
   `wpa_supplicant` 侧重建 EAPOL / 握手状态机 / PMK 缓存（**走内部 RAM**）；
2. **失败路径（`reason=2` 认证失败）不是正常断开**，
   驱动的清理路径**不保证把本次尝试申请的临时缓冲全部归还**；
3. 每次尝试新申请 beacon/probe 缓冲，其**释放时机滞后**于下一次尝试。

**★ 这是 ESP-IDF WiFi 驱动的内部行为，应用层不可控。**
应用层只能：**减少尝试次数** + **避免无谓的失败尝试**（如密码错时不必试满）。

#### 处置（已落地 + 待办）

| 项 | 状态 | 说明 |
|---|---|---|
| `WIFI_MAX_RETRY` 5 → **3** | ✅ 已改 | 省约 **20 KB** 内部 RAM |
| 语义澄清为"总尝试次数（含首次）" | ✅ 已改 | 旧注释"重试次数"含混 |
| 日志 `(2/5)` → `(attempt 2/3)` | ✅ 已改 | 消除"重试 5 次"误读 |
| 连带清理 4 处硬编码 `5 次` 注释 | ✅ 已改 | 改常数必须连带改文案 |
| **密码错误时提前放弃**（不必试满） | ⏳ 待办 | `reason=15(4WAY_HANDSHAKE_TIMEOUT)` / `reason=2` 多为凭据错，可只试 1 次即换下一个 |
| 重试消耗定性（增长型 vs 泄漏型） | ⏳ 取证中 | 靠新增 `[diag-retry]` 三行分辨 |

#### ★ 一般化经验

**"重试"不是免费的。** 任何"失败就重来"的设计，都要先量一次"重来一次的代价"：

```
重试次数 × 单次不可归还资源 = 必须显式设定的资源预算
```

- 若代价是**纯 CPU 时间** → 次数可随手设大；
- 若代价是**不可归还的内存/句柄/连接数** → **必须当成资源预算显式设定**。

**本次实例**：`WIFI_MAX_RETRY=5` → 5 × 10 KB = **50 KB 内部 RAM**。
这个数字**从未被当成"预算"审视过**，只是当年随手填的常数。
而 50 KB 恰好超过 mbedTLS 需要的 20 KB 连续块 → 表现为"天气永远失败"。

> **★ 教训：改一个重试常数前，先测"单次重试的不可归还代价"。**

```
after  esp_wifi_connect:  retry_num=1  internal free=57703   <- 只掉 332 B
in DISCONNECTED evt:      retry_num=1  internal free=57947   <- 只掉 88 B
```

| 结论 | 依据 |
|---|---|
| **增长型**（非泄漏型） | `after connect` 掉、下轮 `before` 没涨回 |
| **单次仅 332 B**（旧的 10 KB 是特例） | 本轮 `reason=201/202`（**非**认证失败）+ 第 3 次即连上，只走 2 次重试 |
| **三行布局验证有效** | 相邻相减即分离"connect 自吃"与"失败归还" |

> **★ 关键修正**：那 10 KB **不是固定开销，而是与失败类型强相关**。
> `reason=2`（认证失败）那种"每次完整跑完握手再失败"才是最贵场景
> → **坐实待办：认证失败应提前放弃，不必试满上限。**

#### 两个反直觉发现

1. **`SCAN_DONE` 反而释放内存：53743 → 58035（+4292 B）**
   → 扫描期驱动预扣多于实际所需。**排查内存不能默认"每步只减不增"**，
   事件回调里同样可能有净释放。
2. **扫描缓存确实落 PSRAM**：`scan rec buf: num=4 size=368 ptr=0x504fb92c`
   （`0x504f_xxxx` = PSRAM）→ 本次未偷内部。
   但代码注释已明确**落点不受控**，仍应改显式 `heap_caps_calloc(..., MALLOC_CAP_SPIRAM)` 固化。

|---|---|---|---|
| **P0** | **RGB panel 帧缓冲降规格** | 省 20~40 KB | 72 KB 最大单块；**DMA 硬性**，只能改数量/像素格式 |

### ★★★ 第三刀：那 72 KB 不是"帧缓冲"，是 **bounce buffer**

> 用户问："这个 RGB panel 帧缓冲是干啥的？是我的壁纸帧搬运吗？还是 lvgl 渲染有关的？"
> **答：都不是。** 吃内部 RAM 的是**第三块东西 —— bounce buffer（弹跳缓冲）**。

#### 三块"看起来都像帧缓冲"的东西，必须分清

| # | 名字 | 归谁 | 大小 | 落点 |
|---|---|---|---|---|
| 1 | **RGB 帧缓冲** `fbs[]` × 2 | RGB 驱动（硬件扫描） | 750 KB × 2 = **1500 KB** | **PSRAM** |
| 2 | **bounce buffer** × 2 | RGB 驱动（DMA 逐行搬运） | 31.25 KB × 2 = **62.5 KB** | **内部 DMA** ★ |
| 3 | **LVGL 绘制缓冲** | LVGL（渲染目标） | **0 B —— 没分配** | — |

**源码依据**：

| 项 | 位置 | 关键代码 |
|---|---|---|
| #1 在 PSRAM | `bsp_display.c` L125 | `.flags.fb_in_psram = 1` → `MALLOC_CAP_SPIRAM\|DMA` |
| #2 在内部 | `bsp_display.c` L113-115 | `.bounce_buffer_size_px = BSP_LCD_H_RES * CONFIG_BSP_LCD_RGB_BOUNCE_BUFFER_HEIGHT` |
| #2 必须内部 | `esp_lcd_panel_rgb.c` L178-180 | `expect_bb_eof_count = fb_size / bb_size`（**DMA 描述符数按它推导**） |
| #2 分配点 | `esp_lcd_panel_rgb.c` L237 | `heap_caps_aligned_calloc(..., MALLOC_CAP_INTERNAL\|MALLOC_CAP_DMA\|MALLOC_CAP_8BIT)` |
| #3 不分配 | `esp_lvgl_port_disp.c` L362-381 | `if (avoid_tearing) { esp_lcd_rgb_panel_get_frame_buffer(...2, &buf1, &buf2); }` |

**账目配平**：`62.5 KB (bounce) + 9.5 KB (结构体/句柄/ISR) = 72.0 KB` ✅ 与实测 73756 B 吻合。

> **★ §28.16 / 上一节把它记作"RGB PANEL 帧缓冲"是措辞不准**。
> 准确说法：**"RGB panel 的 bounce buffer + 驱动结构体"；帧缓冲 1500 KB 全在 PSRAM。**

#### ★ 反直觉：`avoid_tearing=1` 其实是**省内存**的配置

本工程 `CONFIG_BSP_DISPLAY_LVGL_AVOID_TEAR=y` → LVGL **借 RGB 帧缓冲当画布**，
自己不分配 draw buffer。副作用：`CONFIG_BSP_LCD_DRAW_BUF_HEIGHT=100` /
`..._DOUBLE=y` 这两个配置**在本工程完全不起作用**（只在 `avoid_tearing=0` 分支被读）。

若为了"优化"关掉它改用 `direct_mode`：
```
buffer_size 必须 = hres × vres = 384000 px（direct_mode 强制整屏）
buf1 + buf2 = 768000 × 2 = 1500 KB，且 buff_dma=true → 【硬性内部 DMA】
```
**→ 会凭空多花 1500 KB 内部 DMA，比现在多 20 倍。这是必须避开的改动方向。**

> **★ 一般化：`avoid_tearing` / `double_buffer` / `direct_mode` 这些"画面质量"开关
> 同时是内存开关，且方向不直观 —— 改之前必须读实现，不能按名字推。**

#### 可回收量（bounce buffer 降配）

约束 `fb_size % bb_size == 0`（IDF 硬校验）。`fb_size = 768000 B` 固定：

| `BOUNCE_BUFFER_HEIGHT` | ×2 合计 | **可省** | 合法性 |
|---|---|---|---|
| **20（当前）** | **62.50 KB** | — | ✅ |
| 16 | 50.00 KB | 12.5 KB | ✅ |
| 10 | 31.25 KB | **31.25 KB** | ✅ |
| 8 | 25.00 KB | **37.5 KB** | ✅ |
| 5 | 15.62 KB | 46.9 KB | ✅ |

**权衡**：越小 → 每行搬运 DMA 中断越频繁 → CPU 占用升高。
**建议先试 `HEIGHT=10`（省 31.25 KB）**，观察 UI 流畅度。

> **★ 第三类处置：既非"能挪没挪"，也非"挪不动"，而是「可以缩，但要付 CPU 代价」。**
> 记法：bounce buffer 就属这一类。

## F36. 蓝牙音量调节必失败：上游 A2DP SRC 路径漏调 `BTA_AvOpenRc()`（2026-09-21）★★★上游缺陷

### 现象

**A2DP 推流完全正常，但按键调音量必失败**（连按 6 次，档位 60/50/40/30 全败）：

```
I (30560) BTN_SVC: volume -> 60
E (30560) BT_AUD_OPS: Operation failed: vol_ops.set_absolute is not registered
W (30562) BT_SVC: set abs vol failed: ESP_ERR_INVALID_STATE
W (30567) main: bt vol set failed (ESP_ERR_INVALID_STATE), fallback to local codec
```

「一个 profile 活、一个 profile 死」—— 说明问题不在 A2DP，而在 **AVRCP**。

### 根因 1（主因）：AVRCP CT 连接从未建立

`vol_ops.set_absolute` 只在 `ESP_AVRC_CT_CONNECTION_STATE_EVT` 且 `connected=true`
时注册（`bt_audio_avrcp_ct.c:567-601`）。完整链路：

```
BTA_AvOpenRc(handle)               [bta_av_api.c:571]
  → BTA_AV_API_RC_OPEN_EVT
  → bta_av_rc_opened()             [bta_av_act.c:465]
  → BTA_AV_RC_OPEN_EVT             [bta_av_act.c:551]
  → btc_rc_handler→handle_rc_connect  [btc_avrc.c:1085 / 472]
  → btc_avrc_ct_cb_to_app(connected=true)  [btc_avrc.c:508-514]
  → vol_ops.set_absolute 注册      [bt_audio_avrcp_ct.c:587]
```

**断在第一步**。`BTA_AvOpenRc()` 全 IDF **只有一个调用点**：

```c
/* btc_av.c:531-600  BTA_AV_OPEN_EVT */
if (btc_av_cb.peer_sep == AVDT_TSEP_SRC) {
    if (g_av_with_rc) { BTA_AvOpenRc(btc_av_cb.bta_handle); }  /* L561 唯一调用点 */
} else if (btc_av_cb.peer_sep == AVDT_TSEP_SNK) {
    /* For A2DP source, report sink codec caps ... */          /* L565 本工程走这里 */
    /* ← 无 BTA_AvOpenRc() */
}
```

本工程是 **A2DP SRC** → 连上后 `peer_sep == AVDT_TSEP_SNK`（对端是 sink）→ 走 L565 →
**永不建 AVRCP 连接** → `vol_ops` 永不注册。

#### 旁证 A：源码自相矛盾（必有一处是 bug）

| 位置 | 场景 | `CloseRc` 的判断 |
|---|---|---|
| `btc_av.c:861` | src 断开(opened) | `== AVDT_TSEP_SRC` |
| `btc_av.c:1050` | src 断开(started) | `== AVDT_TSEP_SRC` |
| **`btc_av.c:2079`** | **src deinit** | **`== AVDT_TSEP_SNK`** ← **相反** |
| `btc_av.c:2042` | sink deinit | `== AVDT_TSEP_SRC` |

4 处判断，3 处 SRC、1 处 SNK。**必有一处错。**

#### 旁证 B：设计中的正确开关是个**死函数**

`bta_av_aact.c:3010` 的 `bta_av_open_rc()` 检查 `p_scb->use_rc`（意图中的判据，
`btc_av.c:392-406` 调 `BTA_AvOpen(..., use_rc=TRUE, ...)` 正是传的 `TRUE`）：

```c
if (p_scb->use_rc == TRUE || (p_scb->role & BTA_AV_ROLE_AD_ACP)) {
    bta_av_rc_disc((UINT8)(p_scb->hdi + 1));   /* 用主 SM 做 AVRC SDP */
}
```

但 **`bta_av_open_rc()` 全 IDF 无调用点**（只有定义 + 声明）—— 死函数。
`bta_av_rc_disc()` 仅在"**对端主动连过来**"分支被调（`bta_av_act.c:549`）。

> **★ 结论：A2DP SRC 主动发起场景下，整条 AVRCP 建连链路没有入口。上游真实缺陷。**

### 根因 2（潜伏 bug）：量纲双重映射

`bt_audio_avrcp_ct.c:136` 库内转换**期望入参 0..100**：

```c
static inline uint8_t vol_to_avrc(uint8_t app_vol) { return (uint8_t)((app_vol * 127) / 100); }
```

旧代码已映射成 0..127 再传 → **库再乘一次 → 溢出**：

| 本地 | 旧传出 | 库转 | 实际 | 应有 |
|---|---|---|---|---|
| 30 | 42 | 53 | 41.7% | 33 |
| 60 | 85 | 107 | 84.3% | 67 |
| 90 | 127 | **161** | **顶满截断** | 100 |

> **★ 三层量纲必须分清**：本地 `0..90` → **应用层 `0..100`** → AVRCP `0..127`。

1. **`avrcp_ensure_ct_link()`**：应用层主动补调 `BTA_AvOpenRc()`

   | 项 | 值 | 来源 |
   |---|---|---|
   | 拿 handle | `btc_a2d_conn_handle_get()` | `btc_av.c:2275`，声明 `btc_av.h:313` |
   | 开连接 | `BTA_AvOpenRc(handle)` | `bta_av_api.c:571`，声明 `bta_av_api.h:882` |

   > ★ 本工程 `btc_av_cb` / `btc_rc_cb` 因 `CONFIG_BT_BLE_DYNAMIC_ENV_MEMORY` 未开
   > 而是**文件级 static**（不可外部访问）—— 但 `btc_a2d_conn_handle_get()` 是公开
   > getter，返回的正是 `btc_av.c:561` 用的同一个值。

   > ★★ **不能再调一次 `esp_a2d_source_connect()` 来补**：`btc_profile_queue.c:43`
   > 的连接队列**按 uuid 去重**，同 uuid 会被**静默丢弃**。
   > `BTA_AvOpenRc()` 直接 `bta_sys_sendmsg()` 不经队列，是唯一入口。

2. **时机（三拍）**：`delay 800ms` 等 A2DP 建好（SCB 必须先存在，

3. **兜底**：`set_volume` 里遇 `ESP_ERR_INVALID_STATE` 主动补建

4. **量纲修正**：`local_vol_to_avrcp()` → `local_vol_to_app()`，目标 **0..100**。

源码原注释写「`vol_ops.set_absolute` 只要 AVRCP CT 连上就会被注册（条件仅是

> **★ 一般化：当注释描述的是"某个外部条件满足后就会好"，而这个条件在本项目里

## F37. 两次 `Stack protection fault`：真凶是 taskLVGL 栈 7168 不够，却被 panic dump 误导去加大 ISR 栈（2026-09-22~23）★★★判读坑

### 现象

连上蓝牙后**整页重绘瞬间**（点进 SINK、`back to Main`）崩溃，两次签名一字不差：

```
Guru Meditation Error: Core  0 panic'ed (Stack protection fault).
Detected in task "taskLVGL" at 0x2f00025a (_interrupt_handler)
Stack pointer: 0x2f02b100
Stack bounds: 0x2f02a100 - 0x2f02b100    ← 差值恰好 = CONFIG_FREERTOS_ISR_STACKSIZE
```

### 排错步骤（含走过的弯路，按时间顺序）

1. **第一轮（09-22，误判）**：算 `Stack bounds` 差值 = 1536 = 当时的
   `CONFIG_FREERTOS_ISR_STACKSIZE` ⇒ 判"中断栈溢出"。修三处：
   ISR 栈 1536→4096（sdkconfig 双写）、EQ 动画按需起停、poll 副本缓冲改 static
   （后两处本身有价值，但都不是根因）。
2. **复现即警觉**：4096 已确认生效（差值变 `0x1000`），**仍崩且签名一字不差**；
   且两次 dump 的 `Stack pointer` 都**恰好等于上界** —— 真溢出（栈向下长）的 SP
   应该**低于下界**才对。回头重读 `portasm.S`。
3. **关键证据（中断入口逐行读源码）**：
   - `portasm.S:669/:673`：进中断**先把 SP 切到 `xIsrStackTop`**；
   - `portasm.S:699-709`：**再** `esp_hw_stack_guard_set_bounds(xIsrStackBottom, xIsrStackTop)`。
   ⇒ **panic dump 里的 `Stack bounds` 永远是 ISR 栈全区间、`Stack pointer` 永远是
   刚切到栈顶的值 —— 与真凶无关**。守卫中断一到，入口代码就把这两样全改写了，
   守卫处理程序读到的自然是 ISR 栈。"差值 == ISR 栈大小 ⇒ 中断栈溢出"这条判读
   **恒真、恒无信息量**。
4. **重新定位**：ASSIST_DEBUG 守卫是同步触发的——谁的 SP 越界，守卫中断立刻在
   谁的上下文接管 ⇒ dump 里被打断的当前任务 **taskLVGL** 就是肇事者。
   查 `esp_lvgl_port` 的 `ESP_LVGL_PORT_INIT_CONFIG()`：**task_stack=7168、
   `MALLOC_CAP_INTERNAL`、affinity=-1**（§9.6 DISP_DIAG 实测 7528 = 7168+TCB）。
   另排除"守卫竞态误报"：portasm 切栈/切任务前后有 `monitor_stop/start`
   （`:656`、`:844-876`），切换窗口有保护，越界是真实的。
5. **一次到位的验证**：main.c 加 5s `lv_timer` 打
   `uxTaskGetStackHighWaterMark(NULL)`（回调跑在 taskLVGL，NULL 即它自己），
   同时把 task_stack 提到 16384。实测 **HWM=9128B ⇒ 峰值已用 7256B，
   恰好越过旧上限 7168B —— 实锤**；全流程未再复崩。

### 根因

taskLVGL 的 7168B 栈（esp_lvgl_port 组件代建、内部 RAM）被
"整页构建（PageManager → 控件工厂 → 事件回调）+ bin 字体动态字形加载 +
歌词/EQ 动画渲染"的调用链，在整页重绘瞬间压穿。

### 修复

`main/app/main.c`：`bsp_display_start()` → `bsp_display_start_with_config()`，
照抄 BSP 默认 cfg 只覆盖 `lvgl_port_cfg.task_stack = 16384`（+9KB 内部 RAM）；
加栈水位诊断定时器（临时代码，观察 1~2 天后删）。
ISR_STACKSIZE=4096 保留（BT ISR 密集下 4096 比 1536 稳妥，非根因但无害）。
完整记录见 `docs/项目规划/改动记录.md` §28.31。

### 经验（本次沉淀的宝贵经验）

1. ★★★ **`Stack protection fault` 的 panic dump 定位不了真凶**：
   bounds/SP 是中断入口的快照，永远显示 ISR 栈区间 + 栈顶。
   **别再算 bounds 差值——给嫌疑任务加 `uxTaskGetStackHighWaterMark`
   水位日志，看谁贴 0**。IDF v6.1 里该 API 硬编码可用（`FreeRTOSConfig.h:217`），
   无需 sdkconfig；本移植（riscv，`portmacro.h:95`）`StackType_t = uint8_t`，
   返回值**就是字节数**。
2. ★★★ **"按'根因'修完还复现、且签名一字不差" ⇒ 先回头质疑判读本身**，
   而不是加大剂量。第一轮若顺着误判把 4096 再加到 8192，就是第三次白烧 + 白吃 4KB 内存。
3. ★ **组件代建的任务也在栈预算里，"默认值" ≠ "安全值"**：
   esp_lvgl_port 的 taskLVGL 默认 7168 只保证"能跑"；UI 加重（动态字形加载、
   动画、整页重建）后必须重估，且组件不归自己改时用
   `bsp_display_start_with_config()` 这类配置入口覆盖。
4. ★ **判读方法要先对着 port 源码校验"谁在什么时候写边界寄存器"**：
   方法建立在想当然的机制上，后面每一步推理都是空中楼阁——本轮第一轮排障
   五步里错了一步开头，错了整整一轮。
5. 反直觉小知识：**SP == 栈上界不是"溢出到顶"**（栈向下长，真溢出应低于下界），
   而是"守卫中断刚到、栈刚切到顶还没压东西"的快照。
6. 顺带修正：§28.30 的"先算 bounds 差值"判读法作废；`13_内存管理规范.md`
   §9.7 的"LVGL 渲染任务栈外置"候选已按本条以"扩容 16384"方式处理。

### 修正的一处误导性判读（存档）

`portSTACK_TYPE = uint8_t`（`portmacro.h:95`）曾被拿来当"ISR 栈按字节计"的
佐证——这一点本身没错，但它支撑不了"bounds 差值判溢出来源"的推理链，
因为 dump 里的 bounds 根本不是肇事栈的。**任何"佐证"都要挂在正确的因
果链上才有意义。**

## F38. `LINK ONLINE` 后 assert `esp_task_stack_is_sane_cache_disabled()`：F35 外置栈任务做 flash IO（2026-09-23）★★F35 边界

### 现象

设备跑着跑着（实为收到 PC 心跳瞬间）：

```
               (esp_task_stack_is_sane_cache_disabled())
```

且 **PC 端上位机以 0.2s 周期发心跳 → 设备每次重启后第一个心跳即再 ONLINE →
再崩**，形成崩溃循环（除非先关掉 PC 端再烧固件）。

### 根因（机制链完整）

1. F35 把 record_task 栈外置 PSRAM（`xTaskCreatePinnedToCoreWithCaps(..., MALLOC_CAP_SPIRAM)`）；
2. record_task 会做 **littlefs 文件操作**：ONLINE 时 link_cb 投
   `RECORD_CMD_RETRY` → `upload_pending()` 的 `fopen`（哪怕没有待传文件，
   littlefs 查找也是 flash 读）；LOCAL 落盘 fwrite / unlink 同理；
3. flash 操作要关 SPI 缓存；**关缓存期间 PSRAM 不可访问**；
4. IDF v6.1（`CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM` 开启时）在
   `spi_flash_disable_interrupts_caches_and_other_cpu()` 里
   `assert(esp_task_stack_is_sane_cache_disabled())`；
5. `esp_memory_utils.c` 的实现只检查一句话：**当前任务 SP 不在 PSRAM**。
   没有任何自动栈切换/迁移机制。

⇒ 栈在 PSRAM 的任务发起 flash 操作 = 必崩，IDF 用 assert 提前拦。

### 修复（§28.40）

record_task 栈搬回内部 RAM（xTaskCreatePinnedToCore，8192，+8KB 内部 RAM）。
全项目排查其余 PSRAM 栈任务（link_manager / udp_voice×3 / pcnow_rx /
net_time / led / audio×2 / bt_push_proc / bt_sink_proc）：
只碰 socket / GPIO / 蓝牙栈内部处理（bond 的 NVS 写在 btc_task 内部栈），
均不直接做 flash IO，无需改动。
若蓝牙开机再现 F35 症状（internal free 不足），退路是"内部栈文件工作线程"
方案 B：文件 IO 全部挪进一个 ~4KB 内部栈的 worker，队列化。

### 规则沉淀（F35 的边界条款）

- ★ **F35 的"任务栈外置 PSRAM"仅适用于纯 CPU/网络/GPIO 任务**。
  任何要做 **NVS / littlefs / flash 分区文件系统** 的任务，栈必须在内部 RAM
  （关缓存期间 PSRAM 不可访问）。SD 卡（SDMMC/SPI 独立控制器）不属于此列。
- ★ 判读技巧：assert 名字本身就是答案——
  "task stack is sane (when) cache disabled" 直接指出"谁的栈在缓存关闭时不能活"，
  结合 ONLINE 时序（谁在 ONLINE 链上做文件 IO）一步定位。
- ★ 崩溃循环识别：PC 端周期性心跳/轮询会把"一次性崩溃"放大成"每轮重启必崩"，
  排障时先切断 PC 侧触发源。

## F39. 设备"听得到、说不出"——PC→设备 UDP 音频被 WiFi 省电攒包丢弃（2026-09-23）★无线坑

### 现象

PC 端 WAV 推流/对讲下行几乎不可用。设备端 `UDP_VOICE STAT`：

```
STAT: rx=0   lost=32 bad=0  reorder=0    ← 大多数窗口：一个包都收不到
STAT: rx=349 lost=32 bad=0  reorder=0    ← 偶发：巨突发一次性涌入
STAT: rx=78  lost=30 bad=69 reorder=78    ← 突发伴随乱序/旧序号计 bad
```

不对称：设备→PC 方向（麦克风上行）正常，PC→设备方向（下行）大量丢包。

### 根因

全工程没有任何 `esp_wifi_set_ps` 调用 → STA 处于默认 **WIFI_PS_MIN_MODEM**
（调制解调器省电）：设备在 DTIM 间隔内休眠，AP 只能把发往设备的 UDP 包攒着，
DTIM 唤醒才批量下发 ——
- 攒包期间 AP 缓冲溢出 → **大量丢包**（音频 50 包/s 远超缓冲能力，心跳 5 包/s 能活）；
- 批量下发 → **突发 + 乱序**（reorder/bad 计数飙升），jitter buffer 直接被打穿。
- 不对称性由来：设备 TX 发包会即刻唤醒射频，上行不受影响。

包格式/端口/线程模型均排查无误（AUDIO_FRAME_BYTES=640 = PC PCM_BYTES；
设备 RX 绑 50001 = PC 发送端口；WavPlayer 20ms 定步发送正常）。

### 修复（§28.41）

`wifi_manager.c` 在 `esp_wifi_init()` 后加 `esp_wifi_set_ps(WIFI_PS_NONE)`：
- 设置存于 WiFi 驱动，`esp_wifi_stop/start`、STA↔AP 角色切换后仍生效，设一次即可；
- 代价：待机电流 +约 40~60mA（本设备常供电，可接受；电池产品需权衡）；
- 实时音频/低延迟链路（语音、NOW 推流、未来 OTA 拉流）都依赖此设置。

### 规则沉淀

- ★ **ESP32 做实时音频/低延迟 LAN 通信，`esp_wifi_set_ps(WIFI_PS_NONE)` 是必选项**，
  默认省电模式的表现就是"ping 正常、心跳正常，唯独持续 UDP 流大面积丢包/突发"。
- ★ 判读特征：**统计窗口 rx=0 平期 + 偶发数百包突发 + 高 reorder，且收发不对称**
  （同一条 UDP 流一个方向好一个方向坏）→ 先查 WiFi 省电，再查应用层。

## F40. 上电必崩 `Cache error`（MCAUSE 0x19）——字库大读的"cache 关窗"撞上 PSRAM 栈任务（2026-09-24）★★★F38 放大器

### 现象

上电到启动序列末尾必崩，日志停在字库加载之前：

```
I (2803) main: [boot-diag] after PageManager_Load(splash) internal free=61943 largest=31744
                | DMA free=29971 | PSRAM free=12358560
Core N panic'ed (Cache error)
MEPC: 0x2f010984   MCAUSE: 0x00000019
```

崩溃点夹在 `BOOT_DIAG("after PageManager_Load(splash)")`（main.c）与下一个
`BOOT_DIAG` 之间 ⇒ 唯一调用是 `ui_binfont_init()` 的 LittleFS `read()`。

### 根因（反汇编 + IDF 源码双证）

**证据 1 —— MEPC 那条指令是什么。** 用本机 ELF 反汇编：

```asm
2f010972:  jalr memcpy          # 把 flash 数据拷到目标
2f010984:  lw  ra,44(sp)        # ★ MEPC = 这条：函数收尾"从栈上恢复 ra"
2f010986:  lw  s0,40(sp)
```

`MEPC = 0x2f010984` 落在 `spi_flash_hal_read+0xc4`，`RA = 0x2f0109a2` 正是
"memcpy 返回后 `j 2f010984`"的下一句，完全自洽。
⇒ **出事的是一次纯 `sp` 相对访存（弹栈）** ⇒ `sp` 指向的内存不可访问。

**证据 2 —— 为什么"序言压栈没事、收尾弹栈摔"。**
`spi_flash_hal_read` 由 `chip->chip_drv->read` 调用，运行在
`spiflash_start_read()`／`rom_spiflash_api_funcs->end()` 之间。而：

```c
// components/spi_flash/cache_utils.c（ESP32-S3 版）
void IRAM_ATTR spi_flash_disable_interrupts_caches_and_other_cpu(void)
{
    spi_flash_op_lock();
    esp_intr_noniram_disable();
    spi_flash_disable_cache(0, &s_flash_op_cache_state[0]);   // ← 只有这一行
}
```

函数名里的 `and_other_cpu` 在这个实现里是**历史遗留**：它**只关 cache，并不停住另一核**；
`spi_flash_op_lock()` 里的 `vTaskSuspendAll()` 也只挂起**本核**调度器。
⇒ **cache 关闭窗口内，另一核（乃至本核被抢占后恢复的任务）照跑**；只要它访问 PSRAM
（压栈/弹栈、局部变量、参数、PSRAM 数据缓冲）就 **Cache error**。

**证据 3 —— 为什么窗口从 1 个变成 168 个。**

```c
// components/spi_flash/esp_flash_api.c:929（注释原文就是答案）
//when the cache is disabled, only the DRAM can be read, check whether we need to receive
//in another buffer in DRAM.
#define MAX_READ_CHUNK 16384
size_t read_chunk_size = MIN(MAX_READ_CHUNK, length);
do {
    err = spiflash_start_read(chip);      // ← 关 cache
    chip->chip_drv->read(chip, buffer_to_read, address, length_to_read);   // ← spi_flash_hal_read
    err = rom_spiflash_api_funcs->end(chip, err);   // ← 开 cache
    ...
} while (err == ESP_OK && length > 0);
```

`esp_flash_read()` 与目标是否在 PSRAM 无关，**恒定按 16KB 分块**。
字库 2 744 120 B ⇒ **约 168 个"cache 已关"的窗口**（旧版 1 879 788 B ⇒ 115 个，+46%）。

**证据 4 —— 窗口打开时，谁在 PSRAM 上跑。** `main.c` 的启动顺序决定了：

```
fs_service_mount → bt_ctrl_init → bt_push_early_init(local2bt_task,PSRAM栈)
→ bt_sink_early_init(bt2codec_task,PSRAM栈) → bsp_display_start → audio_task(PSRAM栈)
→ led_task(PSRAM栈) → wifi → link_manager(PSRAM栈) → udp_voice×3(PSRAM栈)
→ record_task(内部栈✓) → pcnow_rx(PSRAM栈) → PageManager_Load(splash)
→ ui_binfont_init()  ← 168 次关窗就落在这里
```

即：**字库大读发生时，系统里同时有 8 个以上 PSRAM 栈任务在跑**
（`CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y` + `CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y`
⇒ F35 的"栈外置 PSRAM"是真生效的）。窗口 × 访问者 ⇒ 上电必崩。

### 为什么是"这一轮"才崩

`littlefs_content/fonts/lv_font_cjk_28.bin` 从 1 879 788 B 扩到 2 744 120 B（+韩文+标点，§28.35）
⇒ 关窗次数 115 → 168，且单次读持续更久。
叠加同期改动（新增 `pcnow_rx` PSRAM 栈任务、`WIFI_PS_NONE` 让网络活动更密、record 进度上报 1s→200ms），
把"偶发撞车"推成了"上电必崩"。**根因是既有设计缺陷，字库变大只是放大器。**

### 修复（§28.48）

把字库加载**拆成两段**，让"读 flash"发生在**所有 PSRAM 栈任务诞生之前**：

| 阶段 | 函数 | 位置约束 |
|---|---|---|
| 1/2 读 | `ui_binfont_load()` | **紧跟 `bsp_i2c_init()`** —— 此刻只有 IDLE/esp_timer/ipc/sdmmc 等内部栈任务，taskLVGL 尚未创建 |
| 2/2 解析 | `ui_binfont_attach()` | 紧跟 `bsp_display_start_with_config()` —— 需要 `lv_init()`，纯 RAM 无 flash IO |

✦ 关键：**"读"只需要 POSIX `stat/malloc/open/read`，不依赖 LVGL**；只有
`lv_binfont_create_ex()` 需要 ⇒ 所以两段可以分离，无需改动 BT 初始化顺序、
无需动分区表、零额外 RAM 代价。代价仅是黑屏时间多出约 2s。

### 规则沉淀

- ★★ **`spi_flash_disable_interrupts_caches_and_other_cpu()` 只关 cache，不停另一核。**
  所以判据不是"我的栈在不在 PSRAM"，而是"**此刻系统里还有谁可能在 PSRAM 上跑**"。
  F38 的 assert 只检查发起方当前任务栈 ⇒ 它**保护不了另一核**，表现为 Cache error 而非 assert。
- ★★ **任何"大文件从 flash 读进 PSRAM"都是一个巨大风险源**：次数 = 字节数/16KB。
  要读就放在**启动最早期**（无 PSRAM 栈任务时），或改走 memory-mapped 读（不关 cache）。
- ★ **Cache error 的 MEPC 若落在 `spi_flash_hal_*` 的"函数收尾弹栈"上**，可直接判定
  = "发起这次 flash 访问的上下文，栈在 PSRAM"，不必再猜。
- ★ **§28.40 的"全项目 PSRAM 栈任务排查"结论有漏项**，仍存活的违例（待处理）：
  - `audio_task`（`audio_service.c`，栈 `MALLOC_CAP_SPIRAM`）→ `handle_play_file()`/
    `handle_record_file()` 里 `fopen/fread/fwrite/fseek` —— **PSRAM 栈 + littlefs 读写**；
  - BT Push 的 GMF `local2bt_task` / Sink 的 `bt2codec_task`（`stack_in_ext = true`，
    见 `esp_gmf_oal_thread.c`）→ `local2bt_task` 的输入是 `io_file`（读 MP3）。
  ⇒ 只要再次出现"录音落盘 / NVS 写 / littlefs 元数据写"与它们并发，F38 家族还会复发。
    长期正解：**把有 flash IO 的任务栈全部收回内部 RAM**（F35 的"栈外置"边界需重新收紧）。

## F41. 三个"看起来各自独立"的 1 秒级怪症，其实是三处"约定不一致"（2026-09-24）★★★自检盲区

**用户报告（同时发生，容易被当成一个 bug）**：
1. 按播放/暂停键，PC 端音乐**不暂停**（PC trace 里 3 次全是 `NOW_CMD <- play` → `SMTC -> play`，没有一次 pause）；
2. PC 与设备的进度条都**在 0 和 1 秒之间反复**，永远到不了实际已播时长 ⇒ 设备歌词永不滚动；
3. 设备日志持续 `W PCNOW: lyrics parse failed len=5336 head={"k": "be29c0c5", "ver": 1, ...`。

**三个根因互不相干，但都是"两端/两套 API 的约定没对齐"：**

### 根因 A（按钮）：`lv_event_get_user_data` ≠ `lv_obj_set_user_data`

`tab_pcnow.c` 创建按钮时把命令字挂在**事件**上：

```c
lv_obj_add_event_cb(btn, media_btn_cb, LV_EVENT_CLICKED, (void *)cmd);   /* "play" 字面量 */
...
static void media_btn_cb(lv_event_t *e) {
    const char *cmd = (const char *)lv_event_get_user_data(e);           /* 永远拿到 "play" */
```

而播放态切换时改的是**对象**上的另一份存储：

```c
lv_obj_set_user_data(s_btn_play, info.playing ? "pause" : "play");       /* 白改 */
```

LVGL 里这是两个独立字段：`lv_event_get_user_data()` 读 `lv_event_dsc_t::user_data`（注册时固定），
`lv_obj_set_user_data()` 写 `lv_obj_t::user_data`（`lv_obj.c:1403`）。所以**图标会正确翻转成"暂停"，
但点下去发的永远是 `play`**；而 `try_play_async()` 对已在播放的会话是**空操作** ⇒ 点了毫无反应。

> 为什么 §28.45 没抓到：那次 4 连 `play` 被归因于"`_is_playing` 修好前 PC 恒上报 playing=false"，
> 修完 `_is_playing` 后**这个问题依然存在**——命令字来源根本是另一处。

### 根因 B（进度）：`tl.position` 是 `timedelta(0)`，**不是 `None`**

§28.46 的注释与代码写的是：

```python
pos_known = tl.position is not None          # ← 前提错了
```

实测（`.workbuddy/probe_posknown.py`，winsdk 真机）：

```
position     = datetime.timedelta(0)      ← 不是 None
end_time     = datetime.timedelta(0)
last_updated = datetime.datetime(1601, 1, 1, 0, 0, tzinfo=utc)
>>> 旧判据 tl.position is not None = True     新判据 _timeline_usable(tl) = False
```

网易云与 B 站的 SMTC 时间轴都是"**有轴但零值**"。于是 `pos_known=True` ⇒ pusher 每秒收到
`pos=0` 打点、`_pos_at` 被反复刷新 ⇒ `_interpolated_pos() = _pos + (now - _pos_at)` 永远落在
**0~1 秒**内。PC 本地 UI 与设备端**读的是同一份 `_pos`**，所以两边一起坏。
（`.workbuddy/probe_pusher_clock.py` 里 [A] 段 2.5s 内 pos 恒 0.000，[B] 段修复后 0.5s/拍正常推进。）

### 根因 C（歌词）：调用方用"最后一个字节"当 NUL，正好抹掉 JSON 收尾 `}`

`http_get()` 读满后**不写终止符**，调用方于是自己写：

```c
body[body_len - 1] = '\0';      /* 把 json.dumps 输出的最后一个 '}' 换成 NUL */
```

PC 端 `http_server.py` 返回的是 `json.dumps(...).encode("utf-8")`，**结尾就是 `}`**、带
`Content-Length`、无 NUL。头 48 字节全是合法 JSON（`{"k": ...`），收尾却断了 ⇒ `cJSON_Parse` 恒失败。

> 为什么 §28.47 没抓到：当时在 PC 上 `curl /lyrics.json` 拿到的是**完整合法 JSON**（走回环，
> 且 curl 自己会补 NUL）——**本机验证天然照不到设备端那一行越界改写**。

**修复**（4 个文件）：

| 文件 | 改动 |
|---|---|
| `main/ui/tabs/tab_pcnow.c` | `media_btn_cb` 改从 `lv_event_get_target(e)` + `lv_obj_get_user_data()` 取命令字（保留注册值兜底）；`media_btn_create` 里同时 `lv_obj_set_user_data(btn, cmd)` |
| `main/middleware/network/pcnow_service.c` | `http_get` 分配改 `HTTP_BUF_MAX + 1` 并 `buf[total] = '\0'`（**终止符由本函数负责**）；`lrc_fetch` 删掉 `body[body_len - 1] = '\0'` |
| `pc_host/pcnow/smtc.py` | 新增 `_timeline_usable(tl)`：`last_updated.year > 2000` ∨ `end_time > 0` ∨ `position > 0` 才算"有时间轴"；`pos_known` 改用它 |
| `pc_host/pcnow/pusher.py` | META 判重键加曲长 `(title, artist, int(dur))` ⇒ 解析拿到真实曲长后立即补发一拍，不必干等 3s 周期 |

**验证**：`esp-idf-syntax-check` 两 C 文件 `[OK]`；`py_compile` 通过；
`probe_posknown.py` 真机确认新旧判据结论相反；`probe_pusher_clock.py` 确认 [A] 恒 0 / [B] 推进 /
[C] 暂停固化不归零 / [D] resume 从固化点续走。

### 规则沉淀

- ★★ **LVGL 的"事件 user_data"与"对象 user_data"是两个存储**，混用会静默失效：
  图标对、日志对、就是行为不对。要"随状态改命令字"必须存在**对象**上并在回调里
  `lv_obj_get_user_data(lv_event_get_target(e))` 取。
  （`page_wifi.c` 恰好两处都设了值，所以那边一直正常 —— 属于"运气对了"，别当范例。）
- ★★ **"自述前提"必须实测**：§28.46 把 `position` 当 `None`、§28.47 用本机 curl 验设备端拉取，
  两次都"逻辑自洽但照不到真相"。凡涉及**对端 SDK 的字段语义**（None / 零值 / 枚举），
  一律写一次性只读探针打真值，不靠推断；凡涉及**设备端解析**，本机 curl 不能作为证据。
- ★ **"本机自己能过"不等于"设备能过"**：回环请求、SSH 终端、curl 都会补齐/掩盖边界差异
  （NUL 终止、Content-Length、代理劫持）。判据要用**同一条链路**复现。
- ★ **越界一字节的"补 NUL"是经典地雷**：谁分配谁写终止符，调用方不得改写最后一个字节。

## F42. 通话"下行扬声器无声"——5 个 codec 对象共享一份 I2S enable 位（2026-09-24）★★ 静默失效家族

### 现象

通话（UDP 对讲）建立时：

```
I (139492) BT_SINK: yield codec to 16k session
E (139493) I2S_IF: Current mode record   conflict sample_rate 16000 with peer mode sample_rate 44100
E (139515) I2S_IF: Current mode playback conflict sample_rate 16000 with peer mode sample_rate 44100
I (1395xx) Adev_Codec: Open codec device OK      ← 还打印 OK！
I (1395xx) AUDIO_SVC: stream started, 16k/mono/20ms core=1
```

**BT 已经让位了，16k 的 `set_fmt` 却还是撞 44.1k** ⇒ I2S 停在 44.1k，
16k 的 PCM 灌进 44.1k 管道 ⇒ **下行扬声器听不到**。旁证：`MIC_RMS frames=552/2s`
（≈276 帧/s）而 16k/20ms 应是 100 帧/s ⇒ **I2S 实际确实没切到 16k**。

### 根因：不是"没让位"，是"让位让不干净"

BSP 的 `bsp_audio_codec_speaker_init()` / `bsp_audio_codec_microphone_init()`
（`bsp_audio.c:97/145`）**每调用一次就新建一个** `esp_codec_dev` 对象
（`i2c_ctrl_if` / `es8389_codec_if` / `esp_codec_dev_new()` 全是新建），
但两者拿到的 `data_if` 都是 BSP 里**同一个 `static i2s_data_if`**（`bsp_audio.c:39`）。

而本工程有 **5 个**这样的对象：

| 对象 | 出处 | dev_type |
|---|---|---|
| `spk_codec_dev` | `audio_service.c:87` | OUT |
| `mic_codec_dev` | `audio_service.c:92` | IN |
| `s_codec` | `bt_sink_service.c:534` | OUT |
| `s_codec` | `tab_audio.c:131`（每次进页面新建） | OUT |
| `s_codec` | `tab_video.c:176`（每次进页面新建） | OUT |

于是状态被劈成两半：

- **共享**（在 `i2s_data_t` 里）：`in_enable` / `out_enable` / `fs` / `in_fs` / `out_fs`；
- **每对象私有**（在 `codec_dev_t` 里）：`input_opened` / `output_opened`。

只要出现一次**非对称**的 open/close，共享的 enable 位就与对象状态脱节：

- `esp_codec_dev_close()`（`esp_codec_dev.c:503`）第一句就是
  `if (output_opened == false && input_opened == false) return OK;`
  ⇒ **提前返回，根本不调 `data_if->enable(caps,false)`**；
- `esp_codec_dev_open()`（`:147`）同样在 `input_opened||output_opened` 时提前返回
  ⇒ **既不 `set_fmt` 也不 `enable`**。

而冲突会被**完全静默**：`check_fs_compatible()`（`audio_codec_data_i2s.c:433`）的
"快速分支"要求**对端通道 enable==false** 才把新 fs 直接写进去；脱节的 enable 位让它走
冲突分支返回 `ESP_CODEC_DEV_NOT_SUPPORT`，但 `esp_codec_dev_open()` **不检查
`data_if->set_fmt` 的返回值**（`esp_codec_dev.c:178`）⇒ 照常往下走、照常打印
`Open codec device OK`。**"open 成功"完全不能证明配置生效。**

### 修复

`main/middleware/audio/audio_service.c`：

1. 新增 `force_reset_shared_i2s()`：**不依赖任何 `esp_codec_dev` 对象的状态**，
   直接对共享 `data_if` 把两路都 `enable(..., false)`（幂等）。
   顺序**先 OUT 再 IN** —— S3 系列在"RX 还开着"时 disable TX 会被挂成
   `out_disable_pending`（`audio_codec_data_i2s.c:565+`），先关 OUT 可避开。
2. `audio_stream_start()` 里 `bt_sink_service_audio_yield()` 之后依次：
   `esp_codec_dev_close(mic_codec_dev)` → `esp_codec_dev_close(spk_codec_dev)`
   → `force_reset_shared_i2s()` → 再 open 两个 16k。
   第 2 步的两个 close 是为了绕开 `esp_codec_dev_open()` 的"already open"提前返回。
3. 版本标记：`stream started, 16k/mono/20ms core=1 (rev F42: shared I2S reset)`。

**修复后的日志签名**（用来判断是否真的生效）：

```
I I2S_IF: Paired data: 0x..., current mode: record, paired in_enable: 0, paired out_enable: 0
I I2S_IF: Current mode(playback) and peer mode have same sample_rate 16000, channel 2, bits_per_sample 16
```

**验证**：`esp-idf-syntax-check` → `[OK]`（`-Wall -Werror`，真编译器 `-fsyntax-only`）。

### 规则沉淀

- ★★ **"open 成功"不等于"配置生效"**：只要上层不检查 `set_fmt` 的返回值，
  采样率冲突就是**静默失效**。凡"开了却没声/变调"，第一件事是查驱动侧有没有打
  `conflict sample_rate` 这类日志，而不是怀疑数据通路。
- ★★ **共享总线的 enable/opened 状态被劈成两半时，"让位"必须是"总线级复位"，
  不能是"我把我这个对象关掉"**：同一份硬件状态有 N 个句柄视图，就得有一个
  **不依赖任何视图**的复位入口。
- ★ **同一驱动被多处 `_init()` 时先查它是不是"新建对象"**：BSP 的
  `bsp_audio_codec_*_init()` 看着像单例，实际每次都 `esp_codec_dev_new()`；
  只有 `i2s_data_if` 是 `static` 缓存。**"看着像单例"的 API 必须读实现**。
- ⚠ **遗留结构隐患（未做）**：5 个对象共享一份 enable 状态这件事本身还成立。
  彻底解应统一为**单一 codec 实例**（`codec_bus` 单例 + 引用计数），
  把 `esp_codec_dev_open/close` 收敛到一个所有者。

## F43. 网易云 PC 的播放位置真值只在"进度 DOM 文本"里（2026-09-24）★★ 认知修正

### 背景

F41-B / §28.46 的结论是"网易云 SMTC 时间轴是**零值死轴**，只能本地内插"。
当时怀疑过"是不是 winsdk 投影坏了"。出于"要能校准锚点"的诉求，做了 P1：
试试网易云 CEF 的 `--remote-debugging-port=9222`。

### 实测（真机，Chromium 91 / NeteaseMusicDesktop 3.1.40.205461）

```
/json/version → {"Browser":"Chrome/91.0.4472.169", "Protocol-Version":"1.3"}
/json/list    → 唯一 target: type=page, url='orpheus://orpheus/pub/app.html'
```

能连上 CDP 之后逐项排查"位置到底在哪"：

| 来源 | 实测 | 结论 |
|---|---|---|
| `<audio>` 元素 | `currentTime=0, duration=0, paused=true, src=""` | **恒为 0**，不可用 |
| `navigator.mediaSession.playbackState` | `"none"` | **恒为 none**，不可用 |
| `document.querySelectorAll('iframe').length` | `0` | 没有跨 frame |
| **进度 DOM 文本** | `"00:06 / 04:02"` → 5s 后 `"00:11 / 04:02"` | ✅ **唯一真值** |

`t1.sec=6, t2.sec=11, dur=242` —— **5 秒过去正好 +5 秒**，判定 `ADVANCING=True`。

### 结论（认知修正）

- ★★ **SMTC 死轴不是 winsdk 的问题，是网易云真的没提供**：它既不走 `mediaSession`、
  也不更新 `<audio>` 的时间轴（自绘播放器 + 自己的音频通路）。
  ⇒ 以后遇到"SMTC 只有状态没有进度"，**先怀疑对方应用没实现，再怀疑 SDK**。
- ★★ **CEF 应用（网易云/B站 PC）只要开放 DevTools，就等于给我们开了一个"应用内部状态"
  的只读窗口** —— 比 UIA/MSAA 稳、比截图 OCR 准，且**不需要窗口可见/不最小化**。
- ★ **定位节点不要用类名**：`StyledSliderContainer_smigcsb` 这种带构建 hash 的类名随时会变；
  用**文本形状**（`^\d{1,2}:\d{2}\s*/\s*\d{1,2}:\d{2}$`）遍历 `div,span,p,label,time`，
  取**最深**命中的那个（祖先的 `textContent` 会包含子孙，只取最深才是最小完备节点）。
  性能上扫 `textContent`（不走 layout），只在命中节点上取一次 `innerText`。
- ★ **本机 `127.0.0.1` 也会被 Clash 劫持**：环境里 `http_proxy=http://127.0.0.1:12635`，
  urllib 默认走它 ⇒ 连本地 DevTools 端口都失败，报 `upstream connect failed ... 10061`。
  必须 `ProxyHandler({})`（curl 用 `--noproxy '*'`）。**WS 用裸 socket 天然免疫。**

  `pc_host/restart_cloudmusic_debug.bat`（带端口重启 + 自检）、

## F44. 副屏三连症：闪退 / 封面解码失败 / UDP 丢包率高 —— 三个"位置放错"（2026-09-24）★★★

用户现象三连：① 设备端按"下一首"，PC 上位机**闪退**；② 日志刷屏
`JPEG_DEC: JPEG segment format error` + `PCNOW: cover decode failed (80779989) len=98304 head=1400005014000050`；
③ "PC 端一直在发封面和歌词，UDP 丢包率很高"。三个**根因互不相同**，但都是"东西放错了位置"。

### F44-A 闪退：跨线程直接碰 Qt widget（**最严重**）

`main.py:Ctx.pcnow_log()` 会被 **SMTC asyncio 线程 / pusher 线程 / CDP 线程 / 网易云解析线程**
同时调用；旧实现把它接到 `PcNowPage.append_log` → `QPlainTextEdit.appendPlainText` 上。
**从非 Qt 线程碰 widget 是 Qt 未定义行为**，典型触发点正是"按下一首"：一次换曲连炸
5~6 条日志（`NOW_CMD <- next` / `SMTC -> next` / `track: …` / `解析: …` / `lyrics: …` /
`进度走 CDP 真值 …`），**来自 3 个不同线程** ⇒ 随机闪退。

- 判据/旁证：同工程的 `call_page.py` 本来就是**对的** ——
  `ctx.asr.on_text = lambda t: self._asr_q.put(t)`，由 100ms 的 QTimer 在 Qt 线程里排空。
  副屏这条是唯一违例，属于"抄错了邻居"。
- 修法：`Ctx.pcnow_q`（`queue.Queue(maxsize=4000)`），`pcnow_log()` 只 `put_nowait`（满则丢弃，
  **绝不阻塞工作线程**）；`PcNowPage._poll()` 每拍最多搬 40 行进来落笔。
  `main_window` 构造期补历史日志仍可直接写（那时本就在 Qt 线程）。
- ★ 通用规则：**工作线程只投队列，落笔只在 Qt 线程**。凡是"某操作一触发就闪退"，
  先搜"哪个回调跨线程碰了 widget / QPixmap / QPainter"。

### F44-B 封面解码失败：**诊断本身是错的**（先 free 再读）

`cover_fetch()` 的失败分支里读 `jpg[0..7]` 打 `head=`，但 `heap_caps_free(jpg)` **写在它前面**：

```c
    if (dec) { jpeg_dec_close(dec); }
    heap_caps_free(jpg);                     /* ← 先释放 */
    if (!ok) {
        for (int i = 0; i < 8; i++) snprintf(..., "%02x", jpg[i]);   /* ← 再读 = UAF */
```

⇒ `head=1400005014000050` 是**空闲块被写回的链表信息**，不是收到的字节。
这条"证据"把排查方向彻底带偏（我一度据此断言"PC 发出来的不是 JPEG"，而实测
`?param=240y240` 出来的是 5~13KB 合法 JPEG：`ff d8 ff e0` 开头）。

- ★ 规则：**诊断打印绝不能晚于资源释放**。`head` 这种"只看一眼"的日志最容易被塞到
  释放之后，因为作者觉得"无所谓"。它一旦错，比没有更坏。
- 修法：改成逐级定位原因（非 JPEG / open 失败 / 头解析失败 / **尺寸超限** / process 失败），
  并把 `len>=HTTP_BUF_MAX` 显式标成"★正好顶到 96KB 上限=抓取被截断"，
  再加一条"解码器读到的尺寸 = WxH（超 240 就是 CDN 没按 param 缩）"。
- 真正的数据侧修法见 F44-C。
- 附带：`RGB<->BGR` 交换原本写在 `if` 块中间，**失败路径也会把 `dst->rgb` 改坏**；
  已挪到确认成功之后。

### F44-C 频率/UDP丢包：阻塞 HTTP 跑在 **UDP 收包任务** 里

`handle_meta()` 里**直接** `http_get()` 抓封面/歌词，而 `handle_meta` 是 `rx_task`
（UDP :50004 收包任务）调用的。抓一张封面在 WiFi 上要几百 ms~数秒，这期间 `select/recv`
不被服务 ⇒ lwIP 收包缓冲溢出 ⇒ **META/PROG 成片丢**。现象正是"心跳正常，但进度/歌词/
封面时好时坏"。而且失败后 `s_cover_want` 被清空，PC 每 3s 一拍 META ⇒ **每 3s 重下一张
大图，无限重试** —— 这就是"发得太频繁 + 丢包率高"的完整闭环。

- 一句话：**UDP 收包任务里做任何阻塞 IO，等于自己丢自己的包。**
- 修法（双侧）：
  1. **设备端拆任务**：`rx_task` 只解析 JSON + 登记 `s_lrc_want`/`s_cover_want`；
     新增 `fetch_task`（栈在**内部 RAM**，跑 lwIP/cJSON/JPEG 解码）独占阻塞 IO。
  2. **设备端加上限**：同一 hash 连续失败 `FETCH_MAX_TRIES=3` 次即放弃本曲（换曲清零）。
  3. **PC 端"就绪才宣告"**（★ 这条最关键）：`cover`/`lrc` 字段只在 TrackStore 里**真的
     有这份数据**时才填 hash，否则填空串。从源头消掉"换曲瞬间凭 hash 去拉必然 404"
     的竞态，设备端**每首歌恰好各拉一次**。
  4. **PC 端 META 限 >=1Hz**：`sync_src` 会在 `dom`/`event` 之间抖，只判"key 变了就发"
     会给设备端打出一串无意义 META。
  5. **PC 端封面归一化**：`_shrink_cover()` 用 Pillow 压到 ≤240x240 且 ≤64KB。
     本来合格（≤240px 且 ≤64KB）就**原样透传**，不重编码、不掉画质。
     `?param=240y240` 是网易客户端约定，CDN 一旦没照办，PC 拿到 120~200KB+ 原图 ⇒
     设备端同时踩"撞 96KB 上限被截断"+"尺寸超 240 被拒"。
  6. **NOW_LRC 自动闭嘴**：PC 侧 `http_server` 在 `/lyrics.json` 200 命中时
     `store.mark_lyric_pulled(h)`，pusher 之后不再推单行 —— 全量歌词（v1.1）到位后，
     每换一行再 UDP 推一次是纯冗余。

### 验收（离线，`py_compile` + 真编译器 + 闭环探针）

- `pcnow_service.c` 过 `esp-idf-syntax-check` `[OK]`（含 `-Werror=all`）。
- `.workbuddy/probe_meta_gating.py`：拦下 `_send`、关掉联网解析，三相全 PASS ——
  只就绪歌词时 `lrc=h/cover=""`；补上封面后自动补发 `cover=h` 且 META ≤1Hz；
  `mark_lyric_pulled()` 之后 `NOW_LRC` = 0 条而 `NOW_PROG` 照推。
- `.workbuddy/probe_cover_bytes.py`：确认 `?param=240y240` 出来的是 5~13KB 合法 JPEG
  （原图 120~200KB+），`_shrink_cover` 三分支实测（透传 / 800x800→240x240 625B / 502 文本被拒）。
- **实机验收通过（2026-09-24，用户确认）**：`cover ready 240x240 (xxxx) NNNB`、
  **不再出现** `cover decode failed`、换曲后 META 只带已就绪的 hash、设备端无
  `heartbeat timeout`、按下一首 PC 不闪退。（判据原文保留，作为回归基准。）

## F45. 歌词"一直停在最后一句"——单位契约不一致 + 缓存键选错（2026-09-24）★★★

### 现象

设备端副屏**三行歌词从不随进度变化**，永远显示最后几句；进度条/曲名/封面都正常，
`lyrics ready: 50 lines (177a5a26)` 说明歌词**已经拉到了**。第一反应容易怀疑
"CPU 跑满导致 UI 不刷新"，实测**完全无关**。

### 两条链路，各坏一处（任一条好都不会出这个现象）

设备端取当前行有**两条路**，优先级：

```
① PC 的 NOW_PROG.line  （PC 端已做迟滞，切行最稳）
② 本机 lrc_find_locked(pos_ms) 二分  （line 越界/缺失/刚 seek 完时的退路）
```

**根因 A：单位契约不一致 ⇒ ②这条路恒返回最后一行**

| 来源 | `t` 的单位 |
|---|---|
| ICD §7.3 `GET /lyrics.json` 定义 | **毫秒** |
| 设备端 `t[k] = (uint32_t)jt->valuedouble` | 毫秒 |
| C# agent `tools/pc_now_agent/Program.cs` | 毫秒（`int pos = (int)PosNow()` 与之比较） |
| **PC(Python) `netease.parse_lrc`** | ❌ **秒**（`t = 分*60 + 秒`，float） |

`http_server.py` 是**原样序列化**（`{"t": t, ...}`），于是设备端把 4.2s 存成 **4ms**。
`s_lrc_t[]` 变成 `[4, 12, 30, 65, 200]`，而 `pos_ms` 是 5 位数 ⇒
`if (s_lrc_t[mid] <= pos)` **恒真** ⇒ 二分退化为**永远返回最后一行**。

**根因 B：`pusher._lyr_times()` 缓存键只用 hash ⇒ ①这条路全曲失效**

```python
def _lyr_times(self, h):
    if h != self._lyr_hash:          # ← 只比 hash
        td = self.store.get(h)
        self._lyr_hash = h
        self._lyr_ts = [x[0] for x in td.lyrics] if (td and td.lyrics) else []
    return self._lyr_ts
```

换曲后**第一个 tick**（50ms 内）网易云还没解析完，`store.get(h)` 是 `None` ⇒
缓存被写成 `hash=<新hash> / ts=[]`。2~5s 后歌词到位，**hash 没变** ⇒ 永远命中这张
空表 ⇒ `_line_for()` 恒 `-1` ⇒ **`line` 通道全曲失效**。

连带效应：NOW_LRC 回退通道的发送条件是
`if (line >= 0 and ... and self._lyr_ts and not self.store.lyric_pulled(h))`，
`self._lyr_ts` 为空 ⇒ **也永不发**。⇒ 设备端收不到任何行号，只剩根因 A 那条坏二分。

> ★ 这就是为什么"两条路都要修"：B 把 A 暴露出来，A 让 B 的缺席变得致命。
> 只修一条，现象会从"定在最后一句"变成"偶尔对、seek 后错"。

### 修复

1. **PC 统一毫秒**（对齐 ICD，不再有两套语义）：
   - `netease.parse_lrc()` → `lines.append((int(round(sec * 1000)), text))`；
   - `pusher._line_for(pos_ms, h)` + `_interpolated_pos()` 传 `int(round(pos * 1000))`；
   - `ui/pages/pcnow_page.py` 本地预览 `x[0] <= pos * 1000`；
   - `http_server` 的 `/lyrics.json` 与 `pusher` 的 `NOW_LRC.t` 都是**原样透传**，
     只要 `parse_lrc` 改对，两处自动正确。
2. **缓存键改成 TrackData 对象身份**：`if td is not self._lyr_obj:`。
   对象身份天然覆盖"同 hash 后来才有数据"和"同 hash 被重新解析（`store.put` 换对象）"
   两种情形，且每 tick 一次 `dict.get` 的开销可忽略。
3. **设备端加单位哨兵**（不静默）：`lrc_fetch()` 落库前判
   `k >= 2 && s_duration_ms >= 60000 && t[k-1] <= 3600` ⇒ 打 `ESP_LOGW` 点名
   "t 单位错，已 ×1000 纠正"。判据极紧（真毫秒下末行必为 10^5 量级），不可能误伤。
4. **换曲连 `s_lrc_hash`/`s_cover_hash` 一起清**：它们既是"已持有"标记又是 want 登记的
   判重键，只 `lrc_free_locked()` 而不清 hash，遇到"标题抖动/同曲重播"就是
   **数组已释放、又永不重拉**的静默死状态。

### 规则沉淀

- **跨端字段的"数量级契约"必须在文档里写死单位，并在**接收端**放哨兵**
  （判"量级明显不对"比判"值等于多少"稳）。ICD 写对了也挡不住实现方跑偏。
- **缓存键要选"能区分数据是否就绪"的东西**。用 hash 这种"逻辑标识"做缓存键时，
  必须额外检查值是否为空——"空值被缓存"是这类 bug 的唯一形态。
- 同一语义在四个实现（ICD/Python/C#/C）里各写一遍时，**改一处必须全量 grep 单位**。
  本次已把"改动单位时要同步核对的 5 个文件"写进 `parse_lrc` 的 docstring。

## F46. 副屏顶栏"被 tab 栏压住"——其实是**被父对象裁掉**（2026-09-24）★★

### 现象

设备端 PC 副屏左上角的"● PC NOW 在线"那一行，看起来像被上面的 tab 切换栏压住了
（文字上半截不见）。tab 栏本身只有 48px 高，而状态点标称在 y=60，按说不该重叠。

### 根因：不是"压"，是"裁"

`lv_tabview_add_tab()` 返回的**"页"对象**被默认主题加了 `pad_normal`
（`lv_theme_default.c:774`，`PAD_DEF = LV_DPX(...)`，实机约 13px）。
而 LVGL 9 **总是把子对象裁到父对象边界内**（没有 `OVERFLOW_VISIBLE` 了）。

旧代码：

```c
s_media = lv_obj_create(parent);
lv_obj_set_size(s_media, BSP_LCD_H_RES, BSP_LCD_V_RES - 48);  /* 800x432 */
lv_obj_align(s_media, LV_ALIGN_BOTTOM_MID, 0, 0);              /* 顶边 = 480-432 = 48 */
```

`BOTTOM_MID` 是按**页的内容区**（已扣掉 padding）对齐的，所以
`s_media` 顶边 = 页内容底 - 432 = (480-13) - 432 = **35**，比页对象顶边（48）**高出 13px**
⇒ 上面这 13px 连同里面的东西一起被裁掉。

压死骆驼的是第二步：顶栏状态文字"在线"用的是 **bin 字体（行高 52）**，却用
`lv_obj_align_to(s_state_lbl, hdr, LV_ALIGN_OUT_RIGHT_MID, ...)` 挂在
**行高只有 14 的 montserrat_14** 上 ⇒ 它的盒顶 = `hdr 中线(≈67) - 26 = 41`（绝对坐标），
相对 `s_media` 是 **-7**，再叠加页对象那一刀 ⇒ 上半截彻底没了。

### 规则沉淀

1. **给 tabview 的页建子对象，永远不要在页上写死尺寸 + 用 `*_MID`/`BOTTOM_*` 对齐。**
   正确写法：`lv_obj_set_size(child, LV_PCT(100), LV_PCT(100))` + `lv_obj_set_pos(child, 0, 0)`
   —— 子对象落在父对象**内容区**原点，天然贴合，任何主题内边距都不会被裁。
2. 需要绝对像素布局时，从 `BSP_LCD_*` **减去页对象四边 padding** 得到可用区，
   所有坐标都从它派生：
   ```c
   const int W = BSP_LCD_H_RES - lv_obj_get_style_pad_left(p, LV_PART_MAIN)
                                - lv_obj_get_style_pad_right(p, LV_PART_MAIN);
   ```
3. **不同字号的标签互相 `ALIGN_OUT_*` 对齐时，几乎一定会有一个伸出父对象。**
   本字体 ascent 37 / descent -15 ⇒ 行高 52，挂在 montserrat_14 上时盒顶会比对方高 ~19px。
   要么给整行单独定"视觉中线"，要么把大字号标签改锚到行首（`TOP_LEFT`）。
4. **纵向预算要早算**。406px 可用高度里装不下
   「顶栏 52 + 封面 176 + 时间行 34 + 歌词 3×52」= 418。
   结论：**歌词贴底、封面吃余量**（`cover_box = ly_top - gap - COVER_Y`，夹在设计上下限之间），
   而不是两边都写死。

歌词不压封面、时间行不压歌词 ⇒ **90 PASS / 0 FAIL**。

## F47 ★★ 歌词补偿"改了宏却看不出变化"——两条取行路各走各的（2026-09-24）

**现象**：实机实测设备端高亮行比 PC 端**晚 1.25s**（恒定偏置，不抖动）。

**成因（两层）**

1. **表层**：链路里有一个**固定偏置** —— PC 的 SMTC/内插位置滞后于听感，再叠上
   `NOW_PROG` 只有 1Hz、行号在两拍之间不刷新。偏置恒定 ⇒ 设备端加个常数就能补。
2. **深层（真正的坑）**：设备端取行有**两条路** ——
   ① `NOW_PROG.line`（PC 算好、做过迟滞）　② 本机按 `pos_ms` 二分。
   原实现是"①有值就优先"。于是：
   - 只在 ② 上乘 `pos + LEAD` ⇒ **正常播放时永远不生效**，现象是"改了
     `PCNOW_LYR_LEAD_MS` 毫无变化"；
   - ① 的行号是 PC 按**未补偿**的位置算的，而行号**不是时间** ⇒ 设备端**没有任何
     办法**给它加时间偏移。
   ⇒ 想让提前量落地，必须让**本机二分拿回主导权**。

**修法**（`pcnow_service.c`）

```c
#define PCNOW_LYR_LEAD_MS 1250            /* 实测标定值；换播放器可能不同 */
static uint32_t lyr_pos_locked(void) {    /* 钳到曲长 */
    return min(pos_now_locked() + PCNOW_LYR_LEAD_MS, s_duration_ms);
}

/* get_info：取更靠后者 */
idx = MAX( lrc_find_locked(lyr_pos_locked()),          /* 带提前量 */
           (0 <= s_prog_line < s_lrc_count) ? s_prog_line : -1 );  /* 未补偿+迟滞 */
```

取 `MAX` 而不是"无脑用本机值"，是为了**保住 PC 侧 `_stable_line` 的迟滞价值**：

| 情形 | 谁更大 | 结果 |
|---|---|---|
| 正常播放 | 本机（领先 1250ms，且 PC 行号只 1Hz 刷新、天然落后连续内插） | **提前量真正落地** |
| 位置突然回退（网易云死轴 + CDP 重锚） | PC（那个值做过迟滞） | **不回跳** |
| seek | 两条路一起退，最多保持 1 拍 | 与改前一致 |

**为什么不能改在 PC 侧**：`pusher._interpolated_pos()` 是 PC 自己的副屏预览与推送
**共用**的，在 PC 侧加提前量会把 PC 自己的显示也一起推早。

**为什么不直接改 `out->pos_ms`**：`pos_ms` 是**实际播放位置**，进度条/时间显示要用
真值。把它提前会让进度条虚报 1.25s。故单独拆出 `lyr_pos_locked()`。

**规则沉淀（可复用）**

- ★★ **数据通道与显示通道分离时，任何"全局对齐"改动的第一句话都该是：
  "这个偏移能作用到**所有生效路径**上吗？"** 若某条路径传的是**已算好的结果**
  （行号 / 索引 / 枚举 / 状态），它天然无法被时间偏移修正 ⇒ 要么让它交出主导权，
  要么把补偿**上移到算它的那一端**。**只改一条路 = 静默失效**
  （与 F41-A「两个 `user_data`」同一族毛病：代码全对、日志全对、行为不对）。
- **对齐补偿的验收必须看"换行时刻"，不能看"某一时刻的行号"** ——
  恒偏置下后者看起来永远是对的。
- 探针要写成**反证式**：不仅断言"修后正确"，还要断言
  "错误修法（只给本机加补偿、保留 PC 优先）与不修**逐点相同**"，
  否则证明不了这次改动是**必需**的。

**验收**

- `.workbuddy/probe_lyr_lead.py` ⇒ **16 PASS / 0 FAIL**（含上述反证 + 迟滞 + 钳位用例）。
- **实机验收通过（2026-09-24，用户确认）**：设备端歌词与 PC 端**对齐**（原落后 1.25s 已消除）；
  seek 后仍能对齐；位置抖动时不来回跳；三键同色、按下整键翻青；顶栏只剩 `● PC NOW` + 同步小字。
- 日志：`PCNOW: init done (udp/50004, http pull :50005, lyric lead 1250 ms)`；
  `TAB_PCNOW: built (rev UI3/F47 2026-09-24, area WxH)`。

> ★ **`PCNOW_LYR_LEAD_MS = 1250` 至此是一次"已实机验收的标定值"**，不是猜的。
> 但它绑的是"当前这套 PC + 播放器 + 输出链路"。换播放器后若偏移不同，别再往上加常量，
> 按 `#define` 上方的注释把 lead 上移到 PC 侧（pusher 随 `NOW_META` 按 player 下发 `lead_ms`）。
