# 13 内存管理规范

> 本文件规定本工程**内存使用的硬性红线**与**推荐做法**。
> 背景原理与踩坑复盘见 `14_堆管理宝贵经验.md`；故障案例见 `11_遇到的问题.md`（F19 / F23）。
> 违反本文件的代码，即使"当前能跑通"，也应在评审中要求整改。
>
> 最后更新：2026-09-23
> 适用目标：ESP32-S31-Korvo-1（16MB Flash / 16MB PSRAM / 内部 SRAM 稀缺）

## 0. 为什么本工程需要一份内存规范

本工程内部 SRAM 被**四类长期占用者**同时切分：

| 占用者 | 性质 | 分配时机 |
|---|---|---|
| bluedroid（BTU/BTC 队列 + HCI mempool） | **启动时静态分配**，事后改堆布局会导致其申请失败 | 开机早期 |
| LCD 帧缓冲（800×480） | 大块常驻 | 显示初始化 |
| WiFi / LWIP | 大量缓冲 | 连接时 |
| 音频解码器工作区（GMF `aud_dec` / `aud_asrc` / `aud_enc`） | 不等长、跟随播放 | 蓝牙推流常驻时 |

叠加 MbedTLS、LVGL、SDMMC 的运行期需求后，**内部 RAM 的"最大连续块"极易被切碎**。
已发生过的事实：

- **F23**：`sdmmc_cmd: allocate_dma_buf: not enough mem, err=0x101` ——
  GMF 读盘时要现场申请 DMA 缓冲，减半重试到不足 512B 都没成功，说明内部 DMA 堆已碎到极限；
- **F19**：`WP_OVERLAY: no dma mem for jpeg buf` ——
  JPEG **输入**缓冲被误标 DMA-capable，白占内部 SRAM。

> **核心认知**：本工程的失败模式**不是"内存总量不够"，而是"没有一个足够大的连续块"**。
> 因此规范的重点不是"省字节"，而是**消灭运行期的不确定分配**。
>
> 分配器（TLSF）的机制说明与"三种假性内存不足"的区分方法见
> `14_堆管理宝贵经验.md` §1.6 —— 这也是 §3.3 A4「日志打三元组」的理论依据。
> "去碎片三种手段（A 静态池 / B 预分配常驻 / C 换区域）"见同文档 §1.7。

## 1. 内部 RAM 红线

### 1.1 只有这些东西可以占用内部 RAM

| 类别 | 理由 | 示例 |
|---|---|---|
| **DMA 目标缓冲**（DMA 外设搬运的目标，且 PSRAM 不可直访） | 硬件要求 | LCD 帧缓冲、I2S 收发缓冲 |
| **DMA 源缓冲**（仅当 PSRAM 不可直访时） | 硬件要求 | 老芯片的 SDMMC bounce buffer |
| **中断 / ISR 代码与数据** | 必须驻留 | `IRAM_ATTR` 函数、ISR 使用的变量 |
| **WiFi / bluedroid 强制内部的部分** | 协议栈约束 | HCI mempool、BTU 队列 |
| **小尺寸高频小对象**（< 512B） | 内部访问快、避免 PSRAM 抖动 | 队列、信号量、小状态结构体 |
| **长生命周期任务的任务栈**（除非显式外置） | 见 §4.2 | 已用 `stack_in_ext` 的例外 |

### 1.2 红线（禁止）

> **R1** 禁止把**非 DMA 用途**的缓冲标成 `MALLOC_CAP_DMA`。
> F19 的根因就是 JPEG **输入**缓冲（CPU 读文件用）被标了 DMA。
>
> **R2** 禁止把 **CPU 才能访问的普通数据**（文件字节流、解码中间产物、字符串、JSON）
> 放在内部 RAM —— 一律 PSRAM。
>
> **R3** 禁止在**运行期热路径**（播放循环、事件回调、UI 回调）中做**大块** malloc。
> 大块分配必须在初始化阶段完成。
>
> **R4** 禁止在**未知剩余空间**的情况下假定 malloc 一定会成功。
> 见 §3（`assert` 降级原则）。
>
> **R5** 禁止新增 > 4KB 的内部 RAM 静态占用，而不在 `14_堆管理宝贵经验.md` 的
> "内部 RAM 占用台账"里登记说明理由。

### 1.3 判断"要不要 DMA"的唯一标准

问一句话：**"这块内存是被谁读写的？"**

```
CPU 读写（memcpy / 解码器输出到普通内存 / 字符串处理） → PSRAM 或普通堆，绝不加 DMA
DMA 外设搬运（LCD 送屏、I2S 收发、SDMMC 读写）        → 才考虑 MALLOC_CAP_DMA
```

进一步：即使是 DMA，**先查 PSRAM 能不能被该外设直访**：

```bash
# 查 sdkconfig，若为 y 则优先优先分配到 PSRAM
CONFIG_SOC_SDMMC_PSRAM_DMA_CAPABLE=y      # 本板 = y，SDMMC 可直访 PSRAM
```

F23 的正解就是利用了这一点：32KB bounce buffer 放 PSRAM，**一个字节内部 RAM 都不占**。

## 2. 静态池优先

### 2.1 原则

> **S1** 尺寸固定、生命周期长的缓冲区，**一律用静态数组**（`static uint8_t buf[N]`），
> 不用 `malloc`。
>
> **S2** 流式数据（音频/视频/串口）的收发缓冲，**一律用静态池 + 环形缓冲**。
>
> **S3** 同一个模块的多块小缓冲，合并成一个静态 arena 自行切分，
> 避免多次 malloc 产生的堆元数据开销与碎片。

### 2.2 本工程的正面样板

`main/middleware/audio/audio_service.c` —— 全部走静态池，是工程内最稳的一块：

```c
/* 播放/录音工作缓冲：用第三方 ringbuf 库管理（main/3rd/ringbuf） */
static uint8_t     play_rb_pool[BUFFER_SIZE];      /* 1024B */
static ringbuf_t   play_rb;
static uint8_t     rec_rb_pool[BUFFER_SIZE];       /* 1024B */
static ringbuf_t   rec_rb;

/* Stream buffers deliberately live in internal static RAM.  ringbuf has a
 * 14-bit index, so no pool may exceed 16383 bytes. */
static uint8_t mic_tx_rb_pool[5120];
static uint8_t spk_rx_rb_pool[3840];
static ringbuf_t mic_tx_rb;
static ringbuf_t spk_rx_rb;
```

**为什么这样好：**

| 好处 | 说明 |
|---|---|
| 零堆占用 | 在 `.bss` 段编译期定址，**完全不进堆** |
| 零碎片 | 固定占位、永不释放、不被空洞夹住 |
| 零运行期风险 | 不存在"申请失败"这条失败路径 |
| 可静态审计 | 编译器/`size` 命令直接给出占用，不用跑起来看 |

### 2.3 ringbuf 池的硬上限（14 位索引）

`main/3rd/ringbuf/ringbuf.h` 的索引是 **14 位位域**：

```c
typedef struct{
    ...
    uint16_t read_mirror:1;   /* page 0 or 1 */
    uint16_t read_index:14;   /* Read index —— 最大 16383 */
    uint16_t write_mirror:1;  /* page 0 or 1 */
    uint16_t write_index:14;  /* Write index —— 最大 16383 */
    uint16_t buffer_size;     /* Size of the buffer */
} ringbuf_t;
```

> **S4** 任何 `ringbuf_init()` 的池**不得超过 16383 字节**，否则索引溢出。
> 当前最大池 5120B，距上限还有 3 倍空间，安全。

**注意"容量"与"丢弃阈值"必须显式区分**：

```c
/* spk_rx_rb_pool 容量 3840B，丢弃阈值也是 6*640=3840B —— 恰好相等 */
while (ringbuffer_data_len(&spk_rx_rb) + len > 6 * AUDIO_FRAME_BYTES) {
    ringbuffer_get(&spk_rx_rb, discard, AUDIO_FRAME_BYTES);   /* 丢最旧一帧 */
}
```

`data_len + 640 > 3840` 即丢帧 ⇒ **稳态最多囤 5 帧多**，第 6 帧永远留不住。
"保留最新 6 帧"实为"保留最新 5 帧"。

> **S5** 池容量与丢弃阈值**不得取相同值**。阈值必须留出至少一帧余量，
> 否则策略与容量两个独立常数巧合相等，后续改任一处都会静默改变行为。
> 修法二选一：池扩到 5120B（阈值 6 帧名副其实），或阈值明确降为 5 帧并加注释。

## 3. `assert` 降级原则

### 3.1 现状与本工程的取舍

工程内 `assert()` 与 `ESP_ERROR_CHECK()` 用得很多：

```c
/* audio_service.c —— 初始化期断言 */
assert(spk_codec_dev);
assert(mic_codec_dev);
assert(audio_mux);
assert(audio_cmd_queue);
assert(mic_rb_mux && spk_rb_mux);

/* udp_voice.c / record_service.c / link_manager.c —— 任务创建后断言 */
BaseType_t ok = xTaskCreatePinnedToCoreWithCaps(control_task, "udp_voice_ctl", 8192, NULL, 5, NULL, 0,
                                                MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT);
if (ok != pdPASS) {                                       /* ★ T5：失败要先说话 */
    ESP_LOGE(TAG, "ctl task create failed (stack->PSRAM); check "
                  "CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY");
}
assert(ok == pdPASS);
```

> ★ **F35 补充（关于任务创建断言的正确姿势）**：
> 任务创建断言**允许保留**，但**前置一条 `ESP_LOGE`**。
> 原因：`WithCaps` 失败时**未必是内存不足** —— 若外置栈配置被关，
> 它会稳定返回 `pdFAIL`，而 PSRAM 此时可能还剩十几 MB。
> 只断言不打印，会把排查方向误导到"内存不够"，这正是 F35 前期走过的弯路。

> **这不是错的，但必须有边界。** 断言的价值是"快速失败、暴露问题"；
> 它的危险是"把可降级的故障升级成不可恢复的崩溃"。

### 3.2 分级规则

> **A1 —— 初始化期（`boot` / `init` 函数）允许断言。**
> 理由：此时资源应当充足，失败说明是**配置错误或硬编码尺寸错误**，
> 早崩比带病运行好。例如 `audio_service_init()` 里的 `assert(spk_codec_dev)`。
>
> **A2 —— 运行期（播放/录音/UI 回调/事件处理）禁止断言，必须降级。**
> 理由：运行期失败是**可预期的环境问题**（内存紧、对端异常、文件损坏），
> 应当记录日志 + 返回错误码 + 回退到安全状态，而不是 abort。
>
> **A3 —— 承载"用户可见功能"的资源，即使初始化期也应考虑降级。**
> 例如 SD 卡音乐播放器初始化失败，应当"提示不可用"而非让整机重启。

### 3.3 写法对照

```c
/* ✗ 运行期断言：内存紧就整机崩 */
void on_play_click(void) {
    uint8_t *buf = malloc(size);
    assert(buf);                        /* 用户看到的是重启 */
    ...
}

/* ✓ 运行期降级：记日志 + 返回错误 + 通知 UI */
esp_err_t on_play_click(void) {
    uint8_t *buf = heap_caps_malloc(size, MALLOC_CAP_SPIRAM);
    if (!buf) {
        ESP_LOGE(TAG, "play buf alloc failed, need=%u free=%u largest=%u",
                 (unsigned)size,
                 (unsigned)heap_caps_get_free_size(MALLOC_CAP_SPIRAM),
                 (unsigned)heap_caps_get_largest_free_block(MALLOC_CAP_SPIRAM));
        return ESP_ERR_NO_MEM;          /* 由调用方转为 UI 提示 */
    }
    ...
}
```

> **A4** 任何 `alloc == NULL` 的日志，**必须打印三元组**：
> `申请量` / `free_size` / `largest_free_block`。
> 只打印"失败"的日志没有诊断价值 —— 因为你无法区分"真的没空间"和"被切碎"。

**F23 的教训直接对应这条**：当时日志里只有 `not enough mem`，
是靠着去读 `sdmmc_cmd.c` 的 `allocate_dma_buf()` 源码、
发现"正常失败会一路减半重试"才反推出"碎到连 512B 都没有"这个结论。
**如果当时日志里有 `largest_free_block`，一行就能定位。**

### 3.4 `heap_caps_malloc` 失败的重试纪律

F23 中 IDF 自己的做法值得抄：**拿不到就减半重试，直到一个下限才放弃**。

```c
/* IDF sdmmc_cmd.c 的实际实现（简化） */
static esp_err_t allocate_dma_buf(size_t* actual_size, size_t block_size, void **buf) {
    do {
        if (*actual_size < block_size) {
            ESP_LOGE(TAG, "%s: not enough mem, err=0x%x", __func__, ESP_ERR_NO_MEM);
            return ESP_ERR_NO_MEM;
        }
        *buf = heap_caps_malloc(*actual_size, MALLOC_CAP_DMA);
        if (!*buf) { *actual_size /= 2; }         /* 拿不到就减半重试 */
    } while (!*buf);
}
```

> **A5** 大块申请失败时，**优先考虑"能不能用更小的块完成任务"**
> （分块处理、降分辨率、降缓冲深度），而不是直接放弃或崩溃。

## 4. `heap_caps` 使用规则

### 4.1 caps 速查

| caps 组合 | 含义 | 用途 |
|---|---|---|
| `MALLOC_CAP_INTERNAL` | 内部 SRAM | DMA、ISR、必须在内部的栈 |
| `MALLOC_CAP_SPIRAM` | PSRAM | **绝大多数普通数据** |
| `MALLOC_CAP_DMA` | DMA 可达 | 外设搬运的缓冲 |
| `MALLOC_CAP_8BIT` | 字节可寻址 | 一般与上面组合 |
| `MALLOC_CAP_SPIRAM \| MALLOC_CAP_DMA` | PSRAM 且 DMA 可达 | **最优先**（前提是 SoC 支持） |

### 4.2 规则

> **C1** 默认用 `MALLOC_CAP_SPIRAM`。**不要用裸 `malloc()`** ——
> 本工程 `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0`，
> 裸 `malloc` 的小块也可能落到 PSRAM，行为不直观且不易审计。
>
> **C2** 需要 DMA 时，`MALLOC_CAP_SPIRAM | MALLOC_CAP_DMA` 优先，失败再退 `MALLOC_CAP_DMA`。
> F23 范例：
> ```c
> s_dma_bounce = heap_caps_malloc(32 * 1024,
>                                 MALLOC_CAP_SPIRAM | MALLOC_CAP_DMA | MALLOC_CAP_8BIT);
> if (!s_dma_bounce) s_dma_bounce = heap_caps_malloc(32 * 1024, MALLOC_CAP_DMA);  /* 退回内部 */
> host.dma_aligned_buffer = s_dma_bounce;
> ```
> 前提是 `CONFIG_SOC_SDMMC_PSRAM_DMA_CAPABLE=y`（本板成立）。
>
> **C3** 任务的栈外置，用 caps 版创建 API：
> ```c
> xTaskCreatePinnedToCoreWithCaps(proc_task, "bt_push_proc", PROC_TASK_STACK, NULL,
>                                 prio, NULL, core, MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT);
> ```
> GMF 线程用 `thread.stack_in_ext = true;`（见 `bt_push_service.c`）。
>
> ★ **F35 起这是本项目所有任务的默认姿势**（11/11 处），不再只针对"长生命周期"。
> 同时必须补两个头：`freertos/idf_additions.h`（提供 WithCaps 系列）
> 与 `esp_heap_caps.h`（提供 caps 宏）。
>
> **C4** 外置任务栈**必须**同时确认 `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y`
> 与 `CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y`（本板均已开，见 `sdkconfig`）。
>
> **C5** 使用 caps 分配后，**优先用 caps 版释放**（`heap_caps_free`），
> 保持与分配镜像对称，便于审计与后续替换分配器。

### 4.4 待核查项

~~`fs_service.c` 使用 `jpeg_calloc_align(...)`，分配 `800×480×2 = 768KB`~~
**已核查（2026-09-21）**，结论：

1. **尺寸不是 768KB，是 1152000 字节（≈1.10MB）**。表达式为
   `BSP_LCD_H_RES * BSP_LCD_V_RES * sizeof(lv_color_t)`，而本工程

2. **落点已确认在 PSRAM**：实测日志 `jpeg out buffer 1152000 bytes @ 0x5000d8c0`，

3. **规范做法**：主路径 `heap_caps_aligned_calloc(16, 1, size, SPIRAM|8BIT)`，
   只在 PSRAM 失败时退 `jpeg_calloc_align()`（其内部是
   `heap_caps_calloc_prefer` = **优先内部**）。退路保留但不该被走到；
4. `assert(file_buffer)` 按 §3.2 属 **A3**：壁纸失败不应拖垮整机，建议改为
   打日志 + 置空 + 调用方跳过解码（**待办，尚未实施**）。

#### 5.1.2 改造前（存档）

工程内曾以裸 `xTaskCreate` / `xTaskCreatePinnedToCore` 为主，
`CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y` 与
`CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y` **两项配置都已开启**，
但除了 `bt_push_proc` 外**没有任何一处使用** —— 这是典型的"**知道但没推广**"，
不是认知缺口，是执行遗漏。F35 的 177KB 内部 RAM 亏损中，任务栈占了 ~93KB（含 IDF 自带任务）。

**观察（仍成立）**：工程内**没有使用 `xTaskCreateStatic`**，尽管
`CONFIG_FREERTOS_SUPPORT_STATIC_ALLOCATION=y` 已开启。

### 5.2 规则

> **T1** **长生命周期任务**（开机建、永不退出）**推荐**改用 `xTaskCreateStatic` 系列，
> 栈与 TCB 用静态数组，**从堆里彻底摘出去**。
> 适用于：栈**小**（≤ 4KB）、**访问极频**（如 1kHz 采样回调）的任务 —— 这类放 PSRAM 会因
> 外部总线延迟实际伤害吞吐，静态内部反而更优。
>
> **T2** 短生命周期任务（如 `bt_vol_sync`，一次性同步后退出）保持动态创建即可，
> 但**同样应外置 PSRAM** —— 短命任务恰恰常常在"内存最紧张"的时刻被拉起。
>
> **T3** 大栈任务（≥ 8KB）**必须**外置到 PSRAM（`WithCaps` 系列），
> 不得默认走内部堆。**这是本项目当前的统一做法**（见 §5.1.1）。
>
> **T4** 任务栈尺寸**必须**在文件里以具名宏给出，不得散落魔数。
>
> **T5**（F35 新增）外置栈的**失败分支必须有显式日志**，并在日志里点名
> `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY`。
> 原因：`WithCaps` 返回 `pdFAIL` 时，**大概率不是"内存不够"**（PSRAM 往往还富余十几 MB），
> 而是外置栈路径被配置关掉了。若只写 "task create failed"，会把排查方向带偏到内存不足上。

`xTaskCreateStatic` 范例（适用于 T1 那类"小栈高频"任务）：

```c
#define AUDIO_TASK_STACK_WORDS   (8192 / sizeof(StackType_t))

static StackType_t  s_audio_task_stack[AUDIO_TASK_STACK_WORDS];
static StaticTask_t s_audio_task_tcb;

void audio_service_init(void) {
    TaskHandle_t h = xTaskCreateStatic(audio_task, "audio_task",
                                       AUDIO_TASK_STACK_WORDS, NULL, 6,
                                       s_audio_task_stack, &s_audio_task_tcb);
    assert(h);          /* 初始化期，允许断言（§3.2 A1） */
}
```

`WithCaps` 外置栈范例（本项目 T3 统一做法）：

```c
/* 必须两个头：idf_additions.h 提供 WithCaps 系列，esp_heap_caps.h 提供 caps 宏 */
#include "freertos/idf_additions.h"
#include "esp_heap_caps.h"

BaseType_t ok = xTaskCreatePinnedToCoreWithCaps(link_task, "link_manager", 8192,
                                                NULL, 4, NULL, 0,
                                                MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT);
if (ok != pdPASS) {
    ESP_LOGE(TAG, "task create failed (stack->PSRAM); check "
                  "CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY");   /* T5 */
}
assert(ok == pdPASS);
```

### 5.3 收益与代价

| | 收益 | 代价 |
|---|---|---|
| 静态任务栈 | 消除 8KB×N 的堆占用与碎片 | 内部 SRAM 静态占用增加 |
| 外置到 PSRAM | 内部 RAM 完全不占 | PSRAM 访问慢，栈高频访问有性能损耗 |

> **取舍原则**：**高频小栈**留内部（可静态化），**低频大栈**外置 PSRAM。
> 详见 `14_堆管理宝贵经验.md` §4.1 的"决策树"。

> ★ **一个被反复问到的疑问**：栈放 PSRAM 会不会踩到"DMA 不可达"的坑？
> **不会**。栈只被 CPU 压栈/出栈/存局部变量，**从不作为 DMA 源或目的**。
> `IRAM_ATTR` 中断服务程序用的也是**被中断任务自己的栈**（不另开栈），
> 所以中断嵌套也不会因"栈在 PSRAM"而失效。
> 真正需要留在内部的是**缓冲区**（I2S DMA 描述符、LCD 帧缓冲这类），不是栈。

## 6. 生命周期纪律

> **L1** 资源创建/销毁次数必须**最小化**。反复 `build` / `destroy` 全套资源
> （GMF pool + codec + render）是碎片的主要制造机。
> 能"建一次不毁"的（如蓝牙推流 P3 策略）就不要反复重建。
>
> **L2** 若某资源**必须**随 UI 生命周期重建（如 MUSIC tab），
> 应评估改为**常驻 + 开关**的可行性；确需重建的，应统一走一个中间层模块，
> 而不是散在 UI 回调里（见 `12_音频链路架构.md` §5.5 的 `local_player` 方案）。
>
> **L3** 任何 `malloc` 都必须有**明确的释放责任人**，并在文件头注释里写明。
> 本工程曾出现 `esp_player` 相关的 `# F26` 类问题（契约无机器校验），
> 内存所有权同样需要显式契约。

## 9. 内存优化总账（优化前 vs 优化后，2026-09-21 收尾）

> 本章是 F30 / F34 / F35 三轮内存问题的**最终结算**。
> 所有数字均来自 `build/log/` 下的实测串口日志，可逐条回溯。

### 9.1 数据来源（可求证）

| 版本 | 日志文件 | 特征 |
|---|---|---|
| **优化前** | `build/log/idf_py_stdout_output_2972` | `largest` 恒定 23552；BT 拒绝开机 |
| **优化后** | `build/log/idf_py_stdout_output_44112` | 含 36 处 `[boot-diag]` 埋点；BT 开机通过 |

两版固件的 `heap_init` 行、`BOOT_DIAG` 行、`WIFI_DIAG` 行构成完整证据链。

### 9.2 ★★★ 一个反直觉的结构性事实：可用堆本身变小了

| 版本 | `heap_init` 起始地址 | 长度 | 可用堆 |
|---|---|---|---|
| 优化前 | `0x2F044520` | `0x36A90` | **218.6 KB** |
| 优化后 | `0x2F046700` | `0x348B0` | **210.2 KB** |

- 起始地址**后移了 `0x21E0` = 8672 B**，说明 `.bss/.data` 静态段变大了 8.5 KB；
- 可用堆因此**反而少了 8.5 KB**。

> **★ 结论：本轮优化的收益完全不来自"把堆扩大"，恰恰相反 —— 堆缩小了 8.5 KB。
> 收益 100% 来自「减少堆内碎片」。**
> 这也解释了为什么必须看 `largest` 而不是只看 `free`（详见 `14_堆管理宝贵经验.md` §9.10）。

### 9.3 核心指标对比（同一测量阶段）

测量点选在"页面构建完成 / 蓝牙开机前"，因为这是历史上最紧张的卡点。

| 指标 | 优化前 | 优化后 | 变化 | 出处 |
|---|---|---|---|---|
| `internal free` | 25.4 KB<br>(25991 B) | **51.2 KB**<br>(52431 B) | **+102%** | 2972 拒绝开机行 / 44112 `mem check ok` |
| **`largest` 连续块** | 23.0 KB<br>(23552 B) | **31.0 KB**<br>(31744 B) | **+35%** | 两版全节点日志 |
| `DMA-capable free` | 2.2 KB<br>(2215 B) | **21.3 KB**<br>(21771 B) | **≈10×** | 2972 `[diag]` / 44112 分步 |
| `DMA largest` | 1.7 KB<br>(1728 B) | **14.5 KB**<br>(14848 B) | **≈8.6×** | 同上 |
| `PSRAM free` | 11274 KB | 11230 KB | −0.4% | 两版日志 |

**三项全部转正**：

- `largest` 23.0 → 31.0 KB：**跨过了蓝牙要求的 24 KB 单块门槛**（这是从"拒绝开机"到"通过"的分水岭）
- `internal free` 25.4 → 51.2 KB：跨过 48 KB 门槛
- DMA 池 2.2 → 21.3 KB：F23 那个"保底 32 KB 池见底"的状态回到健康

### 9.5 四笔优化收益

| # | 措施 | 收益 | 实测依据 |
|---|---|---|---|
| ① | **任务栈全量外置 PSRAM** | **≈70.5 KB**<br>(72192 B) | `8192×8 + 4096 + 2560`；也是 `largest` 翻倍的直接原因 |
| ② | **WiFi 重试次数 5 → 3** | ≈20 KB | `WIFI_MAX_RETRY`；重连是"增长型"消耗 |
| ③ | 扫描缓存改显式 PSRAM `calloc` | 小 | `scan rec buf: ptr=0x504fb92c`（`0x5xxxxxxx` 即 PSRAM） |
| ④ | BT_PUSH / vol sync 短命任务栈外置 | 小 | `xTaskCreateWithCaps(..., MALLOC_CAP_SPIRAM)` |

> **★ 关键：①②合计 ≈90 KB，但收益不是简单相加 ——**
> ① 的价值在于"**把切碎堆的小块一次性拿走**"，让 `largest` 从 15360 → 31744（翻倍）；
> 如果只做 ② 不做 ①，`free` 会涨但 `largest` 仍被碎片压住，蓝牙照样开不起来。

### 9.6 分域归类（按 `14_堆管理宝贵经验.md` §9.8 / §9.11 的判据）

| 消费者 | 大小 | 域 | 处置类别 | 说明 |
|---|---|---|---|---|
| 任务栈 | 70.5 KB | 内部 → 已挪 PSRAM | **A 能挪已挪** | 本轮主要战果 |
| WiFi 重连冗余 | ~20 KB | 内部 | **A 能挪已挪**（降配） | 改重试次数即可 |
| BT controller | 41.2 KB | 内部 DMA | **B 挪不动** | 协议栈硬需求 |
| WiFi `esp_wifi_init` | 44.5 KB | 内部 DMA | **B 挪不动** | internal 与 DMA 跌幅**完全相同** |
| **RGB panel** | **72.0 KB** | 内部 DMA | **C 可缩要付代价** | bounce buffer 62.5 KB 可降配 |

RGB panel 那 72 KB 的构成（★ 2026-09-22 凌晨经 DISP_DIAG 细分埋点精确化，修正原"驱动 ≈9.5 KB"的粗归因）：

```
bounce buffer        64000 B (32000 × 2, HEIGHT=20)   ← C 类，可缩
+ LVGL 渲染任务栈     7528 B（esp_lvgl_port 组件内部创建，在内部 RAM！）
+ panel 驱动开销      2140 B（DMA 描述符 / ISR / 句柄）
+ add_disp_rgb        88 B（LVGL display 注册）
= 73756 B ✅ 与实测分毫不差
```

> **★ 勘误**：此前把"LVGL 任务栈 7528 B"算进了"RGB panel 驱动 ≈9.5 KB"。
> 实际上它是独立的 LVGL 渲染任务栈，**理论上可外置 PSRAM**（同 T4 判据），
> 但渲染任务跑 PSRAM 栈可能有性能影响，列为下一刀候选，未执行。

**降配表**（约束 `fb_size % bb_size == 0`，`fb_size = 768000 B` 固定）：

| `BOUNCE_BUFFER_HEIGHT` | ×2 合计 | 可省 | legality |
|---|---|---|---|
| 20 | 62.50 KB | — | ✅ |
| 16 | 50.00 KB | 12.5 KB | ✅ |
| **10（已执行 ★）** | 31.25 KB | **31.25 KB** | ✅ |
| 8 | 25.00 KB | 37.5 KB | ✅ |

代价：bounce buffer 越小 → DMA 中断越频繁 → CPU 占用升高。

## §18 A2DP 推流侧 L2CAP 拥塞分析（2026-09-22）

本节不属于内存管理，但同源于"长时间推流稳定性"排查，故暂记于此，
后续应迁至独立的《蓝牙推流稳定性》文档。

### §18.1 现象

长时间播放（约 511 秒起）后 log 出现：

```
E (511401) BT_L2CAP: l2cab is_cong_cback_context
W (515305) BT_APPL: btc_a2dp_source_enqueue_audio_frame audio tx queue overflow: 28
W (515305) BT_AUD_SRC: Failed to send frame batch: ESP_FAIL, data_len: 616, MTU: 666
```

### §18.2 因果方向（重要）

**不是**"发送失败导致拥塞"，而是**反过来的**：

```
控制器 L2CAP 缓冲耗尽 → 宣告拥塞（511401）
        ↓ 约 3.9 秒后
应用层推流队列积压越限 → 溢出丢帧（515305）
        ↓
该批 616 B 发送失败 → SUSPEND
```

`l2cab is_cong_cback_context` 是**根因**；`audio tx queue overflow` 是**结果**。
时间差 3.9 秒正说明上游先堵、下游才积。

### §18.3 定量核算（源码实测值）

| 项 | 值 | 出处 |
|---|---|---|
| SBC 帧大小 | **119 B** | joint-stereo, 8 subbands × 16 blocks, bitpool 53 |
| 音频 MTU | 666 B | 对端协商结果（日志） |
| MTU 开销扣除 | 50 B | `A2DP_SRC_MTU_OVERHEAD_BYTES` |
| 可用载荷 | `666 − 50 = 616 B` | ← **与日志 `data_len: 616` 完全一致** |
| 每批最大帧数 | `616 ÷ 119 = 5 帧`（595 B） | `calc_max_frames_per_batch()` L173-186 |
| 每 20ms 需求 | **6.89 帧** | `frames_per_tick`，44100 Hz |
| 每秒帧数 | 344.5 帧/s | `44100 ÷ 128` |
| **需求码率（有效载荷）** | **328 kbps** | `119 × 344.5 × 8` |
| 满批可持续码率 | `595 B ÷ 20ms =` **238 kbps** | ← **结构性缺口 90 kbps（27%）** |

**结论**：即使每个 20ms tick 都发满 5 帧，供给仍只有 238 kbps，
低于需求 328 kbps。**积累是结构性的，非偶发抖动。**

### §18.4 库内发送机制的三个缺陷

阅读 `bt_audio_a2dp_src.c` 得出（该文件在 `managed_components/`，可改但升级会丢）：

1. **周期硬编码 20ms**（`A2DP_SRC_SEND_INTERVAL_MS`，L47），
   `esp_timer_start_periodic` 设死，**不可配**；
2. **无反压机制**：`a2dp_src_send_data()` 只有"计数式节流"
   （`calc_frames_to_send` 按时间账核算该发多少）；
   发送失败后**不做任何退避**，20ms 后原样再来；
3. **拥塞回调无消费者**：L2CAP 已宣告拥塞，但库内没有据
   `is_cong` 状态暂停生产的逻辑 → 只能等协议栈自愈。

综合三条 → 拥塞一旦形成，应用层**只能被动溢出丢帧**。

### §18.5 与 HEIGHT=10 的关系（澄清）

`BOUNCE_BUFFER_HEIGHT` 20→10 使行中断频率翻倍（480 行 vs 240 行），
**理论上**会挤占 CPU 时间片。但**不足以解释 616 B 满批发送失败**，理由：

- `a2dp_src_send_task` 优先级 **10**，绑核 **1**；
- L2CAP 的实发动作在**控制器固件的独立线程**，
  不与应用层任务抢时间片；
- 真正的瓶颈是**链路预算**（§18.3），不是 CPU。

→ 两条路径独立。HEIGHT=10 不应为大流量丢帧背责，
但若烧录后**音质出现周期性卡顿**，则应优先怀疑本节问题。

### §18.6 待验证项（需实机）

1. **链路容量实测**：在 `set_volume` 或推流启动处，
   每 5 秒打印一次 `uxQueueMessagesWaiting(data_q)`，
   看水位是否单调上升（可证实 §18.3 的积累判断）；
2. **对端能力核查**：确认耳机是否支持 SBC **XQ / 更高 bitpool**，
   或是否可切 AAC（`CONFIG_BT_A2DP_CODEC_AAC_ENABLED`）；
3. **控制器缓冲参数**：`CONFIG_BT_CTRL_...` 下 ACL / L2CAP 缓冲相关项
   （需查 IDF v6.1 对 esp32s31 的可用项）。

### §18.7 三个候选修复方向（按代价升序）

| 方向 | 手段 | 代价 / 风险 |
|---|---|---|
| **① 降码率**（最省） | 降 bitpool 或强制 mono；或对采样率做下采样 | 音质下降；**但 328→238 kbps 需降 27%，音质损失明显** |
| **② 换编解码器** | 启用 AAC（`A2DP_SRC_AAC_MTU_MARGIN_BYTES=32`，L530 注释可见 AAC 一帧一包） | 需对端支持 AAC；编码 CPU 占用上升 |
| **③ 改库** | 提高 `A2DP_SRC_SEND_INTERVAL_MS` 或让批大小突破 5 帧限制 | 改 `managed_components/`，升级即丢；周期变大影响延迟 |

**建议先做 §18.6 的 1 项**（水位打印），用数据确认是"积累型"还是"突发型"，
再决定是否付降码率的代价。
