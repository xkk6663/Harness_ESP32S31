## 1. 项目概述

本系统由 **ESP32-S31 设备端** 与 **PC 端软件** 两部分组成，通过 Wi-Fi 局域网连接，提供两种互斥工作模式：

- **UDP 实时通话模式**——为"听到对方"优化，20ms 一帧、乱序重排、丢包填静音，端到端 ≤100ms，允许偶发卡顿但绝不等待；
- **TCP 云端录音模式**——为"事后回听完整录音"优化，可靠流式传输、整段落盘 WAV，零丢帧，可断点续传与掉电保护。

两种模式共用同一套 I2S/Codec 驱动与帧格式，仅传输层与播放策略不同，由 UI 触控或物理按键一键切换。

## 2. 系统总体架构（双通道）

```
ESP32-S31 设备端  ⇄  Wi-Fi 局域网  ⇄  PC 端软件（Python）

【通道 A · UDP 实时通话】端口 50000/50001
  麦克风 I2S DMA → 20ms PCM 帧(640B) → UDP 发 → PC pyaudio 实时扬声器播放
  PC 麦克风 → UDP 发 → 设备 I2S TX DMA 播放（乱序重排 / 超时填静音）

【通道 B · TCP 整段录音】端口 50002
  设备麦克风 → 连续 PCM 流 → TCP Client → PC TCP Server → 写入 WAV 文件
  （可选上行）PC 音频 → TCP → 设备播放整段音频

信令通道 UDP 50003：模式切换、开始/停止录音、音量、设备发现（UDP 广播）
```

## 3. 硬件平台（Korvo-1 V1.1）

| 模块 | 规格 | 连接 | 用途 |
|---|---|---|---|
| 主控 | ESP32-S31 双核 RISC-V @320MHz，512KB SRAM | — | Core1 跑音频硬实时；Core0 跑 Wi-Fi/网络/UI |
| 存储 | 16MB Flash + 16MB Octal PSRAM | Octal | PSRAM 放 LVGL 帧缓冲与环形缓冲；Flash 存 UI 资源/字库/NVS |
| 音频 Codec | ES8389 立体声（I2C 0x20） | I2C SDA=GPIO0/SCL=GPIO1；I2S SCLK=GPIO3/LRCK=GPIO4；**MCLK=GPIO42 未连接** | `use_mclk=false`，BCLK 恢复时钟，TDM 帧格式 |
| 音频 I/O | 双 MEMS 麦 + 双 NS4150B 功放 | ES8389 ADC/DAC | 16kHz/16bit；PA GPIO 使能控制静音防爆音 |

| 按键 | BOOT / RST | GPIO | BOOT 短按=PTT/通话，长按 3s=切换 UDP/TCP 模式或配网 |

> **硬件坑位**：① ES8389 必须 `use_mclk=false`；② 收发走 TDM，不能配普通 I2S；③ 官方推荐 16kHz，正好对齐 20ms 语音帧（640B）。

## 4. 模式一：UDP 低延迟实时通话

### 4.1 设备端行为
- I2S RX DMA 双缓冲，每 20ms 产生一帧 640B PCM（16kHz/16bit/单声道）；
- 帧头：`magic(0xA5) + seq(2B) + timestamp(4B) + length(2B) + flags(1B)`；
- UDP 发往 PC IP:50000；同时在 50001 收 PC 回传语音；
- 接收侧 16 帧环形重排窗口，乱序帧重排；超时 40ms 未到则填静音补偿；
- 本地采集→播放回环延迟 **≤8ms**；端到端（经 Wi-Fi）**≤100ms**；
- 支持全双工常开 / PTT 半双工（长按 200ms 防误触）两种，UI 可切；
- 可选 G.722 编码（64kbps）压缩带宽，裸 PCM 为默认模式便于联调。

### 4.2 PC 端行为
- Python 客户端：socket UDP 收包 + sounddevice 输出到扬声器；
- **一份上行 PCM 同时分两路消费**：① 扬声器实时播放；② 喂后台 ASR 引擎实时转文字，文本显示在 GUI；
- 本地麦克风经 sounddevice 采集，**按住"对讲按键"(PTT)** 时按 20ms 组帧、加相同帧头发往设备 50001，松开停止；
- 抖动缓冲（jitter buffer）：默认缓存 2~3 帧（40~60ms）平滑网络抖动；
- 丢包统计：每 2s 打印丢包率/平均延迟/抖动；UI 同步显示；
- Windows/macOS/Linux 跨平台；输入/输出设备可在 GUI 选择。

### 4.3 连接状态机与心跳（SYS tab 绿/红判定）

设备不预先配置 PC IP，由信令通道自动学习对端：

| 状态 | 触发 | SYS tab 指示 | 音频上行目标 |
|---|---|---|---|
| OFFLINE（红） | 上电默认 / 2s 未收到 PC 心跳 | 红点 + "No PC peer" | 无，不推流 |
| ONLINE（绿） | 收到 PC 50003 心跳 | 绿点 + "PC: <ip>" | 记为心跳来源 IP:50000 |

- PC 软件启动后每 **1s** 向局域网广播/组播（或设备已知端口）发 `HEARTBEAT`（含 PC 软件版本、监听端口）；
- 设备 `link_manager` 从收到的包 `recvfrom` 地址学习 PC IP，刷新"最后心跳时间戳"；
- 设备 500ms 检查一次，超过 **2s** 未收到心跳 → OFFLINE；通话中断开则自动停止上行推流；
- 设备也可回 `HEARTBEAT_ACK`（含设备 IP/固件版本/电量），PC GUI 显示已连接设备。

### 4.4 模式一交互时序

1. PC 启动软件 → 周期心跳；设备 SYS tab 由红变绿（LED 状态灯与 WiFi 状态灯逻辑独立，互不影响）；
2. 用户在设备 CALL tab 点**传音按钮（toggle）**：
   - 首次按下 → `udp_voice` START：mic 常开采集、20ms 打包持续发往 PC，按钮变"通话中"+计时；
   - 再次按下 → STOP：停止上行；
3. PC 收到音频流：扬声器实时播放 + ASR 实时转写，文字逐句追加到 GUI 文本区（带时间戳，可清空/导出）；
4. PC 用户**按住对讲键**：采集 PC 麦克风并发往设备，设备 spk 实时播放；松开即停（设备侧 mic 上行不中断，实现边听边说）；
5. PC 软件关闭/心跳停止 2s → 设备 SYS tab 变红，若在通话中自动 STOP。

> 方向语义：**设备→PC = 通话期内持续推流**（支撑连续转写）；**PC→设备 = PTT 按住发言**。
> 若后续要做真正全双工双向常开，只需把 PC 侧 PTT 改为常开，协议不变。

### 4.5 设备端改动设计（分层，仅设计不实施）

| 模块 | 改动 | 说明 |
|---|---|---|
| `middleware/link_manager.c/h`（新增） | 信令 50003、心跳收发、peer 在线状态机、学习 PC IP、事件回调 | 常驻任务+命令队列；不 include lvgl |
| `middleware/udp_voice.c/h`（新增） | tx/rx 常驻任务、帧头打包、16 帧 jitter 重排、超时填静音、START/STOP/PTT 命令 | tx 目标取自 link_manager；栈≥8KB |
| `middleware/audio_service.c/h`（扩展） | 增加**流式模式**：常开 mic 采集 ringbuf 与 spk 播放 ringbuf，对外 `read_mic()/write_spk()` | udp_voice 只读写 ringbuf，不直接碰 codec，守住分层 |
| 任务/核绑定 | 采集+播放钉 Core1 高优先级；UDP/WiFi/LVGL 在 Core0 | 保证音频硬实时，抖动≤1ms |
| `ui/tab_call.c`（改） | 传音按钮接 udp_voice START/STOP、通话计时、peer 在线状态显示 | 只 post 命令 |

## 5. 模式二：录音记录与 PC 同步（TCP）

> V3.1 按用户需求重写：REC 子页录制一段音频（尽量长），**录完自动同步推送到 PC**，
> PC 本地保存并在软件内对录音做停止 / 播放 / 删除。架构同时支持"边录边传"（无限时长），
> 默认先实现"先录后传"。

### 5.0 存储策略与时长（V3.2 定稿：边录边传为主，离线限 5 分钟）

**决策**：不把 Flash 占满（为 OTA 预留）；联网时**边录边传**（时长无限、设备不落地）；
离线时本地最多缓存 **5 分钟 PCM**，联网后自动补传。

硬数字（16kHz/16bit/mono = 32000 B/s）：
- 5 分钟 PCM = 9,600,000 B ≈ **9.16MB**（现 5MB storage 仅够 2.7 分钟，故需重排分区）；
- 当前 app bin ≈ 1.52MB，OTA 双分区每个至少 2MB，不可再压缩；
- UI 素材（壁纸+提示音）仅 ≈0.17MB。

**OTA 分区表（阶段 1.5 已落地；A/B 双区，不实现 OTA 逻辑；以《SPIFFS迁移LittleFS指南》为准）**：

> OTA 槽大小不固定、可在 partitions.csv 自定义，唯一硬约束是 ota_0/ota_1 必须等大。
> 综合取双槽各 **3MB(0x300000)**（现 bin≈1.63MB，余≈1.37MB），剩余空间全给一个 littlefs `storage`，
> 不设独立 assets/rec_cache，也不预留尾部留白（全盘用尽）。素材与录音同盘、分目录管理。

| 分区 | 偏移 | 大小 | 用途 |
|---|---|---|---|
| nvs | 0x9000 | 0x6000 (24K) | 配置/WiFi 凭据/OTA 断点 offset |
| phy_init | 0xf000 | 0x1000 (4K) | RF 校准 |
| otadata | 0x11000 | 0x2000 (8K) | OTA A/B 选择（双扇区） |
| ota_0 | 0x20000 | 0x300000 (3M) | 当前运行 app |
| ota_1 | 0x320000 | 0x300000 (3M) | OTA 备用分区（回滚防砖） |
| storage | 0x620000 | 0x9E0000 (9.87M / 10112KB) | LittleFS：出厂素材 + 录音 + 用户壁纸同盘 |

- 单 `storage` littlefs 读写挂载（format_if_mount_failed=true），挂载点 `/littlefs`；
- storage 内分目录：`/recordings/`（录音）与 `/wallpapers/`（壁纸）隔离；出厂素材（xwkkk.jpg 等）随镜像打包；
- 5min PCM(9.16MB) 落在 9.87MB storage 内，余≈0.7MB 给素材/壁纸；
- OTA 功能本身列入阶段六（esp_ota A/B + 回滚 + PC 拖拽推固件），阶段 1.5 已把分区表改好，避免后期再改分区整片擦写。

### 5.1 设备端行为（record_service，新增中间层，双模状态机）
- START 时查 `link_manager` 在线状态决定模式：
  - **ONLINE → STREAM 边录边传**：mic 帧直接走 `tcp_transport` 上 PC，设备不落地（仅保留 2–3s
    环形缓冲抗网络抖动），**时长无限**；
  - **OFFLINE → LOCAL 离线缓存**：写 rec_cache 的 WAV（44B 占位头），**硬上限 300s**，
    到点自动停止并标记"待传"，空间不足同样自动停；
- 录制中网络变化：STREAM 掉线 → 从断点转写本地（LOCAL），恢复后 PC 按 offset 拼接成完整一段；
  LOCAL 录制中上线不打断，STOP 后再补传（实现简单、状态确定）；
- STOP：STREAM 发 REC_END 收尾；LOCAL 回填 WAV 头、关文件并入"待传队列"，
  一旦 link ONLINE 自动按 REC_BEGIN/分块/REC_END 补传，失败保留可重试；
- 掉电保护：本地写每 64KB flush；上传分块带 offset+CRC，断点续传、错块重发；
- 录音期间设备喇叭静音，避免自采自录回声；上传进度/模式/计时通过事件回调 UI。

### 5.2 PC 端行为（录音库管理）
- TCP Server 监听 50002，按 REC_BEGIN 元信息在 `recordings/` 建 WAV，分块写入、校验 CRC，
  REC_END 回填 WAV 头并入库（sqlite 或 index.csv：文件名/起止时间/时长/大小/校验）；
- PySide6 录音库面板：列表展示每条录音（时间、时长、大小），并提供：
  - **停止**：录制进行中通过 50003 下发 REC_STOP 中止；
  - **播放**：PC 本地 sounddevice 播放（不下发设备），可暂停/进度；
  - **删除**：删除本地文件并从索引移除（带二次确认）；
  - 另支持导出目录、刷新列表；
- 网络中断已落盘部分不损坏，重连后按 offset 续写；
- 录音库与 UDP 通话模块共存，统一走 NetLink 抽象，互不影响。

### 5.3 两种录制形态（运行时按网络自动选择，对 PC 呈现一致）
| 形态 | 触发 | 设备落地 | 时长 | PC 入库 |
|---|---|---|---|---|
| STREAM 边录边传 | START 时 PC 在线 | 仅 2–3s 抗抖环形缓冲 | **无限** | 实时收帧落盘 |
| LOCAL 离线缓存 | START 时 PC 离线 / 录制中断网 | 写 rec_cache WAV | **≤5min PCM** | 上线后自动补传 |
- 两种形态复用同一 mic 流、同一 tcp_transport 与同一套 REC_* 信令/分块协议；
- STREAM 中断网转 LOCAL、再上线按 offset 拼接，PC 最终得到一段连续录音。

### 5.4 阶段二必须预留的接口
1. `audio_service` mic 流支持**多消费者订阅**（UDP 通话与录音可同时/分别取同一份 mic）；
2. `voice_transport` 抽象内 `tcp_transport` 留接口桩（open/send_frame/on_recv 与 udp 同形）；
3. `session_manager` 状态机含 `TCP_RECORD`，与 `UDP_CALL` 互斥切换、复用同一 mic/spk 流；
4. 50003 信令枚举预留 `REC_START/REC_STOP/REC_BEGIN/REC_END/REC_DELETE/REC_LIST_REQ/REC_LIST_RSP`；
5. `link_manager` 在线状态供 record 上传前判断；
6. **分区表阶段二就改成 OTA 友好布局**（双 ota + otadata + assets/rec_cache 拆分，见 5.0），
   不把 Flash 占满、尾部留白，避免阶段三/阶段六再改分区导致整片擦写、素材重刷。

### 5.6 远程文件管理 + 设备端文件浏览器（V3.4）

> 需求：PC 端可远程管理 `/littlefs` 里的图片/音频（上传/下载/删除/设壁纸）；
> 设备端 System 子页可浏览文件、点图片预览、点音频试听。

**结论：LittleFS 本身不提供"远程"，远程读写由 HTTP 做；LittleFS 只提供安全的本地读写
（wear-leveling + 掉电保护 + 原子 rename）。**

**设备端 fs_http_service（中间层，端口 80，禁止 include lvgl）**：
- `GET /fs/list` → JSON 文件列表（按扩展名分 image/audio）；
- `PUT /fs/upload?name=` → 流式分块写 `xxx.tmp`，完成 `rename()` 原子替换（掉电不损旧文件）；
- `GET /fs/file?name=` → 下载；`POST /fs/delete?name=` → 删除；`POST /fs/wallpaper?name=` → 设壁纸；
- 约束：上传前查剩余空间、图片<512KB/音频<2MB 上限、文件名白名单 `[A-Za-z0-9._-]`≤63、拒绝 `../` 路径穿越、简单 token；
  增删完成经事件队列通知 UI，不在 HTTP 回调里碰 LVGL。

**设备端文件浏览器（System 子页 Files 入口）**：
- 列出图片/音频（缩略+大小/时长），点图片走 PPA/JPEG 硬解全屏预览，点音频复用 audio_service 播放；
- 随文件增删事件自动刷新；长列表分页，不一次性加载全部缩略图进 PSRAM。

**PC 端文件管理 Tab（PySide6）**：列文件、拖拽上传（图片先 800×480 缩放压 JPEG）、下载、删除、设壁纸；
EventBus 与通话/录音/OTA 互不阻塞。

#### 5.6.1 与 UDP/TCP 模式的共存（关键权衡）

UDP 通话与 HTTP/TCP **不是二选一，可以同时跑**：它们只是 lwIP 上不同的 socket，
音频钉 Core1，网络/HTTP/LVGL 在 Core0，双核 + 16MB PSRAM 资源足够。
`session_manager` 互斥的是**音频传输模式**（UDP_CALL ↔ TCP_RECORD 抢同一份 mic/spk），
而 **fs_http_service 是常驻后台管理通道，不抢音频链路**。

真正要约束的只有一点——**写 Flash 会短暂关 cache，可能造成音频抖动/丢帧**：

| HTTP 操作 | 通话/录音进行中 | 说明 |
|---|---|---|
| list / download / 图片预览（只读） | ✅ 随时可用 | 不写 Flash，不影响音频 |
| 设壁纸（写小文件，<512KB） | ⚠️ 允许但限速/小块 | 写 Flash 停顿短，可接受 |
| upload 大音频 / delete（写 Flash） | ⏸ 排队到当前会话结束 | 避免长时写 Flash 抖动音频 |
| OTA 推固件 | ⏸ 必须停通话/录音 | 阶段六已定互斥 |

> 设计原则：**管理通道常驻，业务音频模式互斥**。通话中 PC 仍可列文件/预览/下载；
> 只有"写大块 Flash"这类会关 cache 的操作才需要避让。这样既不牺牲实时通话，又保留远程管理能力。

## 6. 双模式对比与切换

| 维度 | UDP 通话模式 | TCP 录音模式 |
|---|---|---|
| 优化目标 | 实时性、对话自然 | 完整性、可追溯 |
| 传输协议 | UDP（无连接） | TCP（可靠流） |
| 延迟目标 | **≤100ms 端到端** | 不敏感（秒级缓冲即可） |
| 丢包策略 | 丢包填静音/插值，可接受 ≤2% 丢包 | TCP 重传，**零丢帧** |
| 音频方向 | 双向全双工 | 设备→PC 为主（可选 PC→设备回放） |
| 数据落盘 | 不保存（实时流） | 整段 WAV 文件 + 索引 |
| 带宽占用 | 32KB/s（裸 PCM）或 8KB/s（G.722） | 32KB/s 连续 |
| 切换方式 | 设备 UI 触控 / 长按 BOOT 3s 循环切换；PC 端通过 UDP 信令 50003 同步模式 | |

### 7.2 进程内线程架构（一份音频两路消费）

```

   ▲ qtSignal(text/stat)
   │
ASR 线程         播放线程(sounddevice 回调)
   ▲ asr_q           ▲ play_q
   └────────┬────────┘
        NetRx 线程：UDP 50000 收包 → 去帧头/重排 → 同一帧 PCM 同时 put play_q 与 asr_q

```

                  └────────────────── EventBus (publish/subscribe, Qt信号队列) ──────────────────┘

- **每业务独立**：独立线程、独立 socket、独立配置分节、独立日志与异常隔离（单业务崩溃不拖垮全局、可单独重启）；

- **设备端同构**：每个 middleware service（audio/led/wifi/record/ota/wallpaper）都是独立任务+命令队列，
  事件经 dispatcher 订阅，互不直接调用（沿用现有 led_service/wifi_manager 模式）。

## 8. 缓冲、接口规范与传输层抽象（UDP/TCP 共用设计）

### 8.1 三级缓冲模型（DMA + 上下行 ringbuf + jitter 窗口）

实时通话在现有"硬件 DMA + 1024B 透传 ringbuf"基础上补成三级：

| 级别 | 所在层 | 职责 | 规格/策略 |
|---|---|---|---|
| L1 硬件 DMA | I2S RX/TX（esp_codec_dev 底层，已有） | 硬件周期搬运，不跑协议 | 6 描述符 × 10ms；DMA 回调只搬数据并 `xTaskNotify` 唤醒任务 |
| L2 任务级 ringbuf | audio_service 流式模式（新增） | 生产/消费速率解耦 | 上行 `mic_tx_rb` 8 帧≈5120B；下行 `spk_rx_rb` 目标水位 2–3 帧 |
| L3 jitter 重排窗口 | udp_voice | 乱序重排、丢包补偿 | 16 帧序号窗口，重排后再入 L2 |

**水位与反压**：
- 上行：正常只压 1–2 帧，上限 8 帧防突发；满则丢最旧并计数；
- 下行：低于低水位 2 帧补静音（防 underrun 爆音），高于高水位 6 帧丢最旧帧（防延迟累积）；
- 任务通知替代 `vTaskDelay` 轮询，调度抖动 ≤1ms；
- L2 为单生产单消费，用 SPSC 无锁 ringbuf（复用 `main/3rd/ringbuf`），仅跨核共享处加临界区；
- 核绑定：mic 采集 / spk 播放任务钉 **Core1**、优先级 7–8；UDP tx/rx、Wi-Fi、LVGL 在 Core0。
- 现有 `play_rb/rec_rb`（1024B 透传）保留给文件播放/录音命令模式，流式模式用独立更大的 ringbuf，互不影响。

**延迟预算**：L1 10–20ms + L2 播放水位 40–60ms + 网络 20–40ms ⇒ 端到端 <100ms；本地回环不经 L3 ⇒ ≤8ms。

### 8.2 通信接口规范（ICD，双端强约束）

双端必须共用同一份契约，详见 `docs/项目规划/通信接口规范_ICD.md`，要点：
- 采样契约：16000Hz / 16bit / mono / 小端 / 20ms = 640B 净荷（设备 C 宏与 PC Python 常量严格一致）；
- 音频帧（50000/50001）固定 12B 帧头：`magic(2)=A5 5A | ver(1) | type(1) | seq(2,LE) | ts_ms(4,LE) | len(2,LE)`；
  type 预留 0=PCM / 1=G.722 / 2=控制；640B+头远小于 1500B MTU，单帧不分片；
- 信令（50003）用 JSON：HEARTBEAT / HEARTBEAT_ACK / SESSION_START / SESSION_STOP /
  PTT_DOWN / PTT_UP / MODE_SWITCH；规定字段名、单位、心跳周期 1s / 超时 2s；
- seq 回绕（uint16）、时间戳基准（设备启动毫秒）、丢包/乱序/超时双端同语义；
- HEARTBEAT_ACK 携带 protocol_version / firmware / sample_rate，PC 启动时做兼容性校验。

### 8.3 传输层抽象（为模式二 TCP 预留）

- **audio_service 与传输无关**：流式只暴露 `audio_stream_read_mic()` / `audio_stream_write_spk()`，
  UDP 与 TCP 都只是 mic 数据的消费者 / spk 数据的生产者，音频层不感知网络；
- **voice_transport 统一接口**：`open/close/send_frame` + 注册 `on_recv_frame` 回调，
  `udp_transport`、`tcp_transport` 为两个实现；统一帧头，TCP 额外带 session_id/offset 支撑断点续传；
- **session_manager 模式状态机**：IDLE / UDP_CALL / TCP_RECORD 互斥，切换时先停旧传输再启新，
  复用同一 mic/spk 流；信令 MODE_SWITCH 预留；
- **PC 端对称**：`NetLink`(UdpLink/TcpLink) 抽象，播放/ASR/落盘只订阅帧流，不感知底层传输；
- 收益：阶段三 TCP 直接复用 2.0 流式音频与统一帧头，不重写音频链路。

### 8.4 实时性 / 稳定性 / 内存硬约束（阶段二必须满足）

1. **全双工任务模型**：拆 `mic_task`/`spk_task`（或单任务双非阻塞循环），ES8389 mic+spk
   会话期一次同时 open、常开，结束再 close；禁止每帧/每次收发 open-close codec。
2. **sdkconfig 实时前提**：`WIFI_PS_NONE` 关 Wi-Fi 省电（modem-sleep 会造成音频抖动尖峰）、
   锁最高 CPU 主频、禁 light-sleep、FreeRTOS tick=1000Hz、调大 LWIP UDP 收发 buffer。
3. **内存**：音频 ringbuf / jitter 窗口 / DMA buffer 必须放**内部 SRAM**（不走 PSRAM/cache）；
   实时队列与缓冲静态分配（`xQueueCreateStatic`）；640B 帧用帧池复用，禁止逐帧 malloc；
   ringbuf 索引 14bit，单 buffer ≤16383B；DMA buffer 4B 对齐、内部 RAM。
4. **核绑定/优先级**：mic/spk 钉 Core1 prio 7–8；udp tx/rx、link、LVGL 在 Core0；
   `uxTaskGetStackHighWaterMark` 实测各任务栈水位留 ≥30%。
5. **回调上下文**：wifi/button/audio 等回调只 post 命令到本模块任务，
   不在回调里直接操作 socket/codec/LVGL（参照 led_service 队列化，避免并发 Cache error）。
6. **网络 IO**：socket 非阻塞 + `select` 超时，单任务循环统一处理收包/命令/心跳，禁止阻塞 recv 卡死。
7. **回声门控**：设备 spk 播放 PC 下行帧期间，对上行 mic 做衰减/静音门控，防止自激啸叫（AEC 留 M5）。
8. **跨核 ringbuf 保护**：第三方 ringbuf 非线程/ISR 安全，双核共享处加临界区；去掉"put 后立刻 get"的透传冗余拷贝。
9. **事件订阅**：中间层事件改观察者/事件队列（多订阅者），替代"后注册覆盖"的单回调槽。
10. **音量单一数据源**：统一音量状态归属，硬件 vol±、UI 滑块、PC 下行播放共用一份。
11. **可观测**：统计丢包率/jitter/ringbuf 水位/栈水位/CPU 负载，供调优与验收。
12. **时钟语义**：帧 ts_ms 仅用于单端排序；双端不同步，延迟用 seq 到达间隔与信令 RTT 估算，禁止跨端绝对时间相减。

## 11. 阶段六：OTA 远程升级（A/B 双区 + 回滚防砖）

> 迁移自既有 STM32 IAP 串口升级项目（自定义分帧/CRC/重传/断电续传/PyQt 上位机），
> 但底层换成 ESP-IDF 原生 OTA 机制，**不自写 bootloader**。

### 11.1 STM32 IAP → ESP32 OTA 的本质区别（先读）
STM32 方案需要一个独立 IAP Bootloader 固件：复位进 bootloader、自己擦写 APP Flash 页、
校验后跳转。ESP32（ESP-IDF v6.1）由 ROM + 二级 bootloader + `app_update`(esp_ota_*) 组件
原生提供这些能力，运行中的 APP 直接把新固件写进**备用分区**，写完切槽重启即可。
因此迁移保留的是**协议工程思想**，落盘/切换/防砖交给 IDF：

| STM32 IAP 做法 | ESP32-S31 阶段六做法 |
|---|---|
| 独立 IAP Bootloader 固件 | 不写，用 IDF 二级 bootloader + app_update 组件 |
| 手动擦写 APP Flash 页 | `esp_ota_begin/write/end` 写备用槽 ota_1 |
| 专用 Flash 页存断电偏移 | nvs 存 offset（可选；WiFi 重下更简单） |
| 校验后跳转 APP | `esp_ota_set_boot_partition` + `esp_restart` |
| 固件级 CRC32 运行校验 | esp_ota 内置 SHA256 校验（签名 secure boot 列后续） |
| 自行判断成败 | **IDF 原生 rollback：PENDING→VALID，失败自动回滚** |
| UART 自定义帧（SOF/EOF/SEQ/CRC32） | WiFi/TCP 应用层 OTA 协议（保留分帧/ACK/offset/块校验思想） |
| '!' 复位进 bootloader | 运行态直接接收，无需复位进独立 bootloader |
| PyQt6 上位机 | pc_host PySide6 OTA 面板（保留错误注入/百分比限制器） |

### 11.2 分区与配置（阶段 1.5 已落地，布局见 5.0）
- ota_0 / ota_1 各 **3MB(0x300000)** + otadata；**不设 factory**（省空间，极端变砖走 USB 重刷）；
- 当前运行槽为 ota_0，烧录走 bootloader+otadata+ota_0（storage littlefs 镜像另烧 @0x620000）；
- app bin 现≈1.63MB，槽余量≈1.37MB，构建脚本需校验 bin 不超槽（超了构建即失败）；
- 开 `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`（回滚）；
- 单 storage littlefs：OTA 只换 app 槽，素材/录音不被擦除；如需 coredump 可后续从 storage 临时划出。

### 11.3 OTA 应用层协议（TCP，端口 50004；控制可复用 50003）
TCP 已保证有序可靠，故 STM32 的 SEQ/CRC 重传可简化，但保留分帧与端到端校验：
1. `OTA_BEGIN`：固件字节数、版本号、整包 **SHA256**、目标槽；设备回 ACK（允许/剩余空间）；
2. 数据块：`len(4,LE) | offset(4,LE) | [crc32(4,LE)] | payload`，建议 4KB/块；
   每 N 块或每块回 `OTA_ACK{next_offset}` 做流控与进度；块 CRC 作纵深防御（TCP 下可选）；
3. `OTA_END`：设备 esp_ota_end → 校验整包 SHA256 → set_boot_partition → 回结果 → 延时重启；
4. 断点续传（可选）：offset 存 nvs，重连后 PC 从 next_offset 续发（对应 STM32 断电续传）；
5. 中止 `OTA_ABORT`：擦除未完成的备用槽，回到 IDLE。

### 11.4 设备端 ota_service（新增中间层，状态机）
`IDLE → RECEIVING(写 ota_1) → VERIFY(SHA256) → PENDING(set_boot+重启) → VALID / ROLLBACK`
- 独立任务 + 命令队列，socket 收块→队列→esp_ota_write，不阻塞 UI/音频；
- **升级期间暂停通话与录音**（与 rec_cache 写 Flash 互斥），UI 进升级进度页；
- 写 Flash 期间会短暂关 cache，禁止在此时段执行 Flash 映射代码/长关中断（规避此前 Cache error 同类问题）；
- **回滚自证（防砖核心）**：新固件首次启动为 `PENDING_VERIFY`，必须满足自证条件后调
  `esp_ota_mark_app_valid_cancel_rollback()`，否则下次重启自动回滚旧槽；
  自证条件建议：启动后关键任务（WiFi/音频/UI）初始化成功 + 30s 内无崩溃 + PC 心跳确认在线。

### 11.5 PC 端 OTA 面板（pc_host/ota + ui/ota_tab，拖拽升级 + 版本控制）
**拖拽升级流程**：
1. OTA Tab 提供拖拽区，拖入构建产物 app bin（或 `bin + manifest.json` 固件包）；
2. `firmware_pkg` 解析 bin 固定偏移内嵌的 `esp_app_desc_t`（version/idf_ver/编译时间）并现算 SHA256、大小；
3. 与心跳上报的**设备当前版本**比对（versioning）：新版=绿色可升级，同版=灰色重复刷，旧版=黄色降级警告；
4. 点开始：OTA_BEGIN 握手（大小/SHA256/版本）→ 分块推送（进度条/速率/ETA，ACK 流控）→
   设备校验切槽重启 → 心跳重新读到新版本号判定成功；若设备回滚旧版则红字提示"未通过自证已回退"。

**版本控制**：
- `firmware/` 按版本归档每个 bin + 自动生成 manifest（版本/git commit/编译时间/SHA256/大小）；
- sqlite 记录升级历史（时间、from→to、结果、耗时、失败原因），可从历史中选任意旧版本重推（回退）；
- 构建脚本（idf.py build 后）自动导出 bin 并生成 manifest，保证拖入即带完整版本元信息。

**迁移自 STM32 上位机的调试利器**：CRC 错误注入、百分比限制器（只发前 N%，测断电/续传/回滚）、
收发包着色日志、中止/续传按钮。

### 11.6 版本与安全
- 用 `esp_app_desc_t` 的 version/idf_ver 上报，PC 做版本比对与降级提示；
- 阶段六先做 **SHA256 完整性**；固件签名（secure boot v2）、加密、eFuse anti-rollback 列后续可选，
  不提前烧 eFuse（不可逆）。

### 11.7 阶段六验收
- 正常 OTA：推新固件→切槽重启→新版本上线、旧槽保留；
- 坏固件回滚：推送故意损坏/无法自证的固件，设备自动回到旧版本且可继续工作；
- 断电测试：传输出错/中途断电不变砖，重连可续传或重下；
- OTA 与录音/通话互斥正确，assets 素材不被擦除；版本号正确上报。
