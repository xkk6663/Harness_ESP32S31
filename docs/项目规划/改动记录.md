## 0. 背景与目标

本工程基于 esp-bsp 官方示例 `display_audio_photo`（单文件 `app_disp_fs.c` 1032 行，LVGL 文件浏览 + WAV 播放/录音）进行多轮重构，目标是在此骨架上迭代出"设备 ↔ PC 双通道传声机"：

- **UDP 低延迟通话**：端口 50000/50001，20ms 帧，乱序重排 + 丢包补偿；
- **TCP 整段录音**：端口 50002，WAV 落盘；
- **信令通道**：端口 50003。

音频参数：16 kHz / 16 bit / mono = 32 KB/s，20 ms = 640 B/包。

## 3. 阶段三：FreeRTOS 常驻任务 + 命令队列重构

### 7.4 卡机修复（2026-09-13 当晚）
- **现象**：开屏上拉进入主 UI 时直接卡死（hard fault）；
- **根因**：`ui_disp.c` 里 `lv_obj_get_child_cnt(tab_btns)` 在 `tab_btns = lv_tabview_get_tab_btns(tabview)` 赋值**之前**就执行了，tab_btns 还是 NULL，NULL 解引用直接崩；
- **修复**：把 tab_btns 赋值、样式、事件注册、子对象 EVENT_BUBBLE 遍历按正确顺序重排（先 get_tab_btns，再遍历子对象，再 add_event_cb）；

- 二次烧录验证：上拉进主 UI 正常，下拉壁纸拉出/上拉关闭正常。

### 7.5 ESP32-S31 2D-DMA / PPA 调研结论
纠正此前"ESP32-S31 没有独立 2D DMA"的错误判断：
- ESP32-S31 集成独立 **2D-DMA**（AXI 主机，4 TX + 3 RX 通道，非对齐传输，宏块重排，CSC）；
- **PPA**（Pixel Processing Accelerator）：旋转/缩放/镜像/叠加，ESP-IDF 组件 `esp_ppa`（路径 `components/esp_driver_ppa/include/driver/ppa.h`）；
- **JPEG 硬解**：`esp_video` 组件支持（本工程 idf_component.yml 已含）。

### 7.6 LVGL 内置 PPA draw unit 尝试（结论：S31 暂不可用）
- 在 sdkconfig.defaults 加 `CONFIG_LV_USE_PPA=y` 尝试编译，两个硬错误：
  1. `#error "CONFIG_LV_DRAW_BUF_ALIGN must be equal to CONFIG_CACHE_L2_CACHE_LINE_SIZE"` —— ESP32-S31 没有 L2 cache，此 Kconfig 只在 ESP32-P4 定义；
  2. `fatal error: driver/ppa.h: No such file or directory` —— 即使 main 组件 PRIV_REQUIRES 加 esp_driver_ppa，LVGL 的 PPA draw unit 代码路径依赖 P4 的 L2 cache 假设；
- **结论**：LVGL 9.5 内置 `lv_draw_ppa` 当前仅支持 ESP32-P4（LVGL 官方文档"Supported devices"也只列 P4）。ESP32-S31 硬件有 PPA，但 LVGL 这版尚未适配；
- 已回退 sdkconfig.defaults（PPA 注释掉），恢复软件渲染；
- **后续路径**：
  - 等 LVGL 新版本适配 S31 后开 `CONFIG_LV_USE_PPA`；
  - 或自己写 draw unit 直接调 `esp_driver_ppa` API（工作量大，暂缓）；
  - JPEG 硬解（`esp_video` 的 PJPG）仍可作为开屏加速方向。

### 8.2 ADC 分压按键
- 硬件：R77=10K 上拉到 3V3，4 键共 ADC1_CH0 = **GPIO42**；
- BSP 默认区间（1770/1240/819/380 mV）与实测偏差大，3 个键不触发；
- 实测 mV（IO42）：
  - **set**  ~260 mV
  - **mode** ~759 mV
  - **vol-** ~1237 mV
  - **vol+** ~1647 mV
- 在 `button_service.c` 直接用 `iot_button_new_adc_device` 创建 4 个按键，配实测区间 ±100 mV；
- 与官方 factory_demo 写法对齐：注册 PRESS_DOWN / PRESS_UP / SINGLE_CLICK / DOUBLE_CLICK / PRESS_END 5 个事件。

### 8.3 音量消息队列 + 互斥锁
- `button_service` 内部 `SemaphoreHandle_t` 保护音量值（初始 70，范围 0–90）；
- 单击 vol-/vol+ → ±10；双击 → ±20；
- 音量变化通过 `QueueHandle_t`（深度 4）发 `btn_vol_msg_t`；
- UI 层 `ui_settings.c` 用 `lv_timer`（100 ms）抽队列，更新滑块并下发 `AUDIO_CMD_SET_VOLUME`；
- 滑块拖动时反向同步 `button_service_set_volume()`。

### 18.2 保留不动、但已写进代码注释的决策

- **P2-5 `cam_task` 不扩栈**：深度推理 `detector->run()` 跑在 **LVGL 线程**（`tab_camera::refresh()`），
  不在 cam_task 上，所以 cam_task 峰值只有 2,140 B。判据留给 `main.c` 的 `[stack]` 表（`hwm ≤ size/8` 报警）。
- **P3-1 摄像头硬件不真关**：`esp_video_deinit()` 确实存在，但 BSP 把 XCLK 句柄丢在
  `bsp_camera_start()` 的**局部变量**里、从不 free ⇒ 两条路都有代价（见方案 §10.3）。收益是功耗不是内存 ⇒ 不动。
- **P3-4 `cam_task` 不做"只建一次"**：那会引入开机常驻任务（6 KB 内部栈），违反方案 §7-6；
  且 **本项目历史已证伪**——2026-09-18 试过"独立 face_load 任务（8 KB 栈）"，结论是"多占内部 RAM、加剧碎片"，
  最后靠回退到"无额外任务"的基线才通。现有"按需建/删 + P0-3 修好的退出确认"更省。
- **P3-3 不做**：省的是 PSRAM，不是内部 RAM，不是当前瓶颈。

### 18.3 三条勘误（避免后人重复踩）

1. **`uxTaskGetStackHighWaterMark()` 是"历史最小剩余"，不是"用量"。**
   上一版全任务水位表拿 hwm×1.5 当 need，结论**完全反向**：几乎不用栈的任务被标"偏紧"、
   吃满栈的任务被推荐缩到 1536。正确口径 `used = size - hwm`，`need = used×1.5`（↑512），
   且 `size - need ≥ 2048` 才值得缩、`hwm ≤ size/8` 该加不该缩。
2. **方案 §4-P2-3 的"合并进 ringbuf pool 直接取址"不可行**：`main/3rd/ringbuf` 只有
   `put/get/peek`，没有 claim/commit 零拷贝、也没有"跳过 N 字节"；`discard[]` 与 `spk_frame`
   分属不同任务，不能共用一个缓冲。
3. **`net_time_service.c` 的缓冲改指针后**，所有 `sizeof(s_http_buf)` 都会静默变成 4/8 ——
   已全部替换为 `NET_TIME_HTTP_BUF`，并在声明处写了约束注释。

### 20.2 花屏根因修复（本次主要内容）

**改动 = 两处配置的 `choice` 互换**（`BSP_LCD_RGB_REFRESH_MODE` 二选一）：

| 文件 | 改动 |
|---|---|
| `sdkconfig` | 删 `CONFIG_BSP_LCD_RGB_BOUNCE_BUFFER_MODE=y` 与 `..._HEIGHT=10`；置 `CONFIG_BSP_LCD_RGB_REFRESH_AUTO=y` |
| `sdkconfig.defaults` | 同步（并在注释里写全原理） |

**一句话原理**：bb 模式要求**软件每 444 µs 在 GDMA EOF 中断里把 16,000 B 从 PSRAM 搬到内部缓冲**；
auto 模式把整帧 768,000 B 预串成一条 DMA link list，**GDMA 自己扫，软件不参与供数**
⇒ flash 擦写窗口内**没有"必须由软件完成"的动作可漏**。

**为什么不打开 `LCD_RGB_ISR_IRAM_SAFE`**：IDF 在 `esp_lcd_panel_rgb.c:1041` 自己写了警告 ——
*"if the frame buffer is behind a cache, and the cache is disabled, crash would happen here when
auto write back happens"*。开 `ISR_IRAM_SAFE` ⇒ 那个 ISR 会**真的去读 PSRAM** ⇒ **崩溃**
（比花屏更糟）。⇒ 它是**反向开关**。

**为什么不选 `SPI_FLASH_AUTO_SUSPEND`**：IDF 6.1 help 明说 *"supported only for specific flash
chips"*、需 *"contact Espressif Business support"* ⇒ 有**变砖**风险，收益与风险不匹配。

**唯一前提**：pclk 只有 **18 MHz**（`esp32_s31_korvo_1.h:497`）。bb 模式的卖点本就是
*"higher PCLK at the cost of higher CPU"*（BSP Kconfig `:105`）⇒ 这个能力本工程用不上。

**诚实边界**：flash 擦写窗口内 GDMA 直读 PSRAM 是否也受影响，**IDF 没有结论**
（`cache_utils.c:172-175` 只保证 "None of these **CPUs** will touch external RAM"，**通篇未提 DMA**）。
⇒ 只能靠上机看图。若仍花屏，下一手 = 实验 B（PHY 校准不落 NVS）。

### 20.3 同步改准的注释（5 个文件）

### 22.1 起因

### 22.2 ★★ 本轮最重要的认知：`CONFIG_BSP_SD_MOUNT_POINT="/littlefs"` 是【故意复用】

**我 v2 方案曾断言它是"改错了、应改回 `/sdcard`"，并据此推荐用 BSP 的
`bsp_sdcard_sdmmc_mount()` 复用其 feature_enable —— 这是错的，已自纠。**

实施时逐行读组件源码才发现：它是**故意的模型路径 hack** ——

| 位置 | 内容 |
|---|---|
| `managed_components/espressif__human_face_detect/human_face_detect.cpp:23` | `path(CONFIG_BSP_SD_MOUNT_POINT) / CONFIG_HUMAN_FACE_DETECT_MODEL_SDCARD_DIR / model_name` = `/littlefs/models/<model>.espdl` |
| `main/middleware/camera/face_service.cpp:53` | `#define FACE_MODEL_DIR (CONFIG_BSP_SD_MOUNT_POINT "/" CONFIG_HUMAN_FACE_DETECT_MODEL_SDCARD_DIR)` = `/littlefs/models` |
| `sdkconfig:4008` / `sdkconfig.defaults:122` | `"/littlefs"`（main 分支同项 = `"/sdcard"`） |
| `littlefs_content/models/` | 正好 4 份 `.espdl`，**合计 1,186,432 B**（已 `ls` 核对）⇒ 路径与文件严丝合缝 |

**★★ 最易看错处**：组件 `human_face_detect.cpp:10-13` 有
`#if !defined(CONFIG_BSP_SD_MOUNT_POINT) #define ... "/sdcard" #endif` ——
它是 **`!defined` 保护**的，而 sdkconfig **定义了**该宏 ⇒ **兜底不生效**。
只看这一句会得出**相反结论**。

**改成 `/sdcard` 的后果**：模型路径变 `/sdcard/models/...` 而文件仍在 littlefs
⇒ **三档人脸模型全部加载失败、FACE 功能彻底废掉**。

**连带认知**：`CONFIG_HUMAN_FACE_DETECT_MODEL_IN_SDCARD=y` 只是"**从文件系统读**"的开关
（不是"放 SD 卡"的意思）；真正决定"哪个文件系统"的是 `BSP_SD_MOUNT_POINT`。

**★ 另一个连带结论**：**不能用 BSP 的 `bsp_sdcard_sdmmc_mount()`** ——
它内部写死 `esp_vfs_fat_sdmmc_mount(BSP_SD_MOUNT_POINT, ...)`（`bsp_storage.c:141`），
会把 FATFS 挂到 `/littlefs`，与 LittleFS **同点注册、必然失败**。

### 23.1 ★★★ 本轮最重要的认知：`VIDIOC_S_FMT` 在 DVP 上**改不了格式**

**这一条推翻了本方案 §2.2 / §2.5.4 / §2.5.6 的一处原始说法**（原写"切格式 = `VIDIOC_S_FMT`"），
必须改口径，否则后续所有 S2a/S2b 的实现都会走错路：

- `esp_video_dvp_device.c:381 dvp_video_set_format()` **写死**：只要请求的
  `width/height != CAPTURE_VIDEO_GET_FORMAT_WIDTH/HEIGHT(video)` ⇒ **直接 `EINVAL`**；
  且它**只校验、不碰传感器**（唯一例外：sensor 当前是 RGB565 时会校验 pixelformat）。
- 真正换格式的入口是 esp_video 的**私有 ioctl**：
  `VIDIOC_S_SENSOR_FMT`（`esp_video_ioctl.h:24`）
  → `esp_video_ioctl_set_sensor_format()`（`esp_video_ioctl.c:355`）
  → `dvp_video_set_sensor_format()`（`esp_video_dvp_device.c:453`）
  → `esp_cam_sensor_set_format()` → `ov3660_set_format()`。
- `dvp_video_set_sensor_format()` 切完后**紧接着重跑 `init_config()`**，
  用**新 sensor 尺寸**重算并分配流缓冲（`esp_video_config_buffer(video, &format, DVP_MEM_CAPS)`）
  ⇒ **方案 §2.5.7 的"风险 1：JPEG 720p 缓冲够不够大"由设计化解** —— 前提是只能从
  `S_SENSOR_FMT` 这条路进；绕道 `S_FMT` 则连门都进不去。

**推论 1**：`ov3660_set_format()` 要求 `format->regs` **非 NULL**
（`ov3660.c:558-577` 会把它强转成 `ov3660_reginfo_t *` 去写寄存器）⇒ 自备描述时必须带完整寄存器表。
**推论 2**：寄存器表在 `esp_cam_sensor/sensors/ov3660/private_include/`（**不导出**），
BSP 与 esp_video 都不暴露 sensor 句柄，`esp_cam_sensor_query_format()` 也拿不到 `regs`
⇒ 只能**引用**该私有目录（见 `main/CMakeLists.txt` 末的 `target_include_directories`）。
**推论 3**：`ov3660_set_format()` **每次都会**重写整组 default regs + AE level + 格式组，
而格式组里**不含** 0x3820/0x3821 的翻转位 ⇒ **翻转必须在每次 start 后重设**（已在 `camera_service.c` 里落实）。
**推论 4**：OV3660 只有 5 档（`ov3660.c:67-151`），**没有 1280×720 RGB565** ⇒
方案 §4.1 的"路线 B（RGB565+软件编码做 720p）"**不成立**，路线 A 是唯一解。

### 24.3 ★★ 关键取舍：录像**在 cam_task 回调里同步写盘**

方案 §5.1-④ 的原文要求是"**不丢帧**，宁可降 fps 也不要丢帧"。
回调内同步 `fwrite` 恰好满足：

- 每一帧**只要被回调到就一定完整写下去**；
- 代价是写盘期间占着 DVP 缓冲 ⇒ **出帧率自然下降** —— 这正是方案认可的降级方向；
- **零额外缓冲**（不必赌 720p JPEG 到底多大，那正是 §2.5.7 风险 1 的未知量）。

反方向（memcpy 进环形池 + 独立写任务）需要 3~4 块 200 KB+ 的 PSRAM，且**池满必须丢帧**

### 24.4 ★ 生命周期上的硬约束（代码里都写了原因）

1. **`fclose` 只在 `camera_service_stop()` 返回 `ESP_OK` 之后做** ——
   只有那一刻才保证"不会再有帧回调触到那个 `FILE`"。
   stop 超时（相机卡死）时**故意泄漏 `FILE`/muxer**，也绝不和活着的 `cam_task` 抢 —— 那是确定的 UAF。
2. **收尾里的重扫（生成 idx1）跑在服务任务里，绝不在 LVGL 线程** ——
   大文件要好几秒，同步等 = UI 直接僵住。
3. 出错（写失败 / 卡拔了）时走 `avi_muxer_abort()` 而**不是** `close()` ——
   后者要 `fseek` 回文件头写十几处并重扫全文件，在坏卡上必然再失败一遍。
4. **拍照/录像都允许接管 CAM 预览**（方案 §2.5.4 步骤①），
   但**绝不接管另一路 MEDIA 会话**（那会掐断别人的录像）。

## §25 2026-09-25 九轮：真机 build 报错/警告清理 + 校验工具的一处**根本性纠错**

用户贴出真实 `idf.py build` 日志（`-Werror` 拦下构建 + 一屏警告），要求"解决报错和警告"。
本轮不止修代码，还**挖出了一个校验工具的盲区** —— 此前几轮"探针全绿"其实一直漏检。

### 25.1 ★★★ 报错根因：`-Werror=format-truncation=` 是**依赖内联**的诊断

```
record_video_service.c:106/107: error: '%s' directive output may be truncated writing
up to 39 bytes into a region of size between 32 and 95 [-Werror=format-truncation=]
   inlined from 'rec_task' at record_video_service.c:195:16
```

拆解（**这句 `inlined from` 是关键**）：

| 项 | 值 |
|---|---|
| `snprintf(out, out_len, "%s/%s.avi", dir, base)` 里的 `base` | 由 `strftime` 填充 ⇒ **GCC 无法界定长度** ⇒ 按 `char base[40]` 的最坏情形估"最多写 39 字节" |
| 目标 `out`（= `char path[96]`）的真实大小 | **只有 `make_video_path()` 被内联进 `rec_task()` 之后** GCC 才知道 |
| 最坏输出 | (dir ≤63) + `/` + (base ≤39) + `"_099.avi"`(8) + NUL = **112** > **96** |

⇒ `char path[96]` 在物理上就装不下最坏情形。这不是"误报"，是**真缺陷**（会静默截断文件名）。

**修法**（三段式，缺一不可）：

```c
#define REC_DIR_BUF      64
#define REC_BASE_BUF     40
/* ① 编译期锁死容量关系，谁改小了立刻编译失败 */
_Static_assert(VIDEO_REC_PATH_MAX > (REC_DIR_BUF - 1) + 1 + (REC_BASE_BUF - 1) + sizeof("_099.avi"),
               "VIDEO_REC_PATH_MAX too small: snprintf may truncate (-Werror=format-truncation=)");

static int make_video_path(char *out, size_t out_len)
{
    /* ② 真防线 + 让 GCC 能推断出 "out_len >= VIDEO_REC_PATH_MAX" ⇒ 才能证明不截断 */
    if (out_len < VIDEO_REC_PATH_MAX) { ESP_LOGE(...); return -1; }
    ...
}
/* ③ 容量 96 → 128（头文件里的 VIDEO_REC_PATH_MAX / CAPTURE_PATH_MAX） */
char path[VIDEO_REC_PATH_MAX] = {0};
```

`capture_service.{c,h}` 是**同一个缺陷**（`CAPTURE_PATH_MAX` 96 → 128），一并修。
日志里只报了录像，但拍照是同样的 `snprintf("%s/%s_%03d.jpg")` 结构 —— **不修就是等下一轮报**。

### 25.2 ★★ 警钟：为什么前几轮的"探针全绿"没抓到它

技能 `esp-idf-syntax-check` 原设计用 **`-fsyntax-only`**。而：

> **`-fsyntax-only` 不跑优化器 ⇒ 所有"依赖内联"的诊断全部消失。**

**对照实验**（同一份故障代码、工程真实 IDF gcc 14.2.0、`-std=gnu23 -O2`）：

| 方式 | `format-truncation` 命中 |
|---|---|
| 真实编译 `-c` | **2 条**（真机 build 就是这里炸的） |
| `-fsyntax-only` | **0 条** ← 探针静默放过 |

⇒ 已把技能与探针的默认行为改成**真实编译**（`-c -o <os.devnull>`，产物丢空设备、不落盘），
代价仅 **约 +1 s/文件**（实测 1.36 s → 2.39 s）。想要快可显式 `--syntax-only` 降级，
但**交付前终检必须用默认真实编译**。

**负向自测实证**（本轮实跑，已复原）：把 `record_video_service.c` 临时还原成故障态
（`path[96]` + 摘掉容量防线）后：

```
[FAIL] record_video_service.c  rc=1
  error: '%s' directive output may be truncated writing up to 39 bytes into a region
         of size between 32 and 95 [-Werror=format-truncation=]
         inlined from 'rec_task' at ...:211:16          ← 与真机日志逐字一致
```

而同一份代码走 `--syntax-only` 依然是 `[OK]`。故障态复原后 md5 与备份一致、`NEGTEST` 残留为 0。

### 25.3 第二个盲区：警告被 ANSI 转义码吃掉

真实编译命令里带 **`-fdiagnostics-color=always`**，输出形如 `\x1b[01m\x1b[Kwarning: \x1b[01m…`，
会把"行首匹配"的正则**整体废掉** —— 症状是"gcc 明明报了警告，探针一个字不显示"。
**修法**：解析前先 `ANSI_RE = re.compile(r"\x1b\[[0-9;]*[A-Za-z]")` 剥色。

### 25.4 第三个盲区：`-Werror` 是"**部分豁免**"的，`returncode==0` ≠ 干净

本工程真实旗标（dump 自 `build/compile_commands.json`）：

```
-Wall -Werror -Wno-error=unused-function -Wno-error=unused-variable
-Wno-error=unused-but-set-variable -Wno-error=deprecated-declarations
-Wextra -Wno-error=extra -Wno-unused-parameter -Wno-sign-compare
-Wno-enum-conversion -O2 -std=gnu23
```

⇒ `deprecated-declarations` / `unused-function` 只是 **warning**，**不拦构建**。
若只看 `returncode`，会把"真机一屏警告"误报成 `[OK]`。
**修法**：探针通过时也**必须列出警告**（`[WARN]` 标签 + 按消息去重计数 + `TOTAL` 行附"其中 N 个带警告"）。

## §26 2026-09-25 十一轮：照片/视频**发紫** —— F49（`0x4514` 读出顺序未随镜像同步）

用户报告："我刚刚检查了 sd 卡里的内容：视频、照片都成功保存了，但是画面是紫色的，
不是相机正常的颜色"。

### 26.1 取证：先拿真值（新增两个**零依赖**探针，已沉淀进技能）

| 探针 | 依赖 | 产出 |
|---|---|---|
| `.workbuddy/jpeg_hdr_probe.py` | 纯 stdlib | JPEG marker 链 / SOF 分量表 / SOS 选择子 / APP14 `transform` |
| `.workbuddy/jpeg_pixel_probe.ps1` | .NET `System.Drawing`（**装不上 Pillow，代理也没开**） | 通道均值 + 「原样 / R↔B 互换」并排对比图 |

样张 `IMG_20260925_220937.jpg` = **50,964 B**，与上电日志 `photo OK: 50964 bytes`
**逐字一致**（先确认"就是设备刚拍的那张"）。头结构 = 教科书级 4:2:2 baseline
（`id=1 2:1` / `id=2,3 1:1`、标准 DHT、**无 APP14 Adobe 标记**）。
通道均值 **R=122.71 / G=92.56 / B=122.22**。

### 26.2 ★★★ 关键推理：均值否掉"红蓝互换"（本轮最省时间的一步）

`R↔B` 互换是**双向重标号**（中性 → 中性）；`Cb/Cr` 互换只改 G、**精确保持 R、B**。
两者**都不能**把一面中性墙变成品红。⇒ 症状是**色度整体被抬高**（反推 ≈ Cb 138 / Cr 141）。
**这一步一次性排除"改通道顺序（0x4300 / 0x501F）"整条路线。**

### 26.3 根因：`0x4514`（读出顺序）未随 HFLIP+VFLIP 同步

依据 esp32-camera 的 `ov3660.c::set_image_options()` —— `0x3820` / `0x3821` / `0x4514`
必须**成组写**，`0x4514` 按 `(binning, vflip, hmirror)` 查表：

| 组合 | `0x4514` |
|---|---|
| 不 binning + 不镜像 | `0x88` ← 供应商 720p 表给的就是它 |
| 不 binning + V翻 + H镜像 | **`0xbb`** ← 本工程 720p 实际需要 |
| binning + 任意镜像 | `0xaa` ← 供应商 240×240 表给的就是它 |

本工程**总是**开 HFLIP+VFLIP（搬走 CPU 侧 180° 旋转）⇒
240×240(binning) 需 `0xaa`、**供应商表恰好同值 ⇒ 漏洞被掩盖 ⇒ 预览正常**；
720p(非 binning) 需 `0xbb`、供应商表给 `0x88` ⇒ **读出相位错位 ⇒ 发紫**。
**供应商表没错，错在"我们加了镜像却没同步 `0x4514`"。**

## §27. VIDEO 页实时取景器（2026-09-25）：硬件 JPEG 解码 + 稀疏抽点

**需求（用户原话）**："就跟正常的相机设备一样，原画面可见，拍摄，录视频的原画面可预览。"
→ 拍照/录像期间取景器必须**继续刷新**，不能只是空闲时有画面。

### 27.1 能力边界勘察结论（三条都核实过，别再重查）

| 问题 | 结论 | 证据 |
|---|---|---|
| `esp_new_jpeg`（espressif__esp_new_jpeg） | **纯软件解码** | `nm -u` 其 esp32s31 静态库只有 `idct_block_8_8/4_4/4_8`、`dct2d`、`jpeg_dec_huffman` 等自带 SW 符号，**无任何 ROM/硬件符号**；支持 scale 但熵解码是全分辨率，缩不掉多少 CPU |
| S31 硬件 JPEG **解码器** | **存在且可用** | `SOC_JPEG_DECODE_SUPPORTED=1`（sdkconfig:824）；IDF `esp_driver_jpeg` 提供 `jpeg_new_decoder_engine / jpeg_decoder_process`；**esp-dl 已经把它拉进构建图**（`esp-dl/vision/image/dl_image_jpeg.hpp` + 其 CMakeLists:68） |
| 硬件解码能否降采样 | **不能** | `jpeg_decoder_process` 无 scale/roi 参数 ⇒ 只能全尺寸出图 1,843,200 B（1280x720 RGB565），再自己稀疏抽点 |

另：`esp_video` 的 `ESP_VIDEO_ENABLE_HW_JPEG_VIDEO_DEVICE` 是**编码器** M2M（`esp_video_jpeg_device.c:14` include 的是 `driver/jpeg_encode.h`），对解码无用；`esp_video_render` 是 GMF 系重型合成框架（自带 20 KB 栈 blend 线程、自管 framebuffer/flush），与本工程 esp_lvgl_port 管线冲突，不用。

**2D-DMA 无争用**：`CONFIG_LV_USE_DRAW_DMA2D is not set`、`LV_USE_DRAW_SW=y` ⇒ LVGL 走软绘，硬件解码独占 2D-DMA。

### 27.2 选型：硬件解码 + 1/4 稀疏抽点

- 720p → **320x180**（4 是 1280 与 720 的公约数；1/2=640x360 每帧读 921 KB，1/8=160x90 太小）。
- 抽点循环只读 **180/720 行**（跳过的行完全不碰 ⇒ 不产生 PSRAM 事务）= 460 KB/帧 + 写 115 KB，约 5 ms。
- 限速 **150 ms/帧（≈6.7 fps）**：把 PSRAM 带宽（~7 MB/s）与 CPU 留给录像；若上机发现"实测 fps"被拉低，先调大 `VF_MIN_INTERVAL_US`（viewfinder.c）。
- 缓冲 **开机预分配、常驻、永不 free**（≈2.2 MB PSRAM：出图 1,843,200 + staging 192 KB + 显示双缓冲 2x115 KB）。理由：PSRAM 被切碎后 1.8 MB 大块运行中拿不回来；且进 `[mem]` 分步账单。
- 解码任务 `vfind`：**core 1、prio 4、4096 内部栈**（cam_task 是 core1/prio5 ⇒ 永远抢得过它）。

### 27.3 ★★ 颜色字节序是钉死的（再"调一下试试"必错）

`esp_hal_dma/include/hal/dma2d_types.h:133-141`：*"This scramble only fits 3 bytes/pixel format. For non-3 bytes/pixel format, the pixels will be messed up if scrambling is used."*
`esp_driver_jpeg/jpeg_decode.c:563-575`：只有 `rgb_order == JPEG_DEC_RGB_ELEMENT_ORDER_RGB` 才给 RGB565 挂 `BYTE2_0_1` scramble。
⇒ **RGB565 必须用 `JPEG_DEC_RGB_ELEMENT_ORDER_BGR`**（= 不 scramble = 小端，正是 LVGL 需要的；对照 tab_camera 收到的 OV3660 原生 RGB565 是**大端**所以才要逐像素 swap）。这条与 F49 的 `0x4514` 无关，别混。

### 27.4 数据通路（关键：观察者让"录像中也能看"成立）

```
cam_task(720p JPEG 帧) ──camera_service 观察者──> viewfinder(限速 + memcpy staging + give 信号量)
                                                      └─> vf 任务(硬解码 → 抽点 → 双缓冲发布)
                                                              └─> tab_video::refresh() → lv_canvas_set_buffer()
```
- `camera_service` 新增 `camera_service_set_observer(cb,user)`：**一帧两个消费者**，先主回调再观察者；观察者必须在 `V4L2_BUF_FLAG_DONE` 层内、但要在 `s_cb &&` **之外**（取景流主回调是 NULL）。硬约束：cam_task 上下文、不得碰 LVGL、只许一次 memcpy。
- `capture_service` / `record_video_service` **零改动**：它们接管后起的仍是 720p JPEG 流，观察者照样收帧 ⇒ 拍照/录像期间取景器继续刷新。
- 取景流 owner 用 **PREVIEW**（不是 MEDIA）：这样拍照/录像的"接管 → 归还"事务结束时 `camera_service_restore_preview()` 会**原样**把取景流拉回来，本页无需参与。
- 格式相同 ⇒ `apply_sensor_format()` 判"已在目标档"直接返回 ⇒ **拍照不再重写寄存器、不再 AE/AWB 黑一下**。

### 27.5 UI（用户拍板："卡片式 + 点击放大"）

- **本页改绝对定位**（原来是 flex）：放大要 `lv_obj_set_pos` 移动画布，flex 会抢定位权；主题 pad 全部归零，内容区 = 776x408。

### 27.7 静态校验 + 顺带修的既有 bug

### 27.8 上机验收判据（重烧后按顺序看）

1. 开机 `[mem] after viewfinder_init`：PSRAM free 应**减 ~2.2 MB**，INT free 基本不动。
2. 切到 VIDEO 页：`CAM: stream fmt: JPEG 1280x720 owner=1` → `VFD: enabled (observer attached, 320x180 @ ~150 ms)` → 画面出现且颜色**正常**。

4. 按 REC：录像继续、`VFD` 持续打点、**画面不冻结**；仪表盘 `fps` 与不开取景器时对比，降幅应在 1 fps 以内。

7. 放大：点画布 → 640x360 居中、四边不被裁；再点 → 还原。
8. `VFD` 的 `dec/drop/xx.x ms`：dec 持续增长、last_decode_us < 30000、drop 不暴涨。

## §28. 分区表改造：OTA 槽 5MB→6MB，storage 后移（2026-09-25）

**触发**：接入取景器（§27，链接 `esp_driver_jpeg`）后 app bin = **0x507ad0**，
超出 0x500000 的 OTA 槽 **0x7ad0（31 KB）**，`app_check_size` 拦下。
★ 注意：改造前 bin 已 ≥ 0x500000−31KB，即**已用到 OTA 槽的 99.4%** ——
就算不加取景器，小智/OTA 一开工也必然撞墙。这不是"这次改多了"，是槽位本来就见底。

**为什么不从代码里抠 31 KB**：要抠就得动 esp-dl/SW codec 的链接面，脆弱且治标；
6 MB/槽才是给小智、OTA 留的合理余量。故改分区表。

**新布局**（16 MB flash 仍被**精确占满**，storage 尾 = 0xC20000+0x3E0000 = 0x1000000）：

| 分区 | 旧 | 新 | 说明 |
|---|---|---|---|
| nvs / phy / otadata | 0x9000 / 0xf000 / 0x11000 | **不变** | WiFi 配置保留 |
| ota_0 | 0x20000 + 0x500000 | 0x20000 + **0x600000** | 6 MB |
| ota_1 | 0x520000 + 0x500000 | **0x620000** + **0x600000** | 6 MB |
| storage (littlefs) | 0xA20000 + 0x5E0000 | **0xC20000** + **0x3E0000** | 3968 KB，素材仅 ~768 KB，余量 5x |

bin 0x507ad0 → 每槽余量 **0xF8530 ≈ 996 KB**。已用 `gen_esp32part.py` 往返转换验证无重叠。

**★★ 改分区表后的烧录顺序（错了会起不来）**
1. `idf.py flash` —— **必须全量**，不能用 `app-flash`：flash_args 里的
   `0x11000 ota_data_initial.bin` 会把 otadata 复位成"从 ota_0 启动"。
   若只烧 app 而 otadata 记着 ota_1，bootloader 会去 0x620000 找固件 —— 那里现在是垃圾。
2. `idf.py storage-flash` —— storage **偏移变了，旧位置的素材无人读**，必须重烧。
   该目标已存在（build.ninja `storage-flash`），会自动按新分区大小重建 storage.bin。
   素材来自仓库 `littlefs_content/`（模型/图标/提示音），**没有数据丢失**。
3. nvs 未动 ⇒ 不用重配 WiFi。

**连带修改**：
- `partitions.csv`（上表）。
- 顶层 `CMakeLists.txt` 的 storage 烧录注释：0xA20000 → **0xC20000**。
  ★ 历史坑叠加：旧注释里的 0x620000（曾是 storage 偏移、落在 ota_1 内）**恰好就是新的
  ota_1 偏移** —— 谁按旧笔记把 storage.bin 烧到 0x620000，这次就会**直接覆盖 ota_1 固件**。
  教训一句话：**分区偏移只有 partitions.csv 一个真源，任何注释/笔记里的地址烧录前必须对照它**。

**不改**：`sdkconfig`（没动 nvs/phy/app 的起始偏移，CSV 里那条 Kconfig 提醒不适用）。

## §29. VIDEO 页预览黑屏修复 + PREVIEW 开关按钮 + Q 按钮改名 JPEG Q8（2026-09-25）

### 29.1 黑屏根因（日志实锤，不是猜的）

## §32. Q1 档取景黑屏：staging 缓冲 192 KB 装不下 Q1 帧（2026-09-26）

**用户实报**："Q1 时无法预览"。代码调查 + 驱动源码核实，根因唯一、证据链完整。

### 32.1 根因

`viewfinder.c` 的 staging（观察者→解码任务的 JPEG 码流中转缓冲）只有 **192 KB**。
`vf_observe()` 对 `size > STAGE_BYTES` 的帧**直接丢弃**（且只告警一次）：

- Q8~Q24 档 720p 帧实测 30~70 KB（§27 仪表盘 max frame 68 KB）⇒ 192 KB 绰绰有余；
- **Q1 = 最高质量 = 码流最大**，单帧轻松超 192 KB ⇒ 每帧都被丢 ⇒ 解码任务收不到
  任何帧 ⇒ 画布永远停在占位黑屏 —— 正是"Q1 时无法预览"。
- 链路其它环节都能过 Q1 帧：驱动 V4L2 缓冲上限 = `w*h*bpp/8`（JPEG bpp=8，
  esp_video.c:2164-2184）= **921,600 B**，本工程 S_FMT 不设 sizeimage ⇒ Q1 帧只要
  < 921 KB 就能被 cam_task 完整交付（`buf.bytesused` 是真实帧长）。
  唯一的丢弃点就是取景器的 staging。

### 32.2 修法（viewfinder.c）

- `STAGE_BYTES: 192*1024 → SRC_W*SRC_H = 921,600`——**取"交付方的最大单帧"做上限**
  （= 驱动 JPEG 缓冲上限），任何质量档的帧都不可能再因 staging 丢。
  代价：常驻 PSRAM +720 KB（viewfinder 总占用 ~2.2 MB → **~2.97 MB**）。
- 顺带修：超限告警旗标从函数级 `static` 提到文件级，`viewfinder_enable()` 时清零——
  原来只吼一次后永远静默，复测/换档后看不到告警。
- Q1 大帧的硬件解码仍 < 30 ms（Huffman 位流更长但硬件吞吐足够），timeout 200 ms 不用动。

### 32.3 校验与验收

- `esp-idf-syntax-check` 真实编译：viewfinder.c 过，0 警告。
- 上机：① 开机 `[mem] after viewfinder_init` PSRAM 应**多减 ~720 KB**（总 ~3.0 MB）；
  ② PREVIEW 开 + 切 Q1 ⇒ 画面恢复（此前黑屏）；③ 仪表盘/日志不再出现
  `VFD: frame size ... > staging` 告警；④ Q8↔Q1 来回切预览连续。
- **注意**：Q1 下录像是另一回事——12 fps × 数百 KB/帧 ≈ 4~10 MB/s，很可能超出
  SD 卡写入带宽（§2.5.7 风险 1 的正主），预览正常≠录像不丢帧，别混为一谈。

### 33.6 上机补正：视频打不开 = demuxer 读错 strh 偏移（2026-09-26）

**现象**：照片预览 OK，所有 AVI `avi_demux_open failed`。
**根因**：demuxer 把 `OFF_STRH_SIZE=104` 当成了 **fourcc 偏移** —— 实际写入流是
`'LIST'@88 + size@92 + 'strl'@96 → 'strh'@100 + size@104 → payload@108`，
即 **'strh' fourcc 在 100**。首版校验 `hdr+104=="strh"` 必然失败 ⇒ 全部视频被拒。
avih（24/32/48/64/68）与 movi（212/220）各偏移核算无误，仅此一处。
**修**：fourcc 校验改 100 并补 'avih'@24 校验；偏移常量加 OFF_*_FOURCC 命名防再犯。
**顺带**：`do_play` 对 demux_open 失败分流诊断日志（not found / too small / format mismatch）。
**教训**：**读侧对着写侧的"OFF_* 常量"抄偏移时，必须先确认那个常量指的是 fourcc 还是
size 字段**（muxer 的 OFF_STRH_SIZE/OFF_STRF_SIZE 都是 size 字段偏移）。校验通过。

### §36.3 M1b audio_service ext 客户端协议（audio_service.h/.c）

audio_service 收权为全链路唯一 codec 所有者，两种借用模式：
- **① 流式**（MP3 等）：`ext_claim(&fmt)` 按调用方格式 open 服务 spk dev →
  `ext_write()` 逐块写 → `ext_release()`；SET_VOLUME 同句柄照常生效。
- **② 独占租借**（小智 AFE 全双工）：`ext_claim_exclusive(&spk,&mic)` **借出服务
  已有句柄**（不再 BSP 二次 init，从根上避开"同一 I2S 双句柄"P0），调用方自行
  open/close（16k 布局自定），close 后 `release_exclusive()` 归还。
- 状态机 `s_ext_mode`(NONE/STREAM/EXCLUSIVE) + `s_svc_busy`（audio_task 同步执行
  播放/录音的标志，含 fopen/头错误早退路径的复位）。占用期间：PLAY_FILE/START_RECORD
  拒（BUSY 日志）、`audio_stream_start()` 返回 INVALID_STATE（record_service/udp_voice
  的入口即此函数 ⇒ 全覆盖）、SET_VOLUME 仅 STREAM 态生效。
- v1 无看门狗：调用方异常不 release 会永久占住，靠 file_mgr/xiaozhi_service
  单状态机兜底（STOP/错误路径必经 release）。
- 现有 WAV/录音/stream 路径行为零变化（静态校验 [OK] 零警告；真机回归待用户）。

## §38. MP3 播放即 ERROR 根因：out_writer 返回值契约搞反（2026-09-26）

**现场**：PREPARING->PLAYING 一瞬间 `ESP_PLAYER_AUDIO_RENDER: Write audio render stream error,
ret: 17640` → 管线 ERROR → 自动回 IDLE。17640 = 44.1k/2ch/16bit 恰好 100ms 字节数
（render 帧大小），即 out_writer **成功**返回的"写入字节数"。

**根因**：`mp_out_write` 写成 `(ext_write()==ESP_OK) ? (int)size : -1` —— 但
esp_audio_render 的 out_writer 契约是 **esp_err_t 语义（0=成功）**，链路三处实证：
1. `audio_render_post_writer`：`ret == 0 ? OK : FAIL`；
2. `audio_render_proc_write`：`proc->pipeline == NULL` 时 writer 返回值**原样透传**
   （proc_num==0 且输入输出采样信息相同 ⇒ 不建 pipeline，本例正是此路径）；
3. `player_audio_render_process`：`!=OK && !=INVALID_STATE` 即判 ERROR。
main 分支 `tab_audio.c` 能跑是因为它直接 `return esp_codec_dev_write(...)`（成功=0）。
对照：av_processor 0.7.0 的 `audio_io_write_cb_t` 同样注释 **ESP_OK on success**，
xiaozhi_service 的 xz_play/rec_write_cb 已按此写，无需改。

**修复**：`media_player_service.c` `mp_out_write` 改为直接 `return audio_service_ext_write(...)`，
注释写死契约与本次证据链。探针 [OK]。
**教训**：第三方回调契约以**头文件注释 + 参考实现**为准，"返回字节数"是流式库的常见
直觉陷阱；同一回调在 main 能跑 ≠ 返回值语义相同（走没走透传路径取决于 proc/pipeline 是否建立）。

## §39. MP3 第二坑：建链窗口被 UI 轮询误杀 STOP（2026-09-26）

**现场**：PLAY 后 ~30ms 出现 `Handling cmd: STOP in state: PREPARING` → `MP_SVC: stopped by
request` → 播放被掐死（THAT.S MY BABY.mp3；第一次 Seven.mp3 躲过是时序侥幸）。

**根因（竞态）**：`open_path()` 置 `s_mode=MODE_MP3` 后 `media_player_service_play()` 只是
**投队列**；mp_task 从取命令到 `s_playing=true` 有 ~50ms 建链窗口（ext_claim + pool/render/
player 惰性重建 + run）。`tab_files refresh()` 50ms 拍插进窗口：`s_mode==MODE_MP3` 但
`is_playing()==false` ⇒ 误判"已结束" → `enter_browse_mode()` → `media_player_service_stop()`
（幂等）→ 误杀。修 out_writer 返回值（§38）只是让它死得早了点，轮询竞态还在。

**修复**：media_player_service 增加 **pending 段**：
- `s_play_pending`：play() 入队成功置位；PLAY 成功 / 任一失败路径 / STOP / FINISHED 清零；
- `is_playing()` = `s_playing || s_play_pending`（.h 注释写死语义与本次实证）。
三个调用者全部受益：refresh 回浏览（修的就是它）、播放态禁按钮（建链窗口内也禁，正确）、
离开 FILES 页取消请求（pending 也取消，正确）。

**教训**：★ "异步命令入队成功"到"执行生效"之间必有窗口，**跨线程查询型 API 必须
把"已请求"算进语义**，否则轮询方必然撞窗口。与 F41-A 的"两个 user_data 存储"同类：
看状态要看全（请求态 + 生效态），只看生效态就会静默误判。

## §47. 小智仍无回应：对照 vocat 仓库修正会话触发序列（2026-09-27）

**验证**：静态校验 [OK]。上机判据：说话停顿后日志出 stt → llm → tts。
**后续（§48 实测）**：wake word detect 扳机**保留至今**（不发 detect 服务器

## §48. 小智首轮能答后续聋：每回合需重发 listen start（2026-09-27）

**现场**（§47 修复后重大进展）：TALK 后服务器**真的答了一句**（52500 处 feeder

**官方权威调查**（用户指路 xiaozhi.me docs → 78/xiaozhi-esp32）：
- 协议文档 docs/websocket_zh.md：tts stop 后"若无更多指令，**回到空闲状态**"
  ——回合关闭；
- 78 官方固件 application.cc:1078：`StartListeningAudio()` 每次进入 Listening

**根因**：listen start 是"一轮"的开票，tts stop 收票。我们只在会话建立时发

**修（xiaozhi_service.c）**：

  WS 任务上下文，阻塞发送有自死锁风险（F44 同族纪律）。

**验证**：静态校验 [OK]。上机判据：招呼回应后继续说话 → 日志出
`re-listen after tts stop: ESP_OK` → stt → llm → tts → 多轮循环。
**后续（实测废弃）**：re-listen 只有紧跟 tts stop 的那一轮可靠（第 2 轮走通、
第 3 轮聋，见 §49 现场）——"每回合需重发 listen start"的认知正确，但
服务器 realtime 状态对端不可控，最终由 §49 manual PTT 用按钮显式开票收票。
`s_relisten_req` 已撤。

## §52. Barge-in 落地：TTS 中按 PTT = 打断（abort_speaking 路径）（2026-09-27）

**现场**：TTS 播放中按住 HOLD TALK → 会话卡死（后续说啥都不再回应）。
§49 的设计是"TTS 期间闸门静音，无 barge-in"，但没拦住按钮本身——PTT 按下
照常发 `listen start`，在服务器 Speaking 态收到开票请求，回合状态机被搅死；
且 `s_ptt_on` 已置 true，随后 tts stop 收票回空闲后**不再补票** ⇒ 永久聋。

**协议正解**（vendor 自带，78 官方固件 Speaking 态按键同款路径）：
`esp_xiaozhi_chat_send_abort_speaking(chat, reason)` → 服务器停 TTS、回
tts stop、回合复位 → 此后才开票说话。

**修（xiaozhi_service.c，全部在上行任务对齐，UI 只置期望态不变）**：
- 新增 `s_ptt_start_pending`（欠票标志）+ `s_tts_quiet_until`（回声静默窗，
  `XZ_ECHO_GUARD_MS=500`——tts stop 事件到 ≠ feeder 播空，feeder 无 flush
  API，窗口内不上行防尾音被转写成垃圾）；
- **打断分支**：按下时若 `s_tts_active` → 发 `abort_speaking
  (WAKE_WORD_DETECTED)`，置 `s_ptt_on=true` + `pending=true`，listen start
  **延后**；否则走原 listen start 分支；
- **补票分支**：`s_ptt_on && pending && !s_tts_active` → 补发 listen start
  （MANUAL）→ 清 pending；
- ★ **tts stop 统一置欠票**（chat_event_cb）：覆盖"按住期间 TTS 才开始"
  的竞态——先开票后 TTS 启动的那一按，同样会在 stop 后欠票，不补 = 聋到
  松手（§48 教训的通用化：stop 后必须重新开票）；
- 闸门追加 `!in_quiet`；水位日志新增 `skip_echo` 计数与 `pend=` 标志；
- teardown 复位新标志；头文件 ptt_start 注释更新为"TTS 中调用 = 打断"。

**验证**：静态校验 [OK]×2。上机判据：
1. TTS 播报中按住 HOLD TALK → 日志 `ptt BARGE-IN abort_speaking: ESP_OK`
   → 喇叭迅速停（本地尾音 ≤0.5s 内耗尽）→ `tts state=0` →
   `ptt RESUME (post-abort listen start): ESP_OK` → 说话有回应；
2. 正常说→答→说多轮回归不变（不打断时行为零变化）；
3. 水位日志 `pend=1` 只应短暂出现（stop 后下一循环即补票清零）；
4. 若打断后仍聋：看 `ptt RESUME` 是否 ESP_OK——失败贴日志（发送层问题）；
   成功但仍聋则属服务器侧回合语义，抓 `listen/abort` 原始报文对账。

## §53. 上行音频两大症状同根：AEC 参考错配（MR 从未实测）+ 会话聋化自愈（2026-09-27）

**现场**（用户日志 + 追问）：
- 症状 A：每轮 STT 只出前 ~5 个字（"你的你的。"/"书包。"/"我说话。"），
  AI 回复"你话说一半"——用户实际说了一大串，只有开头 ~1.5s 被转写；
- 症状 B：第 4 轮起彻底无回应（R1-R3 尚有残转写），日志侧我们的
  `ptt START/STOP: ESP_OK`、`sent` 持续增长、无任何 send 失败——连接活着、
  音频在发，服务器"装聋"。

**根因链（源码实读 + 时间常数指纹）**：
1. `XZ_MIC_LAYOUT="MR"`（ch0=mic、ch1=DAC 回采作 AEC 参考）是照抄 vocat
   板型的假设——S5 §4.6.4 M0 清单第 5 条明写"Korvo-1 是否同样出 MR 待
   M3 上机确认"，**从未实测**；
2. `audio_processor.c:1211` `rec->afe_cfg->aec_init = aec_enable`——AEC
   纯由我们 mask 决定，对 2ch 输入按 MR 语义取 ch1 做自适应参考；
3. 若 ch1 实际是第二颗麦（听得见人声）而非回采，AEC 自适应滤波 ~1s
   收敛后**把人声当回声消掉** ⇒ 每轮只有 AEC 收敛前的 ~1.5s 语音有效
   （症状 A 的时间常数指纹）；跨轮自适应状态保持且越消越干净 ⇒
   第 4 轮起从轮首即全消（症状 B）。

## §54.1 浮窗滚动链误拉：壁纸上拉把 AI 窗"顺带"拖出来（2026-09-27 实测修复）

**现场**：下拉时间壁纸后，在壁纸上上拉关闭时，AI 小智窗会跟着一起从底部
被拉出来。

**根因（LVGL 滚动链泄漏）**：AI 窗隐藏时停在 y=+480，把 `lv_layer_top` 的
内容区撑高到 ~960px；而 layer 默认带可滚动标志。壁纸容器自己
`set_scrollable(false)` 滚不动 ⇒ 上拉手势经**滚动链**传导到 layer_top ⇒
整层上滚——停在屏幕下方的 AI 窗与壁纸一起被"拖"上来，看起来就是
"顺带拉出来"。

**修**（overlay_ai.c init，一处根修）：`lv_obj_set_scrollable(lv_layer_top(),
false)`——层禁滚动，浮窗/壁纸的定位全部由各自手势与动画自管，滚动链到层
即断。壁纸/AI 窗容器本身均已 non-scrollable，无需再动。

**验证**：静态校验 [OK]。上机判据：壁纸下拉/上拉全程 AI 窗不再出现；
SET/MODE 进出 AI 浮窗行为不变。

**根因（两段）**：

1. **能力问题**：POSE 模型 3,117,744 B（3044.66KB），SDCARD 模式下 esp-dl 把整个
   `.espdl` 读进**一块连续** RAM（`fbs_loader.cpp:311` `malloc_aligned(size, MALLOC_CAP_DEFAULT)`）
   ⇒ 需 3.04MB **连续** PSRAM。当时 free=3642KB（够）但 **largest=1280KB**（不够）——
   §3.4 那条"盯 largest 不看 free"的铁律**在 PSRAM 侧第二次复现**；
2. **崩溃放大器**：`new dl::Model(...)` 之后无条件 `m_model->minimize()`（各 detect 包装类同构），
   而 `Model::load()` 失败只打日志、不抛不返空 ⇒ `minimize()→clear_map()` 空指针 ⇒ 直接 panic。
   ⇒ 纪律：**"内存不够"绝不能交给 esp-dl 去失败。**

**本轮改动（P0，零风险）** `main/middleware/camera/face_service.cpp`：

- 新增 `model_bytes()/model_mem_ok()`：切换前判 `PSRAM largest ≥ 最大单文件+64KB`
  **且** `free ≥ 文件之和+256KB`，不过则**拒绝切换并保留当前模型**（与"文件缺失"同一套
  拒绝语义：`s_state = s_detector ? RUNNING : FAIL`）——把 panic 变成"切不动"；
- 预检插入 `do_build()` 的 `unload_all()/build_family()` **之前**；回退分支
  `build_family(s_last_good_id)` 同样过预检（回退失败会踩同一个 panic）；
- 拒绝时一次性 `heap_caps_print_heap_info/dump(MALLOC_CAP_SPIRAM)` 取证（空闲块地址+大小分布）；
- `[resident]` 埋点补 `PSRAM largest`（此前只有 free，看不到碎片）。

**判据**：切 POSE 应出现
`refuse switch to "POSE": need contiguous 3108KB (largest file) + 3555KB total, but PSRAM largest=…KB free=…KB`
且**不再 panic**、FACE/HAND 继续可用。各档预检核算：FACE 548KB ✅ / HAND 977KB ✅（卡在 largest 内）/
POSE 3108KB ❌（本次被拦下）。

**P1 结局**：**§62 用户拍板：阉割 POSE 档，A/B/C 三条都不做**（原三选项留档见
`docs/开发文档/内存优化可执行方案.md` §12.4）：
A 零拷贝（POSE 移出 littlefs → 独立 raw 分区 + mmap，PSRAM 连续块需求 3.04MB→≈0，推荐）；
B 开机常驻预留池（不改分区，但永久吃 3.2MB）；C 碎片整理（最省事，但不保证凑得出）。
先跑一轮拿 §12.3 的 dump 再定。A 会再动 `partitions.csv`（新增 `pose_model` 0x320000、
storage 移到 0xA40000/0x5C0000）⇒ 实施时必须**全套重烧**（含 storage），纪律同 §60c。
