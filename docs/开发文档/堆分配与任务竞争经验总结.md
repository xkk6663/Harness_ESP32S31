# 内部 RAM 堆分配与任务竞争经验总结

> 来源：阶段三 FACE 按钮 NO_MEM 崩溃调试（2026-09-18）
> 教训：加"优化"前先理解原因为什么能跑，不要盲目加任务/改堆布局
>
> ★ 本文是**硬规范/踩坑记录**。要看"内存现状 + 该往哪走"，读 `内存管理规划.md`；
> 要看"某一项怎么做"，读 `内存优化可执行方案.md`。三者的分工见 `内存管理规划.md` 的「文档分工」。

## 一、问题现象

按 FACE 按钮加载 esp-dl 人脸模型时，偶发崩溃重启：

```
ESP_ERROR_CHECK failed: esp_err_t 0x101 (ESP_ERR_NO_MEM)
file: "esp_phy/src/phy_common.c" line 126
func: phy_track_pll_init
expression: esp_timer_create(&phy_track_pll_timer_args, &phy_track_pll_timer)
abort() was called at PC 0x2f00ee3d on core 0
```

关键数据：
- `free internal=72KB, free PSRAM=11MB`（PSRAM 充足，内部 RAM 看着也够）
- 但 `esp_timer_create` 返回 `ESP_ERR_NO_MEM`
- 崩溃在 **WiFi PHY** 的 `phy_track_pll_init`，不是模型加载代码本身

## 二、根因分析

### 2.1 不是堆大小问题，是堆碎片 + 任务竞争

`free internal=72KB` 不代表有连续 72KB 可用。内部堆经过长时间运行（WiFi 初始化、LVGL、音频、摄像头）后碎片化，最大连续块可能只有几 KB。

`esp_timer_create` 需要从内部堆分配 `esp_timer_t` 结构体，虽然不大，但堆碎片时可能失败。

### 2.2 真正的杀手：任务竞争 + 我引入的"优化"

| 我加的改动 | 后果 |
|---|---|
| 独立 face_load 任务（8KB 栈，绑 core1） | 多占 8KB 内部 RAM，和 cam_task 在 core1 抢资源 |
| `esp_wifi_stop()` 暂停 WiFi | wifi_manager 检测到断开，在 WiFi STOP 状态下调 `esp_wifi_set_config` → abort |
| draw buffer 挪 PSRAM | 破坏内部堆布局，WiFi PHY 自己初始化都失败 |
| fopen 检查模型文件 + heap 打印 | 多了几步堆操作，加剧碎片 |

### 2.3 基线为什么能跑

基线代码（6f6137c）直接在 LVGL 按钮回调里同步 `new HumanFaceDetect()`：
- 没有额外任务栈开销
- LVGL 任务栈大（8-16KB），模型加载够用
- 没有停 WiFi，没有改堆布局
- WiFi 已经稳定运行 30 秒后再按 FACE，没有 PHY 重连竞争

## 三、硬规范（必须遵守）

### 3.1 不要盲目加任务

- **先在原上下文跑**，确认有性能问题再拆任务
- 额外任务栈 = 额外内部 RAM 开销（4KB 起），ESP32-S31 内部 RAM 紧张
- 任务绑核前想清楚：core0 跑 WiFi/lwIP，core1 跑 LVGL/摄像头，新任务放哪核不抢资源

### 3.2 不要停 WiFi 来"避让"

- `esp_wifi_stop()` 会触发 wifi_manager 的重连逻辑
- wifi_manager 在 WiFi STOP 状态下调 `esp_wifi_set_config` 会 abort
- 需要"安静期"时，用 wifi_manager 的暂停接口，不是直接停底层

### 3.3 不要轻易改堆布局

- LVGL draw buffer、framebuffer 的位置（内部 RAM vs PSRAM）经过 BSP 调优
- 挪到 PSRAM 看似释放内部 RAM，但会破坏堆连续性，导致 WiFi PHY 等对连续内存敏感的子系统崩溃
- 改之前必须确认：改了之后 WiFi 初始化、esp_timer、PHY 校准都能正常跑

### 3.4 esp_timer_create NO_MEM 的真正含义

- 不是"内存总量不够"，是"堆碎片化到没有连续块"
- 排查顺序：
  1. `heap_caps_print_heap_info(MALLOC_CAP_INTERNAL)` 看最大连续块
  2. 看是不是有其他任务同时在分配内存
  3. 不要靠 `free internal=XXKB` 判断够不够

### 3.5 模型/大资源加载时机

- 模型加载是重操作（~900ms，内部 RAM 分配密集）
- 最佳时机：开机时（WiFi 还没连，没有竞争）或 WiFi 稳定后空闲时
- 不要在 WiFi 重连、摄像头启动、音频流切换等敏感时刻加载

### 3.6 简单优先

- 基线代码能跑就别动
- "优化"前先回答：**原因为什么能跑？我的改动会不会破坏这个前提？**
- 这次调试花了大量时间，就是因为加了太多"优化"，每个都引入新问题

## 四、本次调试踩的坑记录

| 坑 | 现象 | 教训 |
|---|---|---|
| 加独立任务加载模型 | face_load 8KB 栈占内部 RAM，加剧碎片 | 先在原上下文跑，别加任务 |
| 停 WiFi 避让 | wifi_manager 在 STOP 状态重连 abort | 不要直接停底层 WiFi |
| draw buffer 挪 PSRAM | WiFi PHY 自己初始化都失败 | 堆布局不要乱改 |
| 绑核到 core0 | 和 WiFi 同核竞争 esp_timer | 新任务别绑 core0（WiFi 在那） |
| 降 cam_task 优先级 | 闪屏重启问题没解决，模型也崩了 | 优先级调优要和问题对应，不要瞎降 |

## 五、当前稳定配置（6f6137c 基线）

- face_service：直接在 LVGL 回调里同步 new（无独立任务）
- cam_task：优先级 5，绑 core1
- refresh timer：50ms
- draw buffer：内部 RAM（BSP 默认）
- 模型：littlefs/models/，不编固件
- 不做 preload，不停 WiFi，不挪堆
