2 两个关键设计（决定了它安全）

① acquire（拿缓冲）与 enable（开始收帧）是两件事

FILES 页从头到尾没 enable 过，却能用同一个单例解码器 —— 它只需要"缓冲在手"， 不需要"收帧"。把这两件事解耦，才能做到精准按需。

② 释放前必须先让画布"松手"（零拷贝的坑）

lv_canvas_set_buffer() 是零拷贝 —— 只把指针写进 canvas 内嵌 draw_buf。 vf_feed() 已经把取景画布指到了 s_disp[] ⇒ 先 release 再换画布 = 画布指向已释放内存（UAF）。
所以 vf_release_all() 的顺序是：
memcpy(自持缓冲 ← 最后一帧) → lv_canvas_set_buffer(画布 → 自持缓冲) → disable() → release()。
顺带好处：关预览后画面仍停在最后一帧，不会突然变黑。

③ 三道 UAF 关

关位置做什么
①tab_video.c vf_release_all()先让画布换回自持缓冲，再 release
②tab_files.c enter_browse_mode() / destroy() 判 !file_mgr_is_playing() —— files 任务可能还在用 stage （set_active(false) 先 post STOP 就立刻调本函数，而 STOP 是异步的）
③viewfinder.c viewfinder_release() 若解码任务 100 ms 内没退出，拒绝释放并告警 —— 宁可不省，也不 UAF

3 上机要读的三条日志

# ① 开机：这一步不该再有取景器预分配（旧版这里会掉 ~2,925 KB）
I (..) MEM: [after camera_service_init]                       PSRAM free=…
I (..) MEM: [after viewfinder_init (on-demand now, no alloc)]  PSRAM free=…   ← diff ≈ 0

# ② 进 VIDEO 页点 PREVIEW（或 FILES 页预览/播放）
I VFD: [vfmem acquire] INT free=.. largest=.. | PSRAM free=.. largest=.. | viewfinder buffers
W VFD: acquired 2925 KB PSRAM (dec_out 1843200 B contiguous + stage 921600 B + disp x2 230400 B)
       - RELEASABLE: call viewfinder_release() before leaving the page

# ③ 关闭 PREVIEW / 切走 tab
I VFD: [vfmem released] INT free=.. largest=.. | PSRAM free=.. largest=.. | viewfinder buffers freed
判读：② 与 ③ 的 PSRAM free 之差应 ≈ 2,925 KB。
若 ③ 缺失 ⇒ 搜 release SKIPPED: vf task still alive （说明 disable() 的 100 ms 等待窗口不够）。
再看 dl 模型：[recogmem pre] 的 PSRAM largest 应比旧版高约 2.93 MB （旧版加载 FACE 检测模型后是 2,686,976 ⇒ 现在应 ≈ 5.6 MB） ⇒ 应超过 MFN 峰值 2,115,950，模型应当能起。

5 本轮没做的事（写明白，免得以为是修好了）

  • file_mgr 的 s_pv[2]（921,600 B）仍开机常驻 —— "下一轮按需化"的候选。不一起做：释放它要连带处理 s_pv_canvas 的零拷贝指针， 而该画布连占位缓冲都没设过。
  • 不动 MEDIA_BUF_CNT（仍 1）、不动 MFN 的 MODEL_LOCATION_IN_SDCARD —— 那是 P0-A（峰值线的后续）。本轮做完后它优先级下降。
  • 不涉及分区表 / 模型 ⇒ 本次上机不需要 idf.py storage-flash，idf.py build → flash 即可。
  • 约 7.4 MB 未归因 PSRAM（见《内存优化可执行方案》§14.2 更正块）—— 等开机 [mem] 分步账单逐项归因。
