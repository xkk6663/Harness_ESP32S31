2. ★★ face_db"删空人物后重启，人又回来了" —— 真 bug（已修）

成因链：每一环单看都合理，合起来才出事。

步位置代码 / 结果
①face_db_delete() if (s_count == 0) { s_dim = 0; } ⇒ 删到最后一个人时内存 dim=0
②fdb_build_image() fdb_put_u16(buf + 6, s_dim) ⇒ 盘上那份索引的 dim 字段也是 0
③fdb_idx_read() if (dim <= 0 || dim > DIM_MAX) return ESP_ERR_INVALID_SIZE; ⇒ "空库"被判定为坏档
④fdb_load_best() 另一槽"坏了" ⇒ use0 = ok[0] ⇒ 回落到旧世代 = 人复活

为什么只有"删空"才复现

s_dim 只在 s_count 归零那一刻被清 0。删 1 人而库里还有别人时 dim 仍是 512，两份世代都能读，挑选逻辑完全正确。

修复

/* 正确语义：count == 0 时空库是**合法状态**，dim 无意义、不参与校验；
   只有"确有记录却不知道维度"（count>0 && dim 非法）才是真损坏。 */
if (count > 0 && (dim <= 0 || dim > FACE_DB_DIM_MAX)) { ...bad dim... }
if (count == 0) ESP_LOGI(TAG, "%s: empty library - legal state, not corruption", name);

不需要清 SD 卡（自愈）：判据修对后两个槽都可读，空库那份 seq 更大 ⇒ 下一轮挑选自然赢。

被排除的嫌疑（重要）

最初最大嫌疑是 FDB_PROBE_SEED_DEMO（"每次开机往真库写 3 条演示数据： 张三/李四/王五"）—— 行为与用户描述完全吻合。用二进制取证否掉：

cd build && for f in *.elf *.bin; do strings -a "$f" | grep -c '\[SEED\]'; done
→ 对 "[SEED]" / "张三" / "face_db_selftest" 全部 0 命中 ⇒ 该路径根本没参与编译

它还被两层 #if 包着（外层 FACE_DB_PROBE_ENABLE=0） ⇒ 外层关着等价于内层不存在，-DFDB_PROBE_SEED_DEMO=1 也救不回来。

教训：「现象吻合」不等于「就是它」。

3. USER 态打卡改成"右侧圆形按钮"手动触发

按下右侧圆形按钮
   ↓ 前置检查（逐条给话，见下）
armed = true  +  deadline（引擎没就绪时放宽到 8 s）
   ↓ recog_pump() ④：只在 armed 时才提交 IDENTIFY（没按下 ⇒ 一次都不提交）
   ↓ user_on_result()
      ├─ 未命中库（person_id == FACE_DB_GUEST_ID） → 提示 "Not in face db"，不落盘
      ├─ 脸不合格 → 显示 hint，保持 armed（窗口内自动重试）
      └─ 命中 → 画水印 → begin/commit → "Punched: 姓名"

关键实现点

  • 触发闸门：recog_pump() ④ 的 USER 分支第一行 if (!s_punch_armed) return; —— 这一行就是"不自动打卡"的全部实现。
  • 每个终点都必须 punch_disarm()：成功 / 未命中 / 超时 / 冷却 / 无 SD / 库未就绪 / 内存不足。漏一条，按钮就永久停在 SCAN —— 那是"按了没反应"的另一种写法。唯一例外是 PUNCH_PREP_BUSY （写盘只要百 ms 级，保持 armed 等下一拍）。
  • 访客不落盘做成显式开关 PUNCH_RECORD_GUEST（默认 0）； 判据用 person_id == FACE_DB_GUEST_ID，不要用 r->name[0]。
  • 前置检查逐条给话：相机没开 / 录像独占 / 无 SD / 库未就绪 / 库空 / 档位不是 FACE / 检测关 / 一帧都没送到。每一条都是"按了没反应"的真实成因。
  • 按钮视觉：LV_RADIUS_CIRCLE（不是写死半径 —— 改尺寸时会静默变成 圆角矩形）；96×96 悬浮在取景画面右侧（ignore_layout + LV_ALIGN_RIGHT_MID, -34, 0），不参与那条纵向 flex （否则要重算 760 的行宽，连锁出"按钮被挤出可视区"）；文案 PUNCH ↔ SCAN，绿=待命 / 琥珀=扫描中（不用红，红是本工程的"录制中/危险"）。
  • 状态栏改 9 分支引导，直接回答"要按那颗圆按钮"以及"还差什么才能按"。

4. 新增两条诊断：把"卡上到底有没有东西"做成可查的

(a) 写后回读校验（punch_task）

fclose(fp);
struct stat vst;
long on_card = (stat(abs, &vst) == 0) ? (long)vst.st_size : -1L;
if (on_card != (long)jlen)
    ESP_LOGE(TAG, "WRITE VERIFY FAILED: %s on card = %ld B (expect %u) -> "
                  "write did NOT land (read-only? no dir entry? bad sector?)", ...);

理由：FATFS 里"数据刷出去"和"目录项更新成功"是两件事，而 fwrite() 只对前者负责。卡写保护 / 根目录项耗尽 / FAT 表扇区坏掉时， fwrite() 可以返回满计数而文件在卡上根本不存在 —— 那时日志是一句漂亮的 punch OK: ...。这种矛盾只有回读能当场抓住。

(b) 打卡目录体检 punch_service_dump_dir()（新增 API）

把 /sdcard/attendance 逐个子目录的文件数与字节数打到日志：

  • 目录不存在 ⇒ dir does NOT exist -> no punch has ever reached the write step （排查方向立刻从"文件系统"转到"打卡链路"）；
  • 目录在但 0 文件 ⇒ holds ZERO file -> logged OK without landing。

调用时机：punch_btn_cb() 里每次进页面只打一次。 挂按键而不是建页（建页可能早于 SD 挂载完成 ⇒ 误报"SD 未挂载"）， 更不能挂 50 ms 刷新定时器（列几百个文件会卡住 UI 线程）。

5. 「SD 卡里没有打卡图」判读对表

日志结论 / 下一步

7. 上机验收步骤

  1. 烧录：idf.py build → flash。 不涉及分区表 / 模型 ⇒ 不需要 storage-flash。
  2. 验 ① 删除不复活：进 SYS → Face DB，把人全删光 → 重新上电 → 子页应为空态；串口应出现 idx slot x: empty library ... legal state, not corruption。
  3. 验 ② 手动打卡：CAM 页 USER 态应显示 USER mode - tap PUNCH to check in； 按右侧圆按钮 → 按钮变琥珀 SCAN + Hold still - scanning ...； 命中库显示 Punched: 姓名 xxxxxx.jpg； 库里没这个人显示 Not in face db - not recorded（且不产生文件）。
  4. 验 ③ 卡上有图：看日志 punch OK: 的完整路径， 再去 /sdcard/attendance/<NN_姓名>/ 核对； 或每次进页面按第一次 PUNCH 时看 dir dump: 那一行。
  5. 验 ④ 录像流畅：VIDEO 页 fps 应明显高于 MEDIA_BUF_CNT=1 时的实测值，且写盘瞬间不再出现连续 dropped。

8. 这一轮没做的事

  • 没动 s_frame / s_jpeg 的按需释放（仍是 lazy 分配）。
  • 没改 ENROLL 态的任何行为（圆形按钮在 ENROLL 态隐藏）。
