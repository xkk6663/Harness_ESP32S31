## 3. ★ 清单没预料到的发现

### A. ★★★ `panelprobe` 常驻占用 **16,000 B 内部 RAM**，且每秒刷屏 —— **关它只需改一行**

```
W (2871) main: [panelprobe] on: 1 kHz gap + 16 KB PSRAM->INT (带宽指标, ref 444 us), costs 16000 B internal RAM
I (2881) main: [mem] panelprobe: post   INT free=167335 largest=102400 | DMA free=135363
   （对照 pre：             INT free=183375 largest=118784 | DMA free=151403）
                                      ⇒ freed −16,040   largest −16,384
```

- 代码位置：`main/app/main.c:151` `#define PANEL_PROBE_ENABLE 1`（**常开，非 Kconfig**），
  分配在 `panel_probe_start()`（`:214-216`，`MALLOC_CAP_INTERNAL` 16,000 B）。
  **关法 = 那一行改 `0`**（代码自带 `#if` 包裹，注释 `:149` 也写明了这一点）。
- 它是当初为**定位花屏（bounce 模式下的 444 µs 死线）**造的。**花屏根因已修**
  （改为 `BSP_LCD_RGB_REFRESH_AUTO=y`，探针自己也承认"**无死线**"）。
- 代价是**真金白银**：`largest_free_block` 从 **118,784 掉到 102,400**。
  本工程内部 RAM 是**头号结构性风险**（WiFi 那 51 KB 内部 DMA 挪不走）。
- **它还有一个用途没完成前不能关**：注释 `:138-140` 要求"与**改前的历史日志**在同负载下对比
  PSRAM 带宽，看 auto refresh 有没有加剧竞争"。**这次日志正好把"改后"基线补齐了** ⇒ 见下表。

**★ 顺手留档：改后 PSRAM 带宽基线（关探针后就再也测不到了）**

| 阶段 | `memcpy16k avg` | `max` |
|---|---|---|
| 开机空闲（WiFi 之前） | **47 µs** | 48 µs |
| 稳态（主页/预览/拍照/录像） | **85 ~ 140 µs** | 170 ~ 250 µs |
| 重负载（WiFi 关联 / 收尾 / 模型构建期） | 180 ~ 300 µs | 310 ~ 450 µs |
| **全日志最坏** | 249 µs | **452 µs**（出现在 **TLS 握手期**，`I (9214)` 前一行） |

判读：`avg` 稳态 ~110 µs 相对改前 `ref 444 µs` 有充裕余量；
**最坏 452 µs 恰好擦过旧死线 444 µs** —— 这只说明"当年那一刻若还是 bb 模式就该漏填了"，
**现在没有死线，不构成问题**；但它标定了"PSRAM 最紧张的时刻 = TLS 握手期"。

### B. ★★ 内部 RAM 最紧的时刻 = **TLS 期间**，`largest` 掉到 **67,584 B**

```
I (10068) NET_TIME: [mem] http_get: post (TLS+body done)  INT free=139735 largest=67584 | DMA free=107763
```

这是全日志 `largest_free_block` 的**最低值**。若把 §3-A 那 16 KB 还回来，同一时刻就是 **≈83,968 B**
⇒ **A 项修掉的收益直接体现在最紧的那一格上**。

### C. ★ `[stack]` 表报出 **34,304 B 可回收栈**（但不要照抄）

```
[stack] TOTAL size=88064 B | by-watermark need=52224 B | 可省=34304 B | tasks=17
  taskLVGL      12288 → 9728  (省 2560)
  audio_task     8192 → 1536  (省 6656)
  record_service 8192 → 1024  (省 7168)
  udp_voice_ctl  8192 → 1024  (省 7168)
  link_manager   8192 → 2560  (省 5632)
  cam            6144 → 4096  (省 2048)
  led_task       4096 → 1024  (省 3072)
```

- 口径本身是对的（`used = size − hwm`）—— 这张表就是照着 `MEMORY.md §E` 那条"hwm 是**历史最小剩余**
  不是用量"的教训算的。
- **但**：`udp_voice_tx` / `udp_voice_rx` / `audio_stream` 三个是 `not running` ⇒ **从未被测量**，
  它们的省额**不在 34,304 里**，别以为漏了。
- **且**：`record_service` 只用了 352 B，是因为**这次没录音**。⇒ **要缩栈必须先把每条业务路径都跑一遍**
  再回读一次这张表，否则就是按"没走过的路"缩栈 = 拿崩溃赌。
- **建议**：作为 **P1 机会**登记（34 KB > WiFi 那 51 KB 缺口的一半），但**必须二次测量后才动**。

### D. ★ 清单 §4.1 的判据写反了

清单原文：「`fps 应低于标称 12`」。实测 **14.54 > 12**。
- 说明 OV3660 的 `12fps` 只是 DVP 描述符的**标称值**，不是传感器硬上限；
  而"回调内同步 fwrite 会降 fps"这个机理**依然成立**（只是本用例下没降破 12）。
- **⇒ 该行判据应改成"fps 应与 12 同量级；明显低于 5 才算异常"**（清单已改）。

### E. 其它（都属正常，登记以免下次重复查）

- `W (53559) CAM: set jpeg quality ignored: current stream is RGB565` —— VIDEO 页按 Q 时 CAM 预览还占着流。
  **已在 `q_btn_cb` 注释里写明是预期**（值已记下，下次起 JPEG 流自动生效）。
- `CAM: set jpeg quality` 在 JPEG 会话里是 `= 8`，与 VIDEO 页默认档位一致 ⇒ Q 值传递通路成立。
- `wifi:(phy)` 那 30 行 `pwr:20, txing:20` 是驱动固有的功率表，不是问题。
- `NET_TIME: http buf 8192 B -> PSRAM (freed 8192 B internal)` —— 之前的内存优化在真机上生效了。
