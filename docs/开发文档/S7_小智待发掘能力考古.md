## A 级：近期可做

### A1. Vision 拍照问答（价值最高）

**是什么**：语音问"你看看这是什么"，设备拍一张 JPEG 上传服务器视觉服务，
AI 用视觉模型回答。与 CAM 页人脸识别是两条独立链路（那个走端侧 espdet 模型，
这个走云端多模态）。

**源码证据**：
- `esp_xiaozhi_camera.h:54/78/97`：全套 explain 客户端 API——
  `esp_xiaozhi_camera_create / set_explain_url(url, token) / explain(handle, frame{data,len}, question, out_buf, buf_size, out_len)`；
  头文件明说"API 不初始化不控制相机，应用负责抓帧传入"。
- `esp_xiaozhi_vision.c`：底层 HTTP 上传已实现（`esp_xiaozhi_vision_explain_jpeg`）。
- 服务器侧 URL/token **本来就会下发**：MCP initialize 响应带
  `capabilities.vision{url, token}`（联机日志实锤，§44 期间抓到过）。

**缺口（唯一的活）**：vendored `esp_xiaozhi_chat.c:513` 的 mcp_handler 把
initialize 响应**原样透传给 mcp-c-sdk 引擎**，自己不解析 `capabilities.vision`
⇒ 需在 mcp_handler 里加一段 peek：`method=="initialize"` 时解析
`payload.result.capabilities.vision.url/token`，缓存下来喂给 camera client
（走 §53 同款 vendor 补丁模式，改动 ~30 行）。

**硬件**：本分支 OV3660 + camera_service 现成，抓 JPEG 帧即可。

**约束（三条硬的）**：
1. **与 CAM 页互斥**——摄像头独占，explain 拍照前必须走现有取流互斥协议；
2. `explain()` 是**同步 HTTP**（阻塞直至响应回来）⇒ 必须独立任务调用，
   不得在任何回调/LVGL 上下文里调（F44 纪律，同 §53 fetch_task 模式）；
3. 帧大小受 HTTP 上传与内存约束，用 OV3660 小分辨率 JPEG 档（与封面
   96KB 量级对齐），不要拿拍照全尺寸帧直接传。

**难度：中（约一天：vendor peek 补丁 + 拍照取流 + 上传任务 + MCP 触发工具
`self.camera.explain` 或直接在提问时自动拍）**。**价值：高**——AI 从"只能听"
变成"能看"，且是唯一需要云端的点服务端已就绪的功能。

### A2. EMOJI 情绪灯效 / UI 表情

**是什么**：LLM 回复时服务器下发情绪标签（happy/sad/thinking/laughing...）。

**源码证据**：`esp_xiaozhi_chat.c:618-629` llm_handler **已经 emit**
`ESP_XIAOZHI_CHAT_EVENT_CHAT_EMOJI`（event_data = emotion 字符串）——
vendor 侧全通，只差 app 的 event_callback 没接这个事件。

**接法**：`xiaozhi_service` 事件分发处加分支 →
- 方案 a：RGB 灯情绪灯效（复用 §55 ai_light 的底层 set_manual，按情绪映射
  颜色/呼吸节奏）——注意与 LLM 灯控工具的状态互斥（灯正被手动/工具控制时
  情绪灯效要不要抢，需定优先级）；
- 方案 b：AI 浮窗状态行显示表情文字（零风险起步）。

**难度：低（半天）**。**价值：中**——对话"活"感提升明显，先做 b 验证
事件频率再决定要不要 a。

### A3. SYSTEM_CMD（reboot 等服务器命令）

**源码证据**：`esp_xiaozhi_chat.c:631-643` system_handler **已经 emit**
`ESP_XIAOZHI_CHAT_EVENT_CHAT_SYSTEM_CMD`（如 "reboot"），协议层只上报，
注释明说"app 决定是否执行"。

**接法**：event_callback 里 strcmp("reboot") → `esp_restart()`。
**难度：极低（几行）**。**价值：低-中**——"重启一下设备"语音可用；
顺手接，但 reboot 前建议先走 audio 停流 + 落盘等清理（对齐现有停机路径）。

## B 级：需资源 / 设计评估

### B1. MCP 点歌：`audio_playback_play(url)`

**源码证据**：`managed_components/jason-mao__av_processor/include/audio_processor.h:673`
`audio_playback_play(audio_play_handle_t, const char *url)`——av_processor
现成 URL 播放入口（HTTP 音频流），§44 当时裁掉的就是这条路。

**评估**：
- 与 S5 音频租约协议冲突点：对话态 s_spk 已被借出，playback 是**另一条
  通道**，两者的 codec/I2S 共存关系未验证（正撞我们 P0 的 esp_codec_dev
  共享 i2s_data_if 问题，别在 P0 没收口前碰）；
- 价值重叠：PC 副屏已有网易云/Spotify 音源，端侧点歌是第三条音源线。

**结论：挂起，等 P0（I2S 共享）收口后重估。**

### B2. VCMD 离线语音命令

**源码证据**：`audio_processor.h:300`
`AV_PROCESSOR_AFE_FLAG_VCMD_DETECT_ENABLE = BIT(5)`——afe mask 一个开关位。

**评估**：
- 需要 MultiNet 命令词模型：额外模型分区（现 model 分区 912KB 已重排过）
  + 运行内存（AFE 内多一路检测）——**本工程内存是头号约束**（内部 RAM
  余量 ~4KB 的结构性风险没解除前不动）；
- 独特价值：**断网可用**的"小智小智，打开蓝牙/拍照"级命令，是按键之外
  唯一免触路径；与 B3 唤醒词成对出现才有意义。

**结论：挂起，等内部 RAM 手术（任务栈静态化等）后与 M6 一起重估。**

### B3. 唤醒词（S5 §4.2 搁置项，M6）

wakenet 模型 + AFE 常驻内存，当时因内存搁置。有了它，"免按键唤醒 →
A1 拍照问 → B2 离线命令"整条免触体验才闭环。**前置：内存手术。**

### B4. esp_xiaozhi_video 视频流 explain

**源码证据**：`esp_xiaozhi_video.h` 与 camera 同款 API（连续帧流上传）。
实时视频流对带宽/内存/算力三重吃紧，本分支硬件定位（人脸识别+拍照）
不需要。**远期，不建议立项。**

## 验证纪律（沿 §44/§55/§56 口径）

- A1 上机判据：说话"你看到了什么" → `AI_CAM: explain` 日志 → HTTP 200 →
  回复内容与实际画面一致；失败先看 `Unhandled message` / initialize 响应
  里 vision 字段是否真的下发。
- A2 上机判据：对话中日志出现情绪标签（先在事件分发处打 LOG，不接灯），
  统计一轮对话事件次数，再决定灯效方案。
- 所有新工具回调运行在 mcp 协议栈任务上下文（串行分发），状态变量无锁安全；
  但**不得阻塞**（A1 上传必须甩独立任务，回调只置标志/发队列）。
