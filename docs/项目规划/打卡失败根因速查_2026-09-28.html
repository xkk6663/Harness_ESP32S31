打卡 100% 失败 · 根因与上机验收速查

2026-09-28 深夜 · display_audio_photo · §70 · 静态校验 12/12 · 本地干跑 13/13

一句话结论

punch_service.c 里一行判据错配的容量检查（48 >= 160 恒 false，取 ! 后恒 true）让每一次打卡都在最早的几行就 goto finish， 返回 ESP_ERR_INVALID_SIZE；而那条早退不打任何日志。

识别/检测/匹配 全部正常 落盘 100% 失败 UI 却显示 punch accepted 根因 1 处 连带暴露 6 处编译告警

1. 根因：一次恒真的早退

static bool path_cap_ok(size_t len) { return len >= PUNCH_PATH_MAX; }   /* = 160 */

char root[PUNCH_ROOTBUF];                        /* = 48 */
if (!path_cap_ok(sizeof(root))) {                /* 48 >= 160 = false  ⇒  !false 恒真 */
    res.err = ESP_ERR_INVALID_SIZE;
    goto finish;                                 /* ← 每次打卡都从这里出去，且无日志 */
}
snprintf(root, sizeof(root), "%s%s", SDCARD_MNT_PATH, PUNCH_DIR_NAME);  /* 永远执行不到 */

path_cap_ok() 的语义是「这块缓冲够不够装下最长路径（160 B）」—— 只对 char x[PUNCH_PATH_MAX] 有意义。而 root 是专用小缓冲， 只需装 "/sdcard" + "/attendance" = 19 B。

同函数另有 7 个调用点，传的全是 [PUNCH_PATH_MAX] 缓冲、全对， 只有这 1 个传了 48 B 的 root —— 这种「绝大多数都对」最容易漏看。

为什么一直没被发现

  • 这条 goto finish 不带任何 ESP_LOG（原注释写「编译期已锁，运行时再兜一次」）⇒ 完全静默；
  • UI 那行 punch accepted 是在 commit() 返回 OK 时打的 —— 它只表示「作业已投递」，不表示「写盘成功」⇒ 日志与 UI 双双指向「成功」。

修复

/* 删掉错配的运行时检查，改成编译期断言：改宏/换挂载点就直接编译失败 */
_Static_assert(PUNCH_ROOTBUF >= sizeof(SDCARD_MNT_PATH) + sizeof(PUNCH_DIR_NAME),
               "PUNCH_ROOTBUF too small to hold SDCARD_MNT_PATH + PUNCH_DIR_NAME");

2. ★★★ 连带发现：「编译通过」≠「这段代码被编译检查过」

修掉那一行之后，probe_idf_syntax.py 从 0 error 立刻变成 6 error（全是 -Werror=format-truncation=）。

原因：GCC 在编译期就把 path_cap_ok(48) 折叠成常量 false
      ⇒ !false 恒真 ⇒ 它判定 goto finish 之后的整个 punch_task 是死代码
      ⇒ 根本不去分析里面的 snprintf。

一条恒真的早退 / #if 0 / return， 会让后面的代码在 GCC 眼里消失 —— 连同它的全部 -Werror 告警。

判读规则：看到「修好一处逻辑后忽然冒出一堆编译错误」时， 第一反应应当是「这些错误一直存在，只是刚被照亮」，而不是「我引入了新问题」。

那 6 个告警是真问题（不是误报）

全是路径拼接 snprintf(dst, sizeof(dst), "%s/%s", dir, name)， 而 struct dirent::d_name 在 newlib 里是 char[256] ⇒ GCC 按最坏情况算：

位置表达式最坏需求目标容量
315 / 331dir + "/" + d_name303 / 415 B160
465 / 466sub + "/" + base + ".jpg"63 B48
469sub + "/IMG_%04d.jpg"59 B48
530res.name = who->nameGCC 认为无界（报 2135）24

修法（本工程标准出路）：新增两个拼接原语 path_join() / path_append()（= strlen + strnlen + memcpy + 手动补 NUL）。
① 语义显式：超长即截断 ⇒ 截断后路径指向不存在的文件 ⇒ 后续 stat()/fopen() 自然失败 = 安全失败，不是 UB；
② GCC 不报 —— 它分析不了 strnlen 的返回值。

3. 「为什么一直没有检测框」诊断（新增）

UI 上这 四种完全不同的原因都只显示同一句 No face in view。 现在 tab_camera.c 会打一条限频 5 s 的日志：

W TAB_CAM: no-box diag | frames in=N dropped=N | detect calls=N hits=N
           | face_on=1 svc_en=1 state=3 model=FACE
           | canvas=1 buf=1 bbox=1 media=0 cam_run=1
现象含义对策
frames in 不涨相机没把帧送到本页按 STOP 再 START（回调没注册）
dropped ≈ in帧尺寸不是 240×240别的 tab 的档位没切回来
detect calls 不涨帧到了但检测没跑查 face_on / canvas / bbox
calls 涨、hits == 0espdet 真的没检出脸档位 / 光照 / 距离 / 模型状态

外加两条硬故障 ESP_LOGE（连报 2 s 才认、只报一次）：

camera running (owner=N) but ZERO frames reached this page
  -> on_frame() is NOT registered: tap STOP then START
camera running but ALL N frames were dropped as wrong size
  -> stream is not 240x240 (another tab's format still active?)
