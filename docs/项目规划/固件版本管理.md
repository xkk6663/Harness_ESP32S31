# 固件版本管理（三层标识）

> 落地日期：2026-11-12 ｜ 触发：§80 OTA 验收发现 `git describe` 版本（`v2.0-4-g708d4ea-dirty`）
> 让门禁"看不出新旧"，每次重编都得勾 force。

## 一句话

**发布版本由人决定（version.txt），构建来源自动带上（commit），唯一性由 ELF SHA 兜底。**
三者职责不重叠，所以既不会"每次重编都像升级"，又能在现场把问题钉到唯一一个 bin。

## 第 1 层：发布版本 = SemVer，人工 / 流程决定

仓库根 `version.txt`，一行，`x.y.z`：

```
2.1.0
```

- ESP-IDF 的 `project.cmake` 在 `PROJECT_VER` 未显式指定时会**自动读取仓库根的
  `version.txt`** 作为 `PROJECT_VER`（读不到才退回 `git describe`）。
- 只有"要发一版"才动它；日常提交不动 ⇒ 门禁的"版本未提升"才是真信号，
  不再需要无脑勾 force。
- 发布时打同名 tag：`git tag -a v2.1.0 -m '...'`。tag 是**标记**，不再参与版本计算
  （版本计算已经交给 version.txt），两者只在发布那一刻保持一致。

## 第 2 层：构建标识 = commit，写在 SemVer 的 build metadata

**不用额外命令**：`CMakeLists.txt` 在 `project()` 之前就把版本算好了
（`if(NOT DEFINED PROJECT_VER)` 这一段，IDF 的 `project.cmake:822` 正是按这个条件决定
要不要自己去读 `version.txt`）。逻辑等价于：

```powershell
$ver = (Get-Content version.txt).Trim()
$sha = (git rev-parse --short HEAD)
# → PROJECT_VER = "$ver+g$sha"，工作区脏则再挂 .dirty
```

所以 **`idf.py build` 直接跑就得到 `2.1.0+g3343b3d`**；发布包想要干净版本号：

```powershell
$env:RELEASE_BUILD = '1'; idf.py build      # → 2.1.0
```

- 为什么用环境变量而不是 `-DPROJECT_VER`：`-D` 会写进 `build/CMakeCache.txt`，
  之后不带 `-D` 的构建会**沿用缓存里的旧值**（版本滞留）；环境变量只在本次配置生效。
- 换 commit 后靠 `.git/index` + `.git/HEAD` 上的 `CMAKE_CONFIGURE_DEPENDS` 触发重配，
  版本不会滞留。**只挂 `.git/HEAD` 是无效的**：`HEAD` 文件内容长期是
  `ref: refs/heads/main`，commit 改的是 `.git/index` 与 `refs/heads/*`（已踩过）。
- `+` 后面是 SemVer 的 build metadata，**合法且不参与优先级比较**。
- 两端解析都已按此实现，无需改动：
  - 设备端 `ver_parse()`（`ota_service.c:284`）：遇到 `.` 才继续下一段，遇到 `+` / `-` 直接停；
  - PC 端 `compare_semver()`（`session.py:35`）：`s.split("-")[0].split("+")[0]`。
  ⇒ `2.1.0+g708d4ea` 与 `2.1.0` 判为**同一版**（不会互相触发升级）。
- 工作区脏时自动加 `.dirty`（`2.1.0+g3343b3d.dirty`），仍解析成 2.1.0；
  但 `-NoMeta` 的发布构建会**直接拒绝**，防止把不可复现的包发出去。
- 已知边界：`.dirty` 是在**配置阶段**采样的，改完代码没触发重配时可能滞后
  （`git status` 的变化不进 `CMAKE_CONFIGURE_DEPENDS`：它是 git 自己算出来的，不是文件改动）。
  要强制刷新：`idf.py reconfigure`（`tools/build_fw.ps1` 只是包一层 build，不会主动重配）。
- 长度：`2.1.0+g3343b3d.dirty` = 20 B，`esp_app_desc_t.version[32]` 装得下。

## 第 3 层：唯一性兜底 = app_elf_sha256

`esp_app_desc_t` 里 IDF 自动写入 ELF 的 SHA-256（`fw_info.py` 已解析，偏移 `0x20+144`）。
它比 commit 更精确：**同 commit 但 sdkconfig 不同会得到不同的 ELF**。

- `pc_host/ota/fw_info.py`：`FirmwareInfo` 新增 `idf_ver` / `elf_sha256` / `commit` / `date`。
- `GET /firmware.json` 扩成：

```json
{"ver":"2.1.0+g708d4ea","size":5234352,"sha256":"...","elf_sha256":"...",
 "commit":"708d4ea","idf_ver":"v6.1","build_time":"10:41:24","full_size":5234352}
```

- 固件归档 `firmware_store/ota.db` 的 `firmwares` 表按 `sha`（bin sha256）去重，
  本轮再补 `elf_sha256` / `commit` / `idf_ver` 三列（幂等 `ALTER TABLE`）。
- 反查入口：`FirmwareStore.find_by_ver("2.1.0+g708d4ea")` → 精确命中；
  只给 `2.1.0` 时返回该 release 的所有构建（多行），据此定位"设备到底跑的是哪份 bin"。

## 为什么不按"每编译一次 +0.0.1"

可以实现，但会同时破坏上面两层的价值：

1. **不可复现**：同一 commit 两次编译得到两个不同版本号，"2.1.1 出问题"就没法复现回那个 bin；
2. **必须改文件 → 工作区变脏**：版本计数要落盘才算数，落盘就是一次未提交改动，
   正好踩中"不要拿 dirty 构建发 OTA"这条纪律；落库到构建目录又换台机器就丢；
3. **多机漂移**：你和我各编一次，计数各自 +1，两台机器的"同一版"对不上；
4. **语义错误**：SemVer 的 patch 是"修 bug 的发布"，不是"编译次数"。真需要构建序号，
   放在 build metadata 就够：`2.1.0+g708d4ea.b17` —— 照样不参与比较，也不脏工作区。

## 日常操作

| 场景 | 命令 | 结果版本 |
|---|---|---|
| 随便编（默认带 commit） | `idf.py build` | `2.1.0+g3343b3d`（脏工作区则 `…dirty`） |
| 日常构建（带环境初始化 + 体积门禁） | `pwsh -f tools/build_fw.ps1` | 同上 |
| 发布构建（必须干净工作区） | `$env:RELEASE_BUILD='1'; idf.py build` 或 `pwsh -f tools/build_fw.ps1 -NoMeta` | `2.1.0` |
| 构建 + 烧录（调试用） | `pwsh -f tools/build_fw.ps1 -Flash` | 同上，末尾 `app-flash` |
| 发版 OTA | 设备侧只认版本数值：`2.0.0 → 2.1.0` 正常门禁放行，**不需要 force** | — |

## 已知边界

- 同一 release 的两次构建（版本都 2.1.0）互相 OTA 时，门禁会判"版本解析相同 →
  需勾 force"。这是**预期行为**：版本没升就不该 OTA；真要重刷同版，勾 force 即可
  （设备端 `force=1` 放行）。
- `2.1.0+g<sha>` 里的 commit 只在**构建时**注入；用 `idf.py build` 直接编（不走脚本）
  会退回 `version.txt` 的纯 `2.1.0`，不带 commit —— 发布包想要干净版本号时反而该这样。
- `version.txt` 改了不提交就构建，会得到 `2.1.1+g…dirty`：设备看到的是完整的 2.1.1，
  这是**真升级**。发版前请先提交。
