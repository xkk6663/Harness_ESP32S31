## §0 一页速览

| 区域 | 性质 | 现状（2026-09-25） | 头号风险 |
|---|---|---|---|
| **内部 RAM（SRAM）** | 最稀缺，**唯一"碎片化会要命"的区域** | 静态占用 ≈119 KB + WiFi ~51 KB（挪不走） | `largest_free_block` 被切碎 ⇒ `esp_timer_create` 这类"只认内部、零回落"的分配 NO_MEM |
| **PSRAM** | 8 MB，宽裕但**带宽是共享的** | 帧缓冲 1.5 MB + 模型 ~1.04 MB + 相机/画布 ~288 KB + net_time 8 KB | **带宽**（不是容量）：GDMA 持续 36 MB/s + LVGL + 相机 + 推理会互相抢 |
| **DMA 能力内部内存** | 内部 RAM 的子集，**有硬约束** | WiFi ~51 KB、I2S、摄像头 DVP | 只能省不能挪（WiFi 那份是组件里硬写的 `MALLOC_CAP_INTERNAL\|DMA`） |
| **Flash / LittleFS** | 6,160,384 B（storage 分区） | 已占 768,380 B，模型 4 份 ≈1.19 MB | 写入 = 关中断 + 关 cache 上百 ms ⇒ **打乱 WiFi/音频**（花屏已修，见 §7） |

**三条一句话总结**：

1. **内部 RAM 的问题是"碎片"，不是"总量"** —— 所以判读一律看 `largest_free_block`。
2. **PSRAM 的问题是"带宽"，不是"容量"** —— 所以优化方向是"减少事务数/顺序化访问"，不是"搬更多东西过去"。
3. **flash 写是"全局抖动源"** —— 少写一次比省 1 KB 更值钱。

## §1 规划原则（四条，先立规矩）

### 1.1 判读口径：内部 RAM 只看 `largest_free_block`，不看 `free_size`

TLSF 分配器 O(1)、但**不解决碎片**（也**不能**做 compaction —— 指针会失效）。
`free_size` 很大而 `largest` 很小 ⇒ 该分配照样失败。所以：
- **任何 "内存够不够" 的结论，必须用三元组**：`申请量 / free / largest`。
- 本工程已内置该口径的埋点：`MEM_ERR_DIAG()` 与 `MEM_STAGE()`（`main/middleware/mem_diag.h`）。

### 1.2 先测后改；**设想与数据冲突时改文档、不倒数据**

本项目的方案文档已被自己的实测否决过多次（`内存优化可执行方案.md` §1、§10.2、§18.3）。
**这是既定做法，不是意外。** 反过来也成立：**没测过的结论必须标"未实测"**，
不许因为"推理很确定"就写成事实。

### 1.3 栈的"位置"不可挪（只能缩），"区域"可挪（但有前提）

- `uxTaskGetStackHighWaterMark()` 返回的是**历史最小剩余**，不是"用量"。
  ⇒ 正确口径：`used = size - hwm`，`need = used × 1.5`（向上取 512），
  且 **`size - need ≥ 2048` 才值得缩**；反过来 **`hwm ≤ size/8` 说明该加不该缩**。
  （F37 就是照字面用 `hwm×1.5` 判的，结论完全反向。）
- **任何做 flash / NVS / littlefs I/O 的任务，栈必须在内部 RAM**（F35 铁律）。
  本工程 `SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y` + `TASK_CREATE_ALLOW_EXT_MEM=y`
  ⇒ 用 `xTaskCreateWithCaps` 会**真的**把栈放到 PSRAM，然后踩 F38/F40。
- **省栈只能靠量水位缩尺寸，不能靠挪区域。**（全仓 `grep WithCaps` = 0：这个坑一次没踩过，保持。）

### 1.4 只省"确定性"的；**省 internal 才算省**

- 省 PSRAM 而不省内部 RAM 的动作，**优先级一律最低**（PSRAM 不是当前瓶颈）。
- 每个"外移 PSRAM"的动作**必须留降级路径**（分配失败退回内部并告警），
  否则会把"内存紧"变成"功能整个消失"。

## §2 内存地图

### 2.1 内部 RAM（SRAM）—— 唯一会"碎片化致死"的区域

**主要消费者**（★ 全部落内部 RAM）：

| 项 | 约(B) | 位置 / 备注 |
|---|---|---|
| RGB bounce buffer ×2 | **0** | ★ 原本 64,000（HEIGHT=20）→ 32,000（=10）→ **2026-09-25 三轮整体关闭**。详见 §3 |
| `udp_voice` 重排槽 `slots[8]` | **5,152** | `udp_voice.c:254`，槽 644 B（1+pad+2+640） |
| `audio_service.c` 静态缓冲 | **13,952** | `play/rec_rb_pool[1024]×2` + `mic_tx[5120]` + `spk_rx[3840]` + `audio_task_io[1024]` + `discard/mic_frame/spk_frame[640]×3` |
| `record_service.c` chunk ×2 | **8,180** | 函数内 `static uint8_t chunk[4090]` ×2（仍是 .bss） |
| `net_time` HTTP 缓冲 8 KB | **0** | ★ 已外移 PSRAM（失败降级回内部 8,192） |
| taskLVGL 栈 | **12,288** | `main.c:390`（`bsp_display_start_with_config()` 覆盖） |
| main 任务栈 | **3,584** | `ESP_MAIN_TASK_STACK_SIZE` |
| **10 个显式任务栈** | **75,776** | 见 `内存优化可执行方案.md` §2.2；★ **core0 独揽 6×8192** |
| WiFi / lwIP / esp_timer / IPC | **≈51 KB+** | ★ WiFi 那 ~51 KB 是**组件里硬写的** `MALLOC_CAP_INTERNAL\|DMA`，`SPIRAM_TRY_ALLOCATE_WIFI_LWIP` 管不到 |

> **点算口径说明**：以上除 WiFi 那笔外都是源码可核的静态量（`[点算]`）。
> 真值以开机日志的 `[mem] <stage>` 行为准。

**为什么它是"头号结构性风险"**：上电某刻实测
`INT free=127,371 / largest=55,296`，而 WiFi 重建一次就要 **51,200** 连续
⇒ **余量只剩 4 KB**。只要出现"WiFi re-init"路径（掉线重连极端情况、模式切换）就会撞。

### 2.2 PSRAM —— 宽裕，但**带宽**是共享资源

| 项 | 约(B) | 备注 |
|---|---|---|
| RGB framebuffer ×2（= LVGL 画布） | 1,536,000 | `fb_in_psram=1`；AVOID_TEAR 下 LVGL 直接画这里 |
| `face_service` scratch | 172,800 | 240×240×3，`MALLOC_CAP_SPIRAM\|CACHE_ALIGNED` |
| `tab_camera` canvas buf | 115,200 | 240×240×2 |
| esp-dl 模型张量 | **1,088,004** / 档 | 实测：一个模型常驻 = **1,088,004 B PSRAM + 264 B 内部 RAM**（`[resident]` load/unload 两笔账配对） |
| `net_time` HTTP 缓冲 | 8,192 | 2026-09-25 从内部外移 |
| 壁纸 JPEG + 粒子双缓冲 | 待测 | `overlay_*.c` 已 `MALLOC_CAP_SPIRAM` |

**带宽判据**：pclk 18 MHz × 2 B = **GDMA 持续 36 MB/s**（不随模式改变）。
历史日志里 `memcpy16k max` 曾随负载爬升到预算的 **105~136%** ⇒ PSRAM 带宽一度是瓶颈。

### 2.3 DMA 能力内部内存

- **WiFi `esp_adapter.c` 的 `*_internal_wrapper` 是硬写的** `MALLOC_CAP_8BIT|DMA|INTERNAL`
  ⇒ 约 51 KB **挪不走**（`CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP` 只管 `os_malloc` 一族）。
  **别再试图把它赶去 PSRAM。**
- I2S（`esp_codec_dev` 共用 `i2s_data_if`）、摄像头 DVP 帧缓冲同理受约束。
- 判断某个缓冲能否外移的口径：**它是否被 DMA 直接读写？** 是 ⇒ 留在内部或专用区域；
  否 ⇒ 可外移（例：`net_time` 的 HTTP 累积缓冲、JPEG **输入**缓冲）。

### 2.4 Flash / LittleFS

| 项 | 值 |
|---|---|
| storage 分区 | `0xA20000` + `0x5E0000` = **6,160,384 B** |
| 已占 | 768,380 B（模型 495,840 + boot_tone 98,868 + xwkkk.jpg 32,157 + icons 141,515） |
| **2026-09-25 后** | 模型 4 份（224/416/msr/mnp）= **1,186,432 B** ⇒ 已占 ≈1,459,000 B，可用 ≈4.6 MB |
| 烧录 | `esptool ... write-flash build/storage.bin 0xA20000`（**不是 0x620000**，那个落在 ota_1 里） |

★ **连带结论**：`RECORD_MAX_PCM_BYTES = 300×16000×2 = 9.6 MB` 这个"300 秒硬顶"**永远到不了** ——
32,000 B/s × ≈145 s 就先撞 `ENOSPC`。磁盘侧的上限必须按"可用空间"算，不能按常量算。

### 2.5 常量表（`.rodata`）

- 默认放 **flash（XIP）**，不占 RAM、但占"cache 命中"。频繁访问的小表若要进 RAM，
  用 `IRAM_ATTR` 或 `DRAM_ATTR` —— **但那是花 RAM 换速度，别为了让 RAM 数字好看反过来做。**
- Bin 字体表：本工程用 `--format bin` 的 lv_font_conv 产物，**运行时从文件读**，不占 `.rodata`。

## §4 铁律与红线（动内存之前必读）

1. **`esp_timer_create` 只要内部 RAM、零 PSRAM 回落**（`esp_timer.c:112`）⇒
   它是内部堆碎片的**第一个受害者**。看到 `phy_track_pll_init` NO_MEM，往这里想。
2. **`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL` 必须是 0**。设成 16384 会让
   "size ≤ 该值的小分配"优先走内部堆 ⇒ esp-dl 的**小对象海**（算子注册/`std::map`/`std::string`）
   全灌内部堆并把它切碎。**这是碎片的物理来源。**
3. **做 flash / NVS / littlefs I/O 的任务，栈必须在内部 RAM**（F35）。省栈靠量水位缩尺寸。
4. **`uxTaskGetStackHighWaterMark` = 历史最小剩余**；`used = size − hwm`（F37 教训）。
5. **外移 PSRAM 必须留降级**：主路 PSRAM、失败退回内部并 `ESP_LOGW`，两处都失败才拒绝启动。
6. **缓冲改指针后，`sizeof(ptr)` 会静默变成 4/8** ⇒ 长度一律用 `#define` 宏
   （本工程先例：`NET_TIME_HTTP_BUF`）。
7. **`AVOID_TEAR=y` 时 LVGL 画布就是 PSRAM 里的 RGB framebuffer** ⇒
   **不存在"内部 draw buffer"**，`BSP_LCD_DRAW_BUF_HEIGHT` 被忽略。别再提"挪 draw buffer"。
8. **esp-dl 的张量本来就在 PSRAM**（`max_internal_size` 默认 0 ⇒ 走 simulate 路径）。
   **也别再提"挪模型"。** 模型加载期的内部 RAM 消耗只有约 **264 B**（实测）。
9. **PSRAM 与 flash 映射共用同一个 cache**（`cache_utils.c:68-73` 明说 psram cache 不是独立的）
   ⇒ `spi_flash_disable_interrupts_caches_and_other_cpu()` 的窗口内，
   **"所有核碰 PSRAM"都会炸** —— 判据是 `esp_ptr_in_dram()`。
   ⇒ 危险集合 = 该窗口内**任何核的 PSRAM 数据访问**（含中断里的）。
10. **WiFi 的 ~51 KB 内部 DMA 挪不走**（组件里硬写的 caps）。别再试。
11. **ringbuf 是 14-bit 索引** ⇒ **任何单个 pool 不得超 16383 B**。
12. **探针自己就是负载**（观察者效应）：曾用 200 ms × 8 次 16 KB memcpy 制造 PSRAM 独占窗口
    ⇒ 自己制造花屏。现为 1000 ms × 2 次。**加埋点前先估它自己的开销。**
13. **非 LVGL 线程不得碰 LVGL**（回调只置 volatile 标志）。这既是线程安全，也是内存安全
    （LVGL 对象的生命周期不在你手里）。
14. **`LCD_RGB_ISR_IRAM_SAFE` 在本工程是反向开关**：打开会让 ISR 去读 PSRAM 帧缓冲 ⇒ 崩溃。

## §5 明确不做（止损线：想过、查过、决定不做，且记下理由）

| 不做 | 理由 | 将来入口 |
|---|---|---|
| **任务栈整体外置 PSRAM** | 与 F35/F37 直接冲突；做 flash I/O 的任务栈必须内部 | 永不 |
| **堆 compaction / 内存整理** | TLSF 下指针会失效，不可行 | 永不 |
| **停 WiFi / 暂停重连来"避让"内存** | 已试过并**证伪**（`堆分配与任务竞争经验总结.md` §3.2） | 永不 |
| **独立 `face_load` 任务（8 KB 栈）** | 2026-09-18 试过：多占内部 RAM、加剧碎片，回退后才通 | 不重试 |
| **`cam_task` 扩栈** | 深度推理跑在 **LVGL 线程**，cam_task 实测峰值仅 2,140 B（6144 已够） | 若推理改到 cam_task |
| **`cam_task` 改"只建一次"常驻** | 会引入开机常驻 6 KB 内部栈，违反止损线；历史已证伪 | 若相机使用率极高 |
| **摄像头硬件真关（`bsp_camera_stop`）** | BSP 把 XCLK 句柄丢在局部变量里、从不 free；**收益是功耗不是内存** | 做功耗优化时 |
| **`SPI_FLASH_AUTO_SUSPEND`** | IDF help 明说只支持特定 flash 芯片，有**变砖**风险；收益只对那 1~4 次/分钟 | 官方确认本板 flash 后 |
| **省 PSRAM 项（如 P3-3）** | PSRAM 不是当前瓶颈 | 若 PSRAM 真告急 |

## §6 验证与判读口径（怎么证明"改了有效"）

| 观测项 | 口径 | 判据 |
|---|---|---|
| 内部 RAM 健康度 | `[mem] <stage> want=.. INT free=.. largest=.. DMA free=.. PSRAM free=..` | **只看 `largest`**；`largest` 不随反复操作单调下滑 = 无泄漏 |
| 模型常驻/切换 | `FACE: [resident] load #N / unload #N` | 反复切档 10 次后 `largest` 不单调下滑 |
| 任务栈 | `[stack]` 全任务表 | `used = size − hwm`；`size − need ≥ 2048` 才缩；`hwm ≤ size/8` 该加 |
| PSRAM 带宽 | `[panelprobe] memcpy16k avg/max` | **不再有"444 µs 死线"**，只作带宽健康度；与改前同负载对比 |
| flash 写窗口 | `[panelprobe] gap max`（`>1ms` / `>5ms` 计数） | 5~50 ms 尖峰且紧跟 WiFi 重连 ⇒ 命中擦写窗口（仍会打乱 WiFi/音频） |
| 屏幕供数 | 眼看：相机页 + WiFi 重连窗口 | 不再错位花屏（花屏根因已于 §7 修复） |


- **模型侧**：`FACE: model "224" ready` / `[resident] load #N ... largest ...(0)` /
  `switch -> "416"` / `detect OFF | ... stays resident`
- **屏幕侧（唯一要眼看）**：相机页 + WiFi 重连窗口内**不再错位花屏**
- **内存侧**：`largest` 不应比改前更差（会多出原先被 bounce 占用的 32 KB）

### 7.2 P1 —— 栈收敛（**排在 P0 之后**）

日志全表 `TOTAL size=88,064 B | need=51,712 B | 可省=34,816 B | tasks=17`。

**但先别做**，理由：同一份日志里**内部堆 `largest=67,584 B` 且模型加载/卸载全程零变化**
⇒ 内部 RAM 容量当前不紧，而瓶颈在 PSRAM 带宽。缩栈只增加 `free`、**改善不了 `largest`**，
风险却是 F37 的教训。若做，只动 `led_task` / `udp_voice_ctl`，且留 ≥2.5 倍余量。

### 7.3 P2 —— 若要再减内部 RAM，方向是"缩 `.bss`"

`.bss` 先从内部 RAM 切走，缩它 = 直接加**连续**堆。候选（按"风险 ÷ 收益"）：
- `udp_voice` 的槽（已从 20,608 降到 5,152，再动要看重排窗口的丢包率是否恶化）
- `record_service` 的 2×4090 chunk（两者在**不同任务**，不能简单合并）
- 任何"只在某个模式用一次"的大静态缓冲 → 改按需分配 + 用完释放

### 7.4 P3 —— 触发式（不到阈值不做）

| 触发条件 | 动作 |
|---|---|
| `largest` 再次跌破 ~55 KB | 才考虑 P1 栈收敛 |
| 出现 WiFi re-init 路径 | 提前处理 §2.1 那 4 KB 余量（否则必撞） |
| PSRAM 分配失败日志出现 | 才考虑省 PSRAM 项（P3-3） |
