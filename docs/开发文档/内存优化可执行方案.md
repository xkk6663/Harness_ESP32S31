## §1 三条"看上去最该做、实际打偏"的方案（先止损）

### 1.1 ❌ 方案 A：LVGL draw buffer 挪 PSRAM —— 已经是这样了

`FACE加载NO_MEM优化方案.md` 的原话是"LVGL 主 draw buffer 默认在内部 RAM，占 ~150KB，挪 PSRAM 后内部 RAM 富余 150KB+"。

**事实（`[点算]` 组件源码）**：

```c
/* esp_lvgl_port/src/lvgl9/esp_lvgl_port_disp.c:361-369 */
if (priv_cfg && priv_cfg->avoid_tearing) {
    if (priv_cfg->disp_type == LVGL_PORT_DISP_TYPE_RGB) {
        buffer_size = disp_cfg->hres * disp_cfg->vres;
        esp_lcd_rgb_panel_get_frame_buffer(disp_cfg->panel_handle, 2, &buf1, &buf2);
        // ↑ 直接拿 RGB panel 的两个 framebuffer 当 LVGL 画布，不额外分配 draw buffer
```

本分支 `sdkconfig`：`CONFIG_BSP_DISPLAY_LVGL_AVOID_TEAR=y`、`CONFIG_BSP_LCD_RGB_BUFFER_NUMS=2`，
BSP 里 `.flags.fb_in_psram = 1`（`bsp_display.c:111`）。

⇒ 画布 = **2 × 800×480×2 = 1,536,000 B 已在 PSRAM**（`MALLOC_CAP_SPIRAM|MALLOC_CAP_DMA`，`esp_lcd_panel_rgb.c:210`）。
**这条优化没有可做的对象。** 顺带说明：`CONFIG_BSP_LCD_DRAW_BUF_HEIGHT=100` / `DOUBLE=y` 在 `avoid_tearing` 下已被忽略，改它无任何效果（改不动内存，只改代码可读性）。

### 1.2 ❌ 方案 B：加载期间停 WiFi / 暂停重连 —— 已证伪

`堆分配与任务竞争经验总结.md` §3.2 记录：`esp_wifi_stop()` 会让 `wifi_manager` 在 STOP 态调 `esp_wifi_set_config` → abort。
**保留"择时"（挑 WiFi 稳定期加载），删掉"暂停"（改底层状态）**。本方案 §4-P2 用的是择时。

### 1.3 ❌ 任务栈整体外置 PSRAM —— 与 F35/F37 直接冲突

本分支 `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y` + `CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y`，
⇒ 一旦用了 `...WithCaps` 把栈放进 PSRAM，就会踩 F37/F40 的窗口：

- `spi_flash_disable_interrupts_caches_and_other_cpu()` **只关 cache，不停另一核**；
- PSRAM 与 flash 映射**共用同一 cache** ⇒ 关 cache 窗口内**任何核上的任何 PSRAM 访问**都会 `Cache error`；
- 窗口数 = 读数 / 16KB（读 495KB 模型 ≈ 30 个窗口）。

⇒ 规则：**做 NVS / littlefs / flash 分区 IO 的任务，栈必须在内部 RAM。**
本分支里 `record_task`（fopen/fwrite）、`audio_task`（WAV 读）、`net_time_task`（HTTPS 读）**都做 flash IO**，
本身就属于"栈必须内部"的集合 —— 所以**省栈只能靠"量水位 + 缩尺寸"，不能靠"挪区域"**。

## §3 根因链（每条都带可复现证据）

### 3.1 证据一：`esp_timer_create` **只认内部 RAM，且零回落**

崩溃栈是 `phy_common.c:126 phy_track_pll_init` → `esp_timer_create` → `ESP_ERR_NO_MEM`。看 IDF 源码：

```c
/* components/esp_timer/src/esp_timer.c:112 */
esp_timer_handle_t result = (esp_timer_handle_t) heap_caps_calloc(
        1, sizeof(*result), MALLOC_CAP_8BIT | MALLOC_CAP_INTERNAL);   /* ← 只要内部，没有 PSRAM 回落 */
if (!result) {
    return ESP_ERR_NO_MEM;
}
```

⇒ 只要内部堆拿不出这块，**必失败，不会退到 PSRAM**。
这就是"`free internal=72KB` 却 NO_MEM"的机制：72KB 是总量，失败看的是 **largest_free_block**。

### 3.2 证据二：`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=16384` 把 esp-dl 的"小对象海"全灌进内部堆

```c
/* components/heap/heap_caps.c:107-125 */
void *heap_caps_malloc_default(size_t size) {
    if (size <= malloc_alwaysinternal_limit)            /* = CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL */
        r = heap_caps_malloc_base(size, MALLOC_CAP_DEFAULT | MALLOC_CAP_INTERNAL);   /* 只匹配内部 */
    else
        r = heap_caps_malloc_base(size, MALLOC_CAP_DEFAULT | MALLOC_CAP_SPIRAM);
    if (r == NULL && size > 0)
        r = heap_caps_malloc_base(size, MALLOC_CAP_DEFAULT);   /* 才会退到 PSRAM */
```

**`malloc_alwaysinternal_limit = 16384`** ⇒ 所有 ≤16KB 的 `malloc/new/std::string/std::map/std::vector` 节点
**优先吃内部堆**。而 esp-dl 加载模型时会做：

- `ModuleCreator::register_dl_modules()` —— 为每种算子 `new` 出实例 + `std::map` 插入
- `FbsModel::load_map()` —— 把所有张量名建进 `std::map<std::string, ...>`
- `ExponentInfo::copy_exponents()`、`ImagePreprocessor`、各 `Postprocessor`

⇒ **成百上千次小而零碎的内部分配**，正是"内部堆碎片化到没有连续块"的物理来源。

**对照 main 分支 `[实测]`**：main 这里已经是 **`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0`**（小对象全部走 PSRAM），
并且 13/14 号文档 §9 的总账（internal free 25.4→**51.2KB**、largest 23.0→**31.0KB**）就是在这个配置下拿到的。

### 3.3 证据三：esp-dl 的**张量**其实早就在 PSRAM —— 所以"挪模型 / 挪 draw buffer"都打偏

```c
/* dl_memory_manager_greedy.cpp:21-28 */
#if CONFIG_SPIRAM
    if (this->max_internal_size > this->alignment) simulate_with_internal_memory(...);
    else                                          simulate(...);      /* ← 张量全部走 PSRAM */
```

而 `dl_model_base.hpp:86` 的构造函数签名是 `int max_internal_size = 0`，`human_face_detect.cpp` 用的是
`new dl::Model(sd_path.c_str(), fbs::MODEL_LOCATION_IN_SDCARD)`（2 参）⇒ **`max_internal_size` 取默认 0**
⇒ `0 > 16` 为假 ⇒ 走 `simulate()` ⇒ `internal_size = 0` ⇒ `ModelContext::root_alloc()` **不分配 `m_internal_root`**。

⇒ **模型的 495KB 权重和激活张量本来就在 PSRAM**。真正吃内部的是 §3.2 的"小对象海"，不是模型本身。
同时这也给了我们一个**零成本探针**：`dl_model_context.cpp:176` 在失败时会自己打

```
Failed to alloc %.2fKB internal RAM, largest available internal RAM block size %.2fKB
```

**日志里搜这句，就能直接读到当时的"要多少 / 最大连续块多少"** —— 不需要改任何代码。

### 3.4 结论

> **病灶 = 内部堆的"碎片度"。**
> 三条处方因此成立：**①别让小对象进内部（配置）②别让静态大块占内部（尺寸）③让内部只服务"非它不可"的请求（择时/预留）**。
> "free internal 有多少"是**没用的指标**，要盯 `largest_free_block`。

### 10.2 对方案本身的两处**勘误**（后人别再照原公式做）

**① §4-P2-4 的"缩到 `水位 × 1.5`"必须按「用量」口径解释，按字面做会得到**完全相反**的结论。**
`uxTaskGetStackHighWaterMark()` 返回的是**历史最小剩余空闲**，不是用量。
第一版实现直接拿 hwm×1.5 当 need，后果是：几乎不用栈的任务（hwm≈size）算出 need>size 被误标"偏紧"；
吃满栈的任务（hwm≈0）算出 need≈0 被推荐"缩到 1536" ⇒ **照着改必崩**。
正确口径：`used = size - hwm`，`need = used × 1.5`（向上取整 512），
且 `size - need ≥ 2048` 才值得缩、`hwm ≤ size/8` 一律标"偏紧"该加不该缩。

**② §4-P2-5 的前提（"do_load 在 cam_task 栈上跑完整 esp-dl C++ 构建 ⇒ 要 ≥8192"）与实测不符。**
实测峰值仅 2,140 B。原因：**深度推理不在这条栈上** —— `detector->run()` 由
`tab_camera::refresh()` 在 **LVGL 线程**调用，那部分栈深算在 taskLVGL 头上。
⇒ cam_task 保持 6144；真正该盯的栈是 taskLVGL。
**③ §4-P2-3 的"把 mic_frame/spk_frame 合并进 ringbuf pool 直接取址"不可行**：
`main/3rd/ringbuf` 只有 `put/get/peek`，**没有 claim/commit 零拷贝 API**，也没有"跳过 N 字节"，
所以只能做"同一任务内两处暂存合并"这一种；`discard[]` 与 `spk_frame` 分属不同任务，不能并。

### 10.3 P3 的三条**决策记录**（都是"不做"，但都留了将来的入口）

- **P3-1（`camera_service_stop()` 关不掉摄像头硬件）→ 不做。**
  已核对：`esp_video_deinit()` **是存在的**（`esp_video_init.h:275`，与 `esp_video_init` 成对），
  但 `bsp_camera_start()` 把 `esp_cam_sensor_xclk_handle_t` 丢在**函数局部变量**里、从不 free，
  所以"停止 XCLK"这条路径在 BSP 层就已经丢了句柄。两条路都有代价：
  ①直接调 `esp_video_deinit()`：XCLK（LEDC）仍常开 ⇒ 只收回一半，且会把 BSP 的静态状态搞脏
    （`s_bsp_started` 与真实硬件不再一致，再次 START 会重复 `esp_cam_sensor_xclk_allocate`）；
  ②自己重建 DVP 配置、绕开 BSP：等于把 BSP 里那套 pin/时钟配置抄一遍，**出错就是相机彻底不出图**，
    而且收益是**功耗**、不是内存。
  ⇒ 结论：**不为了省功耗去动一块正在工作的显示+相机链路**。要做的话，正确入口是给上游 BSP
    提一个 `bsp_camera_stop()`（内部 `esp_video_deinit` + `esp_cam_sensor_xclk_free` + 句柄改静态），
    属于组件改动，单独排期。
- **P3-4（cam_task 只建一次、事件组驱动）→ 不做。**
  它会引入一个**开机即在的常驻任务**（6 KB 内部栈），直接违反本方案 §7-6
  "不做/不加新常驻任务"；而且**本项目历史已经证伪过这条路**：
  `改动记录.md` 2026-09-18 一节写着"加独立 face_load 任务（8KB 栈）→ 多占内部 RAM，**加剧碎片**"，
  最后是靠回退到"没有额外任务"的基线才跑通的。
  现有的"按需建/删 + P0-3 已修好的退出确认"其实**更省**：栈只在相机页打开期间存在。
- **P3-3（`s_scratch` 与 canvas 双份 240×240）→ 不做。** 省的是 PSRAM，不是内部 RAM。

## 11. 第二轮上机：花屏 / WiFi 断连 归因（2026-09-25，分支 `端侧人脸识别`）

> 用户原话："wifi断连情况和屏幕错位情况还是存在，排查bug并优化内存管理"。
> 本轮**没有**新增内存项，反而把一块此前被当成"内存问题"的症状重新归因成
> **PSRAM 带宽 + flash 擦写**问题。结论是：**本机当前瓶颈已经不是内部 RAM 容量，
> 而是 PSRAM 的带宽与访问时序。** 继续缩内部栈的边际收益很低。

### 11.1 日志给出的三组硬证据

> **★ 两句话讲完（先看这个再看证据）**
> 1. **屏幕花屏有两条完全独立的路**：① flash 擦写时系统会临时关掉 PSRAM 访问 ⇒
>    bounce buffer 搬不动；② 相机/推理期 PSRAM 被抢到带宽不够 ⇒ 一次搬运要 602 us（超预算 136%）。
>    **上一轮只治了 ①，而真正的主因是 ②。**
> 2. **WiFi 断连与 flash 无关**：WiFi 硬件只有 **2 个**收包缓冲（IDF 在本配置下默认给 16 个），
>    CPU 一忙就丢包，**beacon 也是包** ⇒ 连续丢 ⇒ 路由器判你掉线 ⇒ `reason=200`。

**(0) ★★ 权重判读：哪条是真主因（这条决定了"上一轮为什么没效果"）**

| 路径 | 出现频次 | 症状 |
|---|---|---|
| ① flash 擦写窗口 | 1 分钟 **1~4 次**（每次 ~100 ms） | 偶发一闪 |
| ② PSRAM 带宽越预算 | 相机一开就 84~96%、推理期 105~136% ⇒ **几乎帧帧越线** | **持续性花屏** |

用户描述的是"花屏**还是存在**"（持续性），不是"偶尔闪一下" ⇒ **主因是 ②，① 只是偶发叠加。**

**零成本自测（先做这个，不用烧固件）**：只在普通 UI 页停留几分钟，再进相机页开人脸。
日志显示相机关时 `memcpy16k` 只有 66%（余量 34%，安全）⇒ **花屏应当只在相机页出现**。

**(1) flash 擦写窗口被实证（此前只是推测）**

```
W (4807) main: [panelprobe] gap max=94123 us (>1ms:366 >5ms:1) | memcpy16k max=295 us (66%)
W (5792) main: [panelprobe] gap max=156893 us (>1ms:262 >5ms:4) | memcpy16k max=296 us (67%)
```

`panelprobe` 是 1 kHz `esp_timer`，回调间隔被拉长到 94 ms / 157 ms ⇒ 那段时间**非 IRAM
中断被整体关掉**，唯一能做到这一点的就是 `spi_flash_disable_interrupts_caches_and_other_cpu()`
（flash 擦写）。两个时间点都落在 **WiFi scanning → join → auth → assoc** 与**重连**窗口里。

**(2) PSRAM 带宽超预算 = 花屏的第二个、独立触发源（已被实测坐实）**

| 场景 | `memcpy16k` max | 占 444 us 预算 |
|---|---|---|
| 相机关（仅 UI） | ~295 us | 66% |
| 相机开（预览 + 逐像素翻转） | ~370~430 us | 84~96% |
| **模型加载中** | **602 us** | **136%** |
| **人脸推理中** | 463 / 484 / 491 / 546 us | 105 / 109 / 111 / 123% |
| 卸载后回落 | ~285 us | 64% |

预算 444 us = `800 px x 10 line x 2 B ÷ (18 MHz x 2 B/pclk)`，即 bounce buffer 那一批数据
在 GDMA 取走之前必须搬完的时间。**超过 444 us ⇒ 这批 10 行没填完就被读走 ⇒ 错位**；
而 S31 上 `esp_lcd_panel_rgb.c` 的 VBlank 复位分支全被编译掉 ⇒ **错位不自愈**。

**(3) 一个此前被忽略的真凶：静态 RX 缓冲只有 2 个**

```
sdkconfig:      CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM=2
IDF 6.1 Kconfig: default 16 if (SPIRAM_TRY_ALLOCATE_WIFI_LWIP && !SPIRAM_IGNORE_NOTFOUND)
本机实际:        SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y, SPIRAM_IGNORE_NOTFOUND 未开 ⇒ 命中 default 16
build 真值:      #define CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM 2     ← 陈旧遗留值，不等于任何 default
```

IDF 对该项的原话：*"WiFi hardware use these buffers to receive **all** 802.11 frames"*、
*"If ESP_WIFI_AMPDU_RX_ENABLED is enabled, this value is recommended to set equal or bigger than
ESP_WIFI_RX_BA_WIN"*（本工程 `RX_BA_WIN=2`，即 2 只是**勉强压线**）。

⇒ **beacon 也走这几个 buffer。** CPU 被 bounce 中断（每 444 us 一次、每次 ~300 us，
约 **55~75% 的 CPU**）占满时，WiFi 任务来不及腾空 buffer ⇒ 新帧直接丢 ⇒ 连续丢 beacon
⇒ `reason=200 (BEACON_TIMEOUT)`。
**这解释了为什么 `WIFI_PS_NONE` 早就设了却没用**——根因不是省电，是缓冲深度只有 2。

### 11.2 本轮已落地（3 个文件 + 2 处配置）

| # | 文件 | 改动 | 目的 |
|---|---|---|---|
| 1 | `main/middleware/camera/camera_service.c` | `S_FMT` 后新增 `VIDIOC_S_EXT_CTRLS` 设 `V4L2_CID_VFLIP/V4L2_CID_HFLIP=1`（OV3660 `0x3820/0x3821`） | 把预览的 180° 旋转交给传感器 |
| 2 | `main/ui/tab_camera.c` | `refresh()` 的 240×240 双重循环从"跨行倒序 + 行内倒序 + swap"退化成**纯顺序 swap** | 消掉 57,600 次/帧的**逆序** PSRAM 访问 |
| 3 | `main/app/main.c` | `PROBE_COPY_PERIOD_TICK` 200→1000、`PROBE_COPIES_PER_ROUND` 8→2 | 探针自身负载降 20 倍（观察者效应） |
| 4 | `sdkconfig` | `ESP_WIFI_STATIC_RX_BUFFER_NUM` 2 → **16** | 对症 `reason=200` |
| 5 | `sdkconfig.defaults` | 显式钉死 ①~③ 三项真值 + A/B 指引；顺带修复 PPA 那一段的**编码损坏行**（它把 `# CONFIG_LV_USE_PPA is not set` 吞进了中文注释里，导致该行不在行首、不是有效 Kconfig 行） | 防 IDF 升版后默认值静默漂移 |

**为什么 (1)+(2) 一起做**：原代码 `src_row[CAM_W-1-x]` 是逆序访问，一个 64 B cache line
只命中 1 个像素，而源（DVP 帧缓冲 115 KB）与目的（canvas buf 115 KB）**都在 PSRAM**；
改成 HFLIP/VFLIP 由传感器做之后，剩下的循环是顺序访问，一条 cache line 覆盖 16 个像素。
两者**方向必须同时改**（只改一处画面会翻转），且翻转后的像素与原来自算的 `s_canvas_buf`
逐字节一致 ⇒ `face_service_detect()` / `color_hsv_detect_red()` 的坐标系**不用动**。

### 11.3 A/B 实验清单（按"收益 ÷ 风险"排序，需真机验证）

**实验 A（头号候选）：关掉 bounce buffer 模式 —— ★ 2026-09-25 已落地，见 §11.7**

```diff
-# CONFIG_BSP_LCD_RGB_BOUNCE_BUFFER_MODE is not set
+CONFIG_BSP_LCD_RGB_REFRESH_AUTO=y
+# CONFIG_BSP_LCD_RGB_BOUNCE_BUFFER_MODE is not set
```

预期：**一次性解决花屏的两条路径**
- 路径①（flash 擦写）：bb 模式下"每 444 us 必须完成的 16,000 B 软件搬运"**消失了**
  ⇒ 关中断窗口内不再有"漏填 ⇒ 错位"这个动作；
- 路径②（抖动）：**消灭 1699 次/秒的 ISR**（约 55~75% CPU 归还给 WiFi / LVGL / 推理）；
- 附带：省 **32,000 B** 内部 DMA RAM（头文件 `esp_lcd_panel_rgb.h:151` 明说是 **two** DRAM
  bounce buffers ⇒ 2 × 800 × 10 × 2 = 32,000，不是我先前写的 16,000）。

⚠ **机制上有一处必须说清（我第一版写得太绝对，已改）**：
不能说成"GDMA 直读 PSRAM 不经过 cache 所以完全不受 flash 影响"——IDF 只保证
"**这些 CPU** 不会去碰外部 RAM"（`cache_utils.c:172-175`），**通篇没提 DMA**；
而且头文件 `:152` 明说 *"DMA fetching from DRAM bounce buffer is **much faster than** PSRAM
frame buffer"* ⇒ auto 模式的 DMA 是**实时**从 PSRAM 取数、受 PSRAM 延迟直接影响。
所以准确的说法是**换了失稳的形态**：

| | bb 模式 | auto 模式 |
|---|---|---|
| 供数者 | 软件在 1699 Hz 的 ISR 里搬 16 KB | GDMA 硬件按像素时钟自己取 |
| 失稳表现 | **错过一次死线 ⇒ 硬错位，且 S31 无 VBlank 复位 ⇒ 永不自愈** | PSRAM 若供不上 ⇒ 瞬时欠载（可自愈） |
| 平均 PSRAM 流量 | 36 MB/s（**与 auto 相同**） | 36 MB/s |
| CPU 占用 | ~55~75%（不可抢占的中断上下文） | ~0（仅 ~35 Hz 的 vsync 回调给个信号量） |

⇒ **平均带宽不是变量，"有没有软件死线"才是。** 这是本次改动的真正价值所在。

风险与验证：**唯一要眼看的是花屏是否消失**（见 §11.7 验收）。
**若出现整屏花屏/黑屏，立刻把这两行改回来重烧**——这是本清单里唯一"改错就看不见界面"的项。

**实验 B：斩断 PHY 校准落 NVS（治路径①的另一半）**

```diff
-CONFIG_ESP_PHY_CALIBRATION_AND_DATA_STORAGE=y
+# CONFIG_ESP_PHY_CALIBRATION_AND_DATA_STORAGE is not set
```

判据：`[panelprobe] gap max` 是否还出现 >5 ms 尖峰。代价：每次开机重做 PHY 校准（开机变慢）。
**先做实验 A**——如果 A 生效，B 的必要性就大幅下降。

**实验 C（仅当 B 无效）：确认 flash 写者**
把 `wifi_manager` 的 `[panelprobe]` 输出与同时刻的其它日志行对齐（`gap > 1ms` 尖峰前后 ±2 行），
交叉定位触发者。工程侧 NVS 写只有 `wifi_manager.c` 的 `store_commit()`，且已有 F48 的
"凭证没变就跳过"保护（`store_upsert` 返回 changed 才写）——所以嫌疑集中在 IDF 内部（PHY）。

### 11.6 ★ 为什么上一轮的 flash 改动**不可能是**这几次 gap 的成因（时间线反证）

上一轮斩断了两个 flash 写点：

1. `esp_wifi_set_config()` → 已改 `esp_wifi_set_storage(WIFI_STORAGE_RAM)`，不再写 NVS；
2. `save_connected_cred()` → 全文件只有 **1 个调用点**：`IP_EVENT_STA_GOT_IP` 分支
   （`wifi_manager.c:448`）。

而两次 gap 尖峰的统计窗口是 **3.8~4.8 s** 与 **4.8~5.8 s**，落在
**scanning → join → auth → assoc 期间** —— 此刻 `got_ip` 还没发生。

⇒ **第 2 项在那个时刻根本没被调用过；第 1 项已经不写 flash。**
⇒ 这几次 94 ms / 157 ms 的关中断与上一轮改的两处**无关**，真凶在别处
（候选：PHY 校准落 NVS、littlefs 挂载/一致性修复、NVS 页 GC —— 都还没被排除）。

**注意这不等于"上一轮白改"**：那两处是**真实存在**的 flash 写（尤其 `esp_wifi_set_config()`
在默认 storage 下**每次重连都写**），斩断它们本身是对的；只是它们**不是这两个症状的成因**。
⇒ 要定案需要把 `gap` 尖峰与同时刻其它日志行做 ±2 行对齐；
**最省事的排除法是实验 B**（`ESP_PHY_CALIBRATION_AND_DATA_STORAGE=n`）：
一烧就知道是不是 PHY。

**关于 `CONFIG_SPI_FLASH_AUTO_SUSPEND`（想到了但**不推荐**）**：它能把长擦写切碎、缩小关 cache 窗口，
是"不管谁在写都能治"的一刀切方案。但 IDF 6.1 的 help 明确写着
*"supported only for specific flash chips"*、*"contact Espressif Business support to check if the
module has the flash that support this feature"*，贸然打开有**整片 flash 变砖**的风险；
而且既然 ① 只是偶发因素、② 才是主因，**收益与风险不匹配，不采用**。

### 11.7 花屏**根因**修复：bounce buffer 模式 → auto refresh 模式（2026-09-25 落地）

> 用户拍板："直接做 p4 的，然后顺手把花屏的根因做了"。p4 的定稿见
> `多模型加载策略_S1方案.md` §6；本节只讲花屏。

#### 11.7.1 一句话

**不是"调参把窗口变小"，而是"把那个会被打断的动作整个删掉"。**
bb 模式要求软件每 **444 µs** 完成一次"从 PSRAM 搬 16,000 B 到内部缓冲"；
auto 模式把这件事交给 GDMA 硬件，软件不再参与供数。

#### 11.7.2 改了什么（两处配置，`choice` 互换）

| 文件 | 改动 |
|---|---|
| `sdkconfig` | `CONFIG_BSP_LCD_RGB_BOUNCE_BUFFER_MODE=y` + `..._HEIGHT=10` **删除**，改 `CONFIG_BSP_LCD_RGB_REFRESH_AUTO=y` |
| `sdkconfig.defaults` | 同上（**两处必须同值**，否则清库重建后行为突变） |

`BSP_LCD_RGB_REFRESH_MODE` 是 **choice**（BSP Kconfig `:95-106`），二选一，
**两个同时写会撞**；`BOUNCE_BUFFER_HEIGHT` 因 `depends` 失效而自动消失，故一并删掉。

★ 生成文件 `sdkconfig` 里**不写自述注释**——reconfigure 会把自定义注释清掉，
留着会造成"配了但没生效"的错觉。全部说明写在 `sdkconfig.defaults` 与本节。

#### 11.7.3 证据链（全部是 IDF 源码，带行号）

| # | 事实 | 出处 |
|---|---|---|
| 1 | bb 模式的核心动作 = **在 GDMA EOF ISR 里** `memcpy(PSRAM 帧缓冲 → 内部 bounce buffer)` | `esp_lcd/rgb/esp_lcd_panel_rgb.c:1042`（`lcd_rgb_panel_fill_bounce_buffer()`） |
| 2 | **IDF 自己在这行写了警告**：*"if the frame buffer is behind a cache, and the cache is disabled, crash would happen here when auto write back happens"* | 同上 `:1041` |
| 3 | 本工程 `LCD_RGB_ISR_IRAM_SAFE=n`（`sdkconfig:1816`）⇒ 该 ISR **在 flash 擦写窗口被一起关掉** ⇒ 不崩、但**漏填** ⇒ 错位 | `cache_utils.c:171` `esp_intr_noniram_disable()` |
| 4 | EOF 频率：`expect_bb_eof_count = fb_size / bb_size = 768,000 / 16,000 = 48` 次/帧；pclk 18 MHz ⇒ **444 µs/次、1699 次/秒** | `:367-369` + `esp32_s31_korvo_1.h:497` |
| 5 | auto 模式：整个 768,000 B framebuffer **预串成一条 DMA link list**，GDMA 自己扫完整帧 | `:1211-1236`（`gdma_new_link_list` + `mount_cfg.length = fb_size`） |
| 6 | auto 模式 EOF 时**只做回调、不读 PSRAM** | `:1084-1090` |
| 7 | cache 一致性由驱动自己在 flush 时 `esp_cache_msync(C2M)` 兜住，条件正是 `!bb_size` | `:750-753` / `:764-767` |
| 8 | `bb_mode` 在 `esp_lvgl_port` 里**只影响注册哪个回调**（无其它行为依赖） | `espressif__esp_lvgl_port/src/lvgl9/esp_lvgl_port_disp.c:216`（另见 lvgl8:185） |
| 9 | `on_vsync` 回调 = `LVGL_PORT_IRAM` 的、只 `xSemaphoreGiveFromISR` | 同上 `:549-565` |
| 10 | bounce buffer 是 **two** DRAM buffers（⇒ 省 32,000 B）；其设计动机是 **速度**（"much faster than PSRAM frame buffer"）⇒ auto 模式是**默认**模式，不是旁路 | `include/esp_lcd_panel_rgb.h:151-152` |
| 11 | `ISR_IRAM_SAFE` 是**反向开关**：打开 ⇒ ISR 真去读 PSRAM ⇒ 撞 #2 ⇒ **崩溃**（比花屏更糟） | #2 + #3 |

#### 11.7.4 为什么"能切"：PCLK 只有 18 MHz

bb 模式的卖点（BSP Kconfig `:105`）是 *"achieve **higher PCLK** frequency at the cost of
**higher CPU consumption**"*。本工程 pclk 写死 **18 MHz**（`esp32_s31_korvo_1.h:497`）
⇒ **这个能力我们根本不需要**。这是能切的前提条件，也是唯一的前提。

#### 11.7.5 代价与**诚实的残留不确定性**

- 平均 PSRAM 流量**不变**（两种模式都是 36 MB/s）；变的是"有没有软件死线"（见 §11.3 的表）。
- **残留不确定性**：flash 擦写窗口内 GDMA 直读 PSRAM 是否也受影响，**IDF 没有给结论**
  （`cache_utils.c:172-175` 只保证 CPU 不碰外部 RAM，通篇没提 DMA）。
  ⇒ 这条**只能靠上机验收**，不要当成已证明。若改了仍然花屏，说明 DMA 那条路也受影响，
  下一手是实验 B（`ESP_PHY_CALIBRATION_AND_DATA_STORAGE=n`，减少 flash 写次数）。
