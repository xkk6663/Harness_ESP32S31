## 0. 背景与目标

本工程基于 esp-bsp 官方示例 `display_audio_photo`（单文件 `app_disp_fs.c` 1032 行，LVGL 文件浏览 + WAV 播放/录音）进行多轮重构，目标是在此骨架上迭代出"设备 ↔ PC 双通道传声机"：

- **UDP 低延迟通话**：端口 50000/50001，20ms 帧，乱序重排 + 丢包补偿；
- **TCP 整段录音**：端口 50002，WAV 落盘；
- **信令通道**：端口 50003。

音频参数：16 kHz / 16 bit / mono = 32 KB/s，20 ms = 640 B/包。

## 3. 阶段三：FreeRTOS 常驻任务 + 命令队列重构

### 7.4 卡机修复（2026-09-13 当晚）
- **现象**：开屏上拉进入主 UI 时直接卡死（hard fault）；
- **根因**：`ui_disp.c` 里 `lv_obj_get_child_cnt(tab_btns)` 在 `tab_btns = lv_tabview_get_tab_btns(tabview)` 赋值**之前**就执行了，tab_btns 还是 NULL，NULL 解引用直接崩；
- **修复**：把 tab_btns 赋值、样式、事件注册、子对象 EVENT_BUBBLE 遍历按正确顺序重排（先 get_tab_btns，再遍历子对象，再 add_event_cb）；

- 二次烧录验证：上拉进主 UI 正常，下拉壁纸拉出/上拉关闭正常。

### 7.5 ESP32-S31 2D-DMA / PPA 调研结论
纠正此前"ESP32-S31 没有独立 2D DMA"的错误判断：
- ESP32-S31 集成独立 **2D-DMA**（AXI 主机，4 TX + 3 RX 通道，非对齐传输，宏块重排，CSC）；
- **PPA**（Pixel Processing Accelerator）：旋转/缩放/镜像/叠加，ESP-IDF 组件 `esp_ppa`（路径 `components/esp_driver_ppa/include/driver/ppa.h`）；
- **JPEG 硬解**：`esp_video` 组件支持（本工程 idf_component.yml 已含）。

### 7.6 LVGL 内置 PPA draw unit 尝试（结论：S31 暂不可用）
- 在 sdkconfig.defaults 加 `CONFIG_LV_USE_PPA=y` 尝试编译，两个硬错误：
  1. `#error "CONFIG_LV_DRAW_BUF_ALIGN must be equal to CONFIG_CACHE_L2_CACHE_LINE_SIZE"` —— ESP32-S31 没有 L2 cache，此 Kconfig 只在 ESP32-P4 定义；
  2. `fatal error: driver/ppa.h: No such file or directory` —— 即使 main 组件 PRIV_REQUIRES 加 esp_driver_ppa，LVGL 的 PPA draw unit 代码路径依赖 P4 的 L2 cache 假设；
- **结论**：LVGL 9.5 内置 `lv_draw_ppa` 当前仅支持 ESP32-P4（LVGL 官方文档"Supported devices"也只列 P4）。ESP32-S31 硬件有 PPA，但 LVGL 这版尚未适配；
- 已回退 sdkconfig.defaults（PPA 注释掉），恢复软件渲染；
- **后续路径**：
  - 等 LVGL 新版本适配 S31 后开 `CONFIG_LV_USE_PPA`；
  - 或自己写 draw unit 直接调 `esp_driver_ppa` API（工作量大，暂缓）；
  - JPEG 硬解（`esp_video` 的 PJPG）仍可作为开屏加速方向。

### 8.2 ADC 分压按键
- 硬件：R77=10K 上拉到 3V3，4 键共 ADC1_CH0 = **GPIO42**；
- BSP 默认区间（1770/1240/819/380 mV）与实测偏差大，3 个键不触发；
- 实测 mV（IO42）：
  - **set**  ~260 mV
  - **mode** ~759 mV
  - **vol-** ~1237 mV
  - **vol+** ~1647 mV
- 在 `button_service.c` 直接用 `iot_button_new_adc_device` 创建 4 个按键，配实测区间 ±100 mV；
- 与官方 factory_demo 写法对齐：注册 PRESS_DOWN / PRESS_UP / SINGLE_CLICK / DOUBLE_CLICK / PRESS_END 5 个事件。

### 8.3 音量消息队列 + 互斥锁
- `button_service` 内部 `SemaphoreHandle_t` 保护音量值（初始 70，范围 0–90）；
- 单击 vol-/vol+ → ±10；双击 → ±20；
- 音量变化通过 `QueueHandle_t`（深度 4）发 `btn_vol_msg_t`；
- UI 层 `ui_settings.c` 用 `lv_timer`（100 ms）抽队列，更新滑块并下发 `AUDIO_CMD_SET_VOLUME`；
- 滑块拖动时反向同步 `button_service_set_volume()`。

- **根因**：本板 LVGL 是 `CONFIG_BSP_DISPLAY_LVGL_DIRECT_MODE=y` +

- **修复**：
  1. 播放启动时 `lvgl_port_stop()`（`lv_timer_enable(false)` + 停 esp_timer），视频期间真正独占 framebuffer，

  3. `tab_video_destroy()` 里先 `set_event_cb(NULL)` 注销回调、stop/deinit player，再 resume LVGL + 整屏 invalidate。
- **注意**：事件回调跑在 GMF 线程，不能直接调 LVGL 绘制 API，必须 `lvgl_port_lock` 后用 `lv_async_call` 切回 LVGL 线程。

## 19. 蓝牙本地推流（A2DP Source）—— 方案 B2 落地（2026-09-21）

### 19.1 背景：上一版为何失败
上一版 BTPUSH 采用「首次点歌时懒加载」建 GMF pipeline，三条成因叠加踩到 bluedroid 静态内存布局：
1. **建仓太晚**——`ensure_pipeline()` 发生在蓝牙已连接、用户点歌时，此时 LCD 双 framebuffer +
   摄像头 + WiFi + LVGL + bluedroid 已把内部 RAM 切碎，申请不到连续块；
2. **在 BT 事件线程重分配**——`STREAM_STATE_CHG` 回调线程栈小，在里面做毫秒级多块分配易触发 mempool 断言；
3. **静态池 vs 动态堆**——bluedroid 的 BTU/BTC 队列、HCI mempool 是启动时一次性静态分配的，
   其后任何改变堆布局的动作都可能让静态池申请失败。

### 19.2 方案 B2（延迟常驻）—— 四条原则
| 原则 | 落地 |
|---|---|
| **P1 时机前置** | pool + pipeline + task 全部在 `bt_push_service_early_init()` 建，插在 `controller_init()` 之后、`bsp_display_start()` 之前，抢内部 RAM 最空窗口 |
| **P2 显式外置** | GMF task `stack_in_ext=true`（栈进 PSRAM）；uri/ASRC 权重 `heap_caps_malloc(MALLOC_CAP_SPIRAM)` |
| **P3 建一次不毁** | `STOPPED`/`RELEASED` 只 `stop()`+`reset()`，**从不 destroy**；反复播放复用同一 pipeline |
| **P4 销毁异步** | `request_destroy()` 只投递命令；真正销毁走独立上下文，绝不在 BT 事件回调里做 |

**关键设计（对齐官方 `stream_proc.c`）**：所有会阻塞的 pipeline 操作
（`set_in_uri` / `loading_jobs` / `run` / `stop` / `reset` / `pause` / `resume`）
一律投递到命令队列 `s_cmd_queue`，由独立任务 `bt_push_proc` **串行执行**；
BT 事件线程只做「登记 + reconfig」这类非阻塞动作。这解决了上面成因 2。

### 19.3 数据流与文件改动
数据流：`io_file(MP3) → aud_dec(MP3) → aud_asrc(硬件重采样) → aud_enc(SBC) → io_bt`

### 19.4 体积问题与修复（F22）
加完代码后固件 4.71MB → **5.25MB**，超出 ota_0(5MB) **256KB**，`app_check_size` 失败。

**根因**：新代码首次调用 `esp_audio_enc_register_default()`——它是**全家桶注册**，
一旦被引用，链接器就不再 GC 掉未使用的编码器，11 个编码器（AAC/AMR/AMRWB/OPUS/ADPCM/ALAC/LC3/G722/…）

**修复**：`sdkconfig` 关闭 9 个无用编码器，保留 **SBC + PCM**；`register_default` 会自动跳过未启用项，
**源码零改动**。备份 `sdkconfig.bak_before_enc_trim`。预计固件回到 5MB 以内，**无需改分区**。
（`esp_hal_asrc` ~100KB 是推流刚需，不裁。）

```
I ESP_GMF_TASK: One times job is complete, del[... aud_dec_open]
E sdmmc_cmd: allocate_dma_buf: not enough mem, err=0x101    ← ★真凶
E diskio_sdmmc: sdmmc_read_blocks failed (0x101)
E ESP_GMF_FILE: The error is happened in reading data ... I/O error
E BT_PUSH: pipeline error
```

**根因**：与蓝牙无关，是 **SDMMC 驱动的 DMA bounce buffer 分配失败**。
`io_file` 交给驱动的 payload 不对齐 → 驱动现场 `heap_caps_malloc(..., MALLOC_CAP_DMA)`；
`SDMMC_HOST_DEFAULT()` 里 `dma_aligned_buffer = NULL`，每次读盘都要现场申请；
内部 DMA 堆被 bluedroid 静态池 + LCD + WiFi + 音频工作缓冲切碎后，连 512B 都拿不出。
（`allocate_dma_buf` 能打出 "not enough mem" 意味着减到不足一个扇区都没成功。）

**修复**：`sdcard_service.c` 新增 `sdcard_setup_dma_buffer()`，开机预分配 **32KB** 常驻缓冲挂到
`host.dma_aligned_buffer`（优先 `MALLOC_CAP_SPIRAM|MALLOC_CAP_DMA`，本板 `SOC_SDMMC_PSRAM_DMA_CAPABLE=y`
可 PSRAM 直访 DMA，零内部 RAM 占用；失败退回内部 DMA）。这是 IDF 官方 sdmmc 测试的做法。

| 文件 | 改动 |
|---|---|
| `middleware/sdcard_service.c` | 新增常驻 DMA bounce buffer 预分配 |

### 19.7 音量链路：硬件键 + UI 滑块统一归蓝牙管（2026-09-21）
**问题**：耳机正常出声，但按设备端 vol+/vol- 键对耳机音量无效。

**根因**：`button_service.c` 的 `adjust_volume()` 只改本地 `s_volume` 并发消息给 UI 显示，
**从未调用任何蓝牙音量 API**；UI 音量条（`tab_sys_entry.c`）同样只写本地 codec。
两条路都到不了蓝牙。

**架构决策——一个"音量源"，多个"音量出口"**：
```
vol+/vol- 硬件键 ─┐
                  ├─> button_service_set_volume(v) ─┬─> s_volume + UI 条（永远同步）
UI 音量条 ────────┘        （统一入口）              └─> 音量输出回调 ─┬─ 蓝牙已连 → AVRCP
                                                                     └─ 未连     → 本地 codec
```

**改动**：
| 文件 | 改动 |
|---|---|
| `middleware/button_service.h` | 新增 `btn_vol_out_cb_t` 类型 + `button_service_set_vol_out_cb()` |
| `middleware/button_service.c` | `adjust_volume()` / `set_volume()` 统一触发音量输出回调 |
| `middleware/bt_audio_service.c` | 新增 `is_connected()` / `set_volume()` / `set_abs_volume()`；连接时起一次性 `sync_vol_task` 把当前档位同步给耳机 |
| `middleware/bt_audio_service.h` | 对应声明 |
| `app/main.c` | 新增 `on_volume_change()` 分发回调并注册 |
| `ui/tab_sys_entry.c` | 移除重复的本地 codec 命令（改为只写中央状态，出口统一分发） |

**量纲换算**：本地 `s_volume` 0..90 → AVRCP 0..127（四舍五入，两端档位严格对应）。

**关于「绝对 vs 相对」的重要发现**：
`esp_bt_audio` 的 `vol_ops.set_absolute` **只要 AVRCP CT 连上就注册**
（`bt_audio_avrcp_ct.c:587`，条件仅是 `conn_stat.connected`），
即**耳机支不支持 Absolute Volume，协议层返回值都是 ESP_OK，无法感知**。
因此**不做"自动降级"**（那是假象）。默认走绝对音量（A2DP 1.3+ 耳机普遍支持、
两端档位一致），个别老耳机不响应时用 `bt_audio_service_set_abs_volume(false)`
运行时切相对模式。

## 21. 音频链路架构梳理（2026-09-21）

> 产出：`docs/工程规范/12_音频链路架构.md`（新文件）。
> **纯文档工作，零代码改动**。目的是把"以前做的 WiFi 推流"、"现在做的蓝牙推流"
> 以及"SD 卡 MP3 本地播放"三条播放链路的接口理清、把共用底座讲明白、把架构问题摊开。

### 21.1 为什么要做

三条链路是**不同时期、不同思路**做的：WiFi 推流走"裸 PCM 透传 + 自己写协议"，
蓝牙推流走"GMF pipeline + 格式由对端协商"，本地播放走"`esp_player` 高层封装 + 写死 44.1k"。
用户希望判断能否、以及如何做到低耦合高内聚。梳理结论：**差异是本质的，不该强行统一**。

### 21.2 三条播放链路的本质差异（决定"不可统一"）

| 维度 | WiFi 推流（`udp_voice`） | 蓝牙推流（`bt_push_service`） |
|---|---|---|
| 数据来源 | **实时采集**（mic） | **文件重放**（SD 卡 MP3） |
| 数据方向 | **双向** TX + RX | **单向**（只出） |
| 谁定格式 | **我方写死** 16k/16bit/mono | **对端协商**（耳机 A2DP codec info） |
| 处理位置 | 裸 PCM 透传 | 编解码/重采样全在 pipeline 内 |
| 时钟 | 无同步，靠 20ms 节拍 | 框架内部时钟 |
| 生命周期 | 跟随信令开关 | 跟随 A2DP stream 四态 |

### 21.3 共用底座

- **`audio_service` 流式 API**（`audio_stream_start` / `read_mic` / `write_spk`）：
  单条 Core1 常驻任务独占 codec/I2S，网络层只读写 ringbuf ——
  **这是当前分层做得最干净的一块**；
- **`session_manager` 单槽互斥**：`IDLE / UDP_CALL / TCP_RECORD / BT_PUSH`，
  三条业务共用一份仲裁，设计正确。

### 21.4 诊断出的架构问题（原 4 项 + 补链路 C 后新增 2 项）

| # | 问题 | 严重度 |
|---|---|---|
| 1 | `audio_service` 双职责（命令式 + 流式）互斥耦合，**帧长/水位等实现细节泄漏到调用方** | 中 |
| 2 | **格式常量散落五处**（audio_service.h / udp_voice.c / record_service.c / ICD / protocol.py） | **高** |
| 3 | `udp_voice` 职责过重（协议 + 重排 + 送音频 + 编排，288 行） | 中 |
| 4 | **`link_manager` 反向依赖 `udp_voice`**（`bluetooth → audio`，方向倒挂） | 中 |
| 5 | **本地播放链路绕过 `session_manager`** —— 两个 codec 句柄指向同一 ES8389，并发写冲突（补链路 C 时发现，见 §21.8） | **高** |
| 6 | **UI 层直接写 codec + 管 GMF 资源**（`tab_music.c` / `tab_video.c`，补链路 C 时发现） | **高** |

### 21.8 补链路 C：SD 卡 MP3 本地播放（同日再追）

用户追问"SD 卡 MP3 音频本地播放的链路是怎么样的"，补出**第三条播放链路**。

**为什么原来漏了**：前两条链路都在 `middleware/` 里，按目录找很自然；
本地播放**不在 middleware** —— 它的全部实现都在 **UI 层**的 `ui/tabs/tab_music.c`（343 行）。

**链路 C 数据流**：

```
/sdcard/music/*.mp3
   → esp_player（extractor 识别 MP3 + aud_dec 解码）
   → esp_audio_render（GMF pool：ch_cvt / bit_cvt / rate_cvt / alc）
   → audio_out_write() 回调        ← tab_music.c:61，直接持 codec 句柄
   → esp_codec_dev_write(ES8389) → 板载喇叭
```

**关键参数**：目录 `/sdcard/music`、仅 `.mp3`、上限 **16 首**（超出静默丢弃）、
codec **44100/2ch/16bit**（写死）、`process_period` 20ms、初始音量 **60**（硬编码）、
`max_stream_num` 1。

**三条播放链路的本质分歧**：

| 维度 | 蓝牙推流 | SD 本地播放 | WAV 播放页 |
|---|---|---|---|
| 需要编码？ | **要**（SBC，A2DP 要求） | 不要（直接 PCM） | 不要 |
| 需要重采样？ | **要**（`aud_asrc` 硬件 ASRC） | **要**（`rate_cvt` 软件链） | 否（文件即 16k） |
| 框架 | `esp_gmf_pipeline`（手工搭） | `esp_player`+`esp_audio_render`（高层） | 无框架 |
| 代码位置 | ✅ middleware | ⚠ **UI 层** | ✅ UI 层（调 middleware `post_cmd`） |

> **核心差异是"要不要编码"** —— 它决定了蓝牙侧用 `aud_asrc`+`aud_enc`、
> 本地侧用 `rate_cvt`+`ch_cvt`。

**诊断出的 2 项新问题**：

| # | 问题 | 严重度 |
|---|---|---|

## 23. 修复"开蓝牙即崩溃"与"WiFi 连上却不拉天气"（2026-09-21）

> 两个独立故障，一次处理完。分别对应 **F28**（内存护栏缺失）与 **F29**（事件时序）。
> 涉及 5 个源文件。

### 23.1 问题一：点蓝牙开关 → `future_ready` assert 崩溃重启

**现象**：
```
E BT_BTC: btc_config_init unable to create lock.
E BT_OSI: future_new unable to allocate memory for the semaphore.
assert failed: future_ready future.c:64 (future != NULL)
```

**根因**：**内部 RAM 不足，但 host 初始化失败路径没有护栏，直接 assert。**
`esp_bt_audio_init()` 内部要建 BTU/BTC 两个任务栈（各 4~6KB）+ 大量小队列/信号量，
全在内部 RAM，且**一次性、不可重试** —— 任一处失败不返回错误，而是 `assert` → abort → 重启。
时机（开机 73s，UI/WiFi/GMF/LVGL 都在跑）内部 RAM 已被切碎，是 F23 那类"晚分配踩碎布局"的翻版。

**旧代码两处缺陷**：① `set_power()` 无内存门槛，多紧都硬调；② `bt_sw_cb()` 丢弃返回值。

**改动**：

| 文件 | 改动 |
|---|---|
| `middleware/bluetooth/bt_audio_service.c` | 新增 `host_mem_sufficient()`：开 host 前检查内部 RAM **双指标**（`free_size` ≥ 48KB 且 `largest_free_block` ≥ 24KB），不满足则 `return ESP_ERR_NO_MEM` 主动拒绝；体检放在 `esp_bt_audio_init()` **之前**。新增门槛宏 + 诊断口径注释 |
| `middleware/bluetooth/bt_audio_service.h` | `set_power()` 补充返回值契约（`ESP_ERR_NO_MEM` 语义 + 调用方应提示用户） |
| `ui/pages/page_bluetooth.c` | `bt_sw_cb()` 接住返回值；打开失败时**开关弹回 OFF** + 状态栏提示 `Not enough RAM` / `Power on failed`；补 `TAG` |

**行为变化**：内存不足时**不再崩溃**，改为"开关弹回 + 提示"。
`BT_HOST_MIN_*` 为经验值，可按真机实测调。

### 23.2 问题二：WiFi 连接模式下天气/校时任务不启动

**现象**：STA 能连上、屏幕有 IP，但校时与天气**永不刷新**；AP 模式反而正常。

**根因**：`GOT_IP` 事件的派发**早于回调注册**，三条独立成因叠加：

| # | 问题 | 后果 |
|---|---|---|
| 1 | `main.c` 先 `wifi_manager_init()` 后 `set_sys_cb()` | `init()` 内部就 `esp_wifi_start()`+`auto_connect()`；**开机自动连**时 `GOT_IP` 在 `init()` 返回前派发完，`s_sys_cb == NULL` → 通知丢弃 |
| 2 | `page_wifi` 进页面 `set_evt_cb()` 覆盖同一槽位 | 进一次页面就把 app 回调顶掉，后台服务再也收不到通知 |
| 3 | 服务只能由"当时在线的 GOT_IP"拉起 | 启动时已联网 → 既没等到事件也无人补调用 → **永久不启动** |

**改动**：

| 文件 | 改动 |
|---|---|
| `app/main.c` | **注册顺序修正**：`wifi_manager_set_sys_cb(on_wifi_evt)` 提到 `wifi_manager_init()` **之前**（先接线再开机）；`GOT_IP` 响应改用 `net_time_service_notify_network_up()` |
| `middleware/network/net_time_service.c` | **自愈式启动**：新增幂等入口 `notify_network_up()`（任务已建→通知刷新；没建→现在建）；任务改为**先建再等网**（`while (!s_net_up) vTaskDelay(1s)`）；新增 `NET_TIME_WAIT_NET_MS`；**顺手修资源泄漏**（mutex 建成功但 task 建失败时未回滚 `s_lock`） |
| `middleware/network/net_time_service.h` | 新增 `notify_network_up()` 声明 + 两个入口的语义说明 |
| `middleware/network/wifi_manager.c` | `set_evt_cb`/`set_sys_cb` 补语义注释（两槽位必须分开，合成一个就会"进页面顶掉 app 回调"） |
| `middleware/network/wifi_manager.h` | 两槽位语义详解（`sys_cb` = app 级/只注册一次/绝不覆盖；`evt_cb` = 页面级/随进出增删） |
| `ui/pages/page_wifi.c` | 进页面按 `get_ip()` + `get_role() != WIFI_ROLE_AP` **补发一次 GOT_IP**（覆盖"事件早于页面存在"）；`destroy` 里 `set_evt_cb(NULL)` 注销 |

**行为变化**：任务改为"网络一好就开始"，**漏事件/晚事件/重连都能自愈**；
AP 热点仍被正确排除（`get_role()` 判据）。

### 23.5 追问澄清：为什么 host 不能像 controller 一样开机常驻（2026-09-21 追加）

**追问**：既然前面已经用"上电器件预分配"解决了蓝牙初始化，为什么开 host 还会崩？
为什么不把 host 也一并常驻，按钮只做开关？

**结论：controller 已经常驻了（这一步做对了），但 host 在架构上无法常驻。**

读源码确认（`managed_components/espressif__esp_bt_audio/` + `esp-idf/components/bt/`）：

| 层 | 能否开机常驻 | 依据 |
|---|---|---|
| **controller / HCI 内存池** | ✅ **已常驻**（`bt_audio_service_controller_init()`，开机空窗期） | 真正的一次性分配，必须在最空窗口拿 |
| **bluedroid host（BTU/BTC）** | ❌ **不能** | `esp_bt_audio_deinit()` → `bt_audio_host_bluedroid_stack_deinit()` → `esp_bluedroid_disable()`+`esp_bluedroid_deinit()` → `btc_deinit()` → `btc_deinit_bluetooth()`：里面 `vSemaphoreDelete(s_init_done_sem)`、`bte_main_shutdown()`、`osa_alarm_deinit()` —— **真的全部释放** |
| **BTA / A2DP / AVRC（host_config）** | ❌ **不能** | 属 host 层，必须在 controller 之后初始化，无法提到开机预初始化 |

所以：
- `s_on=false` 时的 OFF 是**真 deinit**，下一次 ON 就是**真正的重新 init** ——
  照样会重新分配 BTU/BTC 任务与队列，照样可能内存不足而崩。
- **"开关"是伪开关**：底层并没有保留任何 host 资源，只是让 UI 以为可以随时开关。
- → 闸门必须**每次打开都走**，不能只在开机检查一次。（这也是为什么只做"开之前"检查是对的。）

**可选真正解法**（若希望"开关"名副其实，需另外决策，本次未做）：
1. **真常驻**：改成开机把 host 一次性起好、永不关闭，UI 开关只切"可见/可连接"的软件状态
   （`esp_bt_gap_set_scan_mode` 之类）。代价：内部 RAM 长期被 host 占用，且 UI 开关变成软开关，
   语义要重新设计；**与方案 B 的"GMF 建一次不毁"思路一致**，值得作为后续方向；
2. **保底**：保留现在的闸门（最小改动，本次已做），内存不足时拒绝并提示。

**文档口径修正**：§23.1 与 F28 中"`esp_bt_audio_init()` 内部要建 BTU/BTC 两个任务栈
（各 4~6KB）"这句 —— **"各 4~6KB"是估算，未从源码核实**，不应表述为事实；
代码注释已改为不带具体数字的准确描述。

## 24. 挖出内部 RAM 真凶：750KB JPEG 缓冲落在内部 RAM（2026-09-21）

> 承接 §23。护栏生效后拿到真实数字，顺藤摸到根因。对应 **F30**。

### 24.1 实测日志

```
E (45740) BT_SVC: internal RAM too low for BT host: free=25987 (need 49152)
                  largest=23552 (need 24576) -- refuse to power on
W (45747) PAGE_BT: BT power on failed: ESP_ERR_NO_MEM
```
护栏正确拦截（**没崩**），并且给出了诊断所需的两个数字。

### 24.2 追问：为什么"加音量功能前"能跑通？

**结论：与音量功能无关。音量功能只是把问题暴露出来；真正的触发因素是 F29 修好后
WiFi 才真正工作、天气任务才真正起来，从而改变了内存基线。**

逐个排除嫌疑：

| 嫌疑 | 结论 | 依据 |
|---|---|---|
| `on_volume_change()` / `bt_audio_service_set_volume()` | **无关** | 只在用户按键时执行，**不分配任何内存** |
| `bt_push_service_early_init()`（GMF pool/pipeline/task） | **无关** | `stack_in_ext=true` + uri/weight 均 `MALLOC_CAP_SPIRAM`；且执行在 controller init **之前** |

### 24.3 真凶：`fs_service_init()` 的 750KB 缓冲

```c
/* fs_service.c 原实现 */
file_buffer_size = BSP_LCD_H_RES * BSP_LCD_V_RES * sizeof(lv_color_t); /* 800*480*2 = 768000 ≈ 750KB */
file_buffer = jpeg_calloc_align(file_buffer_size, 16);
```

**`jpeg_calloc_align()` 内部是 `heap_caps_calloc_prefer()`** —— 语义为
**"优先内部 RAM，不够才退 PSRAM"**。已从静态库符号表核实：
`lib/esp32s31/libesp_new_jpeg.a` 中 `jpeg_calloc_align_inner` → `heap_caps_calloc_prefer`。

而 `fs_service_init()` 原调用位置在 `bsp_display_start()` **之后**，
此时内部 RAM 尚有约 750KB 连续空间 → **这 750KB 被吃在内部 RAM**。

### 24.4 因果链（完整）

```
F29 修复（WiFi 事件注册顺序）
  → 天气/校时任务真正启动 → HTTP + cJSON 占用内部 RAM
  + fs_service_init() 的 750KB 缓冲落在内部 RAM
  → 用户点蓝牙 → internal free 仅剩 25KB
  → bluedroid host 分配失败 → assert 崩溃（F28）
```

### 24.5 改动（双保险）

| 文件 | 改动 |
|---|---|
| `middleware/system/fs_service.c` | ① 改用 `heap_caps_aligned_calloc(16, 1, size, MALLOC_CAP_SPIRAM \| MALLOC_CAP_8BIT)` 显式优先 PSRAM，失败才退回 `jpeg_calloc_align()` 并打警告；② 新增 `esp_heap_caps.h`；③ 补分配结果日志（含字节数与地址） |
| `app/main.c` | `fs_service_init()` 前移到 `bsp_display_start()` **之前**，与 controller/GMF 同一个空窗窗口；补一段"大块只分一次活到关机 → 必须在此段拿完"的时序纪律注释 |

**16 字节对齐**：JPEG 解码硬要求，由 `heap_caps_aligned_calloc` 原生支持（第一个参数）。

| 文件 | 改动 |

### 24.7 预期结果与调参

修 F30 前后内部 RAM 的变化（**预期**，待实测确认）：

## 25. 开屏上拉"划两次"修复 + 天气 Key 丢失定位（F31 / F32）

### 25.1 问题一：开屏壁纸上拉要划两次 ★LVGL 命中测试

**现象**：splash 页上滑，第一次无反应，第二次才进主界面。

"第二次才过"的原因：第一次划动没记录起点（`s_press_start_y` 未更新），

3. 按 mtime 排序 `build/log/idf_py_stdout_output_*`，提取每次 configure 的

## 26. 修 `build.ps1` 误报 "RECONFIGURE FAILED"（F33）

### 26.1 现象

按 §25 结论跑 `tools/build.ps1`，CMake **配置实际成功**：

```
-- QWEATHER_KEY: injected from environment (len=32, value hidden)
-- QWEATHER_API_HOST: injected -> ke67cgkc3a.re.qweatherapi.com
-- Configuring done (57.4s)
-- Generating done (3.8s)
-- Build files have been written to: .../build
```

脚本却打印：

```
RECONFIGURE FAILED (exit CMake Deprecation Warning at CMakeLists.txt:5
(cmake_minimum_required): Compatibility with CMake < 3.10 will be removed
... System.Management.Automation.RemoteException ...  0)
```

**`exit` 后面跟的不是数字，是一大段 CMake 警告文本。**

### 26.2 根因：`$c1` 是 `Object[]` 而不是 `Int32`

`Invoke-Build` 内部：

```powershell
& idf.py @Args 2>&1        # 2>&1 把 cmake 的 stderr 转成「错误记录对象」
$rc = $LASTEXITCODE
return $rc                 # 函数输出流 = [错误记录对象们..., 整数0]
```

`2>&1` 会把原生命令的 stderr **转成
`System.Management.Automation.ErrorRecord` 混进 PowerShell 输出流**
（报错里那串 `RemoteException` 即其 `ToString()`）。
`return $rc` 只保证**最后一个元素**是整数，整个流却是"一堆对象 + 一个整数"，
调用方 `$c1 = Invoke-Build reconfigure` 拿到的是**数组**。

于是 `if ($c1 -ne 0)` 变成"数组与 0 比较"——
**PowerShell 的比较运算符作用于数组时是过滤语义**，
返回"不等于 0 的元素集合"，非空即真 →
**配置成功也判 FAILED，且打印时把整个数组拼出来**。

### 26.3 实测复现

同一环境下 OLD / NEW 两种写法并排：

```
OLD: type=Object[]  value=[cmake warning 0]  is-array=True
OLD: $old -ne 0  =>  cmake warning    <-- 非空即真 = 误报
NEW: type=Int32     value=[0]                 is-array=False
NEW: $new -ne 0  =>  False            <-- 正确放行
```

### 26.4 改动

| 文件 | 改动 |
|---|---|
| `tools/idf_common.ps1` | `Invoke-Build` 内 `& idf.py @Args 2>&1` → **`& idf.py @Args 2>&1 \| Out-Host`**：stderr 内容只打到控制台（用户照旧看到全部警告），**不再留在函数输出流**；并 `return [int]$rc` 强制类型。补注释说明为何不能改回原写法 |
| `tools/build.ps1` | 三处调用点全加 `[int]` 强转：`[int](Invoke-Build fullclean)` / `[int](Invoke-Build reconfigure)` / `[int](Invoke-Build build)`。万一将来再被污染，会是明确的类型错误而非静默误判 |
| `tools/flash.ps1` | 原来直接用裸 `idf.py build` / `idf.py -p $Port app-flash` + `$LASTEXITCODE`（正踩 F21：stderr 被判 NativeCommandError）。已改为走 `Invoke-Build`，`-BuildFirst` 时先 `reconfigure` 再 `build`，返回值同样 `[int]` 强转 |

### 26.5 验证结果（端到端实跑）

三脚本 `Parser::ParseFile` 无语法错误。实跑 `tools/build.ps1 -NoReconfigure`：

```
=== BUILD OK ===
[build] artifact: ...\build\display_audio_photo.bin (4.76 MB)
[build] verifying injected symbols in firmware...

  [OK] QWEATHER_API_HOST=ke67cgkc3a.re.qweatherapi.com present
EXITCODE=0
```

并且 `build/compile_commands.json` 中 `net_time_service.c` 的编译命令已含：

```
-DQWEATHER_API_HOST=\"ke67cgkc3a.re.qweatherapi.com\"
-DQWEATHER_KEY=\"a7928653a66a4b82ad2fe36a7a835bf4\"
```

**F32 的问题（Key 丢失）与 F33 的问题（误报）至此都已闭环。**

## 27. 上电内部 RAM 账单 + `jpeg out buffer` 尺寸勘误（2026-09-21）

### 27.1 背景

用户贴出上电初始化日志（`docs/_log_212621.txt`），指出"这内存占用太夸张了吧"，
要求先分析上电后内部 SRAM 的占用情况。

### 27.2 实测账单

日志点由各模块自己打印，相邻两行之间即为一次净消耗：

| 时刻(ms) | 事件 | internal free | largest | Δ free |
|---|---|---|---|---|
| 1572 | `SDCARD` DMA bounce buffer 32KB | **241659** | — | 起点 |
| 1638 | `BT_SVC` early controller init | **241131** | 155648 | −528 |
| 1806 | `BT_PUSH` early init | **198935** | **131072** | **−42196** ⚠ |
| 1813 | `BT_PUSH` ready (resident) | **197687** | — | −1248 |

### 27.3 发现一：`BT_PUSH` 的 42KB 是第三方组件内部预分配

`bt_push_service_early_init()` 本项目自己显式分配的部分**全部在 PSRAM**：
`s_uri`(256B, SPIRAM) / `s_asrc_weight`(64B, SPIRAM) / GMF task 栈(`stack_in_ext`) /
`proc_task`(`SPIRAM|8BIT`) / 命令队列(8 项，内部小对象) —— 合计仅数 KB。

剩余 42KB 来自 **`esp_gmf_pool_init` + 三个元素（`aud_dec`/`aud_asrc`/`aud_enc`）
+ `io_file`/`io_bt` 的内部工作缓冲**，属第三方组件内部预分配，
**不受本项目 `heap_caps_*` 控制**。其中 `aud_asrc`（硬件重采样）是最大头。

→ 代码层无法"改小"，只能靠 **P1 时机前置**（方案 B 四原则之一）抢最空窗口。
若将来还要压，方向是**给 `aud_asrc` 减配，或让 A2DP Source 不走 asrc**
（需评估音质与设备兼容性），而不是改 caps。

### 27.4 发现二：`largest` 掉 24KB 而 `free` 掉 41KB

`largest` 从 155648 → 131072（**恰好 −24×1024**），说明吃掉的是
**一整段连续区间**，而非一堆碎片。且全程 **`largest` ≥ 128KB**。

**★ 由此修正对天气 TLS 失败的判断**：16KB 级的
`CONFIG_MBEDTLS_SSL_IN_CONTENT_LEN` 在"上电完成后"是拿得到的 ——
**问题不在上电阶段，而在 WiFi 起来之后**（LWIP 缓冲再切一刀的时点）。
要在正确时点取证：在 `esp_http_client_perform()` 前打一次
**(申请量 / free / largest) 三元组**（规范 §3.3 A4 已要求），
而不是在上电日志里找原因。

### 27.5 发现三：`jpeg out buffer` 尺寸勘误（750KB → 1.10MB）

| 项 | 原认知 | 核实后 |
|---|---|---|
| 表达式 | `800*480*2` | `800*480*sizeof(lv_color_t)` |
| `sizeof(lv_color_t)` | 2（按 RGB565 假定） | **3**（`CONFIG_LV_COLOR_DEPTH=24`） |
| 结果 | 768000 ≈ 750KB | **1152000 ≈ 1.10MB** |
| 落点 | 内部 RAM（F30 之前） | **PSRAM** `0x5000d8c0` ✅ F30 修正生效 |

`0x5000_d8c0` 落在 PSRAM 地址空间，**证明 F30 的显式 caps 修正确实生效**。
但**尺寸比原估算大 50%** —— 原因是 `CONFIG_LV_COLOR_DEPTH=24` 使
`sizeof(lv_color_t) == 3`，而早期注释按 16 位写了 `*2`。
做内存账、评估 PSRAM 余量时**必须按 1.10MB 算**。

## 28. 内部 RAM 非对称消耗定位：TLS 与蓝牙同时失败（F34 / F35，2026-09-21）

### 28.1 触发

用户贴出新截图：运行到 **811234ms**（≈13.5 分钟）切到 SYS tab 开蓝牙时：

```
E BT_SVC : internal RAM too low for BT host: free=7787 (need 49152)
           largest=7168 (need 24576) -- refuse to power on   （连拦 3 次）
E esp-tls-mbedtls: mbedtls_ssl_setup returned -0x008D
E NET_TIME: 7d failed
```

用户质疑："**但是这次启动 tls 启动不了，蓝牙也不够内存启动，内存现状其实不紧张？到底哪里的问题?**"

### 28.2 ★ 先承认上一轮结论错了

§27 的结论"内存现状其实不紧张（193KB free）"**是错的**，错在**时点**：

```
上电日志覆盖 : 1500ms ~ 5300ms   （app_main 在 5287ms 返回）
故障时刻     : 811234ms          （两个数量级之后）
```

用"开机 2 秒的快照"解释"运行 13 分钟后的故障"，**证据根本不在搜索边界内**。

→ **★ 任何"内存很宽裕"的结论都必须带时点。**

### 28.3 125 倍时点的实测对比

| 时刻 | 场景 | internal free | largest |
|---|---|---|---|
| 1813ms | 开机 `BT_PUSH ready` | **197687** (193KB) | — |
| 811234ms | 点蓝牙开关（切到 SYS tab 后） | **7787** (7.6KB) | **7168** (7KB) |

**差值 185KB 全在 `app_main()` 返回后的运行期被吃掉。**

### 28.4 两个功能的失败是同一根因

TLS 的 `-0x008D` = `PSA_ERROR_INSUFFICIENT_MEMORY`，
蓝牙是 `host_mem_sufficient()` 主动拒绝 —— **都是内部 RAM 见底**。

**★ 判据："功能 A 和 B 同时因内存失败" = 同一个根因**，
不要去分别调 A、B 的代码，去找**共同吃内部 RAM 的那一块**。

### 28.5 三个判定域（只看 INTERNAL 分不出来）

| 域 | 说明 | 本期实测 |
|---|---|---|
| `MALLOC_CAP_INTERNAL` | `2F046700`+ (210KB) + `2F07AFB0`+ (16KB) | **7.6KB** 告急 |
| `MALLOC_CAP_DMA` | 内部，受 `SPIRAM_MALLOC_RESERVE_INTERNAL=32768` 保底 32KB | 待测 |
| `MALLOC_CAP_SPIRAM` | `0x50000000`+ (16MB) | 待测 |

**两个易漏的账（不是内存被偷）**：
1. **RTCRAM 31KB 不计入 `MALLOC_CAP_INTERNAL`**；
2. **开机保留的 32KB 内部 DMA 池不在 `free` 里**
   （`esp_psram: Reserving pool of 32K of internal memory for DMA/internal allocations`）。

→ 所以"物理 210+16KB"与"free 193KB"本来差 30+KB，**属正常**。

### 28.6 最可疑的单一嫌疑：`CONFIG_ESP_TLS_USE_DS_PERIPHERAL=y`

DS 外设路径需把密钥、哈希中间态、RSA/ECC 上下文放进**内部可访问**内存，
且是 **per-operation 分配**（`esp_ds_context` 每次握手都建）。

**这解释了"错误码会飘"**：`-0x0080`(=`BAD_INPUT_DATA`) 与
`-0x008D`(=`INSUFFICIENT_MEMORY`) 交替出现 → 中间分配**碰运气**。

> **★ 通用判据：错误码飘 = 资源竞争；错误码稳定 = 逻辑写错。**

### 28.7 同时并行排查的两条线

| 线 | 判据 |
|---|---|
| **内部 RAM 专项被吃** | PSRAM 尚余十几 MB，只有内部告急 |
| **内存泄漏** | 同一场景反复进出（切 tab 十几次），内部 free **单调下降** |

| 5 | `BT_PUSH` 早建挪回懒加载（**不推荐**） | 回收 42KB | **会重现推流崩溃**（F23） |

### 28.10 对 `BT_PUSH` 那 42KB 的定性（F34）

**保留，不动。** 它是"用长期内部 RAM 占用换短期确定性"的**有意设计**，
收益是"推流不再因碎片崩溃"（F23 / §19.5）。

- `largest` 155648 → 131072，**一步跳掉 24KB** —— 拿走的是**一整段连续区**；
- 本项目自己的分配（`uri`/`weight`/两个任务栈）**全在 PSRAM**；
- 42KB 是**第三方组件的内部工作缓冲**（GMF pool / dec / asrc / enc / io），
  **caps 管不到**，只能靠**换配置项**或**换时机**。

> **★ "某模块吃了 N KB"要区分"我显式申请的"与"组件内部预分配的"** ——
> 前者受 caps 控制可优化，后者只能换配置或换时机。

### 28.15 ★★ 用户三问落地：重连降为 3 + 拆解 99.1KB 盲区（同日）

用户提出三点：① 重连次数改成 3；② 追问"为什么每重连一次都减一点，能不能初始化好、
重连不减少"；③ 在 RGB panel 与各服务 init 前后补埋点，把 99.1 KB 拆开。

#### ① 重连次数 5 → 3（`WIFI_MAX_RETRY`）

**改动**：`wifi_manager.h` 的 `WIFI_MAX_RETRY` 由 5 改为 3，
并**明确语义为"总尝试次数（含首次连接）"**（旧注释写"重试次数"，含混）。

**依据**（实测）：
```
t=2363 (exit init, 内部 42551)  ->  t=6778 (2 次尝试后, 内部 20819)
  掉 21732 B  => 单次尝试约 10 KB，且不归还
旧行为 5 次尝试 ≈ 50 KB 内部
新行为 3 次尝试 ≈ 30 KB 内部   -> 省约 20 KB
```
省下的 20 KB 对 `largest` 尤其关键 —— 本次实测 `largest` 从 31744 掉到 15360，
而 **mbedTLS 需要约 20 KB 连续块**，这正是 `-0x008D` 的直接成因。

**对"能不能连上"无影响**：能连上的场景通常第 1 次就成；重试覆盖的是
AP 刚重启 / 信道切换 / 信号瞬断这类短暂窗口，3 次足够。

**顺带修正的两处表述问题**（属"改数字要连带改文案"）：
- `retry "%s" (%d/%d)` → `retry "%s" (attempt %d/%d)`：明确这是**第几次尝试**，
  而非"第几次重试"。旧写法在 `WIFI_MAX_RETRY=5` 时打印到 `(5/5)`，
  读起来像"重试 5 次"，实际是"共尝试 5 次"（1 次首发 + 4 次重试）；
- `"all saved Wi-Fi failed"` / `"5 次失败自动关"` 等多处过时文案同步改为
  "达到尝试上限" / `WIFI_MAX_RETRY` 宏引用（**避免硬编码 5 在注释里腐烂**）。

#### ② 回答"为什么每次重连都减一点，不能初始化好、重连不减少吗"

**先给结论**：**重连本身就是"不重新初始化"的做法** —— 恰恰是你期望的那个方向。
问题不在"有没有重复初始化"，而在 **WiFi 驱动在失败路径上不归还全部分配**。

代码事实（`wifi_manager.c`）：

| 函数 | 做了什么 | 关键 |
|---|---|---|
| `apply_candidate()` L237 | `esp_wifi_set_config()` + `esp_wifi_connect()` | **只有切换候选 AP / 运行中掉线才走这里** |
| `reconnect_timer_cb()` L272 | `s_retry_num++` + **仅** `esp_wifi_connect()` | **不含 set_config，不重复初始化** |

所以**现存设计已经是"初始化一次、重试只重连"**。那 10 KB/次 来自：

1. **`esp_wifi_connect()` 每次都会重跑一遍 auth/assoc 流程**，
   `wpa_supplicant` 侧要重建 EAPOL / 握手状态机 / PMK 缓存（走内部 RAM）；
2. **失败路径（`reason=2` 认证失败）不是正常断开**，
   驱动的清理路径**不保证把本次尝试申请的临时缓冲全部归还**；
3. 每次尝试还会**新申请 beacon/probe 相关缓冲**，其释放时机滞后于下一次尝试。

**★ 这是 ESP-IDF WiFi 驱动的内部行为，不在应用层可控范围。**
应用层能做的只有两件事：**减少尝试次数**（本次已做 5→3）、
**避免无谓的失败尝试**（如密码错时不必试满 5 次 —— 见下方待办）。

> ★ **一般化经验**：**"重试"不是免费的**。任何"失败就重来"的设计，
> 都要先量一次"重来一次的代价" —— 若代价是**不可归还的资源**（内存/句柄/连接数），
> 那么重试次数就是一个**必须显式设定的资源预算**，而不是随手填的常数。

### 28.17 ★★★ 第三刀：`bsp_display_start` 的 72 KB 查明 —— 是 bounce buffer，不是帧缓冲，也不是 LVGL

**用户提问**："这个 RGB panel 帧缓冲是干啥的？是我的壁纸帧搬运吗？还是 lvgl 渲染有关的？"

**答**：**都不是。** 真正吃内部 RAM 的是**第三块你没提到的东西 —— bounce buffer（弹跳缓冲）**。
而"帧缓冲"和"LVGL 渲染缓冲"这两块反而**一个在 PSRAM、一个根本不存在**。

#### ① 先把三块"看起来都像帧缓冲"的东西分清

| # | 名字 | 归谁 | 大小 | 落点（源码实证） |

| 1 | **RGB 帧缓冲** `fbs[]` × 2 | **RGB 驱动**（硬件扫描用） | 750 KB × 2 = **1500 KB** | **PSRAM**（`fb_in_psram=1` → `MALLOC_CAP_SPIRAM\|DMA\|8BIT`） |
| 2 | **bounce buffer** × 2 | **RGB 驱动**（DMA 逐行搬运用） | 31.25 KB × 2 = **62.5 KB** | **内部**（`MALLOC_CAP_INTERNAL\|DMA\|8BIT`）★ |
| 3 | **LVGL 绘制缓冲** buf1/buf2 | LVGL（渲染目标） | **0 B —— 没分配** | 不适用 |

#### ③ 账目配平


#### ④ 反直觉点：`avoid_tearing=1` 实际上是**省内存**的配置

若有人为了"优化"把它关掉、改用 `direct_mode`：

```
  → buffer_size 必须 = hres × vres = 384000 px（direct_mode 强制整屏）
  → buf1 + buf2 = 768000 × 2 = 1500 KB
  → 而 buff_dma=true → buff_caps = MALLOC_CAP_DMA → 【硬性内部】
```
**即：会凭空从内部 DMA 池里再拿 1500 KB —— 比现在多花 20 倍。** 这是必须避免的改动方向。

> 同时是内存开关，且方向不直观 —— 改之前必须读实现，不能按名字推。**

**→ 再次印证：`largest` 的变化不能单独解读，必须结合"这一步在分配什么"。**
（同 §28.16 的记录：不要因为 `largest` 变大就以为分配器变好了。）

| `enter start_with_config` / `after lvgl_port_init` | LVGL port 初始化（任务/信号量） |
| `after  lcd_init total` / `after  touch_init` | 触摸驱动 |

**注**：这里额外打印了 `DMA largest` —— 因为 bounce buffer 是"要求连续 DMA 块"的分配，
只看 `DMA free` 看不出"够不够放下一块 32 KB"，**必须看 `DMA largest`**。

> ⚠ 这是唯一一处**在 `managed_components/` 里改的代码**（属第三方组件）。
> 已用醒目注释标注"定位完请整段删除"，且不与组件版本升级冲突（升级后需重新插入）。

#### ⑦ 可回收量（bounce buffer 降配）

约束：`fb_size % bb_size == 0`（IDF 硬校验，L369）。
`fb_size = 768000 B` 已固定，故 `HEIGHT` 必须是能整除它的值：

| `..._BOUNCE_BUFFER_HEIGHT` | 单块 | ×2 合计 | **可省** | `fb/bb` | 合法性 |
|---|---|---|---|---|---|
| **20（当前）** | 31.25 KB | **62.50 KB** | — | 24 | ✅ |
| 16 | 25.00 KB | 50.00 KB | **12.5 KB** | 30 | ✅ |
| 10 | 15.62 KB | 31.25 KB | **31.25 KB** | 48 | ✅ |
| 8 | 12.50 KB | 25.00 KB | **37.5 KB** | 60 | ✅ |
| 5 | 7.81 KB | 15.62 KB | **46.9 KB** | 96 | ✅ |

**权衡**：bounce buffer 越小 → 每行搬运的 DMA 中断越频繁 → CPU 占用升高。
`HEIGHT=20` 是 BSP 默认的保守值。**建议先试 `HEIGHT=10`（省 31.25 KB）**，
观察 UI 流畅度与 CPU 占用；若无可感劣化，再考虑降到 8。

> **★ 这是当前唯一"既有明确收益、又能通过配置改动拿到"的一块。**
> 其余（BT controller 42 KB、WiFi 44.5 KB）都是"挪不动"，bounce buffer 属于
> **"可以缩，但要付 CPU 代价"** 的第三类 —— 比"挪不动"好，比"能挪没挪"差。

## 28.18 ★★★ F36：蓝牙音量调节失败 —— 上游 SRC 路径漏调 `BTA_AvOpenRc()`（2026-09-21 结案）

### 一、现象

A2DP 推流完全正常，但按键调音量**必失败**（反复 6 次，档位 60/50/40/30 全败）：

```
I (30560) BTN_SVC: volume -> 60
E (30560) BT_AUD_OPS: Operation failed: vol_ops.set_absolute is not registered
W (30562) BT_SVC: set abs vol failed: ESP_ERR_INVALID_STATE
W (30567) main: bt vol set failed (ESP_ERR_INVALID_STATE), fallback to local codec
```

「音频推流成功，但音量调节失败」—— 两个 profile 一个活一个死，说明问题不在 A2DP，
而在 **AVRCP**。

### 二、根因 1（主因）：AVRCP CT 连接从未建立

`vol_ops.set_absolute` 只在 `ESP_AVRC_CT_CONNECTION_STATE_EVT` 且 `connected=true`
时注册（`bt_audio_avrcp_ct.c:567-601`）。该事件源头链路：

```
BTA_AvOpenRc(handle)                    [bta_av_api.c:571]
  → BTA_AV_API_RC_OPEN_EVT
  → bta_av_rc_opened()                  [bta_av_act.c:465]
  → (*p_cback)(BTA_AV_RC_OPEN_EVT)      [bta_av_act.c:551]
  → btc_rc_handler → handle_rc_connect  [btc_avrc.c:1085 / 472]
  → btc_avrc_ct_cb_to_app(CONNECTION_STATE_EVT, connected=true)   [btc_avrc.c:508-514]
  → vol_ops.set_absolute = avrcp_ct_set_absolute_volume           [bt_audio_avrcp_ct.c:587]
```

**断在第一步**。`BTA_AvOpenRc()` 在整份 IDF 里**只有一个调用点**：

```c
/* btc_av.c:531-600  BTA_AV_OPEN_EVT 处理 */
if (btc_av_cb.peer_sep == AVDT_TSEP_SRC) {
    if (g_av_with_rc) { BTA_AvOpenRc(btc_av_cb.bta_handle); }   /* L561 唯一调用点 */
    else { ... }
} else if (btc_av_cb.peer_sep == AVDT_TSEP_SNK) {
    /* For A2DP source, report sink codec capabilities ... */   /* L565 本工程走这里 */
    /* ← 这一支里没有 BTA_AvOpenRc() */
}
```

本工程角色是 **A2DP SRC**，连接建立后 `peer_sep == AVDT_TSEP_SNK`（对端是 sink），
于是走 L565 分支 —— **那一支里没有 `BTA_AvOpenRc()`**。
结果：AVRCP CT 连接从未建立 → `vol_ops` 从未注册 → 绝对/相对音量全废。

#### 旁证：源码内部自相矛盾，证明是缺陷不是设计

| 位置 | 场景 | 判断条件 |
|---|---|---|
| `btc_av.c:861` | src 断开（opened 态） | `peer_sep == AVDT_TSEP_SRC` 才 `CloseRc` |
| `btc_av.c:1050` | src 断开（started 态） | `peer_sep == AVDT_TSEP_SRC` 才 `CloseRc` |
| **`btc_av.c:2079`** | **src deinit** | **`peer_sep == AVDT_TSEP_SNK`** 才 `CloseRc` ← **相反** |
| `btc_av.c:2042` | sink deinit | `peer_sep == AVDT_TSEP_SRC` |

同一份代码里 4 处 `CloseRc` 对 `peer_sep` 的判断，3 处写 SRC、1 处写 SNK。
若 SRC 场景本该是 SNK，那前两处就是错的；反之 L2079 是错的。**必有一处是 bug。**

更强的一条：设计里其实有正确的开关 —— `bta_av_aact.c:3010` 的 `bta_av_open_rc()`：

```c
if (p_scb->use_rc == TRUE || (p_scb->role & BTA_AV_ROLE_AD_ACP)) {
    ...
    bta_av_rc_disc((UINT8)(p_scb->hdi + 1));   /* 用主 SM 做 AVRC SDP */
}
```

它检查的 `p_scb->use_rc` 才是意图中的判据（由 `BTA_AvOpen(..., use_rc=TRUE, ...)` 传入，
`btc_av.c:392-406` 传的正是 `TRUE`）。但 **`bta_av_open_rc()` 全 IDF 无任何调用点**
（只有定义 `bta_av_aact.c:2984` 和声明 `bta_av_int.h:786`）—— 是个**死函数**。
`bta_av_rc_disc()` 仅在 `bta_av_rc_conn_chg`（**对端主动连过来**）分支被调（`bta_av_act.c:549`）。

**结论：A2DP SRC 主动发起场景下，整条 AVRCP 建连链路没有入口。这是上游真实缺陷。**

### 三、根因 2（潜伏 bug）：`local_vol_to_avrcp()` 量纲错误（双重映射）

`bt_audio_avrcp_ct.c:136` 的库内转换**期望入参 0..100**：

```c
static inline uint8_t vol_to_avrc(uint8_t app_vol) { return (uint8_t)((app_vol * 127) / 100); }
```

而旧版 `bt_audio_service.c` 已经把它映射成了 0..127 再传进去 → **库再乘一次 127/100 → 溢出**：

| 本地档位 | 旧代码传出 | 库再映射 | 实际音量条 | 正确值 |
|---|---|---|---|---|
| 0 | 0 | 0 | 0.0% | 0 ✓ |
| 30 | 42 | 53 | 41.7% | 33 ✗ |
| 60 | 85 | 107 | 84.3% | 67 ✗ |
| 90 | 127 | **161** | **126.8%（截断顶满）** | 100 ✗ |

修法与验证见下文 ④。

### 四、修复实施

#### ① 拿 BTA handle（原计划的唯一障碍，已解决）

需要 `tBTA_AV_HNDL` 才能调 `BTA_AvOpenRc()`。而 `btc_av_cb` 在本工程是**文件级 static**
（因 `sdkconfig:1801` 的 `# CONFIG_BT_BLE_DYNAMIC_ENV_MEMORY is not set` →
`UC_BT_BLE_DYNAMIC_ENV_MEMORY == FALSE` → `A2D_DYNAMIC_MEMORY == FALSE` →
`btc_av.c:123-128` 走 `static btc_av_cb_t btc_av_cb = {0};`），**外部无法直接访问**。

**但 IDF 里有现成的公开 getter**：

```c
/* btc_av.c:2275  声明在 btc_av.h:313，非 static */
uint16_t btc_a2d_conn_handle_get(void) { return btc_av_cb.bta_handle; }
```

**两个必需符号均已在固件中（`build/display_audio_photo.map` 实证）：**

| 符号 | `.text` 地址 | 来源 |
|---|---|---|
| `btc_a2d_conn_handle_get` | `0x400d19ae` | `libbt.a(btc_av.c.obj)` |
| `BTA_AvOpenRc` | `0x400f49c4` | `libbt.a(bta_av_api.c.obj)` |
| `BTA_AvCloseRc` | `0x400f49f4` | `libbt.a(bta_av_api.c.obj)` |

`btc_a2d_conn_handle_get()` 返回的就是 `btc_av_cb.bta_handle` ——
**与 `btc_av.c:561` 用的是同一个值**，即 `BTA_AvRegister(BTA_AV_CHNL_AUDIO)` 分配出的 hndl。
推算公式 `bta_av_main.c:368`：`hndl = (xx + 1) | chnl`，本工程单音频通道 `xx=0`、
`BTA_AV_CHNL_AUDIO=0x40` → **`hndl = 0x41`**（与 debug 打印一致）。

#### ② 为什么用 `extern` 而不是 include

两个函数在 `libbt.a` 里是全局符号。直接 `extern` 声明可避免把
`btc/profile/std/include` 这类 IDF 私有目录加进组件的 `INCLUDE_DIRS`，
也就不会在上游 minor 升级时因头文件路径变动而编译失败：

```c
extern uint16_t btc_a2d_conn_handle_get(void);
extern void     BTA_AvOpenRc(uint16_t handle);
```

#### ③ 为什么必须走 `BTA_AvOpenRc` 旁路，不能再调一次 `esp_a2d_source_connect()`

`btc_profile_queue.c:43` 的连接队列**按 uuid 去重**：

```c
if (node->uuid == p_param->uuid) { return; }   /* 同 uuid 静默丢弃 */
```

再走一遍 `btc_queue_connect(UUID_SERVCLASS_AUDIO_SOURCE, ...)` 会被**静默丢弃**。
`BTA_AvOpenRc()` 直接投 `bta_sys_sendmsg()`，**不经队列**，是唯一可行入口。

#### ④ 代码改动（`main/middleware/bluetooth/bt_audio_service.c`）

**新增 `avrcp_ensure_ct_link()`**：

```c
extern uint16_t btc_a2d_conn_handle_get(void);
extern void     BTA_AvOpenRc(uint16_t handle);

static bool s_avrcp_link_requested = false;

static void avrcp_ensure_ct_link(void)
{
    if (s_avrcp_link_requested) return;

    uint16_t hndl = btc_a2d_conn_handle_get();
    if (hndl == 0) {
        ESP_LOGW(TAG, "avrcp link: bta handle not ready, skip");
        return;
    }

    BTA_AvOpenRc(hndl);
    s_avrcp_link_requested = true;
    ESP_LOGI(TAG, "avrcp link: BTA_AvOpenRc(0x%04x) issued", hndl);
}
```

**`sync_vol_task` 改为三拍**（原为"等 800ms → 直接下发"）：

| 拍 | 动作 | 理由 |
|---|---|---|
| ① `delay 800ms` | 等 A2DP 连接完全建立 | 连接事件早于 SCB 就绪；`bta_av_rc_opened` 要靠 `peer_addr` 匹配到 SCB |
| ② `avrcp_ensure_ct_link()` | 补一脚 AVRCP 建连 | 必须在 A2DP 连好之后（SCB 必须已存在） |
| ③ `delay 600ms` → 下发 | 等 AVRCP 建连 + SDP 协商，再同步档位 | 这之后 `vol_ops` 才被注册 |

**兜底**：`bt_audio_service_set_volume()` 里若 `set_absolute` 返回
`ESP_ERR_INVALID_STATE`（用户比自动同步更早按键），主动调 `avrcp_ensure_ct_link()`，
下次按键即可成功，不必等重连。

**断开时重置**：`s_avrcp_link_requested = false`（随 A2DP 一起关的 RC 需要重连后重建）。

**量纲修正**：`local_vol_to_avrcp()` → 更名 `local_vol_to_app()`，目标量纲由 0..127 改为 **0..100**：

```c
#define BT_VOL_APP_MAX      100   /* esp_bt_audio 应用层量纲上限（勿改） */
#define BT_VOL_LOCAL_MAX    90

static int local_vol_to_app(int vol)
{
    if (vol < 0) vol = 0;
    if (vol > BT_VOL_LOCAL_MAX) vol = BT_VOL_LOCAL_MAX;
    return (vol * BT_VOL_APP_MAX + BT_VOL_LOCAL_MAX / 2) / BT_VOL_LOCAL_MAX;
}
```

修正后映射表：

| 本地档位 | 传出(0..100) | 库转(0..127) | 结果 |
|---|---|---|---|
| 0 | 0 | 0 | 0.0% |
| 50 | 56 | 71 | 55.9% |
| 90 | 100 | 127 | 100.0% ✓ |

共改 4 处调用点（`sync_vol_task` / `set_volume` 绝对路径 / 相对路径差值 ×2）。

### 五、修正的一处误导性注释

`bt_audio_service.c:56-70` 原写：

> `vol_ops.set_absolute` 只要 AVRCP CT 连上就会被注册（见 bt_audio_avrcp_ct.c:587，条件仅是 conn_stat.connected）

**字面正确，但极具误导** —— 因为"CT 连上"这个前提在本工程**永远不成立**。
已改写为完整三层量纲说明 + 前提条件警示 + 指向 `avrcp_ensure_ct_link()`。

### 六、复核

机器可校验复核（Python 正则 + 括号配平）：
